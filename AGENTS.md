# Правила GREEN-API Chat

Работа ведётся в этом проекте, на русском языке. Объясняй разработчику простыми
словами, что меняешь и зачем; особенно серверную часть и хранение данных.

## Обязательный процесс

1. Обсудить одну небольшую задачу. При существенном выборе предложить варианты,
   преимущества и риски. Не выдумывать недостающие требования: запросить решение.
2. Подготовить спецификацию и проверку её качества. Получить согласование.
3. Самостоятельно подготовить технические документы, задачи и read-only анализ.
   Технические исправления выполнять отдельно от анализа; затем повторить его.
   После завершения прохода сохранить полный отчёт в analysis.md выбранной задачи
   и дать пользователю прямую ссылку. Правила отчёта — в docs/spec-kit-workflow.md.
4. Показать полный отчёт и получить отдельное разрешение на реализацию.
   Согласование эпика, наличие файлов и положительный анализ разрешения не дают.
5. Реализовать только разрешённую задачу, проверить соответствие спеке, выполнить
   необходимые проверки и предкоммитное ревью. Дать результат, ограничения,
   обоснованные улучшения, следующие шаги и английское название коммита.

Существующее разрешение из переписки сохраняется: не спрашивать его повторно.
Если меняется согласованное поведение, данные, безопасность или объём,
сначала согласовать затронутое решение. Не переходить к следующей feature
под видом завершения текущей.

## Размер задач

- Продолжать согласованное дробление на небольшие отдельно проверяемые шаги.
  Для возможностей с UI и сервером отдельно обсуждать форму и её поведение,
  серверную логику, их соединение, сохранение состояния и завершение работы,
  когда эти части применимы. Не объединять их в одну реализацию без обсуждения.
- На каждом шаге заранее назвать видимый результат, границы и способ проверки.
  Код, тесты и необходимые проверки этого шага входят в одну задачу.
- Перед следующим шагом обсуждать его с пользователем. Каждая задача проходит
  собственные согласование spec и разрешение на код; готовность одного слоя
  не означает, что весь пользовательский сценарий уже работает.

## Ограничения

- [GIT_POLICY.md](GIT_POLICY.md) — единственный проектный источник правил Git.
  Соблюдать его исключение staging только по прямой просьбе с конкретными путями.
- Не скачивать и не устанавливать сторонние пакеты или ПО. Не выполнять миграции
  и команды изменения данных БД. При необходимости объяснить и дать команды
  пользователю.
- Не сохранять реальные токены, телефоны, идентификаторы аккаунтов или переписку
  в документах, примерах, тестах и журналах.
- Сохранять пользовательские изменения; не откатывать их и не перезаписывать
  документ шаблоном. При конфликте сначала установить принадлежность изменений.
- Документы описывают актуальное состояние, без истории «было → стало».
- Префиксы названия коммита: feat:, fix:, refactor:, chore:. Сам коммит не создавать.
- Параллельные агенты, внешние интеграции и публикация не подразумеваются задачей.

## Обязательный порядок тестирования

- Для новой и изменяемой бизнес-логики и серверных контрактов обязателен TDD:
  Red → Green → Refactor. Сначала тест на согласованное поведение, затем код.
- Тесты и реализация пишутся только после согласования спеки и отдельного
  разрешения на код. До этого фиксируются сценарии и способ проверки.
- Red подтверждается запуском: тест падает из-за отсутствующего или неверного
  поведения. Ошибка установки, импорта или окружения не подтверждает Red.
- Green — минимальная реализация, проходящая тест; Refactor — улучшение кода
  с повторным успешным запуском затронутых тестов. Тесты сохраняются в проекте.
- Для чистого рефакторинга сначала проверить покрытие и успешное выполнение
  существующих тестов; искусственно ломать поведение ради Red не требуется.
- Для конфигурации и оформления способ проверки явно задаётся в каждой спеке.
  Если изменение затрагивает бизнес-логику или серверный контракт, эта часть
  проходит TDD независимо от того, в каком файле находится.
- В plan/tasks задавать зависимости «тест и подтверждённый Red → реализация →
  проверка Green → рефакторинг». В verification фиксировать команды и результаты
  Red/Green и итоговых проверок; TDD нельзя заменять тестами после реализации.

- При подготовке каждой задачи агент самостоятельно определяет нужные тесты,
  включая ошибки и граничные случаи, и выбирает подходящий уровень:
  unit, component, integration или E2E. Не ждать отдельного напоминания пользователя.
- Оценивать достаточность существующих инструментов по конкретной логике задачи.
  Новый инструмент предлагать с причиной, альтернативой и ценой поддержки;
  включать выбор в spec/plan/tasks и согласовывать в обычных точках процесса.
  Не устанавливать пакеты самостоятельно и не добавлять инструменты на перспективу.
- Для существующего поведения добавлять регрессионные проверки; не объявлять
  написанные после реализации тесты подтверждением TDD.

## Константы серверных ответов

- HTTP-коды, имена заголовков и повторно используемые значения хранить
  в src/lib/http/constants.ts; общие статусы JSON-ответов — в src/lib/api/constants.ts.
- Объявлять объекты через as const и добавлять только используемые значения.
  Не связывать общие константы с одним обработчиком или конкретным маршрутом.
- В обработчиках деструктурировать используемые константы на уровне модуля.
  Для совпадающих ключей давать понятные имена: HTTP_OK и RESPONSE_OK;
  для имени заголовка Cache-Control — CACHE_CONTROL_HEADER.
- Не дублировать вручную заголовки, которые корректно формирует выбранный API
  фреймворка; Response.json сам задаёт Content-Type.

## Правила стилей

- Использовать SCSS Modules, БЭМ и вложенность элементов/модификаторов через &.
- Все значения цветов задавать в src/styles/_tokens.scss; в компонентах
  и глобальных стилях обращаться к семантическим SCSS-переменным.
- Общие значения отступов, размеров, скруглений и типографики хранить там же.
  Структурные значения вроде 0, 100% и auto не требуют отдельных констант.
- Повторяющиеся группы CSS-свойств выносить в src/styles/_mixins.scss
  и подключать через @include. Не создавать миксин ради одного свойства
  или гипотетического переиспользования.
- Общие SCSS-модули подключать через @use с пространствами имён tokens
  и mixins. В partial-файлах хранить определения без самостоятельных CSS-селекторов.
- Новые стили во всём проекте проверять на соблюдение этих правил при ревью.
