# Quickstart: данные своего аккаунта и шапка

**Spec**: [spec.md](spec.md)
**Статус**: Реализация и автоматические проверки завершены. Ручная приёмка реального аккаунта ожидает пользователя.

## До начала

Требуются согласованная spec, готовый технический комплект и отдельное разрешение на код. Установки не нужны. Существующий `SESSION_PASSWORD` остаётся в локальном окружении; реальные реквизиты не копируются в документы или тесты.

Рабочая папка — `D:\Pet-projects\green-api-chat`. Для команд также можно использовать NPM Scripts в VS Code. Перед production-проверками остановить dev этой папки; не запускать одновременно соседние проверки, использующие её `.next`.

## Проверка Red

Поведенческий Red подтверждён до реализации следующими командами:

```powershell
npm run test:integration -- tests/integration/account-profile.spec.ts tests/integration/get-account-settings.spec.ts
npm run test:e2e -- tests/e2e/account-profile.spec.ts
```

Серверные тесты выявили отсутствие нормализации и адаптера; браузерные — отсутствие шапки и лишний старый метод при успешной сборке. Фактические результаты приведены в [verification.md](verification.md). В текущей реализации эти команды должны проходить; повторять искусственный Red не нужно.

## После завершения реализации

```powershell
npm run test:integration
npm run test:e2e
npm run lint
npm run lint:styles
npm run typecheck
npm run format:check
```

Интеграционные тесты проверяют серверную логику, E2E — приложение с реальной внутренней авторизацией и подставленным GREEN-API. E2E уже включает production-сборку и запуск. Последние команды проверяют автоматические нормы кода, SCSS, типы и форматирование. Ничего не устанавливать и не исправлять чужие файлы массовой командой `format`.

Если рефакторинг после Green изменил код, соответствующие тесты повторяются после завершения этой серии. Повторять весь набор без новых изменений или проблем не требуется.

## Ручная приёмка

1. Запустить ▶ `dev`, открыть `/` без сессии — должна открыться `/login`.
2. Войти со своими реквизитами. На `/` проверить собственный @username или телефон, аватар либо заглушку и один доступный выход. Настоящие токены и Payload не отправлять агенту.
3. Обновить `/` — данные своего аккаунта и поиск должны оставаться доступны после новой проверки API.
4. Проверить узкую ширину около 360 px: подпись и выход не перекрываются, горизонтальной прокрутки нет, полная подпись читается без наведения.
5. Сменить системную тему при заполненном поиске: фон, шапка, заглушка, поле и кнопки обновляются, введённое значение сохраняется.
6. Нажать «Выйти» — обычная `/login`; открытие `/` снова требует входа.

Не все ошибки воспроизводятся реальным аккаунтом. Варианты без username/телефона, длинная подпись, сбой фото, состояния инстанса и 429 проверяются вымышленными автоматическими сценариями; ради них не меняются Telegram-настройки и личные данные.

## Завершение

Сверить [приёмочный чек-лист](checklists/acceptance.md), изучить `verification.md` и diff. Git staging, коммит и push выполняет пользователь согласно политике проекта. Предлагаемое название коммита после реализации: `feat: display connected Telegram account`.
