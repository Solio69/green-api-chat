# Feature Specification: D02–D03 — данные своего аккаунта и шапка

**Feature Directory**: specs/013-account-profile
**Created**: 2026-10-01
**Status**: Реализована; автоматические проверки пройдены, ручная приёмка реального аккаунта ожидается
**User Approval**: Подтверждено пользователем в переписке 2026-10-01
**Workflow Mode**: Standard
**Implementation Authorization**: Получено от пользователя в переписке 2026-10-01
**Input**: На главной получить данные своего Telegram-аккаунта через `GetAccountSettings` и отобразить шапку в стиле согласованного макета. При входе сохранить `GetStateInstance`. Основная подпись — `@username`, при его отсутствии — телефон; отсутствующий аватар заменяется нейтральной иконкой.

## User Scenarios & Testing

### User Story 1 — Узнать подключённый аккаунт (Priority: P1)

После входа пользователь видит, какой собственный Telegram-аккаунт подключён к приложению. Данные относятся к отправителю, а не к найденному получателю сообщения.

**Why this priority**: Шапка даёт понятный контекст для поиска и дальнейшей переписки, используя реальные данные существующей сессии.

**Independent Test**: Войти с тестовыми реквизитами и открыть `/`. Подставленный ответ `GetAccountSettings` со статусом `authorized` должен определять аватар и подпись аккаунта; поиск и выход остаются доступны.

**Acceptance Scenarios**:

1. **Given** выполнен вход, **When** `GetAccountSettings` возвращает `authorized`, непустой `username` и доступный аватар, **Then** шапка показывает этот username и аватар.
2. **Given** аккаунт авторизован, **When** username отсутствует или пуст, а телефон доступен, **Then** основной подписью становится телефон.
3. **Given** аккаунт авторизован, **When** отсутствуют оба идентификатора, **Then** шапка показывает нейтральную подпись «Telegram-аккаунт», поиск и выход работают.
4. **Given** аккаунт авторизован, **When** аватар отсутствует или изображение не загрузилось, **Then** отображается нейтральная иконка без сломанного изображения и без ошибки входа.
5. **Given** главная уже открыта, **When** пользователь обновляет страницу, **Then** данные снова получаются с сервера и отражают текущий ответ API; дополнительный `GetStateInstance` на главной не вызывается.

### User Story 2 — Сохранить понятное поведение при сбое подключения (Priority: P1)

Пользователь не теряет сессию из-за временной недоступности GREEN-API. Подтверждённая невозможность использовать сохранённое подключение приводит к существующему сценарию завершения сессии.

**Why this priority**: Метод профиля одновременно подтверждает состояние инстанса. Его ошибки не должны создавать ложный успешный вход или менять согласованные правила защищённой страницы.

**Independent Test**: Подставить ответы состояний и ошибок API; проверить доступ к главной, сохранение или завершение сессии, действие повторной проверки и отсутствие поиска до подтверждения авторизации.

**Acceptance Scenarios**:

1. **Given** действующей сессии нет, **When** открывается `/`, **Then** пользователь переходит на `/login`; `GetAccountSettings` не вызывается.
2. **Given** сессия есть, **When** API однозначно сообщает недействительность реквизитов или инстанса, истечение доступности инстанса либо состояние `notAuthorized`, `pendingPassword`, `blocked` или `suspended`, **Then** сессия завершается существующим способом и открывается обычная `/login`.
3. **Given** сессия есть, **When** API недоступен, превышено время ожидания, возвращены неизвестное состояние, некорректный ответ либо состояние `starting`, **Then** сессия сохраняется; главная показывает существующее сообщение о невозможности подтвердить состояние, действие «Повторить проверку» и выход. Шапка с неподтверждёнными данными и поиск не отображаются.
4. **Given** первый запрос `GetAccountSettings` получил HTTP 429, **When** один повтор после действующей задержки возвращает `authorized`, **Then** отображается шапка и поиск без промежуточного экрана ошибки.
5. **Given** повторный запрос тоже получил HTTP 429, **When** проверка завершается, **Then** отображается состояние повторной проверки с сохранением сессии; дальнейшие автоматические повторы не запускаются.
6. **Given** произошёл временный сбой, **When** пользователь нажимает «Повторить проверку», **Then** выполняется новая проверка через `GetAccountSettings`; успешный ответ показывает текущие данные аккаунта и поиск.

### User Story 3 — Пользоваться шапкой на компьютере и телефоне (Priority: P2)

Шапка оформлена в стиле согласованного MAX-макета, остаётся читаемой на узком экране и содержит доступное действие выхода.

**Why this priority**: Получение данных и их отображение согласованы как один законченный шаг. Полная компоновка чата относится к отдельной задаче.

**Independent Test**: Проверить шапку на ширине 360 px и на настольном экране, длинную подпись, клавиатурное управление и существующий сценарий выхода.

**Acceptance Scenarios**:

1. **Given** аккаунт подтверждён, **When** главная открыта на ширине 360 px или на компьютере, **Then** аватар, подпись и выход остаются доступны; шапка не создаёт горизонтальную прокрутку страницы.
2. **Given** подпись длинная, **When** ей недостаточно места, **Then** она не перекрывает выход; полное значение остаётся доступно без наведения мыши.
3. **Given** шапка отображена, **When** пользователь управляет страницей клавиатурой, **Then** действие «Выйти» имеет понятное доступное имя и видимый фокус.
4. **Given** пользователь нажал «Выйти», **When** существующий выход завершён, **Then** открывается обычная `/login`, повторное открытие `/` требует входа; выхода из Telegram или с других устройств нет.

### Edge Cases

- Непустой username имеет приоритет над телефоном. Телефон не требуется дополнительно показывать рядом с username в этом шаге.
- Пустые строки, строки только из пробелов, отсутствующие поля и неверные типы полей отображения считаются отсутствующими данными. Это не меняет результат валидного `stateInstance: authorized`.
- Валидное состояние проверяется отдельно от необязательных данных отображения. Отсутствующий, неизвестный или неверно типизированный `stateInstance` не считается успешным ответом.
- URL аватара не должен приводить к передаче реквизитов или произвольным серверным обращениям за изображением. Недопустимый источник получает ту же заглушку, что отсутствующее фото; конкретный способ получения изображения определяется техническим планом.
- Данные предыдущего аккаунта не используются как замена при ошибке проверки другого подключения.
- HTTP 200 без корректного подтверждения состояния не открывает поиск. Статус ответа страницы Next.js не заменяет проверку тела ответа GREEN-API.
- Автоматическое получение данных ограничено открытием или обновлением главной и согласованным повтором после HTTP 429. Фонового опроса профиля нет.

### Verification Approach

После разрешения реализации новая и изменяемая серверная логика проходит TDD: сначала тесты ответов `GetAccountSettings`, нормализации данных и решений защищённой страницы, подтверждённый Red, затем реализация и итоговый Green. Отдельно проверяются отсутствие лишнего `GetStateInstance` на главной и сохранение его использования при входе.

Браузерные проверки покрывают шапку, приоритет username, телефон и нейтральную подпись, отсутствие и ошибку загрузки аватара, длинное значение, клавиатуру, мобильную ширину и выход. Автоматические проверки используют только вымышленные данные и подставленные ответы API; визуальная приёмка сверяется с согласованным макетом. Ручная проверка реального аккаунта выполняется пользователем без передачи секретов агенту.

Применяются имеющиеся инструменты проекта. Новые тестовые зависимости заранее не требуются. Команды, пути тестов и последовательность проверок уточняются в техническом плане. Проверки запускаются после завершённой задачи или всей серии правок; качество этой спецификации не выдаётся за выполненные тесты продукта.

## Requirements

### Functional Requirements

- **FR-001**: Вход через `/login` и `POST /api/auth/login` использует действующий `GetStateInstance`; получение профиля не добавляет к входу ещё один вызов GREEN-API.
- **FR-002**: На защищённой главной с действующей сессией сервер получает данные своего аккаунта через `GetAccountSettings` вместо отдельного `GetStateInstance`. При отсутствии действующей сессии происходит переход на `/login` без обращения за профилем.
- **FR-003**: Шапка и поиск доступны только после корректного подтверждения `stateInstance: authorized` ответом `GetAccountSettings`.
- **FR-004**: Недействительные реквизиты или инстанс, истечение его доступности, `notAuthorized`, `pendingPassword`, `blocked` и `suspended` обрабатываются существующим завершением сессии и переходом на `/login?reason=access_lost`.
- **FR-005**: Временный сбой, таймаут, `starting`, неизвестное состояние или некорректный ответ сохраняют сессию и показывают существующее состояние ошибки главной с повторной проверкой и выходом. Неподтверждённый профиль и поиск в этом состоянии недоступны.
- **FR-006**: Для `GetAccountSettings` действует существующая политика HTTP 429: один повтор после задержки 1100 ms в пределах общего времени ожидания 10 секунд. Успешный повтор не показывает промежуточную ошибку; повторный 429 завершает проверку как временную ошибку.
- **FR-007**: Шапка показывает непустой username; при его отсутствии — телефон; при отсутствии обоих — «Telegram-аккаунт». Имя человека, online-статус и данные получателя не выдумываются.
- **FR-008**: Аватар собственного аккаунта отображается при наличии допустимого источника и успешной загрузке. При отсутствии, недопустимом источнике или ошибке загрузки отображается нейтральная иконка. Необязательные данные отображения не блокируют подтверждённый доступ.
- **FR-009**: При обновлении `/` запрашиваются актуальные данные. Профиль не сохраняется в cookie, браузерном хранилище или отдельном глобальном state; отдельный клиентский запрос за профилем не добавляется.
- **FR-010**: Шапка содержит одно существующее действие выхода с доступным именем «Выйти». Контракт выхода, срок сессии и её изоляция по текущему браузеру сохраняются.
- **FR-011**: Оформление аватара, подписи и выхода соответствует шапке собственного аккаунта в согласованном MAX-макете. Компоненты и SCSS следуют действующим проектным правилам; полная страница чата не входит в задачу.
- **FR-012**: На ширине 360 px и на настольном экране подпись не перекрывает выход и не создаёт горизонтальную прокрутку; полное значение доступно без hover, действие выхода доступно с клавиатуры и имеет видимый фокус.
- **FR-013**: Реквизиты GREEN-API, содержимое сессии и URL запросов с токеном не передаются в шапку, клиентские ответы, журналы или примеры. UI получает только необходимые данные отображения, а не произвольное тело ответа поставщика.
- **FR-014**: Существующие поиск через `CheckAccount` и выход работают в своих согласованных границах. Этот шаг не меняет настройки или данные Telegram-аккаунта, не добавляет хранение профиля и не реализует отправку или получение сообщений.

### Scope Boundaries

- В объёме: серверный `GetAccountSettings`, подтверждение состояния и обработка ошибок, подготовка данных отображения, шапка собственного аккаунта по макету, заглушка аватара, единая системная палитра входа и главной, её наследование элементами поиска и выхода, необходимые тесты и приёмка.
- Получение данных D02 и шапка D03 из [обзора UI](../../docs/chat-ui-spec.md) согласованы пользователем в одной задаче. Её видимый результат — собственный аккаунт над существующим поиском.
- За пределами: изменения поведения страницы `/login`; новая схема сессии или входа; полный каркас из двух панелей; оформление поиска и найденного получателя; список чатов и переписка; `SendMessage`, `ReceiveNotification`, `DeleteNotification`; Redux; базы данных; новые настройки и публичный API профиля; публикация приложения.

### Data Effects & User Decision

- **Changed data**: Приложение читает состояние и данные собственного Telegram-аккаунта через API; записей в Telegram и БД нет. Меняются только код и проверки согласованного шага после разрешения реализации.
- **Preview**: Пользователь видит аватар или заглушку и идентификатор подключённого аккаунта над существующим поиском.
- **Confirmation**: Получение данных запускается при открытии защищённой главной; дополнительное подтверждение пользователя не требуется. Согласование этой спеки разрешает техническую подготовку; код требует отдельного разрешения.
- **Cancellation**: Отдельного сценария отмены чтения нет; выход завершает текущую браузерную сессию существующим способом.
- **Idempotency and duplicates**: Повторное чтение и обновление страницы не создают аккаунты, чаты или дубликаты; действие выхода в шапке представлено один раз.
- **Failure result**: При временной ошибке сессия сохраняется, доступна повторная проверка; при подтверждённой невозможности использовать подключение сессия завершается. Ошибка изображения заменяет только аватар.

### Key Entities

- **Подключение GREEN-API**: Существующие серверные реквизиты `idInstance` и `apiTokenInstance`; используются для собственного инстанса, а не для получателя сообщения.
- **Ответ об аккаунте**: `stateInstance` определяет доступ; `avatar`, `username` и `phone` дают данные отображения. Поле `chatId` относится к самому аккаунту и не используется как идентификатор получателя. `historySyncProgress` и `suspendedUntil` не добавляют новые функции в этом шаге.
- **Данные шапки**: Только подготовленная подпись собственного аккаунта и допустимый источник аватара; без секретов и произвольных дополнительных полей API.
- **Браузерная сессия**: Действующая зашифрованная HttpOnly-cookie на 24 часа; отдельная сущность хранения профиля не вводится.

## Success Criteria

- **SC-001**: При входе используется `GetStateInstance`; при открытии и обновлении главной — `GetAccountSettings` без дополнительного `GetStateInstance`. Тесты отличают оба пути и отдельно проверяют единственный допустимый повтор после 429. Покрывает FR-001–FR-003, FR-006, FR-009.
- **SC-002**: Все перечисленные подтверждённые отказы доступа завершают сессию; временные ошибки, `starting` и некорректные ответы сохраняют её. Повторная проверка после восстановления показывает профиль и поиск. Покрывает FR-003–FR-006.
- **SC-003**: Проверены варианты username, телефон и нейтральная подпись, а также доступный, отсутствующий и не загрузившийся аватар. При подтверждённом состоянии отсутствие необязательных данных не блокирует поиск. Покрывает FR-007–FR-008.
- **SC-004**: На мобильной ширине 360 px и настольном экране шапка соответствует согласованному визуальному ориентиру, длинная подпись остаётся доступной, нет перекрытия выхода или горизонтальной прокрутки. Клавиатурный фокус виден. Покрывает FR-011–FR-012.
- **SC-005**: Выход доступен один раз, завершает текущую сессию и открывает обычную `/login`; поиск сохраняет существующий контракт. Покрывает FR-010, FR-014.
- **SC-006**: В передаваемых шапке данных, клиентских ответах и новых диагностических выводах отсутствуют реквизиты и содержимое сессии; нет нового хранилища профиля, зависимостей или обращений за профилем из браузера. Покрывает FR-009, FR-013–FR-014.

## Assumptions and Dependencies

- Пользователь подтвердил `GetStateInstance` при входе и `GetAccountSettings` на главной, отображение username с заменой на телефон, заглушку аватара и совместный объём получения данных и шапки.
- [Согласованный UI](../../docs/chat-ui-spec.md) и [макет](../../docs/ui-references/max-chat-mockup.html) задают визуальный ориентир. Моковые имя, фото и ответы не являются источником реальных данных.
- Используются существующие [вход и сессия](../006-login-session/spec.md), [выход](../008-logout/spec.md) и [поиск получателя](../009-recipient-lookup/spec.md). Отдельная задача [редизайна входа](../010-max-login-ui/spec.md) не входит в этот шаг.
- Семантические нормы заданы [CODING_RULES.md](../../docs/CODING_RULES.md), инструменты оформления — [CODE_STYLE.md](../../docs/CODE_STYLE.md), процесс — [AGENTS.md](../../AGENTS.md) и [Spec Kit](../../docs/spec-kit-workflow.md).
- Официальные [GetAccountSettings](https://green-api.com/telegram/docs/api/account/GetAccountSettings/) и [GetStateInstance](https://green-api.com/telegram/docs/api/account/GetStateInstance/) проверены 2026-10-01. Источник предоставляет состояние и поля профиля; отображаемого имени человека в описанном ответе `GetAccountSettings` нет. Наличие фотографии и username для каждого аккаунта не предполагается.
- GREEN-API вызывается через согласованный серверный адрес `https://4100.api.green-api.com`; поле `apiUrl` в форму входа не добавляется.
- `authorized` подтверждает авторизацию собственного инстанса; он не доказывает отсутствие ограничений на конкретную отправку или присутствие получателя online.
