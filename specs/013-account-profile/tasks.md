Минимум сценариев T002:

- Username, телефон, пустой профиль, trim, неверные типы, дополнительное поле и реквизиты в полях отображения.
- Допустимая HTTPS-ссылка, некорректный/относительный URL, userinfo, неподходящие протоколы, сырой и URL-кодированный токен/ID в ссылке.
- Все состояния из контракта, HTTP 401/403/400/5xx, неизвестный HTTP-код, некорректный JSON, отказ сети/редиректа, таймаут.
- 429 → успех, 429 → 429, 429 → другая ошибка; единственный повтор, та же сигнализация общего таймаута, не больше двух обращений.
- Нет сессии — нет API; подтверждённый отказ — завершение; временный — retry; подготовленный профиль передаётся при успехе.
- Реальный внутренний вход, профиль на `/`, refresh, отсутствие лишнего `GetStateInstance`, успешная/ошибочная картинка, смена URL после ошибки, мобильная и длинная подпись, клавиатурный выход.

До изменения сигнатуры `resolveHome` его регрессионные сценарии используют действующий вызов. Изменение всех этих вызовов на именованный объект входит в T004 и не создаёт новый продуктовый контракт.

## Dependencies & Execution Order

`T001 → T002 (сохраняемые тесты и подтверждённый Red) → T003 → T004 → T005 → T006 → T007 (Green) → T008 (Refactor/Review, итоговые проверки) → T009`.

Red-команды:

```powershell
npm run test:integration -- tests/integration/account-profile.spec.ts tests/integration/get-account-settings.spec.ts
npm run test:e2e -- tests/e2e/account-profile.spec.ts
```

Ошибки импорта, недоступное окружение и падение сборки не подтверждают Red и не разрешают переход к функциональной реализации T003–T006. Корректная типизированная заглушка допустима только для запуска теста отсутствующего поведения. Команды Green и итоговых проверок указаны в T007 и [quickstart.md](quickstart.md).

Тесты, подстановка ответа и продуктовый код пишутся только после отдельного разрешения реализации. До него выполняется подготовка этого документа и read-only анализ.
