**Spec**: [spec.md](spec.md)

## Summary

Серверная главная использует `GetAccountSettings` для подтверждения подключения и получения данных своего аккаунта. Результат передаётся в `AccountHeader` над существующим поиском; `AccountAvatar` отдельно обрабатывает ошибку фото. Вход сохраняет `GetStateInstance`, а выход — существующий POST.

Метод вызывается внутри действующего серверного открытия страницы, без нового HTTP endpoint и клиентского запроса профиля. Профиль имеет только безопасные `label` и `avatarUrl`, не записывается в cookie или store. Для HTTP 429 сохраняется один повтор через 1100 ms с общим таймаутом 10 секунд.

## Considered Options

| Вариант                                           | Преимущества                                     | Ограничения и риски                                  | Выбор и причина                    |
| ------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------------- | ---------------------------------- |
| Два метода на главной                             | Раздельные проверки                              | Лишний запрос за тем же состоянием                   | Не выбран                          |
| `GetAccountSettings` на главной, действующий вход | Состояние и профиль в одном ответе               | Новый адаптер и UI                                   | Выбран пользователем               |
| Серверная оптимизация изображения                 | Уменьшение файла                                 | Серверная загрузка внешнего источника и конфигурация | Не нужна для небольшого аватара    |
| `next/image` с `unoptimized`                      | Нет нового серверного загрузчика, есть `onError` | Прямое обращение браузера к источнику фото           | Выбран с проверкой URL и заглушкой |
| Redux или новый endpoint профиля                  | Возможность независимых обновлений               | Не требуются для открытия этой страницы              | Не выбраны                         |

Полные основания и проверенные источники — в [research.md](research.md).

## Technical Context

- Next.js 16.3.7, React 19.3.0, TypeScript 5.9.3, Node.js 24.x.
- Существующие iron-session 9.0.1, зашифрованная HttpOnly-cookie на 24 часа, SCSS Modules и Playwright 1.63.0.
- Действующие host, HTTP-статусы, категории ошибок и состояние инстанса переиспользуются. Новым значимым значениям задаются константы по месту их смысла.
- Собственные компоненты — PascalCase, отдельная папка, SCSS-модуль и публичный `index.ts`. Новые функции с несколькими параметрами получают именованный объект; затронутый `resolveHome` и его вызовы приводятся к этому правилу.
- Существующие классификаторы состояния и 400 экспортируются из `get-state.ts`; поведение входа не переписывается.
- Нативный URL используется для проверки HTTPS, отсутствия userinfo и реквизитов в ссылке. Допустимое изображение загружает браузер; `next.config.ts` не изменяется.
- Только чтение аккаунта. Установки, миграции, новые переменные окружения и Git-запись не требуются.

## Общая тема и оформление

`src/styles/_theme.scss` определяет миксин `system-theme` с единой светлой/тёмной палитрой из `_tokens.scss`. `src/app/globals.scss` подключает его на `:root`; вход не дублирует переменные и фоновый слой. `HomePage.module.scss` связывает шапку и действующий поиск в общей поверхности. Шапка содержит подпись, статус подключения и выход с иконкой; заглушка использует тематический градиент.

`RecipientSearchForm`, `RecipientSearchField`, аватар и выход используют CSS-переменные общей темы. Локальные переменные выхода отвечают за компактность в шапке. Тема не хранится в React, cookie или браузерном storage. Общие тестовые ожидания находятся в `tests/constants.ts`, помощники вычисленных стилей/контраста — в `tests/e2e/ui-theme.helpers.ts`. Два сценария темы используют отдельные фиктивные аккаунты и проверяют 360/1280 px, цвета, контраст, фокус и сохранение поля при смене системной настройки.

## Tasks and Dependencies

Подробные шаги — [tasks.md](tasks.md). Работа последовательная:

1. Проверить актуальное состояние файлов и границы соседней задачи.
2. Написать постоянные серверные и браузерные сценарии; обеспечить только типизированные каркасы новых функций для корректного запуска. Зафиксировать поведенческий Red без ошибок импорта или сборки.
3. Реализовать нормализацию, адаптер и подключение к решению главной.
4. Реализовать шапку, аватар и локальное оформление существующего выхода.
5. Проверить Green после завершения правок, затем выполнить необходимый рефакторинг и итоговые проверки.
6. Сверить со спекой, выполнить ревью, обновить документы и передать ручную приёмку пользователю.

Затронутый существующий `home-flow` сохраняет регрессионные сценарии. При подготовке Red они работают с текущей сигнатурой; при изменении `resolveHome` все его вызовы приводятся к именованному объекту. Эта правка сигнатуры не меняет категорий доступа.

Активные изменения соседнего агента в общих `_tokens.scss` и тестовых файлах нельзя перезаписывать. Перед реализацией сверить свежий diff и принадлежность изменений; если общий файл ещё редактируется параллельно, согласовать очередность работы до правки этого файла. Подготовка документов от этого не зависит.

## Verification

### Red до реализации

Red подтверждён до функциональной реализации: 25 серверных тестов Failed и 7 Passed, затем 9 E2E Failed при успешной production-сборке. Типизированные каркасы обеспечивали разрешённые импорты без извлечения профиля и вызова API. Браузерная подстановка обнаруживала лишний `GetStateInstance` на главной. Команды и причины записаны в [verification.md](verification.md); подготовительные ошибки типизации не считаются Red.

### Green и итоговая проверка

Фактические результаты: 114/114 интеграционных, 60/60 полного E2E и 36/36 итогового затронутого E2E после стилевого рефакторинга. После уточнения негативного случая процентного кодирования ID проверены 7/7 сценариев нормализации. Все автоматические нормы Passed.

По завершении всех правок выполнить полный `npm run test:integration` и `npm run test:e2e`: они включают новые сценарии, действующие вход, выход и поиск. Production-сборка выполняется существующей E2E-конфигурацией; дублирующий отдельный build не нужен.

Затем выполнить `npm run lint`, `npm run lint:styles`, `npm run typecheck`, `npm run format:check`. Если после Green рефакторинг меняет поведение или затронутую разметку, повторить соответствующие тесты один раз после всей серии. Если код не изменился, повтор полного набора не требуется.

Для E2E dev-сервер этой папки должен быть остановлен по действующему процессу проекта. Проверки, затронутые чужой незавершённой работой или отсутствием доступного окружения, фиксируются как Blocked/Failed с причиной и не выдаются за успешные.

Ручная проверка реального аккаунта: шапка, обновление `/`, доступность поиска, fallback изображения, выход и повторное открытие `/`. В `verification.md` отдельно сохраняются команды и причины Red, результаты Green, итоговые проверки и статус ручной приёмки; результаты автоматических проверок Passed, ручная приёмка реального аккаунта NotRun.
