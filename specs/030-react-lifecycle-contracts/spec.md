## User Scenarios & Testing

### User Story 1 — Достоверные проверки жизненного цикла React (Priority: P1)

Разработчик получает проверяемое доказательство корректного запуска и освобождения ресурсов провайдеров при Strict Mode, повторном рендере и размонтировании.

**Why this priority**: Это обязательная часть результата этапа R01; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Vitest и React Testing Library проверяют React lifecycle с управляемыми таймерами и deferred Promise. Это регрессионные тесты существующего поведения; найденное неверное поведение исправляется в отдельной согласованной задаче с подтверждённым Red.

**Acceptance Scenarios**:

1. **Given** провайдеры смонтированы под корневым StrictMode, **When** React выполняет дополнительный цикл эффектов, **Then** тест наблюдает replay и после завершения остаётся ровно один активный читатель.
2. **Given** существует подключение A, **When** происходит rerender, затем смена scope на B, **Then** rerender сохраняет A, а переход на B закрывает A и изолирует новое состояние.
3. **Given** запрос ещё не завершён, **When** компонент размонтирован, затем ответ доставлен, **Then** кеш закрытой сессии не восстанавливается и ACK от её имени не отправляется.

### Edge Cases

- Отложенное освобождение ресурса на ближайшем ходе таймера.
- Закрытие во время получения Web Lock.
- Несколько потребителей одного провайдера.
- Ошибки setup и cleanup не должны оставлять активный ресурс после теста.

### Verification Approach

Vitest и React Testing Library проверяют React lifecycle с управляемыми таймерами и deferred Promise. Это регрессионные тесты существующего поведения; найденное неверное поведение исправляется в отдельной согласованной задаче с подтверждённым Red.

Для существующего поведения используются регрессионные проверки и сопоставление покрытия. Добавление тестов после существующей реализации не называется TDD. Обнаруженный дефект описывается отдельно; изменение продуктового поведения требует согласованного требования и Red → Green → Refactor.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Фактические проверки и ограничения опубликованы в [verification.md](verification.md).

## Requirements

### Functional Requirements

- **FR-001**: Создать изолированные React-проверки настоящих QueryProvider и NotificationProvider с контролируемыми транспортом, блокировкой вкладки и временем.
- **FR-002**: Выполнять lifecycle-набор с development-сборкой React и корневым StrictMode; отдельно наблюдать фактическую последовательность setup, cleanup и повторного setup.
- **FR-003**: Подтвердить, что после replay есть один действующий Query-сеанс и один активный цикл получения; заброшенный экземпляр не удерживает ресурсы.
- **FR-004**: Подтвердить сохранение сеанса при обычном rerender и создание отдельного сеанса при смене connectionScope.
- **FR-005**: При окончательном unmount подтвердить прекращение таймеров, подписок и владения вкладкой; поздние результаты не применяются к закрытой сессии.
- **FR-006**: Заменить ложное заявление production-теста о Strict Mode replay проверкой с соответствующим предметом; полезные браузерные сценарии сохранить.
- **FR-007**: При обнаружении продуктового дефекта зафиксировать его и отделить исправление от переноса теста; проходящий ручной вызов retain/release не подменяет React-проверку.

### Scope Boundaries

- **В объёме**: React-тесты lifecycle и корректировка предмета существующих пересекающихся проверок.
- **За пределами**: Переписывание контроллера уведомлений, смена жизненного цикла приложения и эмуляция настоящих Web Locks вместо браузерных тестов.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Меняются тесты и их фикстуры; приложение сохраняет поведение. Обнаруженные отклонения фиксируются как отдельные результаты.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Пользователь поручил весь согласованный цикл, включая реализацию, проверки, ревью, commit и push; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Монтирование, подписка, retained-ресурс, подключение, контролируемый поздний ответ.

## Success Criteria

- **SC-001**: Есть наблюдаемое доказательство replay, а не только наличие тега StrictMode (FR-001, FR-002).
- **SC-002**: Все сценарии rerender, scope change и unmount проверяют количество живых ресурсов и изоляцию данных (FR-003–FR-005).
- **SC-003**: Названия и документация тестов соответствуют фактическому режиму; продуктовые дефекты не скрыты изменением ожиданий (FR-006, FR-007).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Для этого чата пользователь отдельно разрешил commit и push в refactor; отправка реальных сообщений в тестах не требуется.
