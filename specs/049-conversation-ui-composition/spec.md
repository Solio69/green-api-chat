## User Scenarios & Testing

### User Story 1 — Композиция интерфейса переписки (Priority: P1)

Компоненты переписки отображают готовые состояния и вызывают команды, а правила отправки, истории, выбора и уведомлений остаются в своих моделях.

**Why this priority**: Это обязательная часть результата этапа R08; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: React Testing Library для связок UI и поведения редактора; Vitest для сохранённых контрактов модели; Playwright для отправки через реальные маршруты, IME-событий, фокуса, геометрии и прокрутки.

**Acceptance Scenarios**:

1. **Given** редактор содержит допустимый текст, **When** пользователь отправляет его и сразу выбирает другой чат, **Then** результат связан с исходным чатом и не очищает новый редактор.
2. **Given** провайдер мог принять сообщение, но подтверждение потеряно, **When** показан unknown, **Then** автоматического повтора нет, доступна существующая ручная проверка истории.
3. **Given** пользователь читает старые сообщения, **When** приходит новое или обновляется история, **Then** сохраняется предусмотренное положение прокрутки и доступ к новым сообщениям.
4. **Given** на узком экране открыта переписка, **When** пользователь возвращается к списку и снова открывает чат, **Then** фокус, выбор, история и черновик ведут себя по прежним правилам.

### Edge Cases

- IME composition и сообщение из эмодзи у предела длины.
- Несколько событий статуса на одно сообщение.
- Закрытие сеанса во время send или receive.
- Пустая история, ошибка обновления и неподдерживаемое содержимое.
- Текст, похожий на HTML.

### Verification Approach

React Testing Library для связок UI и поведения редактора; Vitest для сохранённых контрактов модели; Playwright для отправки через реальные маршруты, IME-событий, фокуса, геометрии и прокрутки.

Для сохранения поведения используются исходная карта 028 и подтверждённые регрессионные проверки. Искусственный Red для перемещения кода не требуется. Новая или изменяемая бизнес-логика, включая согласованные защиты от гонок, выполняется через Red → Green → Refactor после разрешения реализации. Обнаруженное расхождение с текущим контрактом сначала фиксируется, а не исправляется незаметно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации сейчас имеют статус **NotRun**: этот документ задаёт объём, а не подтверждает выполненный рефакторинг.

## Requirements

### Functional Requirements

- **FR-001**: По карте 035 перенести компоненты и React-связки переписки, включая выбор, историю, сообщения, отправку, статусы и уведомления; общая рабочая область остаётся местом композиции публичных интерфейсов.
- **FR-002**: Представление получает готовые модели и действия; HTTP, объединение фактов, retry и условия допустимости отправки не дублируются в JSX или нескольких компонентах.
- **FR-003**: Сохранить один активный send на подключение, предел 4096 Unicode code points, значимые пробелы и существующее поведение Enter, Shift+Enter и IME.
- **FR-004**: Сохранить состояния sending, accepted, not_sent и unknown, ручную проверку истории и отсутствие автоматической повторной отправки.
- **FR-005**: Поздний результат относится к исходному чату и редактору; переключение, закрытие и мобильный возврат к списку сохраняют текущие правила черновика и выбора.
- **FR-006**: Сохранить скролл истории, фокус и переходы на узком экране, включая приход сообщения при просмотре старой истории и изменение размеров окна.
- **FR-007**: Сохранить безопасное текстовое отображение сообщений, поддерживаемые статусы, предупреждения, неподдерживаемое содержимое и доступные имена; не вводить HTML из текста провайдера.
- **FR-008**: Разнести hooks поведения и компоненты по ответственности без обязательного выделения хука для каждой простой строки; убрать оставшиеся нарушения карты владения только в пределах UI переписки; связь `chats/ui → conversation/ui` разрывается при композиции в app без изменения отображения.

### Scope Boundaries

- **В объёме**: Перенос и композиция UI переписки, провайдеров и hooks отображения.
- **За пределами**: Редизайн, вложения, редактирование сообщений, виртуализация, новые правила отправки и прочтения.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Отправка остаётся явным действием пользователя; повтор unknown не автоматизируется. Клиентские данные и выбор сохраняют прежний жизненный цикл.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Модель рабочей области, выбранная переписка, редактор, отправка, список сообщений и состояние уведомлений.

## Success Criteria

- **SC-001**: UI обращается к публичным моделям и командам без копий бизнес-правил (FR-001, FR-002, FR-008).
- **SC-002**: Отправка, ограничения текста и поздние результаты проходят регрессию (FR-003, FR-004, FR-005).
- **SC-003**: Браузерные сценарии подтверждают прокрутку, фокус, адаптивность, безопасный текст и статусы (FR-006, FR-007).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Подготовка спецификаций не включает commit, push или отправку реальных сообщений.
