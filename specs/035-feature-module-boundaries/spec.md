## User Scenarios & Testing

### User Story 1 — Ответственности и зависимости функциональных модулей (Priority: P1)

Разработчик понимает, кому принадлежит каждый участок приложения и какие зависимости допустимы при последовательном переносе.

**Why this priority**: Это обязательная часть результата этапа R04; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Сверить карту с фактическим списком src и тестов, проверить граф зависимостей и примеры разрешённых/запрещённых импортов. Точное дерево каталогов оформляется как результат этой задачи; принятие конкретных путей не предполагается до рассмотрения документа.

**Acceptance Scenarios**:

1. **Given** выбран любой текущий исходный файл, **When** разработчик обращается к карте модулей, **Then** видны его владелец, целевая область и задача переноса.
2. **Given** чистая функция объединения сообщений нужна серверу и клиенту, **When** проектируется её зависимость, **Then** она доступна без импорта UI, cookie-секрета и сетевого адаптера.
3. **Given** потребитель использует временный путь импорта, **When** проверяется план миграции, **Then** у переходного пути есть ограниченная роль и задача удаления.

### Edge Cases

- Слоты server/client components на главной странице.
- Провайдеры и хуки, которые сейчас находятся в разных общих папках.
- Общие константы, повторно экспортируемые типы и SCSS partials.
- Различие HTTP DTO, модели сообщения и представления компонента.

### Verification Approach

Сверить карту с фактическим списком src и тестов, проверить граф зависимостей и примеры разрешённых/запрещённых импортов. Точное дерево каталогов оформляется как результат этой задачи; принятие конкретных путей не предполагается до рассмотрения документа.

Это проверка состояния и документация. Новая бизнес-логика не реализуется. Результаты запусков фиксируются только после их выполнения; отсутствие готового окружения обозначается отдельно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации сейчас имеют статус **NotRun**: этот документ задаёт объём, а не подтверждает выполненный рефакторинг.

## Requirements

### Functional Requirements

- **FR-001**: Описать функциональные области auth, account, recipients, chats и conversation; внутри conversation учесть выбор, историю, сообщения, отправку, получение и unread.
- **FR-002**: Отделить композицию Next.js, серверные адаптеры и общие технические средства. Модель предметной области не зависит от React-компонентов, Next.js и транспорта.
- **FR-003**: Предложить карту владения для всех текущих файлов src и соответствующих тестов, включая общие UI-элементы, стили, константы и health route; не оставлять остаточный lib без определённой роли.
- **FR-004**: Определить публичные точки входа и направления импортов, исключающие циклы и обращение бизнес-логики к UI. Общий Query-сеанс не должен импортировать конкретную функцию чатов.
- **FR-005**: Описать проверяемую серверную границу для секретов и адаптеров; общие DTO и чистые функции доступны нужным потребителям без импорта серверного runtime.
- **FR-006**: Сопоставить целевую структуру с действующими правилами компонентов и импортов. Явно сформулировать необходимые изменения этих правил как часть спецификации границ.
- **FR-007**: Установить порядок переносов 036–049 и временные совместимые входы с владельцем и задачей удаления; полный переход подтверждается в 054.

### Scope Boundaries

- **В объёме**: Документ архитектурных границ, полная карта владения и согласование необходимых норм импортов.
- **За пределами**: Перемещение исходников, введение новой БД или state manager и изменение сценариев продукта.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Меняются архитектурные документы и согласуемые правила структуры; код переносится отдельными задачами.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Функциональный модуль, публичный интерфейс, зависимость, серверная граница, переходный импорт.

## Success Criteria

- **SC-001**: Каждый файл src имеет владельца и задачу переноса либо обоснование сохранения на месте (FR-001–FR-003).
- **SC-002**: Карта допускаемых зависимостей не содержит циклов; чистая модель отделена от UI и сервера (FR-002, FR-004, FR-005).
- **SC-003**: Правила структуры и план переходных импортов согласованы между собой (FR-006, FR-007).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Подготовка спецификаций не включает commit, push или отправку реальных сообщений.
