# История и получение уведомлений — согласованные границы

**Дата проверки источников**: 2026-10-02.
**Статус**: схема и перечисленные решения подтверждены пользователем.
Тексты спецификаций 018–025 согласованы 2026-10-02. Отдельная реализация разрешена
для 025 и 018; код остальных задач требует собственного разрешения.
Общий состав, зависимости и согласованные решения:
[комплект спецификаций](../../docs/messaging-specs.md).

## Согласованная схема

Next.js объединяет React-интерфейс и серверное API в одном постоянно работающем
Node-процессе. Сохраняется зашифрованная HttpOnly cookie-сессия; реквизиты GREEN-API
извлекает сервер, клиентский JavaScript их из cookie не читает.

```mermaid
sequenceDiagram
    participant G as GREEN-API
    participant N as Next.js / Node
    participant B as Браузер / Query
    B->>N: Подключение SSE с текущей cookie
    N->>G: ReceiveNotification
    G-->>N: Уведомление или пустой ответ
    alt Валидное уведомление
        N-->>B: Нормализованное событие SSE
        B->>B: Применение или осознанный пропуск
        B->>N: Отдельный HTTP ACK обработки
        N->>G: DeleteNotification проверенного receiptId
    else Повреждённое уведомление
        Note over N,B: Понятная ошибка и приостановка, без ACK и удаления
    else Пустой ответ
        Note over N,G: Подтверждать нечего
    end
    Note over N,G: Чтение последовательное; без активной вкладки остановлено
```

Long polling выполняется между Node и GREEN-API. Браузер получает события через
SSE. Выбор чата не запускает отдельный читатель очереди: уведомления относятся
к инстансу, событие сопоставляется с нужным chatId.

Для одного инстанса допускается одна рабочая вкладка. Вторая показывает явное
ограничение и не отправляет сообщения; сервер также проверяет право отправки.
Разные connectionScope одной очереди не создают независимых читателей.
Проверка владельца и его освобождение определяются в техническом плане.

## Соответствие заданию

Пункт 7 исходного задания ссылается на
[Technology HTTP API](https://green-api.com/v3/docs/api/receiving/technology-http-api/).
Он описывает ReceiveNotification и DeleteNotification с пустым webhookUrl.
Для Telegram [описан тот же механизм](https://green-api.com/telegram/docs/api/receiving/technology-http-api/).
SSE передаёт события нашего сервера браузеру и не заменяет HTTP API GREEN-API.
Webhook Endpoint не входит в выбранную схему.

[ReceiveNotification](https://green-api.com/telegram/docs/api/receiving/technology-http-api/ReceiveNotification/)
возвращает одно уведомление, ожидает его от 5 до 60 секунд и повторяет прежнее,
пока оно не удалено. Конкретный timeout и задержки после ошибок определит plan.
Запись в SSE не доказывает обработку браузером; DeleteNotification разрешён
только после подтверждённой клиентской обработки текущего события.
Неопределённый результат удаления требует отдельного технического разбора.

## История, отправка и временная память

- GetChats восстанавливает список; GetChatHistory — историю выбранного чата.
  При каждом обращении запрашивается свежий count: 10. В 018 свежий ответ
  выводится в консоль; 019 отдельно описывает отображение переписки.
- Известные сообщения сохраняются в памяти Query и объединяются со свежими
  без дублей по connectionScope/chatId/idMessage. Накопленный кеш может превышать
  десять сообщений. Подгрузка старой истории и увеличение count отложены.
- История не стирает уже применённые события и не понижает подтверждённые
  delivered/read устаревшим снимком. Нетекстовый факт обозначается
  «Неподдерживаемое сообщение», без загрузки вложений.
- Отправка текста выполняется через SendMessage. Локальное сообщение добавляется
  после успешного ответа с idMessage; это ещё не доставка. Одна отправка за раз
  на подключение; переключение и закрытие разрешены и очищают ввод. Поздний
  ответ остаётся у исходного чата. Неопределённый исход не запускает autoretry:
  предлагается проверить историю, ручной повтор сопровождается предупреждением.
- Статусы без idMessage не сопоставляются по догадке. Отказ отражается общей
  ошибкой чата или подключения; ранний статус без текста не создаёт пузырь.

Собственная БД, Redis, брокер и постоянное браузерное хранилище не создаются.
Перезагрузка и перезапуск процесса теряют соответствующую временную память.
При отсутствии активной вкладки чтение останавливается; неподтверждённое
уведомление не удаляется. При возвращении чтение очереди возобновляется,
последние десять выбранного чата обновляются.

Очередь провайдера хранит уведомления до 24 часов. Десять сообщений и временный
кеш не гарантируют восстановление всех старых сообщений или статусов;
exactly-once и постоянный журнал не обещаются.

## Размещение и технический план

Конкретная площадка и расходы не выбраны. Публичная демоверсия обязательна,
но размещение и публикация этим документом не разрешены. Несколько серверных
экземпляров не входят в текущую схему.

[Next.js при самостоятельном размещении](https://nextjs.org/docs/app/guides/self-hosting)
поддерживает потоковые ответы; обратный прокси должен пропускать поток без
буферизации. На этапе публикации проверяются длительность соединений,
перезапуск процесса и поведение выбранной площадки.

SSE остаётся выбранным транспортом. В техническом плане023 применяется fetch
с читаемым потоком, чтобы передавать scope и случайное право рабочей вкладки
в HTTP-заголовках. Клиент самостоятельно разбирает SSE и выполняет ограниченное
переподключение; автоматическое поведение нативного EventSource не обещается.
Само восстановление соединения не создаёт журнал пропущенных событий.
DTO, маршруты SSE/ACK, проверка владельца, жизненный цикл, ограничения API
и политика Query заданы в технических документах соответствующих feature.
