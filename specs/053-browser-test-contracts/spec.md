## User Scenarios & Testing

### User Story 1 — Достоверные браузерные и сквозные проверки (Priority: P1)

Playwright подтверждает работу полного приложения и браузерных механизмов, сохраняя устойчивость к безопасным изменениям внутренней разметки.

**Why this priority**: Это обязательная часть результата этапа R09; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Один итоговый прогон затронутых Playwright-наборов после серии правок, проверка реестра покрытия и конфигурации CI. Повторять запуск дополнительно только для расследования конкретного сбоя.

**Acceptance Scenarios**:

1. **Given** приложение собрано для production и провайдер фиктивный, **When** пользователь входит, открывает чат и отправляет сообщение, **Then** реальные маршруты создают сессию и проводят отправку, результат виден в переписке.
2. **Given** открыты две вкладки одного подключения, **When** владелец закрывается, **Then** сохраняется предусмотренное поведение владения без двух одновременно активных читателей.
3. **Given** иконка изменила внутренний path без изменения назначения, **When** выполняется проверка управления, **Then** тест оценивает доступное действие и результат, а не строку SVG.
4. **Given** браузерный сценарий упал в CI, **When** смотрят результат задания, **Then** задание неуспешно и доступен предусмотренный отчёт с фиктивными данными.

### Edge Cases

- Медленный ответ, 429 и потеря доступа.
- Переход между узким и широким экраном.
- Закрытие вкладки с незавершённым receive.
- Повторная доставка уже прочитанного сообщения.

### Verification Approach

Один итоговый прогон затронутых Playwright-наборов после серии правок, проверка реестра покрытия и конфигурации CI. Повторять запуск дополнительно только для расследования конкретного сбоя.

Для существующего поведения используются регрессионные проверки и сопоставление покрытия. Добавление тестов после существующей реализации не называется TDD. Обнаруженный дефект описывается отдельно; изменение продуктового поведения требует согласованного требования и Red → Green → Refactor.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. До выполнения 053 приёмочные проверки имеют статус **NotRun**; фактический результат записывается в `verification.md`.

## Requirements

### Functional Requirements

- **FR-001**: Сохранить связные production-сценарии входа, списка, поиска, истории, отправки, получения, статусов, unread и выхода; fake GREEN-API подменяет внешний сервис, но реальные маршруты приложения участвуют в проверке.
- **FR-002**: Сохранить проверки cookie, потери доступа, изоляции подключений, нескольких вкладок, Web Locks и завершения владения; управляемая подмена внешних условий не заменяет проверяемый browser API.
- **FR-003**: Заменить сравнение внутренней SVG/DOM-разметки и хрупкие селекторы на роли, доступные имена и пользовательские действия; точные геометрические проверки сохранить там, где размер является контрактом интерфейса.
- **FR-004**: Сохранить проверки клавиатуры, фокуса, прокрутки, адаптивности, тем и безопасного отображения текста без обязательного добавления screenshot-тестов ко всем экранам.
- **FR-005**: Использовать ожидания конкретных состояний и изолированные фикстуры; retry runner не маскирует воспроизводимый дефект или гонку.
- **FR-006**: Удалять перенесённые повторы только по карте 028; сквозная проверка может сознательно пересекаться с unit-тестом, если доказывает соединение слоёв.
- **FR-007**: Обновить CI и инструкции: все оставшиеся наборы выполняются, отчёты ошибок доступны, отсутствие браузера или незапущенный набор явно отмечены.

### Scope Boundaries

- **В объёме**: Состав и устойчивость Playwright-проверок, браузерные гарантии и итоговая карта переноса.
- **За пределами**: Реальная переписка через GREEN-API, платные среды, обязательная матрица всех браузеров и новая визуальная инфраструктура.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Сценарии используют синтетические подключения и сообщения; отправка реальным получателям не требуется.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Пользовательский путь, production-приложение, browser context, внешний fake-провайдер, отчёт.

## Success Criteria

- **SC-001**: Карта связывает все критические пути с реальными browser/HTTP проверками без потери контракта (FR-001, FR-002, FR-006).
- **SC-002**: Селекторы и ожидания выражают поведение, а необходимые layout-проверки сохранены (FR-003, FR-004, FR-005).
- **SC-003**: Все оставшиеся наборы включены в CI и имеют воспроизводимые команды и отчёты (FR-007).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Узкое пользовательское разрешение позволяет commit/push только в `refactor`; отправка реальных сообщений не требуется.
