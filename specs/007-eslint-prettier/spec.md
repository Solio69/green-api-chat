# Feature Specification: ESLint и Prettier

**Feature Directory**: specs/007-eslint-prettier
**Created**: 2026-10-01
**Status**: Реализована и проверена
**User Approval**: Правила и объём согласованы в текущем обсуждении.
**Workflow Mode**: Standard с сохранённой предварительной авторизацией
**Implementation Authorization**: Пользователь явно разрешила подготовку документов,
установку нужных зависимостей и исправление кода после завершения соседнего треда.
Тред «Подготовить тестовое Грин-Апи» завершил текущие правки 2026-10-01.
**Input**: Первая из четырёх задач кодстайла: готовые ESLint-правила и Prettier.
Собственные ESLint-правила не входят в объём.

## User Scenarios & Testing

### User Story 1 — проверять и исправлять код из VS Code (Priority: P1)

Как разработчик, я запускаю существующие проверки из NPM Scripts и вижу нарушения
согласованного кодстайла с путём и строкой; автоисправления доступны отдельно.

**Why this priority**: Автоматические проверки уменьшают число ручных замечаний.
**Independent Test**: Проверить корректный и некорректный код через действующие
конфигурации ESLint и Prettier, затем выполнить проверки всего проекта.

**Acceptance Scenarios**:

1. **Given** TypeScript, тест или конфигурация нарушает порядок импортов,
   **When** запускается lint, **Then** проверка завершается с ошибкой и указывает нарушение.
2. **Given** код содержит явный any, лишнюю конкатенацию строк, лишний
   boolean-тернарник или блок стрелочной функции с единственным return,
   **When** запускается lint, **Then** применимое готовое правило отклоняет код.
3. **Given** строка JavaScript/TypeScript заканчивается необязательной точкой с запятой,
   **When** запускается format:check, **Then** проверка сообщает нарушение;
   format исправляет его, сохраняя необходимые защитные символы ASI.
4. **Given** изменения допустимы к автоисправлению,
   **When** запускаются lint:fix и format, **Then** они исправляют код;
   повторное применение не даёт новых изменений.

### User Story 2 — сохранить работающий вход и серверные контракты (Priority: P1)

Как разработчик, я получаю единый стиль приложения и тестов без изменения поведения.

**Why this priority**: Существующая авторизация и её тесты должны остаться рабочими.
**Independent Test**: Итоговые typecheck, lint, format:check, интеграционные и E2E-тесты.

**Acceptance Scenarios**:

1. **Given** готовая форма, сессия и HTTP-маршруты,
   **When** применяются исправления кодстайла, **Then** существующие 66 интеграционных
   и 24 браузерных/HTTP-проверки проходят с прежними ожиданиями.
2. **Given** специальные файлы Next.js и use client,
   **When** сортируются импорты и выделяются type-импорты,
   **Then** серверные/клиентские границы, директивы и обязательные экспорты сохраняются.
3. **Given** в рабочем дереве находятся изменения пользователя и соседнего агента,
   **When** выполняется задача, **Then** эти изменения сохраняются; агент не выполняет операции записи Git index.

### Edge Cases

- Импорты только ради побочного эффекта (например globals.scss) не переставляются
  автоматически: их порядок может влиять на выполнение.
- SCSS Modules с импортированным объектом styles располагаются после обычных импортов.
- Type-only imports следуют группе своего источника, без отдельной группы типов.
- Зависимые от Prettier правила curly не включаются: длинная строка может вызывать
  конфликт форматтера и линтера. Действующее правило коротких if проверяется при ревью.
- no-unneeded-ternary покрывает готовые boolean-упрощения; условный JSX через &&
  и выбор констант не выдаются за полностью автоматизированные проверки.
- Синтаксические точки с запятой в SCSS и защитные символы JavaScript не запрещены.
- Тестовые константы и независимые ожидания публичного контракта сохраняются.

### Verification Approach

Это изменение конфигурации и рефакторинг представления существующего кода.
Новая бизнес-логика и серверные контракты не создаются; искусственный Red не требуется.
Исходное покрытие подтверждено итогом соседнего треда: 66 integration и 24 E2E
прошли перед началом этой задачи. Конфигурации проверяются положительными и
отрицательными примерами через ESLint API и Prettier без сохранения
нарушающих файлов в проекте. После всей серии правок выполняются один итоговый
проход lint, format:check, typecheck, проверка совместимости с Prettier,
интеграционные и браузерные тесты. E2E включает production build.

## Requirements

### Functional Requirements

- **FR-001**: Сохранить готовые проверки Next.js, React, TypeScript и strict-типизацию.
- **FR-002**: Prettier форматирует JavaScript/TypeScript без необязательных конечных
  точек с запятой; действующие два пробела, одинарные кавычки, trailingComma all
  и LF сохраняются. SCSS следует своему синтаксису.
- **FR-003**: ESLint проверяет порядок импортов: Node.js, внешние пакеты,
  внутренние @/, относительные импорты, импортированные SCSS Modules.
  В группах используется алфавит без учёта регистра; пустых строк между import
  нет, после блока одна пустая строка. Порядок side-effect imports сохраняется.
- **FR-004**: ESLint запрещает явный any и неиспользуемые значения в TypeScript;
  type-only imports оформляются явно. Вывод типов сохраняется.
- **FR-005**: Готовые правила требуют шаблонные строки вместо строкового +,
  короткое тело возвращающей стрелочной функции и безопасное упрощение лишних
  boolean-тернарников. Неприменимые смысловые преобразования не выполняются.
- **FR-006**: Применить эти правила к src, TypeScript-тестам и JavaScript/TypeScript
  конфигурациям. Генерируемые файлы, зависимости, секреты и служебный Spec Kit исключены.
- **FR-007**: lint и format:check остаются проверками без автоисправления;
  lint:fix и format явно изменяют файлы и доступны в NPM Scripts.
- **FR-008**: Конфигурации совместимы; повторные lint:fix/format не порождают новый diff.
- **FR-009**: Поведение формы, сессий, API и тестовые ожидания сохраняются. Агент не меняет Git index; изменения других процессов фиксирует без отката.
  Итоговые проверки должны пройти; их фактические результаты записываются.
- **FR-010**: Обновить описание команд и ссылку на автоматические конфигурации;
  сохранить остальные действующие правила до их переноса в отдельной задаче.

### Scope Boundaries

- В объёме: ESLint, Prettier, нужная прямая зависимость, lock-файл, команды,
  применение кодстайла к существующему коду, документы этой задачи и регрессия.
- За пределами: Stylelint, проверки структуры, собственные правила линтера,
  общий check, GitHub Actions, полная замена CODE_STYLE.md, CODING_RULES.md,
  создание skill, функциональные изменения, публикация и БД.

### Data Effects & User Decision

- **Changed data**: Конфигурации, форматирование исходников/тестов и документы;
  пользовательские сообщения, сессии и данные БД не изменяются.
- **Preview**: Результат виден в diff и отчётах проверок.
- **Confirmation**: Авторизация пользователя из переписки действует на текущий объём.
- **Cancellation**: Автоматического отката или удаления чужих изменений нет.
- **Idempotency and duplicates**: Повторное автоисправление не меняет уже корректный код.
- **Failure result**: Ошибки окружения фиксируются отдельно от ошибок поведения;
  обязательная заблокированная проверка не выдаётся за успех.

### Key Entities

Продуктовые сущности и новая модель данных неприменимы.
Конфигурации являются единственным исполняемым источником автоматических правил.

## Success Criteria

- **SC-001**: Положительные и отрицательные примеры подтверждают активность
  согласованных ESLint-правил в приложении, тестах и конфигурациях.
- **SC-002**: Prettier удаляет обычные конечные ; в JS/TS и сохраняет ASI-безопасность.
- **SC-003**: Проверка конфликтов конфигураций и повторный цикл автоисправлений успешны.
- **SC-004**: lint, format:check, typecheck, 66 integration и 24 E2E проходят.
- **SC-005**: Документы описывают действующие команды; агент не выполняет запись Git index, сохраняет текущий staging и фиксирует результаты его контроля.

## Assumptions and Dependencies

- Next.js 16.3.7, ESLint 9.39.5, Prettier 3.9.9 и TypeScript 5.9.3 установлены.
- eslint-plugin-import 2.32.0 уже находится в node_modules как зависимость Next.js.
  Если конфигурация непосредственно импортирует его, он фиксируется как devDependency.
- Установка нужной зависимости в этой задаче явно разрешена пользователем;
  общее ограничение установок для остальных задач сохраняется.
- Chromium и Playwright уже подготовлены; реальные реквизиты не нужны.
