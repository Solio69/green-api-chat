## User Scenarios & Testing

### User Story 1 — Браузерные проверки Playwright в CI (Priority: P1)

CI подтверждает работу production-приложения в Chromium и сохраняет данные, необходимые для разбора браузерного сбоя.

**Why this priority**: Это обязательная часть результата этапа R03; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Локально проверить команды CI на фиктивных данных; после публикации подтвердить production smoke и диагностический сценарий падения на GitHub. Локальный запуск не подменяет удалённый результат.

**Acceptance Scenarios**:

1. **Given** приложение собрано в CI с фиктивным окружением, **When** выполняется вход и обмен сообщениями, **Then** сценарий проходит через настоящее приложение и контролируемый провайдер.
2. **Given** браузерный сценарий падает, **When** job завершена, **Then** общий результат неуспешен, отчёт и trace доступны для разбора.
3. **Given** запускаются основной и query-наборы, **When** CI готовит серверы, **Then** их порты и артефакты не конфликтуют, каждый набор проверяет своё приложение.

### Edge Cases

- Сбой сборки или старта сервера до открытия браузера.
- Различия Windows разработки и ОС CI.
- Наличие внешних аватаров и ссылок: тесты используют контролируемые ответы.
- Отсутствие установленного браузера в чистом runner.

### Verification Approach

Локально проверить команды CI на фиктивных данных; после публикации подтвердить production smoke и диагностический сценарий падения на GitHub. Локальный запуск не подменяет удалённый результат.

Проверяется действующая конфигурация: успешный штатный сценарий и контролируемый нарушающий пример должны дать ожидаемый результат. Ошибка установки или импорта не считается подтверждением TDD. Если выяснится, что требуется изменить бизнес-логику, такая часть выполняется по согласованному контракту через Red → Green → Refactor.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации сейчас имеют статус **NotRun**: этот документ задаёт объём, а не подтверждает выполненный рефакторинг.

## Requirements

### Functional Requirements

- **FR-001**: Добавить к CI запуск Playwright Chromium и установку соответствующего браузера с системными зависимостями в CI-окружении.
- **FR-002**: Проверять production-сборку приложения на синтетическом GREEN-API; предотвращать обращения тестов к реальному провайдеру.
- **FR-003**: Запускать существующий query-стенд до переноса его сценариев; состав выполняемых наборов связывать с реестром 028 и обновлять по мере миграции.
- **FR-004**: Изолировать серверы, порты, каталоги сборки и результаты наборов; исключить ненужную повторную сборку одной конфигурации внутри одной job.
- **FR-005**: При сбое сохранять HTML-отчёт, trace и имеющиеся скриншоты; отсутствие отчёта при ошибке старта должно быть явно диагностировано.
- **FR-006**: Поддержать воспроизводимость времени, фикстур и viewport; повторный запуск не должен скрывать нестабильный тест и выдавать его за безусловный успех.
- **FR-007**: Общий CI успешен только при успехе быстрых и браузерных проверок; итог подтверждается на фактическом удалённом commit.

### Scope Boundaries

- **В объёме**: Браузерная job, запуск production и временного query-стенда, отчёты и итоговый CI-статус.
- **За пределами**: Расширение поддержки браузеров, автодеплой, реальные сообщения и массовая переделка E2E-сценариев.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Меняются CI и необходимые настройки тестового запуска. CI создаёт временные сборки и артефакты без реальных переписок.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Production build, browser context, fake provider, trace, отчёт Playwright.

## Success Criteria

- **SC-001**: Production и остающийся query-набор проходят в чистом CI с установленным Chromium (FR-001–FR-004).
- **SC-002**: Проверенный браузерный сбой даёт доступный диагностический артефакт и неуспешный итог (FR-005–FR-007).
- **SC-003**: Нет запросов к реальному GREEN-API и конфликтов окружений; результат привязан к commit (FR-002, FR-004, FR-007).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Подготовка спецификаций не включает commit, push или отправку реальных сообщений.
