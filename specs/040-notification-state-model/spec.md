## User Scenarios & Testing

### User Story 1 — Явная модель состояний получения уведомлений (Priority: P1)

Состояние подключения определяет допустимые действия и доступность отправки без противоречивых комбинаций независимых флагов.

**Why this priority**: Это обязательная часть результата этапа R06; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Табличные unit-тесты Vitest для переходов, integration-тесты существующего контроллера и React-проверки UI. Для сохранения поведения используются регрессионные тесты; новый контракт при необходимости проходит Red → Green → Refactor.

**Acceptance Scenarios**:

1. **Given** получено валидное событие, **When** оно применено к модели, **Then** состояние допускает ACK и запрещает следующий receive до подтверждения.
2. **Given** соединение работало и временно отказало, **When** оно восстановилось, **Then** отправка вновь доступна и recovery публикуется один раз для этого восстановления.
3. **Given** поколение закрыто, **When** приходит его позднее событие успеха, **Then** новое состояние и доступность отправки не меняются.

### Edge Cases

- Повторные start, retry и close.
- Истечение proof при pending ACK.
- Исходящие уведомления отключены при доступном подключении.
- Ошибка доступа имеет приоритет над восстановлением прежнего поколения.

### Verification Approach

Табличные unit-тесты Vitest для переходов, integration-тесты существующего контроллера и React-проверки UI. Для сохранения поведения используются регрессионные тесты; новый контракт при необходимости проходит Red → Green → Refactor.

Для сохранения поведения используются исходная карта 028 и подтверждённые регрессионные проверки. Искусственный Red для перемещения кода не требуется. Новая или изменяемая бизнес-логика, включая согласованные защиты от гонок, выполняется через Red → Green → Refactor после разрешения реализации. Обнаруженное расхождение с текущим контрактом сначала фиксируется, а не исправляется незаметно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации сейчас имеют статус **NotRun**: этот документ задаёт объём, а не подтверждает выполненный рефакторинг.

## Requirements

### Functional Requirements

- **FR-001**: Описать типизированные состояния connecting, connected, retrying, limited, paused и closed и допустимые переходы по событиям существующего контроллера.
- **FR-002**: Представить чистую функцию перехода без fetch, таймеров, DOM и QueryClient; команды для внешних действий отделены от вычисления нового состояния.
- **FR-003**: Выводить canSend и видимое предупреждение из непротиворечивого состояния; сохранить действующие ограничения отправки при соединении, сбое, паузе и отсутствии владения.
- **FR-004**: Учитывать различие ожидаемого receive и pending ACK, не допуская нового receive до завершения текущего ACK.
- **FR-005**: Явно моделировать ошибки доступа, некорректное событие, неподдерживаемые Web Locks, занятое владение, временный сбой и ручной retry.
- **FR-006**: Сохранить существующие тексты и семантику NotificationNotice, предупреждение об отключённых исходящих уведомлениях и правила публикации recovery.
- **FR-007**: Проверить матрицу переходов, включая повторные и устаревшие события; закрытое поколение не может самопроизвольно стать действующим.

### Scope Boundaries

- **В объёме**: Чистая модель, таблица переходов, подключение её результата к существующему контроллеру и UI.
- **За пределами**: Новый state manager, изменение протокола ACK и переработка всех сетевых эффектов задачи 041.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Меняется внутреннее представление состояния клиента; серверные контракты и память переписки сохраняются.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Состояние, событие, поколение, pending ACK, команда эффекта, состояние доступности отправки.

## Success Criteria

- **SC-001**: Каждая строка таблицы переходов имеет проверку и недопустимые сочетания исключены типами или явной валидацией (FR-001–FR-003, FR-007).
- **SC-002**: Последовательность receive/ACK и реакции на ошибки совпадают с текущим поведением (FR-004, FR-005).
- **SC-003**: UI и число recovery-событий сохранены в регрессии (FR-006).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Подготовка спецификаций не включает commit, push или отправку реальных сообщений.
