## User Scenarios & Testing

### User Story 1 — Общий транспорт GREEN-API и политики операций (Priority: P1)

Серверные адаптеры используют общий транспорт, сохраняя безопасные различия между чтением, получением уведомления, удалением и отправкой сообщения.

**Why this priority**: Это обязательная часть результата этапа R05; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Vitest с fake fetch, deferred ответами и управляемым ожиданием; сохранить независимые проверки методов, URL и результатов. E2E обмена сообщениями проверяет соединение адаптеров с приложением.

**Acceptance Scenarios**:

1. **Given** чтение получает предусмотренный повторяемый 429, **When** адаптер выполняет свою политику, **Then** происходит допустимое число повторов с прежним итоговым результатом.
2. **Given** SendMessage был отправлен, но ответ потерян, **When** транспорт завершает попытку, **Then** возвращается unknown без второго SendMessage.
3. **Given** ответ провайдера содержит некорректный JSON или секрет в описании, **When** адаптер нормализует отказ, **Then** клиент получает безопасный предусмотренный код без сырого тела.

### Edge Cases

- Отмена до отправки и после начала отправки имеют разные последствия.
- Retry-After в секундах и в форме даты.
- Пустой receive, redirect, 400, 401, 403, 429 и 5xx.
- Некорректный idMessage при формально успешном ответе.

### Verification Approach

Vitest с fake fetch, deferred ответами и управляемым ожиданием; сохранить независимые проверки методов, URL и результатов. E2E обмена сообщениями проверяет соединение адаптеров с приложением.

Для сохранения поведения используются исходная карта 028 и подтверждённые регрессионные проверки. Искусственный Red для перемещения кода не требуется. Новая или изменяемая бизнес-логика, включая согласованные защиты от гонок, выполняется через Red → Green → Refactor после разрешения реализации. Обнаруженное расхождение с текущим контрактом сначала фиксируется, а не исправляется незаметно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации сейчас **NotRun**; результаты будут в verification.md.

## Requirements

### Functional Requirements

- **FR-001**: Объединить построение URL, кодирование реквизитов, no-store, redirect policy и получение сырого ответа в серверном транспорте с внедряемым fetch.
- **FR-002**: Оставить адаптерам методов нормализацию DTO и предметную классификацию ответов; исходные тела провайдера и URL с токеном не выходят в клиентские ошибки и логи.
- **FR-003**: Явно задать политику deadline и caller cancellation каждой операции, сохраняя текущие пределы и особенности отправки после начала удалённой попытки.
- **FR-004**: Сохранить повторы чтения после 429 там, где они уже предусмотрены; SendMessage не повторяется автоматически при таймауте, сетевом сбое или неизвестном исходе.
- **FR-005**: Сохранить разбор Retry-After и backoff получения уведомлений, порядок receive/ACK и отдельную семантику DeleteNotification false.
- **FR-006**: Передавать время, ожидание и транспорт как контролируемые зависимости там, где это нужно для детерминированных тестов; не вводить универсальную политику retry для всех методов.
- **FR-007**: Перевести существующие методы провайдера на общий транспорт по одному, сохранив их публичные типы результатов либо совместимые адаптеры до завершения перехода.

### Scope Boundaries

- **В объёме**: Серверный транспорт, действующие адаптеры GREEN-API и их тестовые зависимости.
- **За пределами**: Новые методы провайдера, SDK, автоматические повторы отправки и изменение лимитов продукта.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Меняется внутреннее устройство серверной интеграции. Реальная очередь и реальные сообщения при тестировании не используются.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Транспортный ответ, политика операции, deadline, результат провайдера, нормализованный DTO.

## Success Criteria

- **SC-001**: Все действующие адаптеры используют общие транспортные правила без дублирования URL и базового fetch (FR-001, FR-007).
- **SC-002**: Матрица ошибок, повторов и отмен подтверждает прежние результаты по каждому методу (FR-002–FR-005).
- **SC-003**: Тесты времени воспроизводимы и доказано отсутствие повторного SendMessage (FR-004, FR-006).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Подготовка спецификаций не включает commit, push или отправку реальных сообщений.
