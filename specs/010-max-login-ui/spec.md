# Feature Specification: D01 — экран входа в стиле MAX

**Feature Directory**: specs/010-max-login-ui
**Created**: 2026-10-01
**Status**: Реализована и проверена; ожидает ревью кода пользователем
**User Approval**: Получено 2026-10-01: «ок, готовь» в ответ на требования и предложение подготовки технического комплекта
**Workflow Mode**: Standard
**Implementation Authorization**: Получено 2026-10-01: «можешь приступать к спекам и редизайну страницы логина, делай все сама до моей проверки кода»
**Input**: Оформить существующую `/login` в согласованном стиле MAX и показать заметный индикатор во время реального входа. Серверный вход и сессия уже существуют. Согласованные правки по ревью включают переходы при входе и явном выходе без полной перезагрузки, стабильную геометрию ошибок и ссылку на кабинет.

## User Scenarios & Testing

### User Story 1 — понятный экран входа (Priority: P1)

Пользователь вводит реквизиты GREEN-API на компактном экране, оформление которого соответствует согласованному чату. Он видит подписи полей, управление видимостью токена, кнопку входа и ссылку на кабинет.

**Why this priority**: Это первый экран полного сценария; его можно завершить и проверить независимо от ещё не реализованной переписки.

**Independent Test**: Открыть `/login` на телефоне и широком экране, сравнить с [согласованным макетом](../../docs/ui-references/max-chat-mockup.html), пройти форму клавиатурой.

**Acceptance Scenarios**:

1. **Given** пользователь без сессии открывает `/login`, **When** страница отображается, **Then** видна карточка в теме устройства с заголовком «Подключение к GREEN-API», двумя подписанными полями и акцентной кнопкой «Войти».
2. **Given** токен скрыт, **When** пользователь нажимает глаз внутри поля, **Then** видимость меняется, значение сохраняется, доступное название описывает следующее действие.
3. **Given** форма пустая, **When** нажаты «Войти» или Enter, **Then** ошибки обязательных полей отображаются по действующим правилам формы; при исправлении поля обновляются.
4. **Given** обязательные реквизиты заполнены, **When** пользователь входит, **Then** выполняется существующий серверный сценарий; макет не заменяет его демонстрационным успехом.

### User Story 2 — видеть ожидание и результат проверки (Priority: P1)

Пользователь понимает, что запрос выполняется, не отправляет повторный вход и получает существующий результат авторизации.

**Why this priority**: Визуальная обратная связь нужна сразу при реальном входе, особенно при задержке сервиса.

**Independent Test**: Удержать ответ нашего API средствами браузерного теста, проверить состояние ожидания, затем завершить запрос успехом и ошибкой.

**Acceptance Scenarios**:

1. **Given** запрос входа выполняется, **When** ответ задерживается, **Then** в кнопке виден индикатор и текст проверки, поля и повторное действие заблокированы; размер кнопки не меняется при появлении индикатора.
2. **Given** запрос входа принят, **When** API подтверждает успешный вход, **Then** сохраняется существующий переход на `/`; искусственная задержка для демонстрации индикатора не добавляется.
3. **Given** запрос завершился ошибкой, **When** отображён результат, **Then** индикатор исчезает, форма доступна для исправления и повторной попытки, ошибка поля или формы оформлена согласно её смыслу.
4. **Given** пользователь предпочитает уменьшенное движение, **When** форма ожидает ответ, **Then** текст и статичный индикатор ожидания остаются видимыми без вращения.

### User Story 3 — пользоваться формой на узком экране (Priority: P1)

Пользователь читает сообщения об ошибках и взаимодействует с полями, глазом и кнопкой на телефоне и с клавиатуры.

**Why this priority**: Мобильный вариант согласован как обязательный для полного сценария.

**Independent Test**: Проверить страницу при ширине 320, 360, 390 и 1280 CSS px, длинной ошибке, Tab-навигации и увеличении текста.

**Acceptance Scenarios**:

1. **Given** ширина экрана 320 CSS px, **When** показана форма с длинной ошибкой, **Then** горизонтального скролла нет, сообщения переносятся, элементы не перекрываются.
2. **Given** поле без ошибки, **When** оно получает фокус, **Then** видны тонкая синяя граница и мягкая подсветка.
3. **Given** поле с ошибкой, **When** оно получает фокус, **Then** граница и подсветка соответствуют ошибке, дополнительный синий контур отсутствует.
4. **Given** пользователь проходит форму клавишей Tab, **When** фокус переходит на глаз, кнопку и ссылку, **Then** он остаётся видимым, доступные названия понятны, токен не отправляется нативной HTML-формой.

### Edge Cases

- Быстрый ответ API не требует минимальной искусственной длительности загрузки.
- Повторные Enter и клики во время ожидания не создают второй запрос; существующая защита сохраняется.
- Ошибки сервера, включая потерю доступа, длинный текст и временную недоступность, не скрываются декоративной разметкой.
- При отсутствии JavaScript и до готовности React сохраняется существующая защита от нативной отправки реквизитов.
- Пустые или состоящие из пробелов обязательные поля сохраняют действующее поведение. Дополнительная клиентская валидация только цифр из мокового макета не переносится этой задачей.
- На низком экране допускается вертикальная прокрутка страницы вместо обрезания формы.
- Смена темы устройства обновляет фон, карточку, поля, текст и ошибки без потери введённых реквизитов и без перезагрузки. Отдельного переключателя темы нет.
- Появление и исправление однострочных ошибок реквизитов не меняют высоту и положение карточки. При увеличении текста и длинных общих ошибках доступность содержимого важнее фиксированной высоты.
- Системный режим повышенной контрастности не должен скрывать фокус после удаления стандартной рамки.

### Verification Approach

Задача меняет оформление и визуализацию уже существующего состояния ожидания. Серверная логика, HTTP-контракты и правила проверки полей остаются действующими. Для чистого оформления искусственный Red не требуется. Клиентские переходы при входе/выходе и обработка отказа выхода проверяются по TDD: сохраняемый тест, подтверждённый поведенческий Red, реализация и Green.

После отдельного разрешения реализации используются имеющиеся Playwright-проверки входа и доступности формы, проверка задержанного ответа для индикатора, визуальное сравнение широкого/узкого экрана, контраст и отсутствие переполнения. Если понадобится поведение сверх согласованных клиентских переходов либо изменение серверного контракта, это не включается молча в оформление: соответствующий объём согласуется и проходит TDD.

Тестовые сценарии готовятся до оформления; запуск выполняется после завершения серии правок. Инструменты, команды и пути тестов описаны в техническом плане; фактические результаты — в [verification.md](verification.md). Итоговые проверки выполняются один раз после законченной задачи и серии правок.

## Requirements

### Functional Requirements

- **FR-001**: Оформление `/login` соответствует экрану входа согласованного макета и автоматически следует светлой/тёмной теме устройства: спокойный фон, карточка с мягкой тенью, скругления, синий/сиреневый акцент, без зелёной верхней декоративной полосы.
- **FR-002**: Сохраняются заголовок, подписи двух реквизитов, сведения об обязательности. Под формой есть одна ссылка «Открыть личный кабинет GREEN-API» с акцентом MAX, открывающая отдельную вкладку безопасно. Дополнительных строк «Где взять реквизиты?» и «Откроется в новой вкладке» нет. В интерфейсе нет демонстрационных реквизитов и приглашения войти с произвольными значениями.
- **FR-003**: Переключение токена остаётся глазом внутри поля; оно сохраняет значение, клавиатурную доступность и доступное имя действия.
- **FR-004**: Локальные ошибки появляются после «Войти» или Enter, обновляются при исправлении и связываются с полями по существующим правилам. Ошибки под полями — компактный красный текст 12 CSS px с отступом 6 CSS px от поля; под каждую ошибку заранее резервируется высота одной строки и отступа, поэтому карточка не скачет при пустом submit и исправлении полей. Серверные ошибки и сообщение о потере доступа сохраняются.
- **FR-005**: Во время существующего `isSubmitting` кнопка показывает заметный индикатор и текст проверки. Состояние ожидания доступно вспомогательным технологиям; индикатор не заменяет текст.
- **FR-006**: Повторная отправка и изменение полей во время запроса остаются заблокированы. Оформление не добавляет запрос, задержку, новое правило проверки или изменение срока сессии.
- **FR-007**: При подтверждённом успешном входе выполняется клиентский переход на `/` без полной загрузки документа; серверная проверка сессии сохраняется. При ошибке ожидание завершается и доступна повторная попытка. Оформление не имитирует успех API.
- **FR-008**: Фокус поля без ошибки использует акцентную границу и мягкую подсветку; для ошибочного поля применяется только подсветка ошибки. Фокус глаза, кнопки и ссылки видим. В покое ошибочное поле имеет тонкую красную рамку; подсветка появляется при фокусе.
- **FR-009**: При ширине от 320 CSS px форма и ошибки помещаются по ширине. На низком экране есть вертикальная прокрутка. Области глаза и кнопки — не меньше 44×44 CSS px, размер текста полей на телефоне — не меньше 16 CSS px.
- **FR-010**: Контраст обычного текста, ошибок и текста кнопки в обеих темах — не ниже 4.5:1. При уменьшенном движении индикатор не вращается, а состояние ожидания остаётся понятным.
- **FR-011**: Существующая защита реквизитов до готовности React и без JavaScript сохраняется. Реквизиты не выводятся в логи, URL, локальное хранилище или демонстрационные подписи.
- **FR-012**: Оформление реализуется по текущему кодстайлу: переиспользуются существующие компоненты, SCSS Modules, токены и миксины. Палитра наследуется от корня приложения; вход, главная, поиск и выход следуют одной системной теме без изменения поведения форм.
- **FR-013**: При явном выходе клиент отправляет существующий POST выхода, после подтверждённого ответа открывает `/login` без полной перезагрузки и обновляет данные маршрутизатора. Повторный запрос во время ожидания блокируется. При сбое отображается сообщение рядом с кнопкой, доступна повторная попытка; успех выхода не имитируется. Нативная POST-форма остаётся fallback без JavaScript, а серверный контракт 303/удаления cookie не меняется.

### Scope Boundaries

- В объёме: оформление существующего экрана входа, его состояний, индикатор существующего реального запроса, адаптивность и доступность, согласованные клиентские переходы входа/явного выхода и отображение ошибки выхода.
- За пределами: `GetAccountSettings`, шапка своего аккаунта, изменение поведения формы поиска, чат, сообщения, галочки, новые маршруты, изменение сессии, ручной переключатель темы и публикация макета.
- Существующие серверные контракты [входа](../006-login-session/contracts/login-api.md) и [выхода](../008-logout/contracts/logout.md) не переопределяются.

### Data Effects & User Decision

- **Changed data**: только оформление и представление существующих состояний формы после разрешения реализации. Нет новых сохраняемых данных, миграций и настроек инстанса.
- **Preview**: [макет](../../docs/ui-references/max-chat-mockup.html); точное поведение рабочего входа определяется этой спекой и действующим контрактом, а не демонстрационным скриптом.
- **Confirmation**: обычное «Войти» подтверждает запрос; дополнительное продуктовое подтверждение не требуется. Согласование документа и разрешение агенту писать код — отдельные решения.
- **Cancellation**: пользователь может покинуть страницу без создания нового запроса; отдельная кнопка отмены входа не добавляется.
- **Idempotency and duplicates**: сохраняется существующая защита повторного submit; новых правил API не вводится.
- **Failure result**: форма показывает существующий смысл ошибки и становится доступна после завершения ожидания.

### Key Entities

- Существующие реквизиты формы: `idInstance`, `apiTokenInstance`.
- Существующие состояния: ошибки полей/сервера, видимость токена, готовность React, ожидание запроса.
- Индикатор — представление ожидания, не самостоятельный источник состояния и не новая сущность хранения.

## Success Criteria

- **SC-001**: Экран на 390 и 1280 CSS px соответствует согласованной композиции и синей/сиреневой палитре в обеих темах устройства; есть одна акцентная ссылка на кабинет, дополнительных строк помощи и зелёной декоративной полосы нет. Покрывает FR-001–FR-003.
- **SC-002**: Проверка пустой формы, исправления, переключения токена, серверной ошибки, потери доступа и успешного входа сохраняет действующее поведение. Покрывает FR-002–FR-004, FR-007, FR-011.
- **SC-003**: При удерживаемом ответе API индикатор и текст видны, повторное действие заблокировано; после ответа ожидание прекращается или выполняется переход. Покрывает FR-005–FR-007, FR-013.
- **SC-004**: На 320, 360, 390 и 1280 CSS px нет горизонтального переполнения, длинная ошибка не перекрывает управление; все действия доступны с клавиатуры. Покрывает FR-008, FR-009.
- **SC-005**: Проверка контраста, уменьшенного движения и фокуса проходит для исходного, ожидающего и ошибочного состояний; смена светлой/тёмной темы не очищает поля. Покрывает FR-008–FR-010.
- **SC-006**: Ревью показывает соблюдение кодстайла и отсутствие изменений серверных контрактов, новых зависимостей, потери защиты реквизитов и непредусмотренного изменения соседних форм. Покрывает FR-006, FR-011–FR-013.

## Assumptions and Dependencies

- Визуальный макет утверждён пользователем; [общая спецификация UI](../../docs/chat-ui-spec.md) описывает весь целевой сценарий и его последующие отдельные этапы.
- Вход и сессия уже реализованы в задаче 006, защита формы — в 004; ожидание запроса уже существует в `LoginForm`.
- Наличие имеющихся Playwright, Chromium и SCSS подтверждено проектом. Новые установки не требуются для подготовки документа.
- Фиксированный API origin и метод `GetStateInstance` используются действующим сервером; задача не добавляет поле `apiUrl`.
- Макет не является тестовым стендом реального API. Его локальный успех, данные профиля и имитация задержек не определяют рабочие правила.
- Техническая подготовка описана в [plan.md](plan.md), [research.md](research.md), [data-model.md](data-model.md), [контракте UI](contracts/login-ui.md), [quickstart.md](quickstart.md) и [tasks.md](tasks.md). Полный анализ сохраняется в `analysis.md` после read-only прохода. Разрешение реализации получено отдельным решением пользователя в переписке.
