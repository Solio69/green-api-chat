# Implementation Plan: D01 — экран входа в стиле MAX

**Spec:** [spec.md](spec.md).
**Дата:** 2026-10-01.
**Согласование spec.md:** получено в переписке: «ок, готовь» в ответ на требования и предложение технической подготовки.
**Разрешение на реализацию:** получено 2026-10-01; разрешены спецификации и редизайн страницы логина до проверки кода пользователем.

## Summary

Оформить существующую `/login` по согласованному MAX-референсу, сохранить реальный вход и показать его ожидание. Переиспользовать `LoginForm`, `CredentialField`, `TokenVisibilityButton`, `SubmitButton`, SCSS Modules и текущие тесты. Новые продуктовые компоненты и зависимости не нужны. Согласованная правка явного выхода использует существующий `LogoutButton`.

Палитра изолируется CSS custom properties на оболочке входа. Цвета и повторяемые размеры/тени хранятся в `_tokens.scss`, значения по умолчанию общих компонентов сохраняются. `SubmitButton` получает необязательный `isLoading`, связанный только с существующим `isSubmitting`; доступный статус размещается отдельно от busy fieldset.

## Technical Context

- Существующие Next.js 16.3.7, React 19.3.0, TypeScript, Sass и Playwright 1.63.0 из `package.json`; версии не обновляются.
- `/login` остаётся серверной страницей с клиентской формой. Маршруты, Route Handlers, `iron-session`, GREEN-API и настройки окружения не изменяются.
- Представление существующих состояний и клиентские переходы входа/выхода; новая модель хранения не требуется.
- Светлая/тёмная палитра по `prefers-color-scheme`, общий `color-scheme: light dark` на `:root`; без JS-состояния, хранения или переключателя. Системный font stack без загрузки Inter или других шрифтов.
- Никаких установок, сетевых запросов с реальными реквизитами, Git-записи или изменения БД.

## Tasks and Dependencies

Последовательность [tasks.md](tasks.md): исходное покрытие → сценарии тестов представления → общие токены и миксины → оформление → индикатор существующего запроса → единый итоговый прогон → ревью и отчёт.

Для оформления искусственный Red не требуется; для клиентской навигации и сбоя выхода тест и подтверждённый Red предшествуют реализации. Тесты UI подготавливаются до реализации, без прогона после каждой косметической правки. Клиентские переходы и обработка сбоя выхода согласованы. Изменения серверных правил запроса, валидации, сессии или HTTP-контрактов запрещены этим планом. Если они окажутся необходимы, сначала обсуждение и отдельный TDD-порядок.

## Verification

- Поведенческий Red клиентских переходов: тест фиксирует загрузку документа при входе/выходе и отсутствие сообщения об отказе выхода; ошибка среды Red не заменяет.
- Общая текущая E2E-регрессия включает реализованные вход, профиль 013, слой списка 014, каркас 015 и поиск 016; фактический итоговый запуск приведён в 017 verification. `npm run test:e2e` после завершения серии. Он собирает production и проверяет существующие сценарии входа/безопасности/поиска/выхода плюс D01. Отдельный `npm run build` не дублирует уже успешную сборку этого запуска.
- Затем `npm run typecheck`, `npm run lint`, `npm run lint:styles`, `npm run format:check`. Итоговые команды не запускаются параллельно с работой второго агента или его production-сборкой; требуется свободный момент в общей папке.
- Новые браузерные сценарии: управляемая задержка ответа без фиксированного `waitForTimeout`; видимый индикатор и доступный статус, только один POST, исчезновение ожидания при отказе; начальное состояние и отсутствие ошибки ожидания после завершения.
- Геометрия и фокус: 320/360/390/1280 px, низкий viewport, длинная текущая серверная ошибка, глаза и кнопки 44 px, поля 16 px, отсутствие переполнения; обычный и ошибочный фокус, reduced-motion и forced-colors.
- На 320/1280 px смена темы устройства обновляет фон, карточку, поля, кнопку и ошибки; проверяются 12 px ошибки и сохранение токена.
- Контраст проверяется по вычисленным стилям и ручному осмотру; фиксируются используемые пары, скриншоты и результаты. Цветовые константы сами по себе не тестируются.
- Общая тема: после перехода на `/` поиск, поле и выход наследуют текущую системную палитру; после выхода форма входа сохраняет ту же тему. Ожидания цвета независимы от реализации.
- Существующий keyboard-тест сохраняет видимый outline; новый дизайн не маскирует отсутствие фокуса прозрачным outline.
- Ручной вход с настоящим аккаунтом выполняет пользователь при необходимости; для оформления он не является обязательной заменой управляемому тесту API. Реальные реквизиты не сохраняются.

**Failed:** нарушен FR/SC или существующая регрессия. **Blocked:** окружение/процесс/браузер мешает проверке. **NotRun:** проверка не проводилась. Ничто из этого не называется успешным результатом. Фактические результаты и ограничения — в [verification.md](verification.md).

## Complexity Tracking

Добавляются один необязательный проп, общая системная палитра и один набор тестов представления. У выхода только локальные ожидание/ошибка и защита повторного действия; серверный контракт сохраняется. Нет нового глобального состояния, универсального Button, theme provider, HTTP-endpoint, пакета или хранения. Расширение общего миксина сохраняет его старые вызовы. Последующие экраны обсуждаются отдельно.
