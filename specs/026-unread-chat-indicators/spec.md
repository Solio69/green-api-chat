## User Scenarios & Testing

### US1 — Увидеть сообщение другого чата (Priority: P1)

Пользователь видит синий числовой бейдж у чата, чтобы заметить новые входящие.
**Independent Test**: подать уведомления через синтетический Receive → SSE → ACK и проверить список.

1. **Given** открыт чат А, **When** приходит входящее Б, **Then** у Б счётчик 1.
2. **Given** у Б счётчик 1, **When** повторно обработан тот же idMessage, **Then** остаётся 1.
3. **Given** непрочитанные Б, **When** открыт Б в видимой вкладке, **Then** бейдж Б исчезает; А не меняется.
4. **Given** неизвестный чат, **When** приходит входящее, **Then** существующий session overlay показывает чат с бейджем, даже если GetChats ещё не подтвердил запись.

### US2 — Фоновая вкладка и мобильная навигация (Priority: P1)

1. **Given** открыт А и вкладка скрыта, **When** приходит А, **Then** счётчик А увеличивается.
2. **Given** скрытая вкладка с выбранным А, **When** вкладка становится видимой, **Then** А очищается, остальные сохраняются.
3. **Given** мобильный список скрывает выбранную переписку, **When** приходит её сообщение, **Then** оно считается непрочитанным до открытия переписки.
4. **Given** мобильная переписка, **When** другие чаты имеют непрочитанные, **Then** у «Чаты» отображается общая сумма.

### Edge Cases

Повторы после очистки не возвращают отметку; одинаковые ID в разных чатах независимы. Неподдерживаемое входящее учитывается как одно сообщение. История, исходящие, ignored и статусы доставки не меняют счётчики. Невалидный/чужой scope/owner не меняет память. Поздняя история не сбрасывает отметки. Закрытие подключения очищает память; закрытое подключение не возрождается поздним событием. Смена раскладки учитывает реальную видимость панели. Просмотр старых сообщений в открытой видимой переписке не вводит отдельную семантику прочтения: по согласованному правилу открытый чат считается прочитанным.

### Verification Approach

Бизнес-логика: TDD с поведенческим Red на существующем applyNotification, затем cache/visibility integration и браузерные тесты. Оформление: скриншоты реальных компонентов на 1280/390/320 px, светлая/тёмная тема, переполнение имени и 99+. Реальный аккаунт и очередь не используются.

## Requirements

- **FR-001**: Считать уникальные новые входящие уведомления текущего сеанса отдельно по chatId/idMessage.
- **FR-002**: Не считать историю, исходящие, статусы и ignored; считать нейтральные неподдерживаемые входящие.
- **FR-003**: В открытой видимой переписке не увеличивать счётчик и очищать его при открытии.
- **FR-004**: В скрытой вкладке увеличивать в том числе выбранный чат; при возвращении очищать только реально открытую переписку.
- **FR-005**: На телефоне скрытая панель переписки не считается открытым просмотром; resize должен актуализировать это правило.
- **FR-006**: Повторная доставка после очистки не возвращает счётчик; чужие и невалидные события не учитываются.
- **FR-007**: Бейдж справа от названия соответствует выбранному макету; ноль скрыт, числа больше 99 показаны как 99+.
- **FR-008**: Мобильная кнопка «Чаты» показывает общую сумму, скрывает ноль; доступное описание содержит точное количество.
- **FR-009**: Неизвестный чат получает бейдж через существующий overlay; обновление списка/истории сохраняет отметки.
- **FR-010**: Состояние только в Query RAM подключения, очищается при close/reload/смене scope; без БД, browser persistence, дополнительных provider запросов и Telegram markRead.

### Scope Boundaries

В объёме: счётчики списка и мобильной кнопки, видимость вкладки/панели, идемпотентность, спецификации и проверки. За пределами: browser notifications, звук, toast, превью сообщения, сортировка чатов, пагинация, точный серверный Telegram unread total и новые API.

### Data Effects & User Decision

- **Changed data**: локальные unread IDs и обработанные incoming IDs в памяти Query.
- **Preview**: выбранный HTML-макет «Счётчик»; исходная разметка и палитра приложения сохраняются.
- **Confirmation**: весь цикл и фоновое поведение одобрены в переписке; повторное согласование не требуется.
- **Cancellation**: выход закрывает существующее подключение и очищает его Query.
- **Idempotency and duplicates**: дедупликация chatId/idMessage сохраняется после чтения.
- **Failure result**: существующая ошибка получения сохраняет накопленные отметки; ложных новых отметок не создаётся.

### Key Entities

Unread cache подключения; множество увиденных ID каждого чата; множество непрочитанных ID; идентификатор реально видимой открытой переписки.

## Success Criteria

- **SC-001**: Два разных сообщения Б дают 2, повтор любого даёт те же 2; открытие Б даёт 0 без влияния на А.
- **SC-002**: В браузерной проверке hidden → incoming selected → visible даёт 1 → 0; mobile list → selected incoming сохраняет отметку до открытия.
- **SC-003**: На 320/390/1280 px бейджи не создают горизонтальное переполнение; 100 отображается как 99+, доступное описание сохраняет 100.
- **SC-004**: История, статусы, stale scope/owner и закрытое подключение не создают новые отметки; повтор после чтения также не создаёт.
- **SC-005**: Тесты, typecheck, lint, styles и format проходят; TDD, preview и ревью зафиксированы в verification.

## Assumptions and Dependencies

Получение 022/023, Query 014, история 019 и выбор 025 реализованы. Счётчик отражает уведомления, обработанные текущим приложением, не все непрочитанные Telegram. Фоновая вкладка определяется Page Visibility; не требуется отслеживать внимание пользователя или фокус другого окна. Установки не нужны.
