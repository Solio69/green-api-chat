## User Scenarios & Testing

### User Story 1 — проверять SCSS перед сдачей UI (Priority: P1)

Как разработчик, я запускаю проверку стилей из NPM Scripts и получаю понятную ошибку с файлом и строкой, если SCSS нарушает действующие автоматические правила.

**Why this priority**: Новые компоненты UI используют SCSS Modules; ошибку важно увидеть до коммита.

**Independent Test**: На корректном и заведомо некорректном SCSS проверить успешный и неуспешный запуск Stylelint; затем проверить все стили проекта.

**Acceptance Scenarios**:

1. **Given** корректный SCSS с вложенными БЭМ-селекторами, Sass-переменными и директивой @use, **When** запускается проверка, **Then** она проходит.
2. **Given** ошибка синтаксиса или нарушение активного стандартного правила, **When** запускается проверка, **Then** она завершается неуспешно и указывает место нарушения.
3. **Given** SCSS-файлы компонентов и общие partial-файлы проекта, **When** запускается общая проверка стилей, **Then** каждый применимый исходный файл проверен; зависимости и сгенерированные файлы не проверяются.

### User Story 2 — сохранить совместимость инструментов и интерфейса (Priority: P1)

Как разработчик, я использую Stylelint рядом с Prettier, Sass и Next.js без противоречивых требований и без изменения внешнего вида приложения.

**Why this priority**: Проверка качества не должна ломать существующий UI или заставлять отключать полезные правила целиком.

**Independent Test**: Проверить действующие конфигурации, повторный запуск инструментов и сборку; сверить итоговый diff SCSS на отсутствие изменений поведения.

**Acceptance Scenarios**:

1. **Given** существующий SCSS проекта, **When** применяются согласованные правила Stylelint и Prettier, **Then** итоговые проверки проходят без цикла взаимных автоисправлений.
2. **Given** действующие токены, миксины и БЭМ-вложенность, **When** устраняются найденные нарушения, **Then** состав и поведение интерфейса сохраняются.
3. **Given** правило, конфликтующее с используемым синтаксисом SCSS или форматированием Prettier, **When** конфигурация уточняется, **Then** исключение адресно объяснено и не отключает несвязанные проверки.

### Edge Cases

- Вложенные селекторы с амперсандом, Sass-выражения, partial-файлы и SCSS Modules обрабатываются как SCSS.
- Семантическое решение, нужен ли новый токен или миксин, остаётся правилом для агента и предметом ревью; Stylelint не выдаётся за такую проверку.
- Успех на пустом наборе файлов не считается проверкой проекта.
- Предупреждение или ошибка установки не считается нарушением стиля.

### Verification Approach

Задача меняет конфигурацию и при необходимости оформление существующего SCSS; бизнес-логика и серверные контракты не меняются, искусственный TDD Red не нужен. План задаст команды контрольных положительного и отрицательного примеров, проверки всех SCSS, Prettier, сборки и затронутого UI. Итоговый отчёт отделяет реальные результаты от непроведённых проверок.

## Requirements

### Functional Requirements

- **FR-001**: Проект использует готовые Stylelint и SCSS-конфигурацию с уже установленными пользователем прямыми зависимостями; собственных правил и отдельного проверочного скрипта нет.
- **FR-002**: Проверка доступна через стандартный NPM Scripts и охватывает исходные SCSS-файлы приложения, включая модули и общие partial-файлы.
- **FR-003**: Конфигурация распознаёт Sass-синтаксис, БЭМ-вложенность и существующие директивы @use.
- **FR-004**: Автоматические правила Stylelint и форматирование Prettier не требуют противоположных правок одних и тех же файлов; точечные исключения имеют объяснение.
- **FR-005**: Существующие SCSS-файлы соответствуют согласованной конфигурации без изменения продуктового поведения или визуального контракта.
- **FR-006**: Ошибки проверки содержат путь и место; заведомо некорректный пример не проходит, корректный проходит.
- **FR-007**: Документация проверки указывает действующую команду и границы Stylelint; агент не устанавливает пакеты и не меняет Git index.

### Scope Boundaries

- В объёме: конфигурация Stylelint, команда запуска в package.json, необходимые стилевые исправления, документация и проверки.
- За пределами: новые UI-возможности, рефакторинг компонентов, собственные скрипты проверки структуры, собственные правила линтера, skill, публикация, БД и изменение Git index.

### Data Effects & User Decision

- **Changed data**: Только конфигурации, SCSS при необходимости и документы; пользовательские данные, сообщения и БД не затрагиваются.
- **Preview**: Diff исходных файлов и результаты проверок доступны до пользовательского коммита.
- **Confirmation**: Согласование spec и отдельное разрешение реализации следуют процессу проекта.
- **Cancellation**: Состояние пользовательских и соседних изменений не откатывается автоматически.
- **Idempotency and duplicates**: Повторная проверка и форматирование не создают новых изменений.
- **Failure result**: Неуспешная или заблокированная проверка фиксируется с причиной, без объявления задачи проверенной.

### Key Entities

Продуктовые сущности и модель данных неприменимы.

## Success Criteria

- **SC-001**: Контрольный корректный SCSS проходит, а некорректный даёт диагностику с файлом и местом. Покрывает FR-002, FR-003, FR-006.
- **SC-002**: Все исходные SCSS-файлы проекта проходят проверку Stylelint и Prettier. Покрывает FR-002, FR-004, FR-005.
- **SC-003**: Сборка и подходящие существующие проверки UI проходят; ревью diff не находит изменения поведения. Покрывает FR-005.
- **SC-004**: Повторные запуски не создают циклических правок; исключения, если нужны, адресны и описаны. Покрывает FR-004.
- **SC-005**: Команда доступна из NPM Scripts, документация совпадает с конфигурацией, прямых новых зависимостей сверх согласованных нет. Покрывает FR-001, FR-007.

## Assumptions and Dependencies

- Пользователь установила stylelint 17.14.1 и stylelint-config-standard-scss 17.0.0; это подтверждено локальным npm ls.
- Проект использует Node.js 24, Sass, Prettier и SCSS Modules.
- [Официальное руководство Stylelint](https://stylelint.io/user-guide/get-started/) рекомендует готовую конфигурацию для SCSS; её фактическая совместимость с проектом проверяется на этапе реализации.
- Документ с ручными правилами выделен в отдельную задачу specs/012-coding-rules.
- Спецификация описывает текущее целевое состояние без истории изменений.
