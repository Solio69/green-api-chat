## User Scenarios & Testing

### User Story 1 — Перенос React-проверок в Testing Library (Priority: P1)

Компоненты и hooks проверяются через наблюдаемое поведение в Vitest и React Testing Library, а браузерный стенд содержит только проверки, которым он нужен.

**Why this priority**: Это обязательная часть результата этапа R09; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Vitest DOM-проекты, typecheck и сопоставление реестра; Playwright для сохранённых браузерных сценариев. Контролировать отсутствие React act warnings и необработанных асинхронных ошибок.

**Acceptance Scenarios**:

1. **Given** два компонента читают один сеанс, **When** история обновляется и один компонент размонтируется, **Then** второй видит актуальные данные, а бизнес-действие не дублируется.
2. **Given** провайдер отрисован под корневым StrictMode, **When** происходит development replay, **Then** он действительно наблюдён и активные ресурсы не дублируются.
3. **Given** тест требует размер панели и прокрутку, **When** оценивается миграция, **Then** он остаётся браузерным и отражён в карте.
4. **Given** probe больше не используется после переноса, **When** он удалён, **Then** все связанные сценарии по-прежнему запускаются в штатных командах.

### Edge Cases

- Размонтирование с pending promise.
- Смена scope без полной перезагрузки страницы.
- Ошибка cleanup и повторный mount.
- Проверка, случайно зависящая от CSS вместо состояния.

### Verification Approach

Vitest DOM-проекты, typecheck и сопоставление реестра; Playwright для сохранённых браузерных сценариев. Контролировать отсутствие React act warnings и необработанных асинхронных ошибок.

Для существующего поведения используются регрессионные проверки и сопоставление покрытия. Добавление тестов после существующей реализации не называется TDD. Обнаруженный дефект описывается отдельно; изменение продуктового поведения требует согласованного требования и Red → Green → Refactor.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки выполнены; результаты и границы перечислены в [verification.md](verification.md).

## Requirements

### Functional Requirements

- **FR-001**: По карте 028 перенести оставшиеся проверки состояний форм, команд, React-подписок, выбора, смены scope и cleanup в Vitest с React Testing Library.
- **FR-002**: Использовать доступные роли, имена и наблюдаемое состояние; внутренние поля hooks, SVG-разметка и случайная DOM-структура не становятся основным контрактом теста.
- **FR-003**: Применять реальные проектные провайдеры и QueryClient там, где проверяется их связь; зависимости времени и транспорта контролировать на границе.
- **FR-004**: Сохранить достоверные development-проверки Strict Mode из 030 с наблюдаемым replay; обычный render с похожим именем не заменяет эту проверку.
- **FR-005**: Геометрию, CSS, реальный фокус, прокрутку, Web Locks и асинхронную композицию Server Components оставить в Playwright, поскольку DOM-эмуляция не доказывает их работу.
- **FR-006**: Уменьшать query-app, его probes и маршруты только после переноса всех зависимых сценариев; тестовые входы не добавлять в production-приложение.
- **FR-007**: Обновлять карту покрытия, команды и CI вместе с каждым удалением; отсутствующие жизненные сценарии добавить как регрессию, не объявляя это TDD уже существующей реализации.

### Scope Boundaries

- **В объёме**: Component и hook тесты, завершение переноса query-стенда и удаление неиспользуемых probes.
- **За пределами**: Эмуляция браузерной геометрии как доказательство E2E, новые UI-возможности и замена Playwright.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Изменяются тестовые окружения и вспомогательные страницы; пользовательские данные не затрагиваются.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

React-сценарий, provider wrapper, DOM-окружение, probe, браузерный контракт.

## Success Criteria

- **SC-001**: Все назначенные React-сценарии имеют проверку на наблюдаемое поведение и место в реестре (FR-001, FR-002, FR-007).
- **SC-002**: Жизненный цикл проверяется с настоящими провайдерами и подтверждённым Strict Mode replay (FR-003, FR-004).
- **SC-003**: Браузерные гарантии сохранены, а удалённые probes больше не нужны ни одному активному сценарию (FR-005, FR-006).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Подготовка спецификаций не включает commit, push или отправку реальных сообщений.
