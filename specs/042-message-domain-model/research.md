# Research 042: модель сообщений и статусов

Дата: 2026-10-03. Исходники: `merge-message-facts.ts`, `types.ts`, `validate-message.ts`, `normalize-history.ts`, `normalize-message-status.ts`, `message-cache.ts`; baseline 26/26 targeted integration (history/cache/status) и зелёная CI 041 на кодовом SHA. Новых пакетов/форматов HTTP нет.

## Факты и матрица

| Правило | Текущее поведение | Требуемый инвариант |
| --- | --- | --- |
| Идентичность | `mergeStatusFacts` использует `(chatId,idMessage)`, но `mergeMessageFacts` и карта источников индексируют только `idMessage` | Одинаковые ID разных чатов независимы, включая источник контента |
| Содержимое | accepted-текст сменяется подтверждённым provider/history, известный live-текст не затирается поздней историей | Сохранить приоритеты accepted < history < live и нейтральный unsupported |
| Статус | read/delivered монотонны, failed/noAccount конфликтуют с подтверждением и дают issue | Поздняя история не понижает read, конфликт не скрывается |
| Ранний статус | TTL 300000 ms, максимум 1000; duplicate не продлевает TTL, более сильный факт обновляет его | Сохранить сроки и детерминированное вытеснение |
| Время/порядок | provider timestamp в секундах; acceptedAt в миллисекундах; известные сортируются, неизвестные сохраняют порядок | Не приписывать несуществующее время и не мутировать вход |
| Вход | raw API нормализуется/проверяется до кеша; `MessageDTO` используется и как нормализованный DTO, и как view | Явно назвать факт с source и модель отображения; cache orchestration остаётся задачей 043 |

Прямой `mergeMessageFacts` уже чистый: нет React/QueryClient. Значит перенос всего кеша в 042 добавил бы риск без пользы. Внутри `mergeStatusFacts` есть `result.issue!` и cast статуса, в `normalize-message-status.ts` — несколько cast после runtime проверок. Их можно заменить типовыми guards и явными ветками, не меняя результат.

## Варианты

| Вариант | Преимущества | Цена/риск | Выбор |
| --- | --- | --- | --- |
| Оставить текущий чистый merge и выделить канонический вход `mergeValidatedMessageFacts` с source-tagged фактами, составным ключом и явными типами DTO/fact/view; старый вход сохранить как переходный adapter до 043/054 | Исправляет реальную коллизию, делает источник явным, не трогает Query | Нужен небольшой adapter и таблица регрессии, изменение внутреннего ключа contentSources | Выбран |
| Только переименовать типы и убрать `!` | Малый diff | Коллизия ID остаётся; разделение DTO/fact/view номинальное | Отклонён |
| Переписать весь Query cache и UI вокруг нового типа | Потенциально сразу единый API | Смешивает 042/043/049 и повышает риск регрессии | Отклонён |

Составной ключ источника — JSON пары `[chatId,idMessage]`, как в ранних статусах. Кеш сессии не сохраняется на диск; новые факты используют новый ключ в пределах текущего запуска. Проверки: новый узкий unit Red для двух чатов с одинаковым ID и source provenance, затем Green; существующие 26 integration — базовая регрессия. Node Vitest проверяет чистый модуль без Query/React. Тесты используют только фиктивные chatId/idMessage.
