## User Scenarios & Testing

### User Story 1 — Разделение сетевого цикла и жизненного цикла уведомлений (Priority: P1)

Получение, подтверждение, повторы и владение вкладкой исполняются понятными отдельными операциями с надёжным завершением ресурсов.

**Why this priority**: Это обязательная часть результата этапа R06; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Vitest проверяет runtime на управляемом времени и транспортных ответах; React Testing Library — lifecycle; Playwright — реальные Web Locks и несколько страниц. Сценарии 027 сохраняются как контрактная регрессия.

**Acceptance Scenarios**:

1. **Given** ответ ACK потерян, **When** срабатывает повтор, **Then** отправляется тот же proof и новый receive ожидает завершения ACK.
2. **Given** первая вкладка владеет подключением, **When** вторая пытается подключиться, **Then** она ограничена; после освобождения и ручного retry может стать рабочей.
3. **Given** запрашивается Web Lock или ожидается receive, **When** сеанс закрывается, **Then** новые действия прекращаются, поздние ресурсы освобождаются, данные не применяются.
4. **Given** получение восстановилось, **When** контроллер публикует recovery, **Then** история открытого чата обновляется по прежним правилам без второго читателя очереди.

### Edge Cases

- DeleteNotification false после ранее успешного удаления.
- Пустая очередь и валидный ignored event.
- Закрытие во время паузы, settings, receive или ACK.
- Strict Mode replay, многократный retry и устаревшие поколения.

### Verification Approach

Vitest проверяет runtime на управляемом времени и транспортных ответах; React Testing Library — lifecycle; Playwright — реальные Web Locks и несколько страниц. Сценарии 027 сохраняются как контрактная регрессия.

Для сохранения поведения используются исходная карта 028 и подтверждённые регрессионные проверки. Искусственный Red для перемещения кода не требуется. Новая или изменяемая бизнес-логика, включая согласованные защиты от гонок, выполняется через Red → Green → Refactor после разрешения реализации. Обнаруженное расхождение с текущим контрактом сначала фиксируется, а не исправляется незаметно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации имеют статус **NotRun**; результаты будут приведены в verification.md.

## Requirements

### Functional Requirements

- **FR-001**: Разделить исполнение команд модели 040, HTTP-транспорт, ожидание повторов и Web Lock; сохранить один последовательный сетевой цикл на действующее подключение вкладки.
- **FR-002**: Сохранить receiveTimeout 5 секунд, действующие серверные и клиентские deadline, паузу между запросами и согласованный backoff с Retry-After.
- **FR-003**: Применять или осознанно пропускать валидное событие до ACK; повреждённое событие оставлять в очереди с прежней паузой получения.
- **FR-004**: Повторять потерянный ACK с тем же proof; при его истечении получать новую доставку без дублирования эффектов. Успех удаления не зависит от памяти серверного процесса.
- **FR-005**: Сохранить владельца Web Lock в одном origin/browser context и существующий отказ второй вкладке; отсутствие API остаётся явным ограничением.
- **FR-006**: Сделать now, ожидание, случайную составляющую задержки, transport и acquire/release управляемыми зависимостями для тестирования.
- **FR-007**: При close, logout, смене scope и unmount завершать таймеры, подписки, чтение и владение; позднее получение lock немедленно освобождается.
- **FR-008**: Сохранить восстановление истории открытого чата и ограниченное обновление списка после событий; retry не создаёт параллельные циклы.

### Scope Boundaries

- **В объёме**: Клиентский runtime уведомлений, ресурсы, тестовые зависимости и интеграция с моделью 040.
- **За пределами**: SSE, фоновые серверные процессы, внешняя координация устройств, изменение proof и дополнительных методов API.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Перестраивается клиентский сетевой цикл. Протокол остаётся stateless на сервере; реальные очереди в проверках не используются.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Исполнитель команд, доставка, ACK proof, backoff, browser lease, поколение runtime.

## Success Criteria

- **SC-001**: Все варианты receive/ACK проходят с прежними политиками времени и без параллельного чтения (FR-001–FR-004).
- **SC-002**: Реальные две вкладки подтверждают прежнее владение, а lifecycle-тесты подтверждают освобождение всех ресурсов (FR-005–FR-007).
- **SC-003**: Recovery обновляет историю, обновление списка ограничено, повторные действия не создают дополнительный цикл (FR-008).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Подготовка спецификаций не включает commit, push или отправку реальных сообщений.
