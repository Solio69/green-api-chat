# Verification: E03.2 — вход, сессия и защищённая главная

**Дата**: 2026-10-01
**Статус**: автоматическая проверка и предкоммитное ревью пройдены; ручной вход с настоящим инстансом подтверждён пользователем, остальные ручные сценарии ожидают проверки.

## Соответствие спецификации

- `/login` содержит существующую форму. Полный ввод отправляется JSON-телом только на `POST /api/auth/login`; браузер не вызывает GREEN-API напрямую. Во время ожидания повторная отправка блокируется, ошибки видны на форме, значения сохраняются при отказе.
- Сервер валидирует JSON и ограничивает тело 8 КБ, затем вызывает только `GetStateInstance` на согласованном хосте `https://4100.api.green-api.com`. Общий таймаут — 10 секунд, кеширование и редиректы отключены. HTTP 429 вызывает единственный повтор через 1,1 секунды; второй 429 нормализуется как `rate_limited`. Успех требует HTTP 200 и `stateInstance: authorized`; ответы провайдера нормализуются без возврата токена.
- При успехе `iron-session` создаёт зашифрованную HttpOnly-cookie со сроком 24 часа. Абсолютное время истечения хранится внутри сессии; чтение не продлевает срок. В production cookie имеет `Secure`, всегда — `SameSite=Lax` и `Path=/`. Секрет читается только из `SESSION_PASSWORD`; в репозитории его нет.
- Серверная `/` без действующей сессии перенаправляет на `/login`. С действующей сессией при каждом открытии запрашивается состояние инстанса; подтверждённый `authorized` показывает только `{"stateInstance":"authorized"}`. Подтверждённая потеря доступа удаляет cookie через узкий обработчик и перенаправляет на форму. Временная или неоднозначная ошибка сохраняет сессию и предлагает повторить проверку.
- Контракт `/api/health` сохранён. Чат, сообщения, явный выход и публикация не входят в этот шаг.

## Предкоммитное ревью

Критических и блокирующих замечаний в согласованном объёме нет. Реквизиты не пишутся в URL, логи и браузерные хранилища; разрешён только JSON-тело запроса на наш сервер и зашифрованная cookie после успеха. Ошибки сервера не отражают исходный ответ GREEN-API. `package-lock.json` содержит только зависимость `iron-session@9.0.1` и её транзитивные пакеты после установки пользователем. Агент не выполнял Git staging/commit, установку пакетов, миграции или изменение данных БД.

Ограничение: автоматический E2E не проводит реальный запрос с cookie и GREEN-API; обновление `/` и остальные ручные сценарии требуют отдельной проверки пользователя. Статус upstream-ответа при исходном промежуточном экране не был зафиксирован, поэтому HTTP 429 является обоснованной документацией гипотезой, а не доказанным диагнозом. Для будущего расширения можно добавить изолированный управляемый upstream в E2E, если число сценариев с cookie вырастет. Явный выход стоит проектировать отдельной задачей с учётом ограничений stateless-сессии.

## Действия пользователя

1. Сохранить уже настроенный `SESSION_PASSWORD` в игнорируемом `.env.local`: он нужен для расшифровки действующей cookie. Не публиковать и не присылать секрет.
2. В запущенном `dev` обновить `/`: страница должна снова показать актуальный JSON. Затем проверить ошибку входа на заведомо неверном токене и исправить его. Реквизиты не добавлять в тесты и документы.
3. Просмотреть изменения в VS Code и создать коммит самостоятельно с названием `feat: add GREEN-API login and protected session`. Перед отдельным запуском `test:e2e` остановить dev-сервер в этой папке.

Ручная проверка с настоящим инстансом: **Pass** для входа и прямого перехода к `{"stateInstance":"authorized"}` без промежуточного экрана ошибки; пользователь подтвердил результат. Обновление страницы, неверный токен и прочие ручные исходы: **NotRun**.
