# Research: E03.2 — вход и сессия

## Проверенные факты

- [GetStateInstance](https://green-api.com/telegram/docs/api/account/GetStateInstance/) вызывается методом GET по адресу `{apiUrl}/waInstance{idInstance}/getStateInstance/{apiTokenInstance}`. Документированное поле ответа — `stateInstance`; только `authorized` подтверждает доступ. `starting` — временный запуск инстанса.
- [Общие ошибки GREEN-API](https://green-api.com/telegram/docs/api/common-errors/) связывают 401 с токеном и 403 с ID инстанса или адресом. Указаны 400 для запуска, отсутствия авторизации и истёкшего инстанса; сбои 5xx не являются доказательством неверных реквизитов.
- [Ограничение частоты запросов GREEN-API](https://green-api.com/telegram/docs/api/ratelimiter/) задаёт для `GetStateInstance` один запрос в секунду на инстанс и HTTP 429 при превышении. Один переход после входа выполняет проверку в обработчике и на `/`, поэтому сервер допускает один повтор через 1,1 секунды. Точный upstream-статус ручного сбоя не был записан, поэтому причина 429 остаётся обоснованной гипотезой.
- [Next.js](https://nextjs.org/docs/app/api-reference/functions/cookies) разрешает читать cookie в серверном компоненте, а устанавливать и удалять — в Server Function или Route Handler. Поэтому проверка `/` живёт в серверной странице, а установка/удаление cookie — в обработчиках.
- [iron-session](https://github.com/vvo/iron-session#readme) поддерживает зашифрованные и подписанные stateless-cookie в Next.js App Router. Версия 9 требует Node 22.13+; проект использует Node 24. Сессия читается как частичная структура, поэтому поля проверяются после расшифрования. Размер cookie ограничен браузером примерно 4 КБ.
- [Next.js рекомендует библиотеку сессий](https://nextjs.org/docs/app/guides/authentication). Подписанный JWT без шифрования не подходит для хранения API-токена; самописная криптография добавляет риск ошибок.

## Технические варианты

| Вопрос | Вариант | Плюсы | Минусы | Решение |
| --- | --- | --- | --- | --- |
| Сессия | `iron-session@9.0.1` | Готовое шифрование, подпись, cookie API; без БД | Зависимость и невозможность мгновенно отозвать украденную stateless-cookie | Выбран; отзыв токена GREEN-API прекращает доступ при следующей проверке |
| Сессия | Собственная реализация на Node Crypto | Без нового пакета | Ответственность за IV, AEAD, формат, срок и ротацию ключа | Отклонён как лишний риск для токена |
| Сессия | ID cookie + БД | Централизованный отзыв | БД, миграции, стоимость и настройка | Вне согласованного минимума |
| Форма и сервер | Route Handler + `fetch` из существующей формы | Явный контракт ошибок, минимальное изменение UI | Нужен отдельный HTTP-обработчик | Выбран |
| Форма и сервер | Server Action | Удобная работа с cookie | Перестройка готовой клиентской формы и иной формат ошибок | Не выбран |
| Защита `/` | Серверная страница | Проверка рядом с данными; прямой вход и refresh защищены | Нельзя удалить cookie при рендере | Выбрана вместе с узким обработчиком прекращения сессии |
| Защита `/` | Только proxy или клиентский guard | Ранний редирект | Сам по себе не защищает серверные данные; усложняет отказ GREEN-API | Не выбран |
| Тесты | Существующий Playwright для браузера и серверных интеграционных тестов | Не требует нового test runner | Для серверных функций нужны явные зависимости, которые можно подменить | Выбран; Vitest не требуется |

## Решение для E03.2

1. Единственный production-хост GREEN-API — `https://4100.api.green-api.com`. Его не получает браузер от формы и не задаёт пользователь. Сервер кодирует компоненты URL; запросы идут только по HTTPS, без кеша и автоматического перехода на другой host. Общий таймаут с единственным повтором после HTTP 429 — 10 секунд; пауза перед повтором — 1,1 секунды. Размер входного JSON ограничен 8 КБ. Ветви ошибок задаёт контракт. Документированный 400 `instance is starting or not authorized` неоднозначен: он не прекращает действующую сессию.
2. `POST /api/auth/login` принимает два поля, проверяет форму запроса на сервере, вызывает `GetStateInstance` и выдаёт только нормализованный результат. Успешный ответ создаёт cookie через `iron-session`. Секрет шифрования `SESSION_PASSWORD` находится только в окружении и не имеет fallback в production.
3. Cookie содержит зашифрованные `idInstance`, `apiTokenInstance` и абсолютное время окончания. `ttl` и `maxAge` — 24 часа, чтение cookie не вызывает `save()` и не продлевает срок. Устанавливаются `HttpOnly`, `SameSite=Lax`, `Path=/` и `Secure` при HTTPS. На локальном HTTP Secure выключен только для разработки/тестов.
4. Серверная `/` проверяет структуру и срок сессии, затем заново вызывает `GetStateInstance`. При `authorized` показывает JSON с документированным полем. При подтверждённой потере авторизации направляет в узкий обработчик, который удаляет cookie и перенаправляет на `/login`. При `starting`, таймауте и другом временном сбое cookie сохраняется; показан простой текст и возможность обновить страницу.
5. Удаление cookie возможно только в обработчике, поэтому внутренний GET-обработчик выполняет фиксированный редирект и не принимает произвольный адрес. Его вызов не раскрывает данные; нежелательная сторонняя навигация может лишь прекратить эту браузерную сессию. Явный пользовательский выход остаётся отдельной задачей.
6. Подлинные реквизиты не используются в автоматических тестах. Серверную классификацию и сессию проверяем на фиктивных данных с подменённым `fetch` и cookie store; браузерные сценарии проверяют маршруты, локальную форму и безопасные ответы нашего API. Реальную проверку подготовленного инстанса выполняет пользователь вручную.

## Зависимости и ограничения

- Пользователь выполняет `npm install iron-session@9.0.1 --save-exact`; агент не устанавливает пакет. Если установка не завершится, код с новой зависимостью нельзя объявить проверенным.
- Пользователь создаёт случайный `SESSION_PASSWORD` длиной не менее 32 символов в игнорируемом `.env.local`; для автоматических тестов используется исключительно фиктивное значение.
- Устанавливать БД, выполнять миграции и менять данные Telegram не требуется.
