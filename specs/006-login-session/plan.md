## Summary

Готовая клиентская форма находится на `/login`; после успешного ответа API `router.replace` открывает `/` без полной перезагрузки документа. `POST /api/auth/login` валидирует ввод, запрашивает только `GetStateInstance` на сервере и возвращает безопасный код результата. `authorized` создаёт зашифрованную cookie через `iron-session` на 24 часа. Серверная `/` проверяет cookie и заново вызывает GREEN-API; состояние и безопасный профиль получаются через `GetAccountSettings` по 013, композиция каркаса описана в 015. Отсутствие сессии или подтверждённая потеря доступа дают редирект на `/login`, временный сбой оставляет сессию и предлагает повторить проверку. Чат, дизайн главной и явный выход не входят.

## Technical Context

- Next.js 16.3.7, React 19.3.0, TypeScript 5.9.3, Node 24.x, SCSS Modules.
- Существуют `LoginForm`, `CredentialField`, `SubmitButton`, `TokenVisibilityButton`, Playwright E2E и общий кодстайл. Их поведение обязательных полей сохраняется.
- `iron-session@9.0.1` и lock-файл установлены пользователем. Другие пакеты и БД не нужны.
- В production вызов GREEN-API идёт только на `https://4100.api.green-api.com`. В браузерном запросе реквизиты отправляются JSON-телом на наш same-origin API. Внешний URL с токеном не логируется. `fetch` использует `cache: 'no-store'`, запрет перенаправлений и общий таймаут 10 секунд. HTTP 429 повторяется один раз через 1,1 секунды с тем же дедлайном; второй 429 нормализуется как `rate_limited`. Тело запроса на вход ограничено 8 КБ; неоднозначный 400 `instance is starting or not authorized` не завершает действующую сессию.
- Cookie хранит зашифрованные ID, токен и `expiresAt`; секрет `SESSION_PASSWORD` задаёт пользователь вне Git. `ttl` и `maxAge` равны 24 часам, чтение не вызывает продление. Сервер проверяет форму расшифрованных данных и абсолютный срок.
- Платформа — локальный Node и будущий Vercel; память процесса не используется как сессионное хранилище.

## Tasks and Dependencies

1. Обновить маршруты в браузерных тестах и добавить тест отсутствующей сессии. Подтвердить поведенческий Red на текущем приложении (`/login` ещё не существует, `/` показывает форму).
2. Создать серверные тесты классификации и сценариев с тестовыми двойниками. Если новая импортируемая функция отсутствует, добавить лишь компилируемый пустой контракт, затем подтвердить Red на неверном поведении; ошибка импорта не считается Red.
3. Реализовать запрос к GREEN-API и серверную оркестрацию; получить Green серверных тестов. Далее реализовать сессию и маршруты, получить Green браузерных тестов.
4. Проверить рефакторинг и регрессию старой формы. Выполнить typecheck, lint, форматирование, интеграционные тесты и E2E; обновить документы и итоговый read-only анализ.
5. Ручная проверка реальным инстансом остаётся действием пользователя с его реквизитами. Если она не выполнена, verification фиксирует `NotRun`, а не ложный успех.

Конкретный порядок T-ID и карта FR/SC находятся в [tasks.md](tasks.md). Установку пакета пользователь уже выполнил. `SESSION_PASSWORD` пользователь задаёт для ручного запуска; для автоматических проверок применяется фиктивный тестовый пароль.

## Verification

- Поведенческий Red: редирект `/` и форма `/login` пока отсутствуют; новая проверка сервера возвращает 404/неверный результат. Серверные тесты после компилируемого stub падают на классификации `authorized`, 401/403, `starting` и cookie, а не на импорте.
- Green: ответы нашего API соответствуют [контракту](contracts/login-api.md); E2E проверяет маршруты, обязательность полей, ожидание, ошибки и отсутствие утечек. Интеграционные тесты проверяют шифрование cookie, срок, повреждение, отсутствие продления и обработку провайдера.
- Refactor: повторить затронутые тесты после упрощения логики; регрессионные сценарии формы и `/api/health` остаются зелёными.
- Итог: `npm run test:integration`, `npm run test:e2e`, `npm run typecheck`, `npm run lint`, `npm run format:check`, `git diff --check` и предкоммитное ревью. Не запускать E2E параллельно с dev-сервером в той же папке.
- Ручная проверка `GetStateInstance` настоящего инстанса выполняется пользователем без передачи токена агенту; её статус явно указывается в verification.

## Complexity Tracking

Дополнительная библиотека необходима для зашифрованной cookie с API-токеном. Внутренний обработчик прекращения сессии нужен потому, что серверная страница не может удалить cookie во время рендера. Отдельный Playwright-конфиг использует уже установленный runner и не добавляет пакет. Дополнительной инфраструктуры нет.
