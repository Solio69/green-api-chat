## R1. Минимальный самостоятельный комплект

**Решение**: адаптировать восемь skills основных этапов, пять шаблонов,
пять PowerShell-файлов, правила и документацию. Полный перечень — в plan.md.
Инструменты обслуживают Markdown-файлы; Node.js, Python, Pester, Specify CLI,
менеджер пакетов, облачные интеграции для этой задачи не нужны.

**Причина**: в исходном common.ps1 присутствуют выбор корня через Git,
поиск последней feature, presets/extensions и поддержка композиции шаблонов
через Python. Эти возможности не нужны согласованному последовательному процессу.

**Альтернативы**:
- Полное копирование: меньше первичной работы, но остаются чужие правила,
  лишние зависимости и автоматические hooks.
- Один набор документов без skills и служебных проверок: проще, но не даёт
  согласованный комплект Spec Kit и проверку выбора задачи.

## R2. Сохранение пользовательских документов

**Наблюдение**: исходный setup-plan.ps1 безусловно пишет шаблон в IMPL_PLAN;
при отсутствии шаблона использует создание с Force. Повторный запуск способен
заменить готовый план.

**Решение**: setup-spec и setup-plan создают только отсутствующий файл,
используя семантику CreateNew; существующий обычный файл возвращается
как CREATED=false без изменения байтов. Наличие каталога вместо файла —
ошибка. Намеренное редактирование документа выполняет агент отдельным действием.

**Альтернативы**:
- Принудительное копирование недопустимо по FR-010.
- Автоматические резервные копии не устраняют риск потери актуального документа
  и добавляют ненужные сущности.

## R3. Явный каталог и границы

**Наблюдение**: исходный Get-FeaturePathsEnv требует SPECIFY_FEATURE_DIRECTORY,
но не проверяет принадлежность проекту и не нормализует путь полностью.

**Решение**: корень берётся от расположения локального комплекта.
Перед обращением к документам сравниваются нормализованный каталог из переменной
окружения и обязательный ExpectedFeatureDirectory, переданный текущим этапом.
Разрешается только прямой дочерний каталог specs с именем NNN-slug.
Все допустимые вызовы происходят из корня проекта или его подкаталогов.
Выход за границу, несовпадение выбора, junction/symlink в проверяемом пути
от корня проекта к артефакту отклоняются с понятной причиной.
Одинаковый префикс строк не считается принадлежностью: проверяется разделитель.

**Альтернатива**: определять задачу по Git-ветке или последнему каталогу проще,
но это противоречит FR-009 и не защищает от чужого контекста.

**Предел проверки**: это защита от ошибочного выбора и случайной перезаписи
в локальном процессе с одним писателем. Комплект не обещает блокировку против
произвольной другой программы, одновременно меняющей файловую систему.

## R4. PowerShell без новых зависимостей

**Решение**: поддерживать Windows с PowerShell 7; фактически доступна версия 7.6.5.
Наличие pwsh подтверждено. Пути установки конкретного пользователя не встраиваются
в рабочие инструкции и скрипты. Версия 5.1 в этой задаче не заявляется
поддерживаемой.

Проверки выполняются обычным PowerShell-тестом с отдельными процессами pwsh
и временными фикстурами. Это позволяет проверить отсутствие изменений
и изоляцию без установки тестового фреймворка.

## R5. Первая задача до появления инструментов

**Решение**: использовать предусмотренную spec.md начальную подготовку.
Её документы создаются по исходным инструкциям и шаблонам без переноса
рабочих scripts и skills до разрешения реализации.

Для read-only предпроверок допустим исходный check-prerequisites.ps1:
перед ним задаются абсолютный SPECIFY_FEATURE_DIRECTORY нового проекта
и информационный SPECIFY_FEATURE=001-project-workflow, чтобы не искать
последнюю задачу исходного проекта. Проверяются буквальный ожидаемый путь,
его принадлежность новому проекту и возвращённый FEATURE_DIR.

Фактический запуск PathsOnly вернул:
- FEATURE_DIR — D:/Pet-projects/green-api-chat/specs/001-project-workflow;
- REPO_ROOT — D:/Pet-projects/agent-flow-harness.

Это ожидаемое расположение исходного инструмента при bootstrap.
Оно не используется как корень документов нового проекта и не доказывает
изоляцию ещё не реализованного комплекта.

setup-plan исходника не запускается из-за перезаписи документов.
План создаётся по прочитанному шаблону. setup-tasks исходника допускается
только после проверки его read-only поведения и абсолютного FEATURE_DIR.

Для анализа применяется процедура исходного speckit-analyze с явным контекстом:
spec, plan и tasks — из выбранного каталога нового проекта; нормативная основа —
согласованная spec.md, политика Git и contracts/project-rules.md.
Продуктовая constitution исходного проекта не применяется.
Эта подстановка явно указывается в отчёте; он называется bootstrap-анализом
по процедуре speckit-analyze, а не запуском нового локального комплекта.

После реализации анализ повторяется локальным skill и локальным prerequisite
уже с .specify/memory/constitution.md. Это отдельная приёмочная проверка;
положительный bootstrap-отчёт её не заменяет.

## R6. Единые правила и отсутствие скрытых действий

**Решение**: GIT_POLICY.md переносится с сохранением текста и ограничений.
AGENTS.md и constitution ссылаются на него; не вводят другую политику staging.
Исключение для staging по прямой просьбе сохраняется.
Не переносится префикс tech:, поскольку пользователь согласовал четыре префикса.

Skills не запускают hooks, не публикуют issues, не устанавливают пакеты
и не подключают новые интеграции. Упоминания отсутствующих scripts удаляются
или заменяются точной инструкцией в пределах разрешённого процесса.
Ссылка на текущий план не записывается в общий AGENTS.md.

## R7. Происхождение и ограничения копирования

В docs/spec-kit-provenance.md фиксируются исходный локальный путь,
переносимые группы файлов, фактические метаданные author/source из skills
и характер адаптации. Указания авторства и найденные применимые уведомления
сохраняются. Локальные init-options.json указывают speckit_version 0.8.15;
это сведения об исходной установке, а не гарантия отсутствия локальных правок.
Локального LICENSE для комплекта не найдено. В официальном репозитории
[проверен текст MIT License](https://github.com/github/spec-kit/blob/main/LICENSE)
с Copyright GitHub, Inc.; его сохранение отдельным документом включено в T006.
Чтение LICENSE по URL тега v0.8.15 не удалось, поэтому точное совпадение
этого тега и локальной адаптации не заявляется. Происхождение локальных правок
и проверенный источник уведомления указываются отдельно.

Источник используется при подготовке и реализации E02.1, но не нужен
для штатного запуска готового комплекта. Автоматическое обновление из источника
не предусматривается.
