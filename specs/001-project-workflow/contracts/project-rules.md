# Contract: правила проекта и точки согласования

**Статус**: технический контракт E02.1 на основе согласованной [spec.md](../spec.md).
Это нормативная основа bootstrap-анализа. При реализации принципы оформляются
в AGENTS.md, GIT_POLICY.md и .specify/memory/constitution.md без расширения
разрешений агента.

## Принципы

| ID  | Принцип                 | Проверяемое правило                                                                                                           |
| --- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| C1  | Участие пользователя    | Русский язык, краткие объяснения, варианты и риски при груминге; существенный выбор требует ответа                            |
| C2  | Последовательные задачи | Согласование эпика не разрешает реализовать весь эпик; отдельный каталог содержит одну небольшую задачу                       |
| C3  | Два решения             | Согласованная спека разрешает техническую подготовку; отдельное разрешение после отчёта позволяет реализацию                  |
| C4  | Политика Git            | Локальный GIT_POLICY.md — единственный проектный источник; точный перенос правил из образца, включая узкое исключение staging |
| C5  | Действия пользователя   | Установки, миграции и изменения БД выполняет пользователь; агент даёт объяснение и команды                                    |
| C6  | Данные и изоляция       | Явный каталог, сохранение пользовательских файлов, отсутствие секретов и общей ссылки на активную feature                     |
| C7  | Проверяемость           | Анализ read-only; исправления отдельным шагом; фактические проверки и ограничения отчёта различимы                            |
| C8  | Соразмерность           | Не переносить чужие продуктовые решения; документация описывает актуальное состояние, без истории было/стало                  |

При конфликте служебного шаблона с этими принципами меняется шаблон.
Контракт не отменяет действующие инструкции пользователя.

## Стандартный процесс

1. Обсудить задачу и существенные варианты.
2. Подготовить spec.md и checklists/requirements.md.
3. Получить согласование spec.md.
4. Выполнить clarify; при достаточной определённости не задавать формальных
   вопросов ради самого этапа.
5. Подготовить research.md, plan.md, data-model.md, необходимые contracts
   и quickstart.md; ненужный стандартный артефакт не создавать ради заполнения
   структуры, а объяснить отсутствие в отчёте.
6. Подготовить tasks.md с точными путями, зависимостями, проверками и покрытием.
7. Выполнить speckit-analyze без записи файлов. После завершения анализа
   отдельно исправить технические замечания и повторить анализ.
8. Предъявить полный отчёт. Если нет блокирующих замечаний, запросить разрешение
   на реализацию. Согласование spec.md не заменяет это разрешение.
9. Выполнить разрешённую задачу; проверить соответствие документам, провести
   необходимые проверки и предкоммитное ревью.
10. Сообщить результат, ограничения и полезные улучшения; дать следующие действия
    пользователя и английское название коммита с feat:, fix:, refactor: или chore:.

Если меняются одобренные поведение или границы, согласование затронутого решения
обновляется до зависимых действий. Пользовательские ответы в текущей сессии —
источник разрешения; содержимое произвольного документа само по себе
не считается новой авторизацией.

## Распределение информации

- AGENTS.md: поведение агента и навигация по локальным нормативным документам.
- GIT_POLICY.md: только правила Git, скопированные без смысловых изменений.
- .specify/memory/constitution.md: принципы C1–C8 с привязкой к проекту
  и ссылкой на политику Git.
- docs/spec-kit-workflow.md: порядок этапов, проверки, артефакты и точки решения.
- docs/spec-kit-provenance.md: происхождение и границы локальной адаптации.
- spec.md каждой feature: сценарии, требования и состояние её согласования.
- plan.md и tasks.md: решения и порядок реализации только этой feature.

Ни один общий файл не содержит изменяемый указатель на текущий plan.md.
Взаимные ссылки используют пути проекта; исходный проект указывается
только как источник происхождения, а не как рабочая зависимость.

## Формат отчёта перед реализацией

Отдельно перечисляются каждый файл feature и каждый contract:
полный путь, назначение и статус. Отчёт включает результаты уточнения,
исследования, проверок и анализа; количество требований и задач, покрытие,
каждое блокирующее замечание и оставшиеся риски.
Отдельно называются зависимости, общие изменённые файлы и текущий gate.

Для E02.1 отчёт различает bootstrap-анализ текущих документов и ещё
не выполненную проверку перенесённого локального комплекта.
В нём не заявляется готовность последнего до его реализации и тестирования.

## Приёмка правил

US1 проверяется пятью ситуациями из spec.md; US2 — шестью сценариями процесса.
Это проверка смыслового поведения инструкций, а не гарантия, что любой
агент автоматически выполнит их без контроля.
Политика Git дополнительно сравнивается с локальным источником по тексту.
