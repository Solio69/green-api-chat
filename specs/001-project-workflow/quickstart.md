# Quickstart: проверка E02.1

**Feature**: [spec.md](spec.md).
**Состояние**: инструкция приёмки реализованного комплекта. Фактические результаты
фиксируются отдельно в verification.md; эта инструкция сама по себе их не заменяет.

## Условия

- Сначала получено разрешение на реализацию E02.1.
- Локальные файлы из plan.md подготовлены.
- Доступен PowerShell 7: в текущей среде обнаружен 7.6.5.
- Установка пакетов, Git init, БД, GREEN-API и сетевой доступ для запуска
  проверок не нужны.

## Пример чтения контекста после реализации

Из PowerShell 7 в корне проекта:

```powershell
Set-Location -LiteralPath 'D:\Pet-projects\green-api-chat'
$env:SPECIFY_FEATURE_DIRECTORY = 'specs/001-project-workflow'
$taskFeature = [System.IO.Path]::GetFullPath(
    (Join-Path (Get-Location).Path 'specs/001-project-workflow')
)
& '.\.specify\scripts\powershell\check-prerequisites.ps1' -Json -PathsOnly -ExpectedFeatureDirectory $taskFeature
```

Ожидается exit 0 и FEATURE_DIR, точно равный $taskFeature.
PROJECT_ROOT должен быть новым проектом, а не agent-flow-harness.
Этот вызов ничего не записывает.

После реализации автоматические сценарии:

```powershell
& '.\tests\spec-kit\workflow.tests.ps1'
```

Тест использует текущий доступный pwsh, создаёт собственный временный корень
с уникальным именем, копирует туда минимальный локальный комплект и запускает
проверяемые scripts в отдельных процессах. Производственные документы
не используются как файлы для разрушительных сценариев.

Очистка допускается только для созданного тестом абсолютного каталога
после проверки его принадлежности ожидаемой временной области. Junction
удаляется как ссылка, без обхода её цели; затем удаляются обычные фикстуры.
При неоднозначности очистка останавливается и путь сообщается пользователю.

V01–V12 — автоматические контрактные проверки; V13 сочетает проверку ссылок
и смысловое ревью именованных команд. V14–V18 — ревью и фактические проверки
процесса; они не подменяются тестами, сравнивающими только текст инструкций.

Для V01 тестовые заглушки git/git.exe регистрируют попытку вызова и завершают
её ошибкой; реальный Git не вызывается. Дополнительно в V13 проверяется
отсутствие обходных запусков Git по абсолютному пути или через другой процесс.
Отсутствие обращений к Git и чтения его служебных файлов подтверждает, что
имя ветки не участвует в выборе feature; создавать репозиторий или менять
ветки ради проверки не требуется.

Если среда не позволяет создать reparse-point фикстуру, V05 отмечается
Blocked с точной причиной. Полное прохождение SC-004 в таком случае
не заявляется. Ошибка записи вне моделируемых сценариев фиксируется
по контракту tooling.md; фиктивная проверка частичного сбоя не отмечается Passed.

## Контрольный прогон процесса

После подготовки локальных правил пройти сценарии US1 и US2 без реализации
новой продуктовой feature. Допускаются временные учебные документы, явно
отмеченные как фикстуры. Их статусы не являются разрешением менять проект.
Для проверки реального локального analyze используется текущая E02.1.

До read-only анализа фиксируется список и SHA-256 всех файлов проекта
за исключением .git, если пользователь самостоятельно создаст репозиторий.
После прохода перечень и хеши должны совпасть.
Редактирование findings проводится после окончания прохода; затем запускается
новый анализ.

## Завершение

Зафиксировать реальные результаты V01–V18, соответствие SC-001–SC-006,
невыполненные проверки и причины. Провести предкоммитное ревью.
Передать пользователю краткие следующие шаги и название коммита.
Git-команды с записью, публикация проекта и установка приложения
не являются частью этого прогона.
