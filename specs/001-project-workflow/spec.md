# Feature Specification: E02.1 — Правила проекта и подготовка Spec Kit

**Feature Directory**: `specs/001-project-workflow`

**Created**: 2026-09-29

**Status**: Реализована и проверена; результаты в [verification.md](verification.md)

**User Approval**: Согласована пользователем 2026-09-29

**Workflow Mode**: Standard

**Implementation Authorization**: Разрешена пользователем 2026-09-29

**Input**: Подготовить правила разработки GREEN-API Chat и адаптировать локальный
комплект Spec Kit из `agent-flow-harness`. Сохранить две точки согласования:
спецификацию и разрешение начать реализацию после подготовки и анализа
технических документов. Создание приложения выделить в отдельную задачу.

## User Scenarios & Testing

Пользователи этой возможности — владелец проекта и агент-разработчик.
Результат E02.1 — рабочий процесс разработки, а не возможность интерфейса чата.

### User Story 1 — Начать работу по понятным правилам (Priority: P1)

Как владелец проекта, я хочу, чтобы агент в новой сессии находил правила в самом
проекте и соблюдал мои ограничения без повторного объяснения.

**Why this priority**: правила определяют допустимые действия во всех следующих
задачах и сохраняют участие пользователя в существенных решениях.

**Independent Test**: открыть проектные инструкции и проверить по контрольным
ситуациям, можно ли однозначно определить разрешённое действие и следующий шаг.

**Acceptance Scenarios**:

1. **Given** новая сессия в проекте, **When** агент изучает локальные инструкции,
   **Then** он находит правила общения, область текущего проекта, процесс Spec Kit
   и единственный проектный документ с политикой Git.
2. **Given** согласован только объём задачи или её `spec.md`, **When** агент
   выбирает следующий шаг, **Then** он готовит разрешённые документы и не начинает
   реализацию до второго решения пользователя.
3. **Given** для работы нужна установка зависимости, миграция или изменение данных
   в БД, **When** агент готовит следующий шаг, **Then** он объясняет назначение
   действия и передаёт пользователю команды для самостоятельного выполнения.
4. **Given** пользователь просит добавить конкретные файлы в staging, **When**
   агент выполняет запрос, **Then** применяется исключение из политики Git
   с проверкой содержимого и явно перечисленными путями; разрешение на коммит
   из этой просьбы не выводится.
5. **Given** обнаружена существенная неоднозначность, **When** она влияет на
   поведение, данные, безопасность или границы задачи, **Then** агент объясняет
   варианты и задаёт вопрос до принятия решения.

### User Story 2 — Провести небольшую задачу через согласование (Priority: P1)

Как владелец проекта, я хочу обсуждать и реализовывать задачи по одной,
видеть проверяемую спецификацию и принимать два понятных решения.

**Why this priority**: процесс должен помогать проверять результат каждой задачи
и не превращать согласование эпика в разрешение реализовать всё приложение.

**Independent Test**: пройти по описанию процесса на небольшом контрольном примере
от обсуждения до отчёта о готовности; проверить ожидаемые документы и обе точки
решения, не переходя к реализации примера.

**Acceptance Scenarios**:

1. **Given** обсуждена небольшая задача, **When** агент готовит `spec.md`,
   **Then** документ описывает сценарии, требования, границы, влияние на данные
   и критерии приёмки; рядом находится проверка качества спецификации.
2. **Given** пользователь согласовал `spec.md`, **When** агент готовит
   технические документы, **Then** он уточняет требования, составляет план
   и небольшие проверяемые задачи, анализирует согласованность без отдельного
   согласования каждого технического файла.
3. **Given** при подготовке меняется согласованное поведение, **When** агент
   обнаруживает расхождение, **Then** затронутое решение возвращается пользователю;
   прежнее согласование не распространяется на новое поведение.
4. **Given** документы готовы, **When** агент выполняет `speckit-analyze`,
   **Then** анализ не изменяет файлы. Технические замечания исправляются отдельным
   шагом, после чего анализ повторяется.
5. **Given** блокирующие замечания устранены, **When** агент запрашивает разрешение
   на реализацию, **Then** пользователь получает перечень каждого артефакта
   с путём и статусом, результаты анализа и проверок, зависимости и оставшиеся
   риски. Отсутствие необязательного документа объясняется отдельно.
6. **Given** реализация разрешена и выполнена, **When** агент завершает задачу,
   **Then** он проверяет соответствие спеке, проводит предкоммитное ревью,
   сообщает результаты проверок, предлагает улучшения с объяснением,
   даёт следующие шаги и английское название коммита. Сам коммит не создаётся.

### User Story 3 — Использовать комплект внутри текущего проекта (Priority: P2)

Как агент-разработчик, я хочу получать шаблоны и инструкции из текущего проекта
и работать только с явно выбранной задачей.

**Why this priority**: перенос должен дать самостоятельный комплект и исключить
случайный выбор документов другого проекта или другой задачи.

**Independent Test**: проверить комплект на изолированном примере, включая
отсутствующий и неверный каталог задачи, повторную подготовку и запуск проверки
из разных допустимых каталогов проекта.

**Acceptance Scenarios**:

1. **Given** комплект подготовлен в GREEN-API Chat, **When** выполняется штатный
   локальный процесс, **Then** ему не требуется доступ к исходному
   `agent-flow-harness`, загрузка файлов из сети или установка пакетов.
2. **Given** явно выбран каталог задачи, **When** этап определяет рабочие пути,
   **Then** полученный `FEATURE_DIR` соответствует выбранному каталогу внутри
   текущего проекта; выбор по последней созданной задаче или текущей ветке
   не подменяет явный выбор.
3. **Given** каталог не задан, расположен вне проекта или разрешается в другую
   задачу, **When** запускается этап, **Then** обработка останавливается
   с понятной причиной до чтения и изменения документов другой задачи.
4. **Given** документы задачи уже существуют, **When** повторно выполняется
   подготовка, **Then** существующее содержимое сохраняется; его замена требует
   осознанного редактирования в рамках текущей задачи, а не копирования шаблона
   поверх документа.
5. **Given** Git-репозиторий ещё не создан или ветка имеет произвольное имя,
   **When** агент готовит документацию явно выбранной задачи, **Then** процесс
   не создаёт репозиторий или ветку и не требует этого для подготовки документов.
6. **Given** локальный файл или необходимый инструмент отсутствует, **When**
   этап проверяет готовность, **Then** он сообщает, чего не хватает, и следующий
   допустимый шаг; успешный запуск отсутствующего инструмента не заявляется.

### Edge Cases

- Шаблон содержит правило другого продукта, несогласованный архитектурный выбор,
  автоматическую установку или изменяющее Git-действие: такой фрагмент не входит
  в рабочий комплект без адаптации к требованиям этой спецификации.
- Внутренняя инструкция ссылается на отсутствующий файл или этап: это замечание
  к готовности комплекта, а не основание считать этап выполненным.
- Путь содержит пробелы, кириллицу или переход за границу проекта: корректный путь
  внутри проекта обрабатывается, выход за границу отклоняется.
- Повторная подготовка встречает пользовательские изменения: они сохраняются;
  при неоднозначности агент сообщает конкретный конфликт.
- Проверка или запись завершается ошибкой после частичного выполнения: агент
  перечисляет фактически изменённые файлы и незавершённые действия. Автоматический
  откат через Git или удаление пользовательских файлов не выполняется.
- Подготовка технических документов выявляет новую продуктовую неоднозначность:
  работа, зависящая от ответа, приостанавливается до решения пользователя.
- Спецификация относится к документам и инструментам, а не к данным приложения:
  ненужные продуктовые сущности, серверные API и схемы БД ради шаблона не вводятся.

## Requirements

### Functional Requirements

- **FR-001**: В проекте должны быть локальные правила разработки `AGENTS.md`,
  политика `GIT_POLICY.md` и описание процесса Spec Kit. Политика Git переносится
  из согласованного источника без изменения разрешений и запретов.
- **FR-002**: Правила должны закреплять русский язык общения, краткое объяснение
  действий и причин, обсуждение вариантов при груминге, вопросы при существенной
  неоднозначности и работу по одной небольшой задаче.
- **FR-003**: Основной процесс должен включать обсуждение, `specify → clarify →
plan → tasks → analyze → implement` и две точки решения пользователя:
  согласование спеки и разрешение на реализацию после отчёта о готовности.
- **FR-004**: После согласования спеки подготовка технических документов и
  устранение технических замечаний выполняются без согласования каждого файла,
  пока сохраняются одобренные поведение и границы задачи.
- **FR-005**: Анализ должен быть доступен как локальный `speckit-analyze`
  и работать без изменений файлов. Исправления и повторный анализ должны быть
  отдельными шагами; ручной чек-лист не выдаётся за запуск этого этапа.
- **FR-006**: Отчёт перед реализацией должен перечислять каждый артефакт
  и контракт с путём и статусом, результаты проверок и анализа, исправленные
  и открытые замечания, зависимости, риски и текущее решение, ожидаемое
  от пользователя.
- **FR-007**: Локальный комплект должен предоставлять шаблоны и инструкции
  основных этапов, проверки качества спецификации и общих принципов разработки
  проекта. Служебные инструкции и доступные средства подготовки документов
  должны ссылаться на существующие части комплекта.
- **FR-008**: Проектные принципы и шаблоны должны сохранять согласованные
  ограничения и описывать текущее состояние. Запрещено переносить требования
  другого продукта, историю его изменений и несогласованные решения о БД,
  сессиях, дизайне или зависимостях нового приложения.
- **FR-009**: Этапы должны использовать явно заданный
  `SPECIFY_FEATURE_DIRECTORY` и проверять разрешённый `FEATURE_DIR`.
  Общий указатель `.specify/feature.json` и выбор активной задачи по ветке
  или последнему каталогу не используются.
- **FR-010**: Средства подготовки должны ограничивать работу текущим проектом
  и выбранной задачей, сохранять существующие документы при повторном запуске
  и отклонять неверный выбор до работы с документами другой задачи.
- **FR-011**: Штатная подготовка документов должна работать без созданного
  Git-репозитория и без зависимости от имени ветки. Автоматические изменяющие Git-действия,
  внешние публикации и действия расширений с такими последствиями
  не входят в процесс.
- **FR-012**: После подготовки комплект должен быть самостоятельным:
  исходный проект допускается указывать как источник происхождения,
  но его файлы не должны быть нужны для запуска этапов в новом проекте.
- **FR-013**: Агент не скачивает и не устанавливает пакеты или ПО,
  не запускает миграции и не изменяет данные в БД. Если действие требуется,
  пользователь получает объяснение и команды для самостоятельного выполнения.
- **FR-014**: Результаты проверок должны различать проверку документа,
  фактический запуск инструмента и непроведённую проверку. При ошибке
  сообщаются причина, выполненные изменения и оставшиеся действия.
- **FR-015**: Завершение реализации должно включать проверку соответствия
  спецификации, необходимые проверки, предкоммитное ревью, объяснение
  улучшений, следующие шаги и название коммита с одним из префиксов
  `fix:`, `feat:`, `refactor:`, `chore:`. Коммит выполняет пользователь.
- **FR-016**: Проектные документы, примеры и проверки не должны содержать
  реальные токены, номера телефонов, идентификаторы аккаунтов и личную переписку.
- **FR-017**: Переносимый комплект должен иметь понятную локальную инструкцию
  использования и сведения о происхождении. Подключения к внешним сервисам,
  автоматические Git hooks и публикация задач во внешние системы исключены
  из объёма E02.1.

### Scope Boundaries

**В объёме E02.1**:

- Правила разработки, политика Git, общие принципы проекта и описание процесса.
- Необходимые локальные шаблоны, инструкции этапов и средства подготовки
  документов из существующего комплекта с адаптацией.
- Проверка внутренних ссылок, выбора задачи, повторных запусков,
  соблюдения границ и возможности пользоваться комплектом самостоятельно.
- Документация использования и актуализация обзора проекта.

**За пределами E02.1**:

- Создание Next.js-приложения, выбор и установка его зависимостей.
- Размещение на Vercel, создание удалённого репозитория и изменяющие Git-команды.
- Реализация чата, серверных обработчиков, сессий, истории или базы данных.
- Изменение согласованного флоу поиска получателя.
- Новые обращения к GREEN-API, сообщения собеседнику или изменение аккаунтов.
- Настройка параллельной работы агентов, расширений и внешних интеграций.
  Явный выбор каталога задачи сохраняется как защита от работы не с теми файлами.
- Реализация других задач E02 под видом подготовки инструментов.

### Data Effects & User Decision

- **Changed data**: на этапе подготовки — документы текущей feature и обзор
  проекта. При реализации — локальные правила, описание процесса и необходимые
  файлы комплекта в проекте; полный перечень путей будет в техническом плане.
  Пользовательские аккаунты, исходный проект и внешние сервисы не изменяются.
- **Preview**: пользователь видит эту спецификацию, затем полный комплект
  технических документов и отчёт о готовности с перечнем будущих изменений.
- **Confirmation**: согласование объёма E02.1 разрешает подготовить `spec.md`;
  согласование `spec.md` разрешает подготовить технические документы.
  Реализация начинается после отдельного разрешения пользователя.
- **Cancellation**: при отмене сохраняются уже подготовленные документы;
  дальнейшие изменения прекращаются. Документы автоматически не удаляются.
- **Idempotency and duplicates**: повторная подготовка использует тот же каталог
  feature, не создаёт дубликат задачи и не заменяет готовые документы шаблонами.
- **Failure result**: пользователь получает сведения о частично выполненных
  изменениях и ошибке. Успех непроверенного этапа не заявляется, исходный комплект
  и чужие документы не изменяются.

### Key Entities

- **Правила проекта** — согласованные ограничения и принципы; используются
  во всех задачах и не содержат указателя на текущую feature.
- **Каталог feature** — отдельный набор документов одной задачи, её статус
  согласования и разрешение на реализацию.
- **Артефакт этапа** — спецификация, проверка качества, исследование, план,
  необходимые модели и контракты, инструкция проверки или список задач.
- **Отчёт анализа** — результаты проверки согласованности, покрытия требований
  задачами и блокирующие замечания; сам анализ не изменяет документы.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Для пяти ситуаций из User Story 1 локальные правила однозначно
  определяют допустимый следующий шаг без повторного объяснения ограничений
  из переписки.
- **SC-002**: Контрольная задача проходит все этапы подготовки до отчёта
  о готовности. Обе точки решения различимы, а реализации без разрешения
  пользователя не происходит.
- **SC-003**: Все внутренние ссылки, необходимые для основных этапов процесса,
  ведут к существующим локальным документам или инструментам. Ссылки
  на исходный проект служат только указанием происхождения.
- **SC-004**: Все шесть сценариев User Story 3 проходят проверку; неверный выбор
  задачи не приводит к обработке её документов, повторная подготовка
  сохраняет существующее содержимое.
- **SC-005**: Проверка анализа подтверждает отсутствие изменений файлов;
  в итоговом отчёте отдельно указаны реально выполненные и непроведённые проверки.
- **SC-006**: Перечень изменений E02.1 содержит только согласованные служебные
  файлы и документы. Политика Git сохраняет смысл и ограничения источника,
  реальные реквизиты отсутствуют, приложение и внешние сервисы не изменяются.

## Assumptions and Dependencies

- Источник адаптации — локальный `D:\Pet-projects\agent-flow-harness`.
  Его доступность проверена. Зафиксированные в нём продуктовые решения
  не являются решениями для GREEN-API Chat.
- Целевой проект — `D:\Pet-projects\green-api-chat`. Текущая рабочая среда —
  Windows и PowerShell. Поддержка других сред этим этапом не обещается.
- Существующий обзор проекта сохраняется и используется как источник
  согласованных решений: [project-overview.md](../../docs/project-overview.md).
- E01 подтвердил обмен текстом через найденный по username chatId.
  Успешный поиск по телефону остаётся отдельной незавершённой проверкой;
  для подготовки локального рабочего процесса его результат не требуется.
- Эта feature подготавливает сами инструменты Spec Kit. Её первая спецификация
  и чек-лист составлены по локальному образцу до появления комплекта в целевом
  проекте. Это подготовка документов, а не подтверждение работы локальных
  scripts или прохождения `speckit-analyze`.
- Технический план должен описать начальную подготовку и анализ E02.1
  до появления локального комплекта, сохранив обе точки согласования
  и честное указание доступных проверок.
- Точные состав файлов, зависимости служебных средств и способы их проверки
  определяются при техническом планировании. Несогласованных предположений
  о поведении приложения эта спецификация не вводит.
