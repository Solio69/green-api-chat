# Исследование E04.1 — поиск получателя в форме

**Дата**: 2026-10-01

**Спецификация**: [spec.md](spec.md)

**Состояние**: реализовано; автоматические проверки пройдены

## GREEN-API и ограничения

`CheckAccount` вызывается методом POST по `{apiUrl}/waInstance{idInstance}/checkAccount/{apiTokenInstance}`. Тело содержит либо числовой `phoneNumber`, либо строковый `username` с ведущим `@`. `force` необязателен и по умолчанию равен `false`; для этой задачи его не передаём. `exist: true` с непустым `chatId` даёт идентификатор будущего получателя, `exist: false` не доказывает отсутствие аккаунта при поиске по телефону. Сервис может вернуть лимит в теле HTTP 200 как `status: false` и `data.reason: rate_limit_exceeded`, а также HTTP 469 при ограничении Telegram. [CheckAccount](https://green-api.com/telegram/docs/api/service/CheckAccount/).

Для Telegram Developer разрешён обмен с тремя чатами, `CheckAccount` ограничен 100 вызовами в месяц; частота `CheckAccount` — 10 запросов в секунду. Поиск при каждом нажатии клавиши неоправданно расходовал бы лимит, поэтому запрос только по отправке формы. `SendMessage` в задачу не входит; найденный `chatId` не означает успешную отправку. [Тарифы](https://green-api.com/telegram/docs/about-tariffs/), [ограничение частоты](https://green-api.com/telegram/docs/api/ratelimiter/).

HTTP 401 означает проблему с токеном. HTTP 403 может означать ошибочный `idInstance` или адрес запроса, поэтому одного этого статуса недостаточно, чтобы уверенно признать сессию недействительной. Для HTTP 400 возможны состояния запуска или отсутствия авторизации инстанса. [Стандартные ошибки](https://green-api.com/telegram/docs/api/common-errors/).

Обычные Telegram username имеют длину 5–32 символа, но коллекционные имена могут быть короче пяти. Локальная проверка поэтому допускает 1–32 символа: она отсекает чрезмерный ввод, не решая за Telegram, существует ли короткий username. [Telegram API](https://core.telegram.org/method/account.checkUsername), [Telegram FAQ](https://telegram.org/faq#collectible_usernames).

## Выбор подключения формы

| Вариант                                                                                                   | Плюсы                                                                              | Риски                                                                                                     | Выбор       |
| --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ----------- |
| Браузер вызывает GREEN-API напрямую                                                                       | Меньше серверного кода                                                             | Токен оказывается в URL браузерного запроса и доступен клиентскому коду; нет безопасной сессии для поиска | Не подходит |
| Браузер вызывает собственный POST Route Handler, тот читает существующую сессию и вызывает `CheckAccount` | Реквизиты остаются на сервере; сервер контролирует формат, ошибки и лимит повторов | Нужен явный контракт и тесты                                                                              | Выбрано     |

Для формы используется существующая авторизация: серверная страница `/` вызывает `GetStateInstance` через `resolveHome`, затем показывает форму. При поиске Route Handler повторно читает cookie, но не выполняет дополнительный `GetStateInstance` перед каждым `CheckAccount`: лишний вызов создавал бы задержку и собственный лимит. Токен не включается в тело запроса из браузера. Положительный результат не сохраняется; следующий этап отдельно решит работу с чатом.

## Классификация ответов

- HTTP 200 с `exist: true` и непустым строковым `chatId` — найдено; `exist: false` — не найдено, без `chatId`.
- HTTP 200 с `status: false`, `data.reason: rate_limit_exceeded`; HTTP 429 и 469 — ограничение, не «не найдено».
- HTTP 401 — однозначная ошибка токена: удалить cookie текущего браузера и потребовать вход. HTTP 403 остаётся безопасной ошибкой поиска, потому что причина может быть в адресе запроса; cookie автоматически не удаляется.
- Документированное состояние запуска и HTTP 5xx — временная ошибка; неизвестная форма ответа, несовместимое тело или положительный ответ без `chatId` — некорректный ответ провайдера.
- Тело ошибки GREEN-API и полный URL с токеном не выводятся в браузер или журнал. Для исходящего запроса используются таймаут, `cache: no-store` и запрет автоматического редиректа по аналогии с существующим `GetStateInstance`.

## Проверки без новых пакетов

Интеграционные тесты Playwright вызывают чистую функцию проверки/классификации и серверный обработчик с фиктивной сессией и подменённым `fetch`. Браузерные тесты запускают настоящую главную страницу, а не её HTML-копию. Для этого тестовый Node-процесс Next.js предзагружает локальную TypeScript ESM-фикстуру через `NODE_OPTIONS=--import` с `file://` URL на Windows; она перехватывает только исходящие запросы к фиксированному хосту GREEN-API и возвращает документированные ответы. Node 24 удаляет типы при загрузке `.ts`, а `npm run typecheck` отдельно проверяет типы по `tsconfig.json`. Поэтому фикстура использует относительный импорт JSON и не зависит от алиаса `@/`. Локальный `tests/e2e/fixtures/package.json` задаёт `type: module` только для этой папки: Node не приходится угадывать модульный формат `.ts`, а настройки всего приложения остаются прежними. Playwright задаёт окружение только запускаемому webServer. Фикстура и вымышленный `SESSION_PASSWORD` включаются только командой `test:e2e`; продуктовый код и production-конфигурация API-хоста не получают тестового переключателя. Так проверяется реальный путь формы, сессии и сервера без сторонней библиотеки и без расхода лимита GREEN-API. [TypeScript в Node.js](https://nodejs.org/api/typescript.html), [Playwright webServer](https://playwright.dev/docs/api/class-testconfig).

Альтернатива — отдельная тестовая страница формы: её проще изолировать, но она добавляет маршрут в продуктовую сборку и не проверяет настоящую защищённую главную страницу. Прямые запросы к реальному инстансу в автотестах потребовали бы секреты и расходовали бы лимит. Предзагрузка фикстуры проверена входом на настоящую защищённую главную страницу перед поведенческим Red. Сбой окружения не считается проверкой отсутствующего поведения.

## Зависимости

Next.js, React, iron-session, Sass и Playwright уже установлены в проекте. Новые пакеты, миграции и изменения БД не требуются. Ручной поиск на реальном инстансе выполняет пользователь после реализации, не публикуя реквизиты.
