# Implementation Plan: E04.1 — поиск получателя в форме

**Spec**: [spec.md](spec.md)

**Дата**: 2026-10-01

**Согласование spec.md**: пользователь подтвердил «да ок» 2026-10-01

## Summary

Защищённая главная страница по-прежнему проверяет инстанс методом `GetStateInstance`. После успешной проверки вместо временного JSON она показывает минимальную форму с одним полем и режимами «Телефон / @username». Отправка формы вызывает собственный `POST /api/recipients/search`; Route Handler читает существующую зашифрованную cookie, проверяет ввод и один раз вызывает GREEN-API `CheckAccount`. Форма показывает «Пользователь найден» с `chatId`, сообщение «не найдено» или безопасную ошибку. Метод `SendMessage` не вызывается.

## Considered Options

| Вариант | Преимущества | Ограничения и риски | Выбор и причина |
| --- | --- | --- | --- |
| Одно поле с явными режимами | Малый интерфейс, понятный способ поиска | Нужно сбрасывать старое значение при переключении | Выбрано пользователем |
| Два поля одновременно | Оба способа видны сразу | Неясно, какое поле отправлять; больше элементов | Не выбрано |
| Собственный Route Handler перед `CheckAccount` | Токен остаётся на сервере; ошибки и формат проверяются централизованно | Нужны контракт и тесты | Выбрано |
| Прямой вызов GREEN-API из браузера | Меньше серверного кода | Выдаёт браузеру токен из сессии | Недопустимо |
| Локальная предзагрузка ответов провайдера для Playwright E2E | Проверяет настоящую страницу и cookie без живого API и новых пакетов | Нужна тестовая фикстура | Выбрано; проверяется в Red |
| Дополнительная тестовая страница компонента | Легко подменить API браузером | Тестирует обходной экран и добавляет маршрут в сборку | Не выбрано |

## Technical Context

Next.js 16 App Router, React 19, TypeScript 5, Node 24, iron-session 9, Sass и Playwright уже установлены. UI остаётся русскоязычным; SCSS Modules, БЭМ, токены и миксины следуют [CODE_STYLE.md](../../docs/CODE_STYLE.md). Результат и `chatId` хранятся только во временном состоянии формы. БД, миграции и новые пакеты не нужны. Тариф Telegram Developer ограничивает `CheckAccount` 100 вызовами в месяц, поэтому поиск не запускается при вводе и не повторяется автоматически.

Существующий `HomePage` и `resolveHome` сохраняют проверку `GetStateInstance` и правила редиректов. В успешной ветке рендерится форма. Для POST-поиска используется отдельный серверный маршрут и тот же `SESSION_PASSWORD`; данные cookie не сериализуются в JSX или клиентский запрос.

## Research and Design

- [research.md](research.md) фиксирует официальный контракт `CheckAccount`, лимиты, варианты подключения и тестовый стенд.
- [Контракт собственного API](contracts/recipient-search.md) задаёт запрос, ответы, коды и границу с GREEN-API.
- [quickstart.md](quickstart.md) описывает будущую проверку с фиктивными данными и ручной сценарий без публикации секретов.
- `data-model.md` не нужен: постоянных сущностей и миграций нет. Временные структуры `SearchRequest` и `SearchResult` заданы контрактом и будут типизированы в коде.

`check-account.ts` строит запрос к фиксированному хосту GREEN-API, передаёт `phoneNumber` числом или `username` с `@`, классифицирует документированные ответы, таймауты и лимиты. Серверный обработчик проверяет JSON, действующую сессию и формат; возвращает только безопасный результат. Клиентская форма управляет режимом, значением, ошибкой и загрузкой. Значимые и повторяемые строки, статусы и значения хранятся в константах по правилам проекта.

Тело запроса поиска читается стандартным `request.json()`, тело запроса входа — `request.text()` с последующим разбором JSON и существующей проверкой размера. Ошибки чтения и некорректный JSON возвращают безопасный HTTP 400. Новый маршрут проверяет `Content-Type` и строгую структуру `{mode,value}`. Телефон остаётся строкой в браузере, а перед GREEN-API преобразуется в безопасное целое число; username нормализуется с одним `@`. Длина телефона не более 15 цифр, ведущий ноль и иные символы отклоняются. Username с `@` или без него содержит только латинские буквы, цифры и `_`; длина имени без `@` — от 1 до 32 символов. Синтаксически допустимое значение не объявляется существующим до ответа провайдера.

Сервер сначала проверяет наличие пригодного `SESSION_PASSWORD`: его отсутствие даёт `503 server_unavailable`, а не ложное «сессия истекла». Затем проверяет cookie, потом JSON и значение поиска. Отсутствующая сессия и HTTP 401 провайдера дают собственный `401 session_required`. При HTTP 401 провайдера cookie удаляется в Route Handler, после чего форма направляет на `/login`. HTTP 403 провайдера не удаляет cookie: он допускает как неверный `idInstance`, так и неверный адрес запроса. Тело HTTP 200 проверяется до признания успешного поиска, поскольку лимит может находиться внутри `status: false`. Лимит внутри тела, HTTP 429/469, временный сбой и неожиданный формат разделяются по [контракту](contracts/recipient-search.md). Поиск не вызывает дополнительный `GetStateInstance`.

## Tasks and Dependencies

Последовательность проверки задачи: рабочая фикстура для Playwright и базовый вход; сохраняемый браузерный тест через настоящий HTTP-маршрут и главную страницу с поведенческим Red на 404 API и отсутствующей форме; интеграционные тесты модулей до их реализации; серверный Green; UI Green; рефакторинг и итоговая регрессия. Ошибка импорта теста не считается поведенческим Red. Команда `test:e2e` строит production-сборку, отдельная `npm run build` не нужна.

Старые тесты входа, состояния инстанса и выхода остаются регрессионными. В `playwright.config.ts` окружение webServer задаёт вымышленный `SESSION_PASSWORD` и `NODE_OPTIONS` для предзагрузки фикстуры; `reuseExistingServer: false` исключает случайное использование пользовательского dev-сервера. Команды и зависимости детализируются в [tasks.md](tasks.md). При работающем dev-сервере пользователь остановит его перед production/E2E-проверками; агент не устанавливает пакеты и не обращается к реальному GREEN-API.

## Verification

- Интеграционные тесты: оба режима; нормализация username; один POST `CheckAccount`; `exist: true/false`; отсутствующий `chatId`; лимит внутри HTTP 200, HTTP 429/469, HTTP 401/403, HTTP 5xx и сетевой сбой; отсутствие токена в ответе.
- Серверный маршрут: отсутствующая/повреждённая сессия, неверный JSON/media type/значение, удаление cookie только при однозначной ошибке токена, `Cache-Control: no-store`.
- E2E: доступ к форме после входа, переключение режимов, Enter/кнопка, ошибка поля с исправлением, найденный `chatId`, подсказка username, отсутствие старого результата, блокировка поля/режима/повтора во время запроса, очистка результата после перезагрузки, отсутствие `SendMessage` и выход.
- Red — падение по отсутствующему поведению при рабочей фикстуре. Сбой предзагрузки, сборки или импорта — Blocked до исправления окружения, не Red. Green — поведение проходит; после рефакторинга проверки повторяются одним итоговым запуском.
- Ручной сценарий пользователь выполняет со своим инстансом: поиск тестового собеседника по номеру, затем по username, показ найденного `chatId`. Реквизиты, номер и `chatId` не присылаются в чат и не фиксируются в документах.
- Автоматический результат: 80 интеграционных и 34 браузерных теста прошли; ручная проверка реального инстанса ожидается. Фактические команды и ограничения приведены в [verification.md](verification.md).
