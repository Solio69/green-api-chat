# Контракт поиска получателя

**Дата**: 2026-10-01

**Маршрут приложения**: `POST /api/recipients/search`

**Внешний метод**: GREEN-API `CheckAccount`

**Статус**: реализован и проверен интеграционными и браузерными тестами

## Запрос браузера к приложению

`Content-Type: application/json`. Тело содержит ровно два поля:

```json
{ "mode": "phone", "value": "12345678901" }
```

или

```json
{ "mode": "username", "value": "example_user" }
```

`mode` принимает только `phone` или `username`. `value` — строка. Для телефона допустимы цифры без `+`, пробелов и разделителей, первая цифра не ноль, длина не превышает 15 цифр; интерфейс объясняет необходимость кода страны. Это проверка формы записи, а не доказательство существования номера. Для username допустимы латинские буквы, цифры и `_`, с одним необязательным `@` в начале; длина имени без `@` — от 1 до 32 символов. `@` без имени, слишком длинное имя и посторонние символы отклоняются. Структура JSON проверяется сервером; тело читается стандартным `request.json()`. Реквизитов GREEN-API в запросе нет.

Сервер сначала проверяет конфигурацию сессии и саму сессию, затем читает и проверяет тело запроса. Без сессии ответ всегда `401 session_required`, даже если тело повреждено; `CheckAccount` не вызывается. Невалидный JSON, другой media type, лишние поля, некорректные `mode`/`value` при действующей сессии отклоняются до `CheckAccount`. Сервер повторяет проверку ввода независимо от браузерной валидации.

## Вызов GREEN-API

Сервер извлекает `idInstance` и `apiTokenInstance` только из зашифрованной HttpOnly-сессии. Для `phone` он передаёт провайдеру `{ "phoneNumber": 12345678901 }` с числом, безопасно представимым в JavaScript; для `username` — `{ "username": "@example_user" }`. Один запрос формы создаёт не более одного POST `CheckAccount`; `force` не указывается. Полный URL с токеном не раскрывается клиенту и не журналируется. [Документация CheckAccount](https://green-api.com/telegram/docs/api/service/CheckAccount/).

## Ответы приложения

Каждый JSON-ответ имеет `Cache-Control: no-store`. `Response.json` сам задаёт `Content-Type`. Ошибки содержат только код, понятный приложению; исходный ответ GREEN-API не возвращается.

| HTTP | Ответ                                                                    | Значение для формы                                                               |
| ---- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| 200  | `{ "status": "ok", "result": "found", "chatId": "10000000" }`            | «Пользователь найден» и `chatId`                                                 |
| 200  | `{ "status": "ok", "result": "not_found" }`                              | Подсказка согласно выбранному режиму; `chatId` отсутствует                       |
| 400  | `{ "status": "error", "code": "invalid_request" }`                       | Ошибка формата ввода                                                             |
| 401  | `{ "status": "error", "code": "session_required" }`                      | Переход на `/login`; cookie удаляется при подтверждённой ошибке токена           |
| 429  | `{ "status": "error", "code": "rate_limited" }`                          | Ограничение проверок; сессия сохраняется                                         |
| 502  | `{ "status": "error", "code": "invalid_upstream_response" }`             | Поиск не подтверждён; сессия сохраняется                                         |
| 503  | `{ "status": "error", "code": "service_unavailable" }` или `retry_later` | Временный сбой; сессия сохраняется                                               |
| 503  | `{ "status": "error", "code": "server_unavailable" }`                    | Секрет шифрования сессии не настроен на сервере; браузер не получает подробности |

При отсутствии или истечении сессии `401` возвращается без обращения к GREEN-API. Если `SESSION_PASSWORD` отсутствует или не соответствует минимальным требованиям, возвращается `503 server_unavailable`: повторный вход не исправит конфигурацию сервера. Однозначный HTTP 401 от GREEN-API также приводит к `401 session_required` и удалению cookie текущего браузера. HTTP 403 провайдера не считается однозначным доказательством неверных реквизитов: документация допускает ошибочный адрес запроса; клиент получает `502 invalid_upstream_response`, а сессия сохраняется. Клиент переходит на `/login` при любом `401` своего маршрута.

HTTP 200 с `status: false` и `data.reason: rate_limit_exceeded`, HTTP 429 и 469 провайдера отображаются как `429 rate_limited`. `exist: true` без непустого строкового `chatId` и неизвестные структуры ответа отображаются как `502 invalid_upstream_response`. HTTP 5xx, ошибка сети и таймаут отображаются как `503 service_unavailable`; документированное временное состояние запуска — как `503 retry_later`. При `exist: false` ответ не содержит `chatId` независимо от других полей провайдера.

Поиск получателя не вызывает `SendMessage` и не обещает возможность отправки. При последующей отправке будет использоваться полученный `chatId`, но отправка входит в другую задачу.
