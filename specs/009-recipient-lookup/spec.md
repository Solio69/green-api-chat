# Feature Specification: E04.1 — поиск получателя в форме

**Feature Directory**: specs/009-recipient-lookup

**Created**: 2026-10-01

**Status**: Реализована; автоматические проверки пройдены, ручная проверка ожидается

**User Approval**: Да, 2026-10-01

**Workflow Mode**: Standard

**Implementation Authorization**: Получено от пользователя («делай», 2026-10-01)

**Input**: Авторизованный пользователь ищет получателя будущего сообщения по телефону или Telegram username в минимальной форме на главной странице. Сервер использует GREEN-API `CheckAccount`; найденный `chatId` отображается пользователю. Отправка сообщения через `SendMessage` и работа с перепиской выполняются отдельными задачами.

## User Scenarios & Testing

### User Story 1 — найти получателя по телефону (Priority: P1)

Как пользователь с действующей сессией, я могу ввести номер с кодом страны и увидеть, найден ли получатель будущего сообщения.

**Why this priority**: Поиск по телефону — первый шаг согласованного сценария создания чата.
**Independent Test**: Открыть главную страницу с фиктивной сессией, отправить номер из формы и подменить ответ `CheckAccount`; проверить вызов сервера, найденный `chatId` и подсказку при `exist: false`.

**Acceptance Scenarios**:
1. **Given** действующая сессия и открытая главная страница, **When** страница загружается, **Then** пользователь видит одно поле поиска в режиме «Телефон», переключение на «@username», кнопку «Найти» и существующую кнопку выхода вместо временного JSON состояния инстанса.
2. **Given** действующая сессия и номер с кодом страны, состоящий только из цифр, **When** пользователь отправляет форму и `CheckAccount` возвращает `exist: true` с непустым `chatId`, **Then** форма показывает «Пользователь найден» и `chatId`.
3. **Given** действующая сессия и корректный номер, **When** `CheckAccount` возвращает `exist: false`, **Then** форма показывает «Не удалось найти пользователя по номеру. Проверьте номер или попробуйте поиск по @username» и действие «Найти по @username». Это не утверждает, что аккаунта Telegram нет: номер может быть скрыт настройками приватности.

### User Story 2 — найти получателя по username (Priority: P1)

Как пользователь, я могу переключить способ поиска на username сразу или после неуспешного поиска по телефону, чтобы получить `chatId` собеседника.

**Why this priority**: Поиск по телефону для согласованного тестового собеседника уже вернул отрицательный результат, а поиск по username — положительный.
**Independent Test**: Проверить переключение формы и оба варианта ввода — `name` и `@name` — с подменённым GREEN-API. Сервер отправляет провайдеру username с одним `@`, а форма показывает найденный `chatId`.

**Acceptance Scenarios**:
1. **Given** открытая форма, **When** пользователь выбирает «@username» напрямую либо через действие после неуспешного поиска по телефону, **Then** поле принимает Telegram username; прежние значение и результат поиска очищаются, новый запрос автоматически не запускается.
2. **Given** действующая сессия, **When** пользователь отправляет username с `@` или без него, **Then** сервер приводит значение к формату `@username` для `CheckAccount`; при `exist: true` с непустым `chatId` форма показывает «Пользователь найден» и `chatId`.
3. **Given** корректный username, **When** GREEN-API возвращает `exist: false`, **Then** форма показывает «Пользователь не найден. Проверьте @username и попробуйте ещё раз» без `chatId`; поиск по другому значению остаётся возможным.

### User Story 3 — отличать отсутствие результата от ошибки (Priority: P1)

Как пользователь, я вижу понятную ошибку, когда поиск не состоялся из-за ввода, сессии, лимита или сбоя сервиса, и могу исправить ввод или повторить попытку.

**Independent Test**: Проверить пустой и некорректный ввод в форме, отсутствие сессии, подтверждённый отказ в доступе, лимит GREEN-API, сетевой сбой и неожиданный ответ; убедиться, что интерфейс не сообщает «не найдено» и не запускает лишние запросы.

**Acceptance Scenarios**:
1. **Given** сессия отсутствует, истекла или повреждена, **When** пользователь открывает главную страницу или отправляет поиск, **Then** приложение переводит его на `/login`, а поиск не обращается к GREEN-API.
2. **Given** поле пустое или значение не соответствует выбранному способу поиска, **When** пользователь нажимает «Найти» или Enter, **Then** форма показывает ошибку ввода и запрос к GREEN-API не выполняется; при исправлении ввода ошибка обновляется.
3. **Given** `CheckAccount` однозначно сообщает, что сохранённые реквизиты недействительны, **When** сервер обрабатывает ответ, **Then** он завершает сессию текущего браузера и переводит пользователя на `/login`.
4. **Given** GREEN-API сообщает о лимите, временной недоступности либо возвращает неожиданный ответ, **When** сервер обрабатывает его, **Then** форма показывает безопасную различимую ошибку вместо «не найдено», сессия сохраняется и повторный поиск возможен по действию пользователя.

### Edge Cases

- Поиск запускается только по нажатию «Найти» или Enter. Во время проверки поле, переключение режима и повторная отправка недоступны; сервер не делает автоматических повторов и не запрашивает принудительный обход кеша `CheckAccount`.
- Положительный ответ без непустого `chatId` не считается найденным получателем.
- Телефон передаётся только с кодом страны и цифрами; username при отправке провайдеру начинается ровно с одного `@`.
- Поиск по username не запускается автоматически после `exist: false` для телефона: username должен указать пользователь. При смене способа поиска прежние ввод, ошибка и результат очищаются.
- Редактирование значения и новый поиск скрывают прежний результат, чтобы старый `chatId` не выглядел результатом другого запроса. Найденный `chatId` сам по себе не подтверждает возможность отправки или доставки сообщения.
- Неизвестные данные ответа GREEN-API, технические причины ошибок и URL с токеном не передаются браузеру и не записываются в журнал приложения.

### Verification Approach

После отдельного разрешения на реализацию серверный контракт, классификация ответов и поведение формы проходят TDD: сохраняемые тесты, поведенческий Red, минимальная реализация, Green и рефакторинг. Интеграционные тесты проверяют сервер с фиктивной сессией и подменённым ответом GREEN-API; браузерные тесты проверяют ввод, переключение, состояния поиска и показ результата без настоящих реквизитов. Ручную проверку настоящего инстанса выполняет пользователь; она дополняет автоматические проверки. Оформление проверяется отдельно с учётом существующего кодстайла.

## Requirements

### Functional Requirements

- **FR-001**: После подтверждения авторизации на главной странице отображается минимальная форма поиска с одним полем, режимами «Телефон» и «@username», кнопкой «Найти» и существующей кнопкой выхода. Режим по умолчанию — «Телефон»; временный JSON состояния инстанса не показывается.
- **FR-002**: Пользователь запускает поиск кнопкой или Enter. При переключении режима прежние ввод, ошибка и результат очищаются; переход к username после отрицательного поиска по телефону не запускает запрос автоматически.
- **FR-003**: Форма проверяет обязательность и формат значения после отправки и обновляет ошибку при исправлении. Сервер независимо проверяет действительность сессии и принимает ровно один способ поиска за запрос: номер с кодом страны и только цифрами либо Telegram username с `@` или без него. Неверный ввод отклоняется до обращения к GREEN-API.
- **FR-004**: Реквизиты GREEN-API берутся только из действительной защищённой сессии; браузер не передаёт `idInstance` и `apiTokenInstance` в теле поиска. Без действительной сессии поиск не выполняется и пользователь переходит на `/login`.
- **FR-005**: Сервер обращается к `CheckAccount` по выбранному способу поиска. Username передаётся провайдеру в формате `@username`; телефон — как номер в международном формате без символов форматирования. Поиск не запускается при каждом вводе символа, автоматически не повторяется и не обходит кеш провайдера принудительно.
- **FR-006**: При `exist: true` и непустом `chatId` форма показывает «Пользователь найден» и `chatId`. При `exist: false` она показывает соответствующее сообщение «не найдено» без `chatId`; после отрицательного поиска по телефону предлагает действие «Найти по @username».
- **FR-007**: Лимит запросов, временная недоступность и некорректный ответ GREEN-API не преобразуются в «не найдено»; форма показывает безопасную различимую ошибку и сохраняет сессию. При однозначном отказе GREEN-API из-за недействительных реквизитов приложение завершает сессию текущего браузера и переводит пользователя на `/login`.
- **FR-008**: Во время поиска поле, переключение режима и повторная отправка недоступны, виден статус проверки. Редактирование значения и новый поиск скрывают предыдущий результат; повторный поиск доступен без перезагрузки.
- **FR-009**: Сервер не вызывает `SendMessage`, не отправляет сообщение, не создаёт и не сохраняет чат, не изменяет инстанс и не записывает результат поиска в БД. Результат формы не сохраняется после перезагрузки страницы.
- **FR-010**: Реквизиты сессии, URL провайдера с токеном и необработанное тело ошибки GREEN-API не включаются в ответ браузеру или журналы приложения. Телефон и username не сохраняются в собственном хранилище.

### Scope Boundaries

- В объёме: минимальная форма на главной странице, серверный поиск по телефону и username, проверка ввода и сессии, результаты и ошибки на экране, автоматические проверки.
- За пределами: автоматический поиск по username после отрицательного ответа для телефона, экран чата и список чатов, `SendMessage`, отправка/получение сообщений, история переписки, хранение результата и изменение настроек GREEN-API.

### Data Effects & User Decision

- **Changed data**: Приложение не сохраняет и не изменяет данные переписки. Завершение сессии при подтверждённой ошибке реквизитов удаляет cookie текущего браузера. Вызов `CheckAccount` может расходовать лимит провайдера и использовать его кеш.
- **Preview**: Перед запросом пользователь видит выбранный способ поиска и введённое значение; статус и найденный `chatId` появляются только после ответа.
- **Confirmation**: Нажатие «Найти» или Enter запускает одну проверку; отдельное подтверждение не требуется.
- **Cancellation**: До отправки запроса значение можно изменить или переключить способ. Результат не сохраняется после перезагрузки и не создаёт чат.
- **Idempotency and duplicates**: Повторный ручной поиск не создаёт чат и не отправляет сообщение, но может расходовать лимит провайдера; параллельная повторная отправка из формы блокируется.
- **Failure result**: Ошибка отличается от «не найдено», не содержит реквизитов или необработанных подробностей провайдера и не показывает устаревший `chatId`.

### Key Entities

- **Запрос поиска**: один тип поиска и одно значение; реквизиты инстанса к нему не относятся.
- **Результат поиска**: «найден» с `chatId`, «не найден» либо ошибка, отображаемые формой. Постоянной записи о результате нет.

## Success Criteria

- **SC-001**: На главной странице пользователь может выполнить поиск по телефону и напрямую либо после отрицательного результата переключиться на username. Переключение очищает прежний ввод и результат; каждый отправленный поиск вызывает не более одного `CheckAccount`, ввод без отправки его не вызывает.
- **SC-002**: При достоверном положительном ответе форма показывает «Пользователь найден» и `chatId`; при `exist: false` не показывает `chatId` и даёт согласованную подсказку для текущего способа поиска.
- **SC-003**: Одинаковый username с `@` и без него приводит к одному формату запроса GREEN-API и одинаковому результату на экране.
- **SC-004**: Отсутствующая сессия и неверный ввод не вызывают `CheckAccount`; подтверждённая ошибка реквизитов завершает сессию, а лимит, сбой и неожиданный ответ показывают ошибку без ложного «не найдено».
- **SC-005**: Во время проверки виден статус ожидания и недоступна повторная отправка; форма не вызывает `SendMessage` и не сохраняет результат после перезагрузки. Тесты не используют настоящие реквизиты; ответы сервера и журналы не содержат токен. Подтверждены Red → Green → Refactor, браузерные сценарии формы и итоговая регрессия затронутого входа и выхода.

## Assumptions and Dependencies

- Используется существующая сессия E03.2 и общий адрес GREEN-API для Telegram, согласованный в проекте.
- Официальный `CheckAccount` принимает `phoneNumber` или `username`, возвращает `exist` и при положительном результате `chatId`; `exist: false` по телефону допускает скрытый номер. [Документация GREEN-API](https://green-api.com/telegram/docs/api/service/CheckAccount/).
- Для последующей отправки по `SendMessage` рекомендуется найденный `chatId`, а не исходный телефон или username. Положительный `CheckAccount` не является проверкой доступности отправки или доставки. [Документация GREEN-API](https://green-api.com/telegram/docs/api/chat-id/).
- На тарифе Telegram Developer обмен сообщениями ограничен тремя чатами, а число вызовов `CheckAccount` — 100 в месяц; это ограничения инстанса GREEN-API, а не правило формы. [Тарифы GREEN-API](https://green-api.com/telegram/docs/about-tariffs/).
- Наблюдаемое поведение описано здесь; маршрут, форма JSON и коды HTTP зафиксированы в [техническом контракте](contracts/recipient-search.md).
