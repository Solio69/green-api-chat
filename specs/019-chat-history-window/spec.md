# Feature Specification: история выбранного чата и кеш

**Feature Directory**: specs/019-chat-history-window
**Created**: 2026-10-02
**Status**: PassedSynthetic, включая SC-005; ограниченная высота и прокрутка проверены 2026-10-03. Реальный GREEN-API — NotRun.
**User Approval**: Согласована пользователем 2026-10-02 в составе спецификаций 018–025
**Workflow Mode**: Standard
**Implementation Authorization**: Разрешено пользователем 2026-10-02: отображение истории строго по макету, с отдельными компонентами.
**Input**: При каждом новом обращении к чату получать свежие последние десять сообщений. Сохранять прежние сообщения в памяти Query и объединять со свежими без дублей. Нетекстовые элементы обозначать «Неподдерживаемое сообщение». Подгрузку старой истории отложить. Сохраняются Next.js, зашифрованная HttpOnly cookie и макет; отображение отдельно разрешено строго по макету.

## User Scenarios & Testing

### User Story 1 — Читать доступную историю переписки (Priority: P1)

Пользователь выбирает существующий личный чат либо открывает переписку с
подтверждённым найденным получателем и читает доступные сообщения по макету.
При каждом новом обращении выполняется свежий запрос последних десяти.

**Why this priority**: Источник данных проверяется консольным шагом 018;
эта feature делает доступные данные читаемыми в переписке.
**Independent Test**: Выбрать чаты с непустым, коротким, пустым и нетекстовым
ответом тестового API; вернуться после изменения ответа. Проверить новый
count: 10, представление результата и принадлежность выбранному chatId.

**Acceptance Scenarios**:

1. **Given** подключение подтверждено и выбран личный чат, **When** начинается новое обращение, **Then** выполняется свежий GetChatHistory с count: 10 через Next.js; история чужого чата не отображается как его переписка.
2. **Given** успешный ответ содержит текст, **When** он относится к текущему выбору, **Then** сообщения показываются по UI-014: входящие слева, исходящие справа, с текстом и временем.
3. **Given** у чата нет известной истории и API успешно вернул пустой список, **When** загрузка завершилась, **Then** отображается пустая переписка по UI-012, отличимая от ожидания и ошибки.
4. **Given** чтение завершилось ошибкой, **When** пользователь повторяет его, **Then** повтор принадлежит новому обращению; ошибка не создаёт вымышленную пустую историю и не удаляет чат.
5. **Given** текст содержит переносы, длинные слова или HTML-подобные строки, **When** он отображается, **Then** переносы сохраняются, горизонтальный скролл страницы не появляется, HTML не исполняется.
6. **Given** «Написать» передало подтверждённый chatId найденного личного получателя, **When** открывается переписка, **Then** запрашивается его история; пустой ответ допустим, а открытие само по себе не создаёт строку списка.
7. **Given** ответ содержит нетекстовый тип, **When** отображается его место в истории, **Then** показано «Неподдерживаемое сообщение»; вложение не скачивается и не отображается.

### User Story 2 — Сохранять известные сообщения и принадлежность ответов (Priority: P1)

Возврат к чату получает свежие десять, сохраняя известные сообщения в Query.
История и будущее событие не должны стирать либо дублировать друг друга.
Разные чаты и подключения остаются изолированными.

**Why this priority**: Пользователь выбрал сохранение в памяти; подмена истории
и исчезновение уже обработанного сообщения нарушают чтение.
**Independent Test**: Управлять ответами A → B → A, изменить последние десять
между обращениями, завершить подключение до ответа. После интеграции получения
передать новое текстовое событие до завершения запроса истории.

**Acceptance Scenarios**:

1. **Given** запрос A выполняется, **When** выбран B, **Then** поздний ответ A не меняет текущую переписку B.
2. **Given** выбран A, затем B, затем A, **When** поздно приходит ответ первого A, **Then** он не объявляется свежим результатом второго A.
3. **Given** подключение завершено или заменено, **When** приходит его поздний ответ, **Then** прежние данные не отображаются и не попадают в новое подключение.
4. **Given** в Query есть сообщения чата, **When** при возврате приходит свежий count: 10, **Then** прежние сообщения сохраняются, новые добавляются без дублей; отсутствие сообщения в свежем окне само по себе его не удаляет.
5. **Given** отдельная feature получения уже обработала новое текстовое сообщение, **When** завершается пересекающийся запрос истории, **Then** новое сообщение остаётся один раз и не исчезает из-за замены снимком запроса.
6. **Given** в Query есть известные сообщения, **When** новое чтение вернуло пустой ответ либо ошибку, **Then** они не уничтожаются и не выдаются за свежий успешный ответ. Пустое окно не означает пустую накопленную переписку.

### Edge Cases

- count: 10 относится к сообщениям API, включая нетекстовые, а не к десяти текстовым пузырям или пределу всего кеша. Накопленная история и будущие события могут дать больше десяти видимых элементов.
- Сохранение старого и свежие десять не доказывают заполнение промежутка за время отсутствия. Короткий ответ не доказывает полноту истории Telegram.
- Одинаковые время и текст разных сообщений не делают их дублями; порядок ответа не объявляется гарантией сортировки.
- Исходящие сообщения могут быть отправлены вне приложения. Отсутствующий статус не становится доставкой/прочтением; синхронизация редактирования и удаления отложена за рамки минимума.
- Сеть, ограничения GREEN-API, неверный ответ, отказ сессии и смена подключения различаются по существующим контрактам. Интервалы и новые повторы здесь не выбираются.
- Query теряется при перезагрузке. Сама схема ReceiveNotification/SSE не гарантирует заполнение пропусков; восстановление принадлежит отдельной feature получения.

### Verification Approach

Свежая загрузка, объединение и принадлежность сообщений и серверный контракт
проходят TDD после отдельного разрешения: подтверждённый Red → Green → Refactor.
Plan задаёт уровни и команды с существующими инструментами.
В браузере отдельно проверяются макет, текст вместо HTML, отсутствие
горизонтального скролла, состояния и неподдерживаемые сообщения.
Реальные реквизиты и переписка не сохраняются в фикстуры и отчёты.
Синтетические проверки, включая совместную интеграцию SC-005, выполнены; фактические Red/Green, итоговые команды и ограничения описаны в [verification.md](verification.md). Реальные provider-сценарии не выполнялись.

## Requirements

### Functional Requirements

- **FR-001**: История существующего личного чата либо подтверждённого найденного получателя получается по выбранному chatId через Next.js/GetChatHistory и текущую зашифрованную HttpOnly cookie; токен недоступен клиентскому JavaScript.
- **FR-002**: Каждое новое обращение, включая возврат, получает свежий count: 10. Прежние сообщения сохраняются в памяти текущего подключения и объединяются с новыми без дублей.
- **FR-003**: Ожидание, пустой успешный ответ, непустой ответ и ошибка различимы. Пустая переписка требует отсутствия известных сообщений и успешного пустого ответа; ошибка не считается пустым успехом.
- **FR-004**: Текст показывается по UI-012/UI-014/UI-016 с направлением и временем, безопасно и без редизайна списка/поиска. Число сообщений не увеличивает высоту окна: история прокручивается внутри него, шапка и форма остаются на месте, при открытии видны последние сообщения.
- **FR-005**: Ответ предыдущего выбора, обращения или подключения не подменяет текущую переписку; изоляция Query сохраняется.
- **FR-006**: Запросы истории используют count: 10 без расширения окна и подгрузки по прокрутке. Это не ограничивает число накопленных сообщений и событий.
- **FR-007**: История, новое событие и принятая отправка объединяются по безопасной области подключения connectionScope, chatId и idMessage, а не по тексту или времени. Одно сообщение отображается один раз. При отсутствии idMessage приложение не угадывает сообщение.
- **FR-008**: После отдельной интеграции получения ответ истории не удаляет уже обработанное новое текстовое сообщение; совместные сценарии сохраняют изоляцию и отсутствие дублей.
- **FR-009**: Нетекстовый элемент обозначается «Неподдерживаемое сообщение» без скачивания/отображения вложения. Отсутствие текста не считается пустым ответом.
- **FR-010**: Сообщения и статусы не выдумываются. Поздняя история не понижает уже подтверждённые delivered/read устаревшим статусом; ранний статус без сообщения не создаёт пузырь. UI последующих статусов и статусные события относятся к отдельной feature.
- **FR-011**: История хранится только в памяти Query, без своей БД, localStorage или IndexedDB; завершение подключения очищает его данные.
- **FR-012**: Отображение подключается к согласованному макету; текущий UI другого агента сейчас не меняется. Новое оформление не добавляется под видом интеграции.

### Scope Boundaries

- В объёме: свежие последние десять, сохранение и объединение известных сообщений, состояния, отображение по макету, изоляция и совместимость с будущими событиями.
- За пределами: подгрузка старой истории, count: 20/30 и далее, cursor/offset, автоматическое заполнение всех промежутков, отправка, очередь/SSE/ACK, настройки инстанса, своя БД, редизайн, синхронизация редактирования/удаления, вложения и публикация.
- Пользователь отложил подгрузку; её пределы, завершение и сохранение позиции не блокируют этот шаг.
- «Написать», выбор строки, мобильный возврат и закрытие задаёт [025](../025-conversation-selection/spec.md). История принимает выбранный chatId. 025 реализована и обеспечивает открытие найденного получателя; номер не задаёт порядок реализации.
- Отдельный результат 018 — консоль, этого шага — читаемая история. Получение и отправка не объединяются с ним в один проход реализации.

### Data Effects & User Decision

- **Changed data**: История в памяти Query и выбранная переписка; сообщения Telegram, настройки и реквизиты сессии не меняются чтением.
- **Preview**: Чат выбирается действием интерфейса; отдельного подтверждения чтения не требуется.
- **Confirmation**: Спецификация согласована 2026-10-02; сохранение/объединение, неподдерживаемое обозначение и перенос подгрузки подтверждены. Разрешение кода остаётся отдельным решением.
- **Cancellation**: Прежний результат не публикуется как текущий; завершение подключения очищает данные без восстановления поздним ответом.
- **Idempotency and duplicates**: Чтение не создаёт сообщений; пересечения используют общий контракт, время и текст сами по себе не задают идентичность.
- **Failure result**: Ошибка конкретного обращения не уничтожает известные сообщения и не выдаёт их за свежий успешный ответ.

### Key Entities

- **Подключение**: безопасная область cookie-сессии и её Query-данных.
- **Выбор**: chatId и конкретное обращение; закрытие не удаляет переписку Telegram.
- **Свежий ответ**: последние сообщения count: 10, включая пустой или короткий список.
- **Известная история**: сохранённые в памяти данные обращений и будущих событий, потенциально больше одного ответа; полнота и непрерывность не обещаются.

## Success Criteria

- **SC-001**: Выбор, возврат и открытие найденного подтверждённого chatId дают свежий count: 10 для правильного чата без секретов в клиентском ответе. Покрывает FR-001–FR-002, FR-006, FR-011.
- **SC-002**: Пустой, короткий, непустой, нетекстовый ответ и ошибка различимы; текст соответствует направлению/времени/UI-012/UI-014 без исполнения HTML, вложения не скачиваются. Покрывает FR-003–FR-004, FR-009–FR-010, FR-012.
- **SC-003**: Возврат добавляет неизвестные сообщения и сохраняет прежние, отсутствующие в fresh10; пересечения одной connectionScope/chatId/idMessage не дублируются. Разные сообщения с одинаковым текстом сохраняются раздельно. Пустой ответ или ошибка не уничтожают накопленное. Покрывает FR-002–FR-003, FR-007, FR-011.
- **SC-004**: A → B → A, выход и смена подключения не показывают чужой/устаревший ответ и не переносят данные в новое подключение. Покрывает FR-005, FR-011.
- **SC-005**: После отдельной интеграции повторное событие и пересекающийся ответ истории оставляют одно новое сообщение, без стирания снимком; устаревшая история не понижает подтверждённый delivered/read, а ранний статус не создаёт вымышленный пузырь. Покрывает FR-007–FR-008, FR-010; требует feature получения и отображения статусов.
- **SC-006**: Diff разрешённой реализации не содержит расширения count, подгрузки, своей БД, реализации отправки/очереди/SSE, редизайна и вымышленных статусов. Покрывает FR-006, FR-010–FR-012 и Scope Boundaries.

## Assumptions and Dependencies

- Готовы 014/015, cookie-сессия и Query. [018](../018-chat-history-console/spec.md) задаёт консольный шаг; [025](../025-conversation-selection/spec.md) — выбор/открытие и переходы по UI-011/UI-013/UI-023.
- Пользователь выбрал сохранение и объединение известных сообщений со свежими десятью, нейтральное обозначение нетекстовых элементов и перенос подгрузки на будущее.
- [Макет](../../docs/chat-ui-spec.md), особенно UI-012/UI-014/UI-016, задаёт отображение; подготовка документа не разрешает изменять UI.
- [GetChatHistory](https://green-api.com/telegram/docs/api/journals/GetChatHistory/) проверен 2026-10-02: chatId/count, последние десять и смешанные типы; offset/cursor и обещание полной истории не документированы.
- Получение отдельно согласовано через ReceiveNotification на одном постоянном Node-процессе и SSE браузеру; требования Technology HTTP API сохраняются.
- Маршруты, DTO, Query-параметры и модули определены в plan/contracts после согласования; новые продуктовые лимиты здесь не вводятся.

## Shared Messaging Contract

Общий контракт сверен координатором со спецификациями отправки и получения:
[комплект сообщений](../../docs/messaging-specs.md). Это документальная сверка,
spec согласована пользователем 2026-10-02; сверка не является разрешением на код.

- Клиентские публикация и кеш изолируются по connectionScope/chatId/idMessage. Читатель очереди GREEN-API принадлежит инстансу; его владение не определяется только клиентской областью кеша.
- История, новое текстовое событие и принятая отправка объединяются по этой идентичности. Поздняя история не стирает новое сообщение и не понижает подтверждённые delivered/read устаревшими данными.
- При отсутствии идентификатора нельзя угадывать сообщение. failed/noAccount без idMessage относятся к общей ошибке чата/подключения, а не к произвольному пузырю.
- Статус до сообщения сохраняется только как частичный факт в памяти по идентичности; он не создаёт пузырь без сообщения. Пузырь локальной отправки появляется после успешного HTTP-ответа с idMessage, по отдельной feature отправки.
- ACK, мультивкладки и восстановление SSE принадлежат получению; статусные события и галочки — соответствующей отдельной feature. Редактирование и удаление в этот минимум не добавляются.
