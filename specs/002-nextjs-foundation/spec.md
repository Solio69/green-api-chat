## User Scenarios & Testing

### User Story 1 — запустить интерфейс и проверить сервер (Priority: P1)

Как разработчик, я хочу запустить приложение одной командой из корня проекта
и независимо проверить страницу и сервер, чтобы иметь рабочую основу следующих
возможностей без реквизитов GREEN-API.

**Why this priority**: Последующие возможности требуют работоспособного
React-интерфейса и собственной серверной части.

**Independent Test**: После установки зависимостей пользователем запустить режим
разработки, открыть / и выполнить GET /api/health. Проверить страницу, HTTP-статус
и JSON-ответ; реквизиты провайдера не задавать.

**Acceptance Scenarios**:
1. **Given** зависимости установлены и порт свободен, **When** разработчик запускает
   приложение по инструкции, **Then** доступны главная страница и серверное API.
2. **Given** приложение запущено, **When** посетитель открывает /, **Then** видит
   заголовок GREEN-API Chat и краткое пояснение, что это основа будущего приложения;
   страница не имитирует готовый чат или подключение к Telegram.
3. **Given** приложение запущено без реквизитов GREEN-API, **When** выполняется
   GET /api/health, **Then** сервер обрабатывает запрос и возвращает HTTP 200,
   Content-Type application/json и тело {"status":"ok"}.
4. **Given** / и /api/health уже открывались, **When** их запрашивают повторно,
   **Then** результат сохраняет тот же смысл и пользовательские данные не создаются.

### User Story 2 — изменять основу с понятными проверками (Priority: P1)

Как разработчик, я хочу писать типизированные компоненты и привычный SCSS
и отдельно запускать проверки, чтобы обнаруживать ошибки до коммита.

**Why this priority**: Проверяемые правила нужны до появления прикладного кода.

**Independent Test**: Проверить применение модульного SCSS на стартовой странице
и выполнить отдельные команды проверки типов, линтера и форматирования.

**Acceptance Scenarios**:
1. **Given** стартовая страница, **When** просматриваются её компонент и стили,
   **Then** используются SCSS Modules и БЭМ-имена; элементы и имеющиеся модификаторы
   записаны через &, а локальные стили импортируются через объект модуля.
   Цвета и общие значения подключены из SCSS-констант; повторяющиеся группы
   свойств оформлены миксинами без изменения внешнего вида страницы.
2. **Given** реализация соответствует правилам проекта, **When** запускаются
   проверки типов, линтера и форматирования, **Then** каждая завершается успешно.
3. **Given** в проверяемом файле есть нарушение соответствующего правила,
   **When** запускается проверка без автоматического исправления, **Then** она
   завершается ненулевым кодом и позволяет определить причину ошибки.

### User Story 3 — воспроизвести production-запуск по README (Priority: P1)

Как проверяющий, я хочу получить проект из репозитория, установить зависимости
и запустить его по README, чтобы оценить результат без устных инструкций.

**Why this priority**: Воспроизводимость нужна для проверки задания и раннего деплоя.

**Independent Test**: По README выполнить проверки, собрать приложение
и запустить production-режим. Повторно проверить / и /api/health.

**Acceptance Scenarios**:
1. **Given** окружение соответствует README и зависимости установлены,
   **When** запускается production-сборка, **Then** сборка завершается успешно
   без реквизитов GREEN-API и обращений к его API.
2. **Given** сборка готова, **When** разработчик запускает production-режим,
   **Then** / и /api/health выполняют те же требования, что и в режиме разработки.
3. **Given** репозиторий содержит приложение и локальный Spec Kit,
   **When** проверяющий читает README, **Then** понимает назначение проекта,
   текущие возможности, требования к окружению, команды и участие ИИ в разработке.

### Verification Approach

Для готовой основы используются реальные HTTP-запросы в dev/production,
браузерная проверка страницы, typecheck, lint, format:check и build.
Конфигурация инструментов проверяется также отрицательными примерами;
стили — ревью исходников, компиляцией Sass и просмотром страницы.
HTTP-коды, имена заголовков и повторно используемые значения задаются общими
константами; статусы JSON-ответов API хранятся в общем модуле отдельно от HTTP-кодов.
В обработчиках используемые значения деструктурируются на уровне модуля;
совпадающие ключи получают понятные имена.
При их извлечении контракт подтверждается до правки и после неё;
искусственный Red для чистого рефакторинга не требуется.
Для новой и изменяемой бизнес-логики и серверных контрактов обязателен TDD
с постоянными тестами согласно правилам проекта.

### Edge Cases

- Реквизиты GREEN-API отсутствуют: это не препятствует запуску и сборке основы.
- Сервер не запущен: ответ /api/health недоступен; статический ответ не подменяет
  проверку доступности запущенного серверного обработчика.
- GET /api/health повторяется: метод не создаёт сессию, не отправляет сообщения,
  не читает очередь уведомлений и не меняет состояние внешних сервисов.
- Зависимости не установлены, версия среды не поддерживается или порт занят:
  инструкции помогают проверить причину и исправить окружение; собственный
  установщик или обработчик системных ошибок в этой задаче не создаётся.
- В репозитории уже есть правила и Spec Kit: подготовка приложения сохраняет их.
- Нарушены типы, правила линтера или форматирования: соответствующая команда
  сообщает об ошибке; успешная сборка не заменяет эти отдельные проверки.

## Requirements

### Functional Requirements

- **FR-001**: Приложение на Next.js, React и TypeScript содержит интерфейс
  и собственный HTTP-обработчик в одном существующем проекте.
- **FR-002**: Главная страница / показывает название GREEN-API Chat и краткое
  пояснение о подготовленной основе; имеет один основной заголовок и читаемое
  содержимое без элементов, обещающих ещё не реализованные действия.
- **FR-003**: GET /api/health обрабатывается сервером при запросе и возвращает
  HTTP 200, JSON Content-Type и только {"status":"ok"}. Клиенту и промежуточным
  кешам не предлагается сохранять ответ для повторного использования.
- **FR-004**: Главная страница, health-проверка, локальный запуск и сборка
  не требуют реквизитов, БД или обращения к GREEN-API. Health-проверка означает
  только способность серверного обработчика ответить на текущий запрос.
- **FR-005**: Стили компонентов используют SCSS Modules, БЭМ и & для элементов
  и модификаторов. Цвета и общие значения оформления хранятся в именованных
  SCSS-переменных; повторяющиеся группы свойств переиспользуются через миксины.
  Правило применяется ко всем стилям проекта. Глобальные стили ограничены
  общей базой страницы. Неиспользуемые классы, миксины и искусственные состояния
  ради примера не добавляются.
- **FR-006**: TypeScript работает в строгом режиме. Проверка типов, линтер
  и проверка форматирования доступны отдельными командами из корня проекта;
  ошибки отражаются ненулевым кодом, режим проверки не исправляет файлы.
- **FR-007**: Доступны документированные команды режима разработки,
  production-сборки и запуска собранного приложения. Обе среды выполняют
  FR-002–FR-004.
- **FR-008**: Состав зависимостей и файл фиксации их версий позволяют повторить
  установку. Версии среды и команды задаются согласованным техническим планом;
  скачивание и установку выполняет пользователь.
- **FR-009**: В README описаны назначение, доступные возможности, требования
  к окружению, установка, запуск, проверки, смысл /api/health, типовые проблемы
  окружения и ссылки на правила/обзор. Участие ИИ обозначено кратко и честно.
- **FR-010**: Локальные секреты, установленные зависимости и результаты сборки
  исключены из Git. В исходниках и документации нет реальных реквизитов
  и персональных данных из ручных проверок.
- **FR-011**: Существующие правила, Spec Kit, тесты процесса и документация
  сохраняются. Команды проверки приложения имеют явно описанный охват и
  не подменяют отдельные проверки PowerShell-комплекта.
- **FR-012**: Результат сопровождается фактическими проверками, ревью соответствия
  спецификации и предкоммитным ревью. Непроведённые проверки отмечаются отдельно;
  пользователь получает необходимые дальнейшие команды и название коммита.

### Scope Boundaries

- В объёме: основа приложения, простая стартовая страница, /api/health,
  согласованные стили, проверки, локальная production-сборка и README.
- За пределами: публикация на Vercel и CI; интерфейс чата по образцу MAX;
  подключение инстанса и сессии; формы поиска и отправки; получение уведомлений;
  история, БД, мобильная компоновка будущего чата и дополнительные UI-библиотеки.
- Планирование последующих возможностей не требует реализации их заглушек
  или выбора хранилища в этой задаче.

### Data Effects & User Decision

- **Changed data**: Будут созданы файлы приложения и конфигурации; обновлены
  документация и правила игнорирования. Данные аккаунтов и БД не меняются.
- **Preview**: До реализации пользователь получает эту спецификацию,
  затем технический план, перечень шагов и отчёт об их согласованности.
- **Confirmation**: Согласование спецификации разрешает техническую подготовку;
  код пишется после отдельного разрешения на реализацию. Установку выполняет
  пользователь по предоставленным командам.
- **Cancellation**: До реализации остаются документы. Прерывание последующей
  работы не запускает автоматический откат файлов или Git-операции.
- **Idempotency and duplicates**: Повторные GET не изменяют данные; подготовка
  приложения не перезаписывает существующие правила шаблонами генератора.
- **Failure result**: Ошибка проверки фиксируется с причиной и дальнейшим шагом.
  Частично выполненная работа или неподтверждённый запуск не отмечаются как готовые.

### Key Entities

Прикладных сущностей и хранилища нет. Единственный контракт данных —
статический по форме ответ health {"status":"ok"}, формируемый сервером
на текущий запрос; он не содержит информации об аккаунте или окружении.

## Success Criteria

- **SC-001**: В режиме разработки / открывается с согласованным содержимым,
  а GET /api/health соответствует FR-003. Проверка не требует реквизитов.
- **SC-002**: Те же проверки страницы и API проходят после успешной
  production-сборки и запуска собранного приложения.
- **SC-003**: Команды проверки типов, линтера и форматирования завершаются
  без ошибок на итоговом состоянии; соответствие SCSS Modules/БЭМ проверено ревью.
- **SC-004**: README содержит все действия от подготовки окружения до проверок
  и production-запуска; зависимости воспроизводимы по файлу фиксации версий.
- **SC-005**: Итоговое ревью подтверждает сохранность Spec Kit и правил,
  отсутствие секретов в изменениях и исключение локальных артефактов из Git;
  отчёт различает выполненные и непроведённые проверки.
