# Контракт HTTP: GET /api/health

**Связанные требования**: FR-003, FR-004, FR-007.
**Статус**: реализован; контракт проверен в dev и production.

| Параметр         | Контракт                                               |
| ---------------- | ------------------------------------------------------ |
| Путь             | /api/health                                            |
| Основной метод   | GET                                                    |
| Авторизация      | Не требуется                                           |
| Запрос           | Без тела и обязательных параметров                     |
| Успешный статус  | 200                                                    |
| Content-Type     | application/json; допускается charset=utf-8            |
| Cache-Control    | no-store                                               |
| Тело             | JSON-объект с единственным полем status и значением ok |
| Побочные эффекты | Отсутствуют                                            |

Тело: {"status":"ok"}. Пробельное оформление JSON не является частью контракта.

Обработчик работает в Node.js runtime и отвечает при текущем запросе.
await connection() из next/server предшествует Response.json; статический
экспорт, предварительно сохранённый ответ и внешние запросы не используются.
Страница / не обращается к health автоматически.

HTTP-код задаётся явно через HTTP_STATUS.OK из src/lib/http/constants.ts.
В этом же модуле находятся HTTP_HEADERS.CACHE_CONTROL и CACHE_CONTROL.NO_STORE.
Статус тела ответа API_RESPONSE_STATUS.OK определяется в общем модуле
src/lib/api/constants.ts и доступен другим обработчикам API.
Он обозначает успешный результат в JSON и хранится отдельно от HTTP-кодов.
Константы объявляются через as const; содержат только используемые значения.
Перед GET на уровне модуля они деструктурируются в HTTP_OK, RESPONSE_OK,
CACHE_CONTROL_HEADER и NO_STORE. Ответ использует эти имена.
Content-Type формирует Response.json, вручную он не дублируется.

При извлечении констант контракт проверяется реальными запросами до правки
и после неё: два GET и POST. Итоговая проверка повторяется в production.
Это рефакторинг с сохранением поведения, искусственный Red не требуется.

Ответ не включает версию среды, время работы, реквизиты или диагностику провайдера.
Он не гарантирует работоспособность GREEN-API и будущих зависимостей.
При остановленном сервере ожидается ошибка соединения; приложение не может
сформировать собственный JSON-ответ из отсутствующего процесса.

Экспортируется GET. HEAD и OPTIONS остаются стандартным поведением Next.js;
не реализованные POST/PUT/PATCH/DELETE возвращают 405 средствами фреймворка.
Отдельный формат ошибки для них не вводится.

Приёмка в dev и production: два последовательных GET дают 200, JSON по схеме
и Cache-Control: no-store. POST даёт 405. В отчёте сборки /api/health определяется
как динамический маршрут; при невозможности подтвердить это выполнение на
каждый запрос проверяется временной серверной диагностикой с удалением до ревью.
Серверная функция не содержит обращений к БД, аккаунтам или очереди уведомлений.
