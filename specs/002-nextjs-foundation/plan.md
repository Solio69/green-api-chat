## Summary

Одно приложение Next.js App Router в существующей папке. Статическая по содержанию
страница / служит точкой входа, Route Handler /api/health проверяет сервер.
SCSS Modules + БЭМ, TypeScript strict, ESLint и Prettier обеспечивают
согласованный способ разработки. Локальный production-запуск проверяется
до отдельной задачи размещения на Vercel.

## Considered Options

| Вариант | Преимущества | Ограничения и риски | Выбор и причина |
| --- | --- | --- | --- |
| Ручная минимальная основа | Контроль файлов и зависимостей, сохранность правил | Нужно проверить конфигурации | Выбрана; существующий проект содержит Spec Kit |
| Генератор в отдельном каталоге с переносом | Типовая структура | Дополнительный перенос и участие пользователя в запуске генератора | Для этой небольшой основы не требуется |
| Route Handler в Next.js | Общий запуск, небольшой объём | Нужно понимать серверную границу Next.js | Выбран для health |
| Отдельный Express-сервер | Независимый жизненный цикл | Дополнительные запуск и деплой | Задача такой независимости не требует |
| ESLint + Prettier | Пресеты Next и поддержка SCSS | Два инструмента с отдельными командами | Выбраны; конфликтующие правила форматирования отключаются |
| Biome | Единый инструмент | Понадобится отдельная оценка покрытия выбранного стека | Не включается |

### Страница и стили

layout.tsx задаёт html lang=ru, body, metadata с названием GREEN-API Chat
и импортирует globals.scss. page.tsx содержит main, один h1 GREEN-API Chat
и пояснение: «Основа приложения готова. Подключение к Telegram и переписка
появятся на следующих этапах.» Это описание текущей стадии разработки.

page.module.scss: блок foundation, элементы через &__title и &__description.
Классы берутся из импортированного объекта styles. Искусственный модификатор
не создаётся. Общая база: box-sizing, сброс отступов body, цвета и системный шрифт.
Все цвета и общие значения оформления находятся в src/styles/_tokens.scss.
Повторяющаяся типографика заголовка и описания подключается через миксин typography
из src/styles/_mixins.scss. Используются @use с пространствами имён; partial-файлы
не содержат самостоятельных селекторов. Значения оформления при рефакторинге сохраняются.
Страница читаема при обычном изменении ширины, без фиксированной ширины,
обрезающей текст; мобильная компоновка будущего чата здесь не проектируется.
Удалённые шрифты, картинки, дополнительные компоненты и кнопки не нужны.

### Сервер

GET в src/app/api/health/route.ts: Node runtime, await connection(),
Response.json с единственным полем status: ok и Cache-Control: no-store.
HTTP_STATUS.OK, HTTP_HEADERS.CACHE_CONTROL и CACHE_CONTROL.NO_STORE
переиспользуются из src/lib/http/constants.ts. API_RESPONSE_STATUS.OK хранится
в общем src/lib/api/constants.ts отдельно от HTTP-кодов. Все объекты — as const.
Перед GET константы деструктурируются на уровне модуля: HTTP_OK, RESPONSE_OK,
CACHE_CONTROL_HEADER и NO_STORE. Ответ использует эти имена.
Набор ограничен используемыми значениями, Content-Type формирует Response.json.
Handler не использует секреты, токены, сессию и сетевые запросы.
Health не вызывается страницей и не превращается в постоянный опрос.
Источник назначения функций — research, точный ответ — контракт.

### Конфигурация и воспроизводимость

Новые файлы добавляются вручную; генератор не вызывается.
package.json содержит точные версии из research, команды из tooling и private: true.
next.config.ts содержит типизированную конфигурацию с agentRules: false:
Next.js не дописывает автоматически правила в AGENTS.md/CLAUDE.md.
Статический экспорт и экспериментальные возможности не включены.
package-lock.json создаётся только установкой пользователя, вручную не сочиняется.
После появления lock-файла повторная установка выполняется через npm ci.
Область форматирования не затрагивает существующие документы и PowerShell.
.gitattributes закрепляет LF для новых файлов приложения: локальный core.autocrlf=true
не должен вызывать повторные ошибки форматтера после checkout. next.config.ts
явно включается в typecheck вместе с исходниками.
Реализация приложения сохраняет действующие правила и тесты процесса.
AGENTS.md закрепляет согласованные правила стилей, общих API-констант,
их деструктуризации и обязательный TDD;
изменения процесса требуют отдельного согласования пользователя.

## Verification

Для извлечения констант HTTP и JSON-ответов сначала подтвердить действующий контракт
реальными HTTP-запросами к dev, затем выполнить рефакторинг, повторить контракт,
typecheck, lint, format:check и production build/HTTP. Сохранить результаты
в verification.md. Поведение API не меняется, искусственный Red не нужен.
Конфигурация и стили проверяются способами ниже; новые изменения поведения
выполняются по обязательному TDD из действующих правил проекта.

- Установка: наличие lock-файла, npm ls --depth=0 без missing/invalid;
  установка по lock-файлу пользователем для подтверждения воспроизводимости.
- Качество: typecheck, lint, format:check; отрицательные примеры дают ненулевой
  exit code, удалены; итоговые проверки проходят на чистом от примеров состоянии.
- HTTP: главная страница 200; health — два GET с требуемыми телом/заголовками,
  POST 405. Повторить в dev и production.
- Серверное исполнение health: динамический маршрут в отчёте сборки
  либо временная диагностика выполнения с удалением до ревью.
- Браузер: заголовок, пояснение, применённые стили, отсутствие ошибок страницы,
  читаемость и отсутствие горизонтального переполнения при уменьшении ширины.
- Сохранность: SHA-256 всех защищённых существующих файлов;
  git diff --check, просмотр отслеживаемых и новых файлов, git check-ignore
  для зависимостей/секретов и отрицательные проверки для lock-файла/правил.
- Не использовать Git для отката временных примеров или остановки проверки.
- Failed — выполненная проверка обнаружила дефект; Blocked — отсутствует
  необходимое окружение/установка/доступ; NotRun — ещё не выполнялась.
  Неподтверждённая браузерная приёмка не заменяется одним HTTP 200.
