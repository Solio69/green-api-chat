## User Scenarios & Testing

### User Story 1 — CI для типов линтеров и тестов Vitest (Priority: P1)

Изменения репозитория автоматически проверяются в чистом окружении, а разработчик видит конкретную причину ошибки.

**Why this priority**: Это обязательная часть результата этапа R03; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Проверить структуру workflow и эквивалентные локальные команды. После разрешённой публикации проверить положительный и отрицательный CI-результат. Названия веток, актуальные версии actions и лимиты выбираются в технической подготовке по данным репозитория.

**Acceptance Scenarios**:

1. **Given** создан pull request с корректными изменениями, **When** workflow выполняется с чистым кешем, **Then** все предусмотренные проверки запускаются и дают успешный итог.
2. **Given** в тесте или исходнике есть установленная проверкой ошибка, **When** workflow исполняется, **Then** соответствующий шаг и общий результат неуспешны, причина доступна в отчёте.
3. **Given** workflow подготовлен локально, но ещё не опубликован, **When** обновлён статус задачи, **Then** локальная готовность отмечена отдельно, удалённая приёмка остаётся NotRun.

### Edge Cases

- Запуск без repository secrets и из pull request с ограниченными разрешениями.
- Отсутствие кеша зависимостей.
- Несколько последовательных push и незавершённый прежний запуск.
- Недоступность GitHub Actions или лимита аккаунта учитывается как Blocked, без подключения платных услуг.

### Verification Approach

Проверить структуру workflow и эквивалентные локальные команды. После разрешённой публикации проверить положительный и отрицательный CI-результат. Названия веток, актуальные версии actions и лимиты выбираются в технической подготовке по данным репозитория.

Проверяется действующая конфигурация: успешный штатный сценарий и контролируемый нарушающий пример должны дать ожидаемый результат. Ошибка установки или импорта не считается подтверждением TDD. Если выяснится, что требуется изменить бизнес-логику, такая часть выполняется по согласованному контракту через Red → Green → Refactor.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации сейчас имеют статус **NotRun**: этот документ задаёт объём, а не подтверждает выполненный рефакторинг.

## Requirements

### Functional Requirements

- **FR-001**: Подготовить workflow GitHub Actions для pull request и push в основную ветку, а также ручного запуска; точное имя основной ветки проверить перед реализацией.
- **FR-002**: Использовать совместимые с engines Node 24 и npm 11; устанавливать зафиксированные зависимости через npm ci в чистом окружении.
- **FR-003**: Запускать полную проверку типов, ESLint, Stylelint, Prettier, согласованные наборы Vitest и остающийся Playwright integration-набор до его переноса в 051; падение любой проверки делает результат неуспешным.
- **FR-004**: Работать на фиктивных данных без реального GREEN-API, SESSION_PASSWORD пользователя и секретов, недоступных в pull request.
- **FR-005**: Назначить минимально необходимые разрешения workflow, ограничение времени и отмену устаревших запусков одной ветки; отчёты должны помогать диагностировать сбой.
- **FR-006**: Считать кеш зависимостей только ускорением: его отсутствие не меняет результат и не заменяет npm ci.
- **FR-007**: Разделить статусы подготовки workflow и подтверждения работы на GitHub. Не объявлять CI работающим до фактического удалённого запуска после публикации по политике Git.

### Scope Boundaries

- **В объёме**: Workflow быстрых проверок, отчёты, инструкция и подтверждение запуска при доступности публикации.
- **За пределами**: Автоматическая публикация приложения, изменение защиты веток, покупка CI-ресурсов и браузерная стадия 034.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: После реализации создаётся конфигурация GitHub Actions. Удалённое выполнение создаёт CI-запуски и отчёты; публикация выполняется по GIT_POLICY.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Workflow, job, проверка, commit запуска, отчёт, итоговый статус.

## Success Criteria

- **SC-001**: Чистый удалённый запуск на выбранном commit проходит все быстрые проверки (FR-001–FR-004, FR-006).
- **SC-002**: Контролируемое нарушение обнаруживается workflow; ограничения и диагностические отчёты действуют (FR-003, FR-005).
- **SC-003**: Есть ссылка на фактический запуск либо явно указанное препятствие удалённой приёмке (FR-007).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Подготовка спецификаций не включает commit, push или отправку реальных сообщений.
