# Feature Specification: Серверный получатель уведомлений Telegram

**Feature Directory**: specs/022-notification-receiver
**Created**: 2026-10-02
**Status**: Approved — согласована; реализация разрешена
**User Approval**: Approved 2026-10-02 — пользователь согласовал все 018–025
**Workflow Mode**: Standard
**Implementation Authorization**: CodeAuthorized
**Input**: Согласованная цепочка GREEN-API → ReceiveNotification на единственном Node-сервере Next.js → SSE → браузер; подтверждение через DeleteNotification.

## User Scenarios & Testing

### User Story 1 — Получать сообщения независимо от выбранного чата (Priority: P1)

Пользователь подключает свой инстанс и получает уведомления, не создавая отдельный читатель при каждом переключении чата. Этот шаг даёт серверный получатель и проверяемый транспортный контракт; применение событий браузером относится к 023.

**Why this priority**: Получатель обеспечивает требование 7 задания и служит источником для SSE.
**Independent Test**: Поддельный GREEN-API возвращает уведомление; авторизованный потребитель получает нормализованное событие; журнал поддельного API показывает последовательное получение и удаление только при согласованном условии подтверждения.

**Acceptance Scenarios**:

1. **Given** действующее подключение и одна активная вкладка, **When** очередь возвращает текстовое сообщение чата A, **Then** получатель передаёт событие подписчику текущего подключения независимо от того, выбран A или B.
2. **Given** ReceiveNotification вернул пустой ответ, **When** цикл продолжается, **Then** DeleteNotification не вызывается и пустой ответ не становится ошибкой или сообщением.
3. **Given** одна вкладка уже владеет рабочим чатом инстанса, **When** другая пытается работать с тем же инстансом, **Then** второй читатель не создаётся, второй вкладке возвращается явное ограничение без сведений о владельце первой; она не может отправлять сообщения.
4. **Given** активная вкладка отключилась и других допустимых подписчиков нет, **When** сервер завершает подписку, **Then** дальнейшее receive прекращается, неприменённое уведомление не удаляется; при возвращении авторизованной активной вкладки получение возобновляется из очереди провайдера.

### User Story 2 — Подтверждать обработку без ложной гарантии доставки (Priority: P1)

Пользователь согласовал подтверждение только после обработки браузером и отдельного HTTP ACK серверу. Для сообщения обработка означает применение; для валидного события вне объёма — осознанный пропуск. Запись в поток сама по себе не разрешает DeleteNotification. Подтверждение кеша в памяти не означает постоянного сохранения.

**Independent Test**: Разорвать поток до и после выбранной точки подтверждения; сравнить количество DeleteNotification и состояние повторного получения.

**Acceptance Scenarios**:

1. **Given** уведомление передано, но ACK применения активной вкладкой ещё не получен, **When** возникает обрыв, **Then** сервер не подтверждает его как успешно обработанное.
2. **Given** активная авторизованная вкладка подтвердила применение отдельным HTTP ACK, **When** DeleteNotification завершается успешно, **Then** цикл переходит к следующему уведомлению без создания второго экземпляра сообщения.
3. **Given** ответ DeleteNotification потерян либо содержит result=false, **When** получатель восстанавливается, **Then** он не объявляет успешное удаление на основании одного HTTP 200 и не запускает бесконечный быстрый цикл повторов.
4. **Given** корректное принадлежащее инстансу уведомление с проверенным receiptId имеет тип вне объёма, **When** активная вкладка осознанно пропустила его и подтвердила обработку HTTP ACK, **Then** сервер удаляет это уведомление и очередь не блокируется.
5. **Given** уведомление повреждено или его принадлежность/receiptId нельзя проверить, **When** получатель разбирает ответ, **Then** он приостанавливает обработку с понятной общей ошибкой без сырых персональных данных и не вызывает DeleteNotification как после успеха.

### Edge Cases

- Повтор одного receiptId и повтор сообщения с тем же idMessage; это разные уровни идентичности.
- Получение при истёкшей cookie, выходе, смене подключения и позднем завершении старого запроса.
- Несколько cookie-сессий одного инстанса: connectionScope включает срок сессии и не является идентификатором очереди провайдера.
- Старый и обновлённый токен одного инстанса; нельзя создавать два читателя или доверять подписчику только по совпадению idInstance.
- ReceiveNotification и DeleteNotification возвращают 429, сетевую ошибку или непустой webhookUrl.
- Неподдерживаемое корректное событие осознанно пропускается браузером с ACK; повреждённое не удаляется и приводит к приостановке с общей ошибкой, без превращения в текст и без сохранения сырого payload.
- Остановка Node-процесса теряет оперативную память; уведомления, уже удалённые у провайдера, не обещаются к восстановлению.

### Verification Approach

После отдельного разрешения на реализацию: TDD Red → Green → Refactor для последовательного цикла, контракта получения/подтверждения и изоляции. Интеграционные проверки используют поддельный provider и контролируемое разрывание потребителя; реальные уведомления не удаляются в тестах. Числа таймаутов и задержек определит plan по проверенным ограничениям. Код и тесты реализованы по прямому поручению пользователя; автоматические проверки — **PassedSynthetic**. Настройки реального провайдера агент не изменял.

## Requirements

### Functional Requirements

- **FR-001**: Уведомления получать только сервером через ReceiveNotification и подтверждать через DeleteNotification; webhook Endpoint не используется.
- **FR-002**: Реквизиты извлекать из существующей зашифрованной HttpOnly cookie-сессии; не передавать токен в SSE, URL браузера или клиентский код.
- **FR-003**: Для одного инстанса допускается одна активная вкладка всего рабочего чата и один читатель внутри единственного Node-процесса; второй вкладке возвращать явное ограничение, отправка в ней недоступна. Разные connectionScope одной очереди не разрешают создавать разные читатели. Серверное состояние права работы используется также 020/021/023; вторая вкладка не обходит ограничение прямым SendMessage. Освобождение занятого инстанса, переподключение, связь права с запросами и обновление реквизитов определит plan без обхода авторизации или раскрытия данных другой вкладки.
- **FR-004**: Для читателя выполнять получение последовательно; предыдущий receiptId сохранять до определённого исхода обработки и удаления. Не выбирать конкретное число receiveTimeout без технического плана.
- **FR-005**: Пустой ответ означает отсутствие уведомления; он не требует DeleteNotification.
- **FR-006**: Для DeleteNotification использовать проверенный receiptId фактически полученного уведомления только после отдельного HTTP ACK обработки активной вкладкой: применения поддерживаемого события либо осознанного пропуска валидного события вне объёма. ACK должен соответствовать текущему уведомлению и авторизованному активному подписчику; произвольный receiptId от клиента не является правом удалить событие.
- **FR-007**: Не считать result=false доказательством успешной обработки. Различать возможное ранее выполненное удаление и ошибочный receiptId; поведение неопределённого результата уточняется в plan без гарантии exactly-once.
- **FR-008**: Ошибки чтения и удаления должны иметь различимые наблюдаемые состояния; повторные попытки не должны становиться быстрым бесконечным циклом или превышать ограничения провайдера.
- **FR-009**: Проверять принадлежность события инстансу, нормализовать необходимые поля и не пересылать сырой ответ с instanceData, телефоном или токеном. Известное входящее нетекстовое сообщение — факт сообщения с идентичностью и нейтральным обозначением без вложения; оно отличается от служебного события вне объёма, которое осознанно пропускается. Формат входящего сообщения согласовать с 018/019/023; статусы — с 024. Группы, редактирование, реакции и полноценный live-поток внешних исходящих сообщений не расширяют согласованный объём.
- **FR-010**: Выход, истечение сессии и смена подключения прекращают доставку соответствующему подписчику. Неактивная вкладка не имеет права подтверждать уведомление или прекращать читатель активной вкладки.
- **FR-011**: При отсутствии активной вкладки остановить ReceiveNotification; без ACK не вызывать DeleteNotification. При возвращении допустимой авторизованной вкладки возобновлять очередь провайдера; браузер отдельно обновляет последние 10 сообщений выбранного чата по 023/019. Не создавать постоянный журнал или обещание полного восстановления ранее удалённых событий и старых статусов. Отмена активного запроса и освобождение серверной памяти уточняются в plan.
- **FR-012**: Сначала проверить receiptId, структуру и принадлежность события инстансу. Валидное событие вне объёма передать как нормализованный осознанный пропуск без сырого payload; после обработки активной вкладкой и HTTP ACK удалить его. Повреждённое или непроверяемое событие приостанавливает получатель с общей ошибкой, не получает ACK успешной обработки и не удаляется. Не сохранять реальные данные в диагностике и не создавать бесконечный быстрый цикл повторов; восстановление после исправления причины определит plan.
- **FR-013**: Для работы требуется пустой webhookUrl и включённые необходимые виды уведомлений. Документировать действия пользователя; не вызывать SetSettings и ClearWebhooksQueue.

### Scope Boundaries

- В объёме: серверный цикл одной очереди, авторизация подписчиков, нормализация, последовательное подтверждение, остановка и ошибки.
- За пределами: код UI, история и её пагинация, SendMessage, браузерное объединение кеша, DB/Redis/broker, несколько Node-экземпляров, гарантия восстановления всех событий, изменение настроек аккаунта или публикация.

### Data Effects & User Decision

- **Changed data**: При будущей реализации DeleteNotification удаляет уведомление из очереди GREEN-API, но не само Telegram-сообщение. Сервер хранит только необходимое временное состояние в памяти.
- **Preview**: Пользователь выбрал ACK обработки браузером и ограниченное восстановление без DB; будущая обработка каждого события не требует отдельного диалога подтверждения.
- **Confirmation**: Согласование этой spec и отдельная авторизация кода. Разрешение написать черновик не разрешает удалять реальные уведомления.
- **Cancellation**: Без активной вкладки чтение прекращается. Уведомление без клиентского ACK не считается обработанным и не удаляется; ранее удалённое не обещается к восстановлению.
- **Idempotency and duplicates**: receiptId идентифицирует доставку; connectionScope/chatId/idMessage — сообщение на клиенте. Повтор после неопределённого удаления возможен.
- **Failure result**: Соединение/получатель сообщает отказ без раскрытия реквизитов; состояние переписки не выдаётся за полное после потери оперативной памяти.

### Key Entities

Очередь инстанса; авторизованный подписчик; непрозрачный connectionScope; уведомление с receiptId; нормализованное событие; состояние читателя. Связь очереди и клиентского scope не делает их одним ключом.

## Success Criteria

- **SC-001**: В сценариях одной очереди максимальное число одновременно активных ReceiveNotification равно одному, независимо от переключения чатов и допустимого числа подписчиков (FR-003/004).
- **SC-002**: Пустые ответы и невыполненное условие подтверждения дают ноль DeleteNotification; успешно обработанное уведомление подтверждается своим receiptId (FR-005/006).
- **SC-003**: После прекращения авторизации старый подписчик не получает ни одного нового события; неактивная вкладка не подтверждает его уведомления и не прекращает его получатель (FR-002/003/010).
- **SC-004**: Ошибка чтения, ошибка удаления, result=false и неправильная конфигурация различимы в контрактных проверках; токен и сырой instanceData отсутствуют в клиентском ответе (FR-007/008/009/013).
- **SC-005**: При отсутствии активной вкладки дальнейшие ReceiveNotification и DeleteNotification неприменённого события отсутствуют; при возвращении получение продолжается из очереди (FR-011).
- **SC-006**: Валидное ненужное событие удаляется только после осознанного клиентского пропуска и ACK; повреждённое не удаляется, даёт общую ошибку и приостановку. ACK, одна активная вкладка, остановка и ограниченное восстановление одинаково описаны в 022/023 (FR-006/012).

## Assumptions and Dependencies

- Next.js работает в одном постоянно запущенном Node-процессе. Сессия и Query scope уже существуют в 014; получение не меняет политики GetChats.
- [Общий контракт пласта](../../docs/messaging-specs.md) задаёт различие scope/инстанса, обработку фактов, одну рабочую вкладку и границы восстановления; технические адреса, DTO и lease он не выбирает.
- 023 реализует SSE-потребителя, маршрутизацию и применение события; 024 определяет реальные статусы исходящих сообщений.
- История последних десяти сообщений — отдельный ограниченный снимок, а не журнал потерянных уведомлений.
- Наличие включённых исходящих уведомлений и готовность публичного размещения не проверены.

## Open Questions

**Согласованные ответы 2026-10-02**: Q-REC-01 — отдельный HTTP ACK после обработки в браузере, затем DeleteNotification; Q-REC-03 — одна активная вкладка на инстанс, другим явное ограничение. Детали координации и смены токена — технический план, а не разрешение допускать конкурирующие читатели.

Ограничение Q-REC-03 относится ко всему рабочему чату: вторая вкладка не отправляет сообщения, а не только не получает SSE. Контракт права работы совместно используют 020/021/022/023.

Q-REC-02 — без активной вкладки остановить receive, не удалять событие без ACK; при возвращении возобновить очередь. Q-REC-04 — собственная DB не создаётся, после возврата обновляются последние 10 выбранного чата; полнота более старых сообщений и статусов не гарантируется. Пагинация отложена, 019 сохраняет известные данные в памяти и объединяет свежую десятку.

Q-REC-05 согласован пользователем: ненужные валидные события осознанно пропускать в браузере с HTTP ACK, затем удалять; повреждённые не удалять, приостанавливать обработку и показывать общую ошибку. Открытых продуктовых вопросов по получателю нет. Лимиты, lease, атомарная координация, отмена и очистка остаются техническому плану, без автоматического расширения инфраструктуры.
