# Исследование D05

**Дата:** 2026-10-01. Read-only исследование фактической формы/стилей/валидатора/тестов; продуктовые проверки не запускались.

## Факты

RecipientSearchForm владеет mode/value/hasSubmitted/isSubmitting/result/serverErrorCode и guard requestPending; поле/режимы отключаются при запросе. parseSearchRequest возвращает нормализованный username с @ либо phoneNumber. SubmitButton уже имеет isLoading и индикатор с reduced-motion, общий стиль width 100%. Результат found содержит chatId; сейчас его показывают строкой. Регрессия 009 проверяет поиск, отсутствие лишних запросов, ошибки и доступ. _theme.scss и server modules изменяются другими агентами.

Макет `.mc-search-row` размещает input и «Найти» рядом; `.mc-modes` — две кнопки, `.mc-found` — статус и карточка с «Написать», `.mc-result[data-error]` — мягкая ошибка. Нормативные тексты ошибок остаются из 009; inline-script макета не переносится.

## Подпись результата

Небольшой чистый `format-recipient-label.ts` получает валидированный RecipientQuery и возвращает username либо строковое значение нормализованного номера. Это единственная новая логика данных D05, поэтому тестируется через TDD. Не преобразовывать независимо произвольную строку/не использовать chatId вместо подписи. При успешном ответе добавить label в существующий found-result формы из captured parsedInput текущей отправки; отдельного состояния label нет. Editing/mode switch продолжают очищать весь result.

## Доступность и кнопка

Успешный статус отделён от карточки и её действий; ошибка not-found/сервиса объявляется отдельно. Постоянное ожидание role=status расположить вне disabled fieldset и busy button. Placeholder «Написать» type=button, именованный handler формы с комментарием `D06` и пустым телом, без fake-toast/запроса. По read-only конфигу запрет no-empty-function в проектном eslint явно не задан; окончательный lint текущего конфига обязателен. Не ослаблять правило ради placeholder: если фактический конфиг изменится, сообщить владельцу и выбрать минимальное явно обоснованное локальное исключение без новых действий.

## Первичные источники

- [WAI Button Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/button/): кнопки и aria-pressed; сохраняем текущие два toggle-контрола вместо введения tablist.
- [React: сохранение состояния](https://react.dev/learn/preserving-and-resetting-state): не менять положение/ключ формы ради темы и ширины.
- Локальная 009/spec и текущий parseSearchRequest — источник контрактов ввода; дизайн берётся из согласованного HTML, не из сторонних форм.

Новые `tests/integration/recipient-label.spec.ts` проверяют нормализованный username/номер и неизменность входа, не внутреннее устройство helper. `recipient-search-ui.spec.ts` покрывает композицию, объявление ожидания, карточку, кнопки, theme/focus/overflow. Поведение no-op проверяется отсутствием запроса/навигации, не количеством вызовов пустой функции.

## Уточнения интерфейса — 2026-10-02

В режиме username под вводом всегда видна подсказка «Можно вводить с @ или без него». При переключении phone/username высота формы без результата, ошибки и ожидания остаётся одинаковой при той же ширине окна, теме и масштабе текста. Области подписи поля и подсказки учитывают переносы более длинного текста в каждом режиме. Ошибки и результаты могут естественно расширять форму.

Добавить текст username в константы формы. Обе подсказки разместить в одной области CSS Grid: скрытая подсказка участвует в расчёте естественной высоты, но имеет visibility:hidden и aria-hidden. Видна и доступна для чтения только активная подсказка; aria-describedby указывает на действующее описание. Для подписи применить тот же естественный расчёт: связанный label и скрытый aria-hidden span являются соседями в одной ячейке Grid. Не задавать фиксированную высоту формы и не измерять DOM через JavaScript. Дополнительные зависимости не требуются.
