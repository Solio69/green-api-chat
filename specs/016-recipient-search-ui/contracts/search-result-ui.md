# Контракт карточки и placeholder D05

RecipientSearchResult получает различимый существующий result/error и доступные handlers через пропсы. Собственного fetch/state/store нет. Точные публичные пропсы типизируются по модели; несколько аргументов собственной функции объединяются в именованный объект по CODING_RULES.

| Состояние                   | UI                                                                        |
| --------------------------- | ------------------------------------------------------------------------- |
| Нет результата              | Карточки нет                                                              |
| Успех                       | Отдельный «Пользователь найден» как статус; карточка с label и «Написать» |
| Телефон not-found           | Прежнее пояснение на мягком фоне ошибки, «Найти по @username»             |
| Username not-found          | Прежний отрицательный текст без карточки успеха                           |
| Сбой/лимит/невалидный ответ | Безопасная существующая ошибка, не ложный not-found                       |

chatId остаётся в данных результата, но не является основной пользовательской подписью. Username из нормализованного запроса показывается с одним @; телефон из нормализованного phoneNumber — строкой. Не загружать имя/фото/статус получателя через новый API.

«Написать»: native button type=button, доступное имя, keyboard focus, цель 44×44 px. Владелец формы объявляет именованный пустой обработчик с комментарием о D06 и передаёт его по имени; обработчик не вызывает запрос/submit/навигацию/изменение списка/сообщений. Никаких toast или индикатора, имитирующих выполнение. Это намеренно промежуточный UI по прямому решению пользователя; D06 реализует функцию отдельно.

Длинная подпись переносится; кнопка переносится на новую строку без перекрытия текста. Alert/status находятся вне контейнера с интерактивными действиями. Исправление ввода/смена режима удаляют старую карточку по прежним правилам.
