## User Scenarios & Testing

### User Story 1 — Полная проверка типов приложения и тестов (Priority: P1)

Одна документированная команда обнаруживает ошибки типов во всех поддерживаемых исходниках и тестовых конфигурациях.

**Why this priority**: Это обязательная часть результата этапа R02; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Положительные и отрицательные проверки действующих TS-конфигураций, затем один итоговый общий typecheck. Контрольные ошибки не сохраняются в репозитории.

**Acceptance Scenarios**:

1. **Given** в query-стенде есть ошибка типов, **When** выполняется общий typecheck, **Then** команда падает и указывает ошибочный файл.
2. **Given** генерируемых типов Next.js ещё нет, **When** запущена штатная команда, **Then** необходимые типы подготовлены до проверки приложения.
3. **Given** все подпроекты корректны, **When** команда запущена после установки зависимостей, **Then** все области проверены и процесс завершён с кодом 0.

### Edge Cases

- Глобальные типы matchers Vitest не загрязняют Playwright.
- Разные пути алиасов у query-стенда.
- Новый тестовый файл в предусмотренной папке автоматически входит в проверку.

### Verification Approach

Положительные и отрицательные проверки действующих TS-конфигураций, затем один итоговый общий typecheck. Контрольные ошибки не сохраняются в репозитории.

Проверяется действующая конфигурация: успешный штатный сценарий и контролируемый нарушающий пример должны дать ожидаемый результат. Ошибка установки или импорта не считается подтверждением TDD. Если выяснится, что требуется изменить бизнес-логику, такая часть выполняется по согласованному контракту через Red → Green → Refactor.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Фактическая приёмка опубликована в [verification.md](verification.md).

## Requirements

### Functional Requirements

- **FR-001**: Включить приложение, Node-тесты, React-тесты, существующий query-стенд и конфигурации Vitest и Playwright в явно определённые TypeScript-проекты.
- **FR-002**: Исключить из исходных областей зависимости, отчёты и сборочные артефакты, сохранив необходимые генерируемые типы Next.js.
- **FR-003**: Предоставить общий typecheck, который готовит необходимые типы и завершает работу ошибкой при сбое любого подпроекта.
- **FR-004**: Сохранить strict-проверку и разделение типов окружений; не маскировать ошибки добавлением any, необоснованных suppressions или отключением проверки тестов.
- **FR-005**: Проверить обнаружение временной ошибки отдельно в приложении, Vitest-тесте и query-стенде; после проверки исходные корректные файлы восстановлены без изменения поведения.
- **FR-006**: Документировать состав команды и проверить её на чистом состоянии генерируемых типов, чтобы локальный кеш не был скрытым условием успеха.

### Scope Boundaries

- **В объёме**: Конфигурации TypeScript, команда typecheck и необходимые исправления типов без изменения поведения.
- **За пределами**: Смена языка или версии TypeScript ради обновления, новые продуктовые функции и массовая переработка кодстайла.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Меняются настройки и документированные команды; допускается генерация игнорируемых типов Next.js.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Пользователь поручил весь цикл согласованного рефакторинга с commit/push; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

TypeScript-проект, исходная область, генерируемые типы, результат общей команды.

## Success Criteria

- **SC-001**: Контрольная ошибка обнаруживается в каждой из трёх проверяемых областей (FR-001–FR-003, FR-005).
- **SC-002**: После восстановления корректного кода общий запуск проходит, strict сохраняется (FR-004).
- **SC-003**: Команда воспроизводима без прежнего кеша типов и описана в документации (FR-002, FR-006).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Commit/push в refactor разрешены пользователем для этого чата. Реальные сообщения в тестах не отправляются.
