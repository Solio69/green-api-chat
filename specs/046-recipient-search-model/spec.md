## User Scenarios & Testing

### User Story 1 — Модуль поиска получателя (Priority: P1)

Поиск получателя имеет ясные границы валидации, запроса и отображения, сохраняя существующие режимы и открытие найденной переписки.

**Why this priority**: Это обязательная часть результата этапа R08; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Vitest для валидации, форматирования и адаптеров; React Testing Library для формы; Playwright для открытия переписки, маршрута поиска и адаптивности.

**Acceptance Scenarios**:

1. **Given** выбран один из существующих режимов, **When** введены валидные данные и подтверждён поиск, **Then** отображается соответствующий результат без изменения правил выбранного режима.
2. **Given** API подтвердил получателя, **When** пользователь открывает переписку, **Then** выбран правильный chatId и подпись, исходящее сообщение не отправляется.
3. **Given** запрос завершился отказом, **When** пользователь исправляет ввод и пробует снова, **Then** форма сообщает причину и позволяет предусмотренный повтор.
4. **Given** запрос начат в старом подключении, **When** после смены подключения приходит ответ, **Then** ответ не меняет результат и выбор нового подключения.

### Edge Cases

- Повторный выбор текущего чата.
- Пробелы и предельные значения допустимого ввода.
- Повторный submit и смена режима при pending.
- Неожиданный ответ провайдера и потеря доступа.

### Verification Approach

Vitest для валидации, форматирования и адаптеров; React Testing Library для формы; Playwright для открытия переписки, маршрута поиска и адаптивности.

Для сохранения поведения используются исходная карта 028 и подтверждённые регрессионные проверки. Искусственный Red для перемещения кода не требуется. Новая или изменяемая бизнес-логика, включая согласованные защиты от гонок, выполняется через Red → Green → Refactor в согласованном цикле реализации. Обнаруженное расхождение с текущим контрактом сначала фиксируется, а не исправляется незаметно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы тестов фиксируются в техническом плане. Приёмочные проверки реализации выполнены; результаты приведены в [verification.md](verification.md).

## Requirements

### Functional Requirements

- **FR-001**: Собрать UI, клиентский адаптер, правила валидации и серверную прикладную часть поиска в модуль recipients с разделением клиентских и серверных входов.
- **FR-002**: Вынести управление режимом, полями, submit и результатом из отображения; сохранить действующие режимы поиска, формат данных и условия доступности переключения.
- **FR-003**: Сохранить состояния ошибки ввода, ожидания, отсутствия получателя, отказа провайдера и успешного результата без превращения разных причин в одинаковый успех.
- **FR-004**: Привязывать результат к актуальному запросу и подключению; размонтирование или смена подключения не позволяют позднему ответу открыть чужую переписку.
- **FR-005**: Открывать найденный чат и передавать его нормализованную подпись через публичный контракт выбора; поиск сам по себе не отправляет сообщение.
- **FR-006**: Сохранить повторный выбор того же получателя, правила обновления подписи, защиты от повторного submit и существующие ограничения на смену режима во время запроса.
- **FR-007**: Сохранить доступность ошибок, клавиатуру, фокус и адаптивное размещение элементов; чистое форматирование подписи не импортирует React или серверные зависимости.

### Scope Boundaries

- **В объёме**: Модуль recipients, поведение формы и связь с выбором переписки.
- **За пределами**: Новые способы поиска, адресная книга, сохранение контактов и автоматическая отправка.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Поиск читает данные провайдера; открытие результата меняет только существующее клиентское состояние выбора и подписи.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Направление, детализация и полный цикл реализации согласованы действующим поручением; повторное разрешение не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Режим поиска, запрос, результат, нормализованная подпись, действие выбора.

## Success Criteria

- **SC-001**: Модуль имеет явные границы и отдельно проверяемое поведение формы (FR-001, FR-002).
- **SC-002**: Оба существующих режима проходят успех, отказ, повтор и проверки устаревшего ответа (FR-003, FR-004, FR-006).
- **SC-003**: Открытие результата сохраняет идентификатор, подпись, отсутствие отправки и доступность интерфейса (FR-005, FR-007).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
