# Feature Specification: Соединение формы текста с отправкой

**Feature Directory**: specs/021-message-composer
**Created**: 2026-10-02
**Status**: Approved — спецификация согласована
**User Approval**: Согласована пользователем 2026-10-02 в составе 018–025
**Workflow Mode**: Standard
**Implementation Authorization**: CodeNotAuthorized
**Verification Status**: NotRun — код, UI и исполняемые тесты сейчас не меняются
**Input**: Описать отправку из существующего согласованного макета через серверную
задачу 020, состояние попытки и первый чат, не менять оформление.

## User Scenarios & Testing

### User Story 1 — Отправить текст выбранному получателю (Priority: P1)

Пользователь видит выбранного получателя и текст, явно отправляет его и отличает
ожидание от принятия API и ошибки.

**Why this priority**: Замыкает пользовательский сценарий отправки задания.
**Independent Test**: После разрешения кода проверить реальный React-компонент
с фиктивным API и HTTP-интеграцию; оформление сверять с согласованным макетом.

**Acceptance Scenarios**:

1. **Given** выбран личный получатель и непустой текст,
   **When** нажата отправка либо Enter вне композиции ввода,
   **Then** создаётся одна попытка для исходного получателя и scope.
2. **Given** пользователь вводит многострочный текст,
   **When** нажаты Shift+Enter либо Enter в активной композиции,
   **Then** сообщение не отправляется автоматически; Shift+Enter добавляет строку.
3. **Given** выполняется текущая попытка,
   **When** повторно нажата её отправка,
   **Then** дубликат этой попытки не создаётся. Пока она выполняется, другая
   отправка того же подключения также не начинается; поле текущей попытки
   заблокировано. Переключение и закрытие остаются доступны.
4. **Given** получен idMessage,
   **When** подтверждение применяется к текущему подключению,
   **Then** сообщение связано с исходным чатом и отображает принятие API,
   без выдуманной доставки. До idMessage пузырь исходящего сообщения не появляется.

### User Story 2 — Начать новый чат после успешной отправки (Priority: P1)

Найденный получатель становится чатом только после принятия первого сообщения.

**Why this priority**: Уже согласованное UI-011 отделяет поиск от создания чата.
**Independent Test**: Проверить список до и после успешной отправки, ошибку и
наличие того же chatId в исходном GetChats.

**Acceptance Scenarios**:

1. **Given** получатель найден и выбран действием «Написать»,
   **When** пользователь ещё не отправил текст,
   **Then** новый чат не появляется в списке только из-за открытия.
2. **Given** такой получатель и подтверждённый idMessage первого сообщения,
   **When** применяется успех,
   **Then** чат добавляется единожды по chatId с фактически известной подписью.
3. **Given** ошибка первой отправки без подтверждения принятия,
   **When** применяется результат,
   **Then** ошибка сама по себе не создаёт чат.
4. **Given** новый принятый чат и последующий GetChats,
   **When** поставщик ещё не включил его в список,
   **Then** принятый в текущем сеансе чат остаётся в списке без дубликата;
   принадлежность сеансу хранится только в памяти текущего подключения.

### User Story 3 — Сохранить связь попытки с исходным текстом и чатом (Priority: P1)

Поздний ответ не должен отправить текст другому получателю или затереть новую
работу пользователя. При переключении чата введённый текст очищается; отдельные
черновики по чатам не сохраняются. Это прямое решение пользователя 2026-10-02.

**Independent Test**: Переключить А → Б во время отправки А, получить поздний
успех/ошибку и проверить исходный чат, актуальный текст и изоляцию scope.

**Acceptance Scenarios**:

1. **Given** отправка текста в А выполняется,
   **When** выбран Б и приходит ответ А,
   **Then** текст и результат А не становятся сообщением Б.
2. **Given** после начала попытки А выбран Б и в нём введён другой текст,
   **When** приходит успех старой попытки А,
   **Then** текст Б не очищается как уже отправленный. При возврате А → Б → А
   старый ответ также не очищает новый ввод по одному совпадению chatId.
3. **Given** статус конкретного idMessage получен до HTTP-ответа, но текста
   соответствующего сообщения ещё нет,
   **When** позднее применяется подтверждение с тем же idMessage,
   **Then** статус объединяется с подтверждённым сообщением в этом чате и scope,
   без создания отдельного пузыря по раннему статусу или совпадению текста.
4. **Given** подключение закрыто либо сменилось,
   **When** приходит поздний результат старой попытки,
   **Then** он не пополняет новый Query-кэш, список или черновики.

### Edge Cases

- Пустое и whitespace-only содержимое; переносы и предельная длина согласуются
  с серверной спецификацией 020. Текст выводится как текст, не как произвольный HTML.
- Enter при IME, двойной клик и Enter вместе с кликом, ошибка без очистки нового
  текста, закрытие переписки во время отправки.
- Ввод в другом выбранном чате и завершение запроса: не очищать чужой текст.
- HTTP 200/idMessage не означает delivered/read; реальные статусы обрабатывает
  задача уведомлений. Принятый сервисный чат может позднее дать failed.
- Сетевой разрыв и отмена запроса не доказывают, что сообщение не было принято.
- Перезагрузка удаляет данные в памяти; сохранение черновиков в localStorage,
  cookie или собственной БД не согласовано.
- GetChatHistory, ответ отправки и событие SSE могут поступить в любом порядке.
- Ранний статус idMessage может ещё не иметь текста сообщения; он не создаёт
  вымышленный пузырь и не связывается с текущей попыткой по совпадению текста.

### Verification Approach

После согласования спеки и отдельного разрешения на код — TDD для обработки
попытки, клавиатуры, блокировки дубля, позднего ответа, очистки нужной редакции,
создания чата и объединения по идентичности. Компонентные проверки выполняются
на настоящем React; E2E проверяет сценарий поиска → выбора → первого сообщения
с фиктивными данными и доступность. Макет проверяется без самостоятельного
редизайна. Команды и объём регрессии уточняются в plan/tasks после решений.
Сейчас Acceptance = NotRun; новых тестов и UI-кода нет.

## Requirements

### Functional Requirements

- **FR-001**: Форма использует подтверждённый chatId выбранного получателя и
  серверный контракт 020; токен и idInstance клиенту не передаются.
- **FR-002**: Enter отправляет вне IME; Shift+Enter добавляет перенос. Пустой и
  whitespace-only текст не создаёт попытку. Поле и отправка имеют доступные
  названия и подсказку, доступную при фокусе и на мобильном экране (UI-017/018).
- **FR-003**: Видимые состояния ожидания, принятия и ошибки различаются. На
  подключение выполняется одна отправка за раз; поле текущей попытки и повторная
  отправка заблокированы до результата. Переключение/закрытие чата разрешены,
  но новый чат не может начать другую отправку до завершения текущей.
  Одинаковые отдельные явные отправки после завершения попытки не запрещаются
  как дубликаты без отдельного согласования.
- **FR-004**: Принятие API определяется idMessage, не таймером или локальным
  изменением. Пузырь исходящего сообщения появляется после успешного ответа API
  с idMessage; до ответа блокируется повторная отправка текущей попытки.
  Optimistic-пузырь не вводится. Это прямое решение пользователя 2026-10-02.
- **FR-005**: Поздний результат связан с connectionScope, исходным chatId и
  попыткой; не меняет другой чат, новую редакцию текста или закрытое подключение.
- **FR-006**: HTTP-ответ отправки, история и уведомление статуса этого сообщения
  объединяются по connectionScope + chatId + idMessage. Ранний статус без текста
  не создаёт пузырь; поздний ответ не создаёт дубль уже известного сообщения.
  Детали общего объединения согласуются с историей и обработкой уведомлений,
  без самостоятельного optimistic tempId-контракта и угадывания по тексту.
- **FR-007**: Первый подтверждённо принятый текст добавляет чат единожды по chatId;
  поиск, «Написать» и ошибка без подтверждения принятия этого не делают.
  Принятый в текущем сеансе чат не исчезает при последующем GetChats, даже если
  поставщик ещё не включил его в ответ. Сопоставление по chatId исключает дубли.
  Данные о принятом чате сохраняются только в памяти текущего подключения;
  конкретный способ объединения выбирается при техническом планировании.
- **FR-008**: Автоматического повтора после неопределённого исхода нет. Сначала
  предлагается проверить историю, повтор остаётся ручным с предупреждением о
  возможном дубле. Отсутствие текста в окне истории не доказывает отсутствия
  отправки; попытка не связывается с найденным сообщением по совпадению текста.
- **FR-009**: При переключении чата текст очищается; отдельного хранилища
  черновиков по чатам нет. Ошибка/неопределённый исход сохраняют текст, если
  пользователь по-прежнему в исходном чате; поздний результат старой попытки
  не восстанавливает текст поверх ввода другого чата. Крестик закрывает чат и
  очищает текст; поле текущей попытки при ожидании заблокировано. Начатая отправка
  остаётся связанной только с исходным чатом и не отменяется логически закрытием.
- **FR-010**: Текст, направление и состояния следуют UI-014/019; галочки
  delivered/read и ошибки failed/noAccount появляются по фактическим данным
  отдельной задачи статусов, не по успеху мутации или таймерам макета.
- **FR-011**: Не менять согласованное оформление, Enter/Shift+Enter и мобильные
  переходы. Кнопка «Чаты» сохраняет выбор, крестик снимает его; политика текста
  следует FR-009. Кнопка «Чаты» не равна смене получателя или закрытию.
- **FR-012**: Рабочий чат доступен только в одной вкладке; нерабочая вкладка
  показывает ограничение и не может отправлять. Право рабочей вкладки предоставляют
  задачи 022/023; в 021 отдельный механизм выбора вкладки не создаётся.
- **FR-013**: Непустой допустимый исходный текст отправляется без изменения
  пробелов и переносов; trim используется только для проверки пустоты, а не
  изменения отправляемого содержимого. Конкретный Unicode-подсчёт лимита 4096
  определяется техническим контрактом 020.

### Scope Boundaries

- В объёме: поведение существующей формы текста, соединение с 020, состояния
  попытки, изоляция выбранного чата, первый принятый чат и безопасное объединение.
- За пределами: редизайн, медиа, группы, реакции, цитирование, typing-уведомления,
  браузерные/системные push-уведомления, автоматическая повторная отправка,
  собственная БД, persist Query и черновики между перезагрузками.
- Эта задача не реализует историю, пагинацию, Receive/Delete или SSE-подключение
  самостоятельно. Использует согласованные контракты соответствующих задач.
- Полноценная обработка исходящих realtime-сообщений, отправленных вне приложения,
  не согласована в 020/021. Такие тексты доступны через историю; поддержка типов
  событий отдельно определяется получением. Ранние статусы по idMessage можно
  объединять с подтверждённым сообщением без угадывания связи по тексту.

### Data Effects & User Decision

- **Changed data**: Явная отправка имеет внешний эффект SendMessage; в памяти
  меняются состояние попытки, данные сообщений и список нового принятого чата.
- **Preview**: Перед отправкой видны исходный получатель и введённый текст.
- **Confirmation**: Кнопка/Enter — явная отправка; отдельного диалога обычной
  отправки нет. Ручной повтор при неопределённом исходе предупреждает о дубле;
  перед повтором сначала предлагается проверить историю.
- **Cancellation**: Закрытие или смена чата не равны отмене принятого сообщения.
  Ответ остаётся исходного чата; смена получателя очищает текст. Очистка при
  закрытии также выполняется; поле текущей попытки при ожидании заблокировано.
- **Idempotency and duplicates**: Блокируется повтор текущего действия и повтор
  представления одного подтверждённого idMessage. Это не exactly-once отправка.
- **Failure result**: Ошибка и неопределённый исход различаются; сохранение
  исходного текста выполняется, если исходный чат по-прежнему открыт. При
  неопределённом результате сначала предлагается проверить историю; повтор
  только ручной с предупреждением о возможном дубле согласно 020.

### Key Entities

- **Selected recipient**: Подтверждённый chatId и фактически доступная подпись.
- **Draft**: Только текст текущего выбранного чата; при смене получателя
  очищается, по чатам не хранится. БД и browser storage не создаются.
- **Send attempt**: Исходный scope, chatId и снимок текста текущего действия.
- **Accepted message**: idMessage от API, объединяемый с историей и уведомлениями.
- **Session-started chat**: Новый чат после принятия первого сообщения;
  остаётся при обновлении GetChats в памяти текущего подключения без дублей.

## Success Criteria

- **SC-001**: Допустимые Enter/клик создают одну попытку; whitespace-only,
  Shift+Enter и IME-Enter создают ноль отправок (FR-001/002/003).
- **SC-002**: Поздний ответ А не изменяет получателя/текст Б и новое подключение
  ни в одном согласованном сценарии переключения (FR-005/009).
- **SC-003**: Первый подтверждённый успех создаёт ровно одну запись chatId;
  поиск/открытие/неподтверждённая ошибка — ноль новых записей. Последующий ответ
  GetChats без нового принятого чата не убирает его в текущем сеансе (FR-007).
- **SC-004**: История, SSE и HTTP-ответ одного idMessage отображаются единожды;
  успех мутации не рисует неподтверждённую доставку (FR-004/006/010).
- **SC-005**: Неопределённый сетевой исход не создаёт автоматическую повторную
  попытку и не очищает постороннюю редакцию текста (FR-005/008/009).
- **SC-006**: Нерабочая вкладка не отправляет текст. При выполнении одной попытки
  новая отправка подключения не начинается; переключение и закрытие работают,
  очищают ввод и не перенаправляют результат (FR-003/009/012).
- **SC-007**: Внешний запрос получает исходный текст с сохранёнными пробелами и
  переносами; whitespace-only не отправляется. Неопределённый исход предлагает
  проверку истории перед ручным повтором с предупреждением (FR-002/008/013).

## Assumptions and Dependencies

- [020 серверная отправка](../020-send-message-api/spec.md) — отдельная согласованная spec;
  успешная подготовка документа не означает готовность исполняемого API.
- [014 Query lifecycle](../014-chat-list-query/contracts/query-layer.md) —
  существующая граница сессии и памяти; черновики по чатам не добавляются.
- [Выбор получателя и мобильные переходы](../025-conversation-selection/spec.md)
  — отдельная задача 025;
  видимая история — задача 019. Их API и callbacks уточняются в технических
  контрактах после согласования; эта задача не присваивает себе их реализацию.
- [Согласованный интерфейс](../../docs/chat-ui-spec.md) — UI-011, UI-013–024;
  визуальные изменения выполняет другой агент, сейчас UI не меняется.
- Пользователь согласовал один Node-сервер и ReceiveNotification → SSE;
  отправка текста остаётся отдельным HTTP-действием, SSE — направление сервер →
  браузер. Под «отправкой уведомлений» отдельная push-функция не подразумевается.
- Продуктовые требования подтверждены ответами пользователя; технические детали
  уточняются в планировании без самостоятельного изменения этих требований.
- [Общий контракт пласта](../../docs/messaging-specs.md) задаёт shared identity,
  роли Query-кэша и объединение истории/HTTP-результата/событий. Форма не создаёт
  независимую коллекцию сообщений и не угадывает корреляцию по тексту.

## Продуктовые решения

Существенных открытых продуктовых вопросов по этому шагу нет. Подтверждены
пузырь после idMessage, одна отправка на подключение, блокировка поля текущей
попытки, сохранение принятого нового чата, очистка при смене/закрытии, ручной
повтор с предупреждением после предложения проверить историю и исходный текст
без изменения пробелов/переносов. Полный текст согласован пользователем
2026-10-02; отдельного разрешения кода нет. Unicode-подсчёт и точные DTO относятся
к планированию 020.
