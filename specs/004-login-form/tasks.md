Команда Red/Green:
npm run test:e2e -- tests/e2e/home.spec.ts tests/e2e/login-form.spec.ts tests/e2e/login-form-safety.spec.ts

Ожидаемый Red: приложение и runner работают, новая форма/её элементы отсутствуют,
сценарии падают по этим ожиданиям. Ошибки импорта, сборки, зависимостей, порта
и общего таймаута не являются Red. При них не переходить к T003.

Распределение проверок T002:
- home.spec.ts: успешное открытие /, согласованный h1, наличие двух полей.
- login-form.spec.ts: скрытие/показ без submit, пустые/частичные/пробельные
  значения, исправление и повторное очищение, сохранение ввода и ведущих нулей,
  Enter, фокус, клавиатура, заполненная форма без перехода/успеха.
  Ссылка на кабинет проверяется через перехват на уровне browser context.
- login-form-safety.spec.ts: новые чистые contexts для обычного режима,
  отключённого JS и заблокированных JS-ресурсов. Проверка disabled, noscript,
  отсутствия реквизитов в URL/запросах/console/хранилищах и сброса при reload.
  Размеры 320×568 и 1280×720: отсутствие горизонтального переполнения
  в исходном состоянии и с ошибками, доступность верхних полей при прокрутке.
- После page.goto проверять появление ожидаемого элемента через auto-wait;
  не маскировать отсутствие формы произвольными sleep/retries.

## Dependencies & Execution Order

Разрешение → T001 → T002 (подтверждённый Red) → T003 (Green) →
T004 (Refactor + Green) → T005 → T006 → T007 → T008 → T009.

При неуспешном Red из-за окружения реализация не начинается.
При регрессии после рефакторинга завершение блокируется до восстановления Green.
Новый смысл поведения возвращается пользователю; технические исправления
в согласованном объёме не требуют отдельного согласования каждого файла.
