## User Scenarios & Testing

### User Story 1 — Модуль списка чатов (Priority: P1)

Список чатов получает готовую модель через интерфейс своего модуля, сохраняя обновление, временные записи, выбор и непрочитанные.

**Why this priority**: Это обязательная часть результата этапа R08; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Vitest с QueryClient для списка и overlay; React Testing Library для состояний и действий; Playwright для клавиатуры, выбранной строки и адаптивного списка.

**Acceptance Scenarios**:

1. **Given** список уже показан, **When** ручное обновление завершилось ошибкой, **Then** сохранённые строки остаются доступны и показана существующая возможность повторить.
2. **Given** уведомление создало временную запись неизвестного чата, **When** провайдер затем возвращает этот чат, **Then** в списке одна запись с согласованной подписью и unread.
3. **Given** у чата больше 99 непрочитанных, **When** строка отображается и выбирается, **Then** виден 99+, доступно точное число и открывается соответствующая переписка.

### Edge Cases

- Пустой список при наличии локальных фактов.
- Дубли chatId и некорректные элементы внешнего ответа.
- Повторное открытие того же чата.
- Обновление одновременно со сменой подключения.

### Verification Approach

Vitest с QueryClient для списка и overlay; React Testing Library для состояний и действий; Playwright для клавиатуры, выбранной строки и адаптивного списка.

Для сохранения поведения используются исходная карта 028 и подтверждённые регрессионные проверки. Искусственный Red для перемещения кода не требуется. Новая или изменяемая бизнес-логика, включая согласованные защиты от гонок, выполняется через Red → Green → Refactor после разрешения реализации. Обнаруженное расхождение с текущим контрактом сначала фиксируется, а не исправляется незаметно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации сейчас имеют статус **NotRun**: этот документ задаёт объём, а не подтверждает выполненный рефакторинг.

## Requirements

### Functional Requirements

- **FR-001**: Разместить получение списка, нормализацию, query-настройки и UI в модуле chats; компоненты потребляют готовые записи и действия вместо структуры Query Cache.
- **FR-002**: Сохранить объединение списка провайдера с фактами текущего подключения, уникальность chatId, подписи, порядок и существующее поведение неизвестных чатов.
- **FR-003**: Сохранить различие первоначальной загрузки, ошибки без данных, пустого списка, успешного результата и ошибки обновления при сохранённом списке.
- **FR-004**: Сохранить ручное обновление и восстановление после уведомлений, их защиту от лишних запросов и текущие сроки кеша.
- **FR-005**: Связать выбор и unread через публичные интерфейсы соответствующих моделей; повторный выбор текущего чата сохраняет семантику открытия истории.
- **FR-006**: Сохранить визуальный предел 99+ и точное доступное количество непрочитанных, доступное имя строки, клавиатурное управление и отображение выбранной строки.
- **FR-007**: Общий QueryProvider не импортирует список чатов, а модуль списка не зависит от внутренних компонентов переписки.

### Scope Boundaries

- **В объёме**: Модель и UI списка, query-настройки и связи с выбором и unread.
- **За пределами**: Новая сортировка, поиск по списку, превью последнего сообщения, серверная пагинация.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Сохраняется текущая память списка и выбор пользователя; изменение структуры модулей не добавляет запись провайдеру.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Запись чата, список провайдера, факты подключения, состояние списка и badge.

## Success Criteria

- **SC-001**: Модуль списка и общий QueryProvider соблюдают определённые границы (FR-001, FR-007).
- **SC-002**: Загрузка, пустота, ошибка обновления и overlay проходят прежние сценарии без потери данных (FR-002, FR-003, FR-004).
- **SC-003**: Выбор, unread и доступные имена сохраняются, включая 99+ и повторное открытие (FR-005, FR-006).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Реализация включает разрешённые commit/push в refactor; отправка реальных сообщений не входит в задачу.
