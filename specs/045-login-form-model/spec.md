## User Scenarios & Testing

### User Story 1 — Поведение и отображение формы входа (Priority: P1)

Форма входа остаётся доступной и безопасной, а запрос авторизации и управление её состоянием проверяются отдельно от разметки.

**Why this priority**: Это обязательная часть результата этапа R08; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Vitest для клиентского адаптера; React Testing Library для состояний и действий формы; Playwright для cookie, навигации, отсутствия утечки до гидратации и реального фокуса.

**Acceptance Scenarios**:

1. **Given** введены корректные фиктивные реквизиты, **When** пользователь отправляет форму, **Then** выполняется один запрос, после успеха открывается рабочая область.
2. **Given** сервер отклонил вход, **When** пользователь исправляет данные и повторяет действие, **Then** ошибка видна и доступна, повторная попытка возможна.
3. **Given** JavaScript ещё не гидратировал форму, **When** пользователь пытается отправить её, **Then** токен не появляется в URL и не уходит нативным GET-запросом.
4. **Given** пользователь авторизован, **When** он выходит, **Then** серверная сессия и клиентское состояние завершаются согласно существующему сценарию.

### Edge Cases

- Двойной submit и медленная сеть.
- Невалидный или неожиданный ответ API.
- Размонтирование при незавершённом запросе.
- Отправка с клавиатуры и переключение видимости токена.

### Verification Approach

Vitest для клиентского адаптера; React Testing Library для состояний и действий формы; Playwright для cookie, навигации, отсутствия утечки до гидратации и реального фокуса.

Для сохранения поведения используются исходная карта 028 и подтверждённые регрессионные проверки. Искусственный Red для перемещения кода не требуется. Новая или изменяемая бизнес-логика, включая согласованные защиты от гонок, выполняется через Red → Green → Refactor в согласованном цикле реализации. Обнаруженное расхождение с текущим контрактом сначала фиксируется, а не исправляется незаметно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы тестов фиксируются в техническом плане. Приёмочные проверки реализации выполнены; результаты приведены в [verification.md](verification.md).

## Requirements

### Functional Requirements

- **FR-001**: Разделить клиентский вызов входа, управление submit и состояниями формы, отображение полей и сообщений; разместить их в модуле auth по карте 035.
- **FR-002**: Сохранить текущую валидацию, состояния ожидания и ошибок, показ и скрытие токена, доступные имена и связь ошибок с полями.
- **FR-003**: Сохранить защиту формы до гидратации: реквизиты не попадают в URL, историю навигации и непредусмотренный нативный запрос.
- **FR-004**: Блокировать повторную отправку во время активного запроса; после отказа разрешать существующий сценарий исправления и повторного входа.
- **FR-005**: Сохранить серверное создание сессии и существующую навигацию после успеха; ответ старой размонтированной формы не управляет новой формой.
- **FR-006**: Не хранить реквизиты в общем кеше, постоянном хранилище и диагностике; поведение очистки полей и ошибки при выходе сохранить по текущему контракту.
- **FR-007**: Разделить поведение выхода и его кнопку в том же модуле, сохранив завершение клиентского сеанса и серверной сессии.
- **FR-008**: Сохранить визуальную компоновку, клавиатурную отправку и фокус; не вводить библиотеку форм или глобальное состояние формы.

### Scope Boundaries

- **В объёме**: Клиентские сценарии входа и выхода, их адаптеры, хуки и UI.
- **За пределами**: Новый механизм аутентификации, изменение срока cookie, библиотека форм и редизайн.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Действие пользователя по-прежнему создаёт или завершает сессию; рефакторинг не добавляет автоматический вход или сохранение токена.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Направление, детализация и полный цикл реализации согласованы действующим поручением; повторное разрешение не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Данные формы, состояние submit, результат входа, действие выхода.

## Success Criteria

- **SC-001**: Запрос, управление сценарием и UI имеют отдельные проверяемые ответственности без дублирования состояния (FR-001, FR-007).
- **SC-002**: Проверены успех, отказ, повтор и поздний ответ; двойной submit не создаёт второй запрос (FR-002, FR-004, FR-005).
- **SC-003**: Браузерные проверки подтверждают защиту до гидратации, выход, клавиатуру и прежний интерфейс (FR-003, FR-006, FR-008).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Подготовка спецификаций не включает commit, push или отправку реальных сообщений.
