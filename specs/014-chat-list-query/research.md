## R1 — Данные поставщика

[Официальный GetChats](https://green-api.com/telegram/docs/api/service/GetChats/) описывает GET и массив объектов с chatId, name, type, phoneNumber, username. Типы: user, group, supergroup, channel. phoneNumber — число, 0 означает скрытый номер. Превью, аватар и время последнего сообщения в описанном ответе отсутствуют.

Выбор: только user; безопасный DTO с явными полями; порядок поставщика сохраняется. Подробная валидация и дубли — в data-model.md. Корректный [] принимается как успех по согласованной spec, хотя документация упоминает пустой ответ также в таблице проблем: реальная причина пустоты не выводится автоматически. Нужна ручная проверка на инстансе пользователя.

## R3 — Свежесть и обновления

[Настройки Query](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults) требуют осознанного выбора: стандартные staleTime, повторы и обновление при событиях браузера не подходят как неявная политика API. Наш выбор: свежесть 60 секунд, удержание неактивного результата 5 минут, без фонового интервала и повторов клиента; stale список обновляется при новом потребителе или восстановлении сети. Фокус окна не запускает запрос. Ручное обновление разрешено и для свежих данных.

Вариант staleTime=0 проще для всегда свежего списка, но вызывает больше запросов при переключении компонентов. Infinite не подходит: без следующего шага уведомлений изменения аккаунта могут остаться незамеченными. Одна минута — компромисс, технический параметр, не обещание доставки уведомлений. gcTime не хранит данные после перезагрузки и не ограничивает время жизни активного запроса.

## R4 — SSR и изоляция подключения

[Рекомендации SSR](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr) учитывают выполнение Client Components также на сервере. QueryClient создаётся для конкретного провайдера; серверный глобальный singleton исключён. Для списка не требуется prefetch/dehydrate/HydrationBoundary: запрос начинается у клиентского потребителя. Suspense hooks в 014 не используются. Провайдер стабилен на повторных render и сменяется по key подключения.

| Вариант идентификатора                     | Польза                                                         | Риск                                                    | Выбор                             |
| ------------------------------------------ | -------------------------------------------------------------- | ------------------------------------------------------- | --------------------------------- |
| idInstance/token в query key               | Простой ключ                                                   | Реквизиты оказываются на клиенте                        | Запрещён FR-011                   |
| Случайный ключ только на клиенте           | Простая смена кэша в одной вкладке                             | Сервер не обнаружит смену общей cookie в другой вкладке | Недостаточен для привязки запроса |
| Непрозрачная серверная подпись подключения | Привязка к существующей cookie без новой БД и изменения сессии | Один helper и проверка заголовка                        | Выбран                            |

connectionScope = HMAC-SHA256 от JSON массива ["chat-query-v1", idInstance, apiTokenInstance, expiresAt], ключ SESSION_PASSWORD, результат base64url. [Node 24 crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptocreatehmacalgorithm-key-options) предоставляет createHmac. Только сервер импортирует helper. Scope не заменяет cookie и не является новым токеном доступа. GET /api/chats сверяет заголовок с текущей сессией до GetChats; несовпадение возвращает 409 без удаления действующей cookie. Старый клиент очищается и запрашивает новый серверный контекст.

Это защита при следующем запросе/навигации. Мгновенная синхронизация выхода во всех вкладках через BroadcastChannel не входит в 014; уже открытая вкладка может показывать прежний результат до следующего обращения. Её запросы не должны записывать данные нового аккаунта в старый scope. Нет общего кэша между вкладками. Одновременные вход/выход разных вкладок не гарантируют бесшовность: уже начатый ответ с удалением cookie может затронуть более новое подключение. Полная координация таких действий потребует отдельного обсуждения; scope защищает принадлежность query-данных, а не атомарность изменения общей cookie.

## R5 — Отмена и ошибки

[Отмена Query](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation) использует AbortSignal queryFn. Его нужно передать fetch и проверять актуальность подключения перед возвратом результата. При close сначала запретить новые запросы/выдачу данных, затем cancelQueries и clear. Позднее разрешение promise не должно активировать закрытый контекст. При подтверждённой ошибке сессии обработка централизована и выполняется один раз на подключение.

На сервере сохранить подход адаптеров: no-store, redirect:error, общий timeout 10 секунд; при 429 пауза 1100 мс и максимум одна повторная попытка в том же deadline. Не добавлять повторный GetState/GetAccountSettings на каждый список. Временные ошибки сохраняют cookie; подтверждённые отказы очищают её в API, клиент переходит на login. Ошибка logout оставляет клиент активным.
