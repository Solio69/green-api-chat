# Data model: список чатов

Дата: 2026-10-02. Модель реализована и проверена; результаты — verification.md. БД и миграции отсутствуют.

## PersonalChat

| Поле DTO | Тип             | Правило                                                                                                        |
| -------- | --------------- | -------------------------------------------------------------------------------------------------------------- |
| chatId   | string          | Обязательная непустая строка, trim, не выводится из username/телефона                                          |
| name     | string или null | Непустая trim строка поставщика; иначе null                                                                    |
| username | string или null | Непустая trim строка поставщика; иначе null; формат не достраивается                                           |
| phone    | string или null | Только положительный safe integer phoneNumber, перевод в десятичную строку; 0/отсутствие/невалидный тип → null |

Сервер создаёт новый объект по allowlist. Нет type, lastMessage, timestamp, avatar, любых неизвестных полей. Проверяются отсутствие реквизитов и credential-bearing URL: если текст содержит текущий idInstance/apiTokenInstance или их encodeURIComponent представление, необязательное поле отбрасывается; такой chatId делает ответ некорректным. Не логиировать raw payload или URL поставщика. Дополнительные поля не копируются. Клиент также валидирует форму успешного внутреннего ответа и создаёт DTO по allowlist, вместо утверждения типа через as.

## Нормализация ответа

Корень — массив. Каждый элемент — ненулевой объект (не массив) с непустым string type. user требует корректный chatId. group/supergroup/channel пропускаются, их остальные поля не используются. Неизвестный непустой type пропускается: он не превращается в user. Отсутствующий/нестроковый/пустой type, некорректный элемент или chatId личного чата → invalid_upstream_response для всего ответа, не частичный успех.

Правила name/username/phone применяются после фильтрации. Дубликаты chatId удаляются, остаётся первый личный элемент и его подготовленные поля; поля из разных записей не объединяются. Сохраняется порядок поставщика. [] или корректный ответ без user → успешный []. Не сортировать по отсутствующему времени сообщения.

## Server connection context

Существующая SessionPayload: idInstance, apiTokenInstance, expiresAt, только в зашифрованной HttpOnly cookie/серверном коде. Формат cookie не меняется.

connectionScope: 43 символа base64url от HMAC-SHA256. Каноническая строка и источник ключа определены в research R4. Серверная главная вычисляет scope только после действующего authorized результата и передаёт его провайдеру. Сервер API повторно вычисляет его из проверенной текущей сессии; входящий scope не выбирает аккаунт. Новые реквизиты/expiresAt меняют привязку; новый mount после logout имеет новый QueryClient даже при совпадении scope.

## Query state

Ключ: readonly ['chats', connectionScope]. Значение query — PersonalChat[]. Единственный владелец данных — QueryClient; UI может хранить selectedChatId и прочее локальное состояние интерфейса отдельно, но не копию списка.

Состояния хука: initial pending (data undefined), success empty (data []), success nonempty, refresh (имеющиеся data + isFetching), initial error (нет data), refresh error (прежние data + error), closed (data undefined, запросы запрещены). Закрытый контекст необратим, новый вход/смена scope создаёт новый контекст. Lifecycle-флаг закрытия является состоянием подключения, а не вторым store серверных данных.

## Errors

Сервер: существующие категории API плюс connection_changed для несовпадения scope. Клиентская ChatsQueryError содержит только безопасные code/status, не Response, URL поставщика или тело неизвестного ответа. Неизвестная/повреждённая форма ответа и недоверенные коды → invalid_upstream_response; сетевой сбой → service_unavailable. Отмена не отображается как отказ доступа.
