**Workflow Mode**: Standard

**Input**: Получать список личных чатов подключённого Telegram-аккаунта через GetChats и управлять загрузкой и временным кэшем через TanStack Query. Изолировать кэш между подключениями и очищать его после успешного выхода. Профиль оставить серверным, перенос существующего поиска отложить. Редизайн пользователь поручает другому агенту.

## User Scenarios & Testing

### User Story 1 — Получить существующие личные чаты (Priority: P1)

После подтверждённого входа интерфейс получает список существующих личных чатов аккаунта. Список включает переписки, начатые вне приложения. Поиск получателя не является условием восстановления списка.

**Why this priority**: Список нужен для выбора переписки после открытия приложения и повторного входа; ручное восстановление через поиск исключено пользователем.

**Independent Test**: Войти на фиктивном аккаунте и подключить потребителя публичного хука списка к провайдеру. Проверить данные личных чатов, отсутствие групп и каналов, состояния ожидания, успешного пустого ответа и ошибки. Серверный контракт проверяется отдельно через HTTP API.

**Acceptance Scenarios**:

1. **Given** главная подтвердила действующую сессию, **When** потребитель запрашивает список, **Then** наш сервер получает реквизиты из сессии, вызывает GetChats и возвращает только подготовленные данные личных чатов.
2. **Given** ответ содержит личные чаты, группы, супергруппы и каналы, **When** он обработан, **Then** потребитель получает личные чаты без остальных типов.
3. **Given** запрос выполняется, **When** данных ещё нет, **Then** потребитель может отличить ожидание от успешно полученного пустого списка.
4. **Given** успешно получен корректный пустой список или в корректном ответе нет личных чатов, **When** обработка закончена, **Then** результат является успешным пустым списком.
5. **Given** сессии нет или она истекла, **When** вызывается наш API списка, **Then** GetChats не вызывается и возвращается существующая категория отсутствия сессии.
6. **Given** пользователь обновил страницу или снова вошёл в аккаунт, **When** новый потребитель запрашивает список, **Then** данные восстанавливаются через API, без постоянного браузерного хранилища.

### User Story 2 — Пользоваться общим кэшем запросов (Priority: P1)

Потребители списка используют один кэш TanStack Query внутри текущего подключения. Данные, ожидание, ошибка и возможность повторного запроса доступны через публичный хук без оформления UI в этой задаче.

**Why this priority**: Управление серверными данными не должно дублироваться в нескольких компонентах будущего каркаса чата.

**Independent Test**: Подключить два потребителя одного списка. Проверить общий результат, отсутствие параллельных одинаковых обращений, явное обновление и возможность получить данные после временной ошибки. Точные сроки актуальности и удержания кэша фиксируются в техническом плане до разрешения реализации.

**Acceptance Scenarios**:

1. **Given** одинаковый список запрашивают два потребителя текущего подключения, **When** первый запрос ещё выполняется, **Then** библиотека использует общее выполнение запроса и оба потребителя получают его результат.
2. **Given** в кэше есть свежий список, **When** потребитель снова подключается, **Then** доступен кэшированный результат без обязательного нового запроса.
3. **Given** уже получен список, **When** выполняется его обновление, **Then** состояние обновления отличимо от первоначального ожидания; временная ошибка не превращает ранее полученные чаты в успешный пустой список.
4. **Given** произошёл временный сбой, **When** потребитель инициирует повторную загрузку после восстановления, **Then** получает текущий список.

### User Story 3 — Не увидеть данные предыдущего подключения (Priority: P1)

Выход и новое подключение не оставляют доступного списка предыдущего аккаунта. Временный сбой загрузки или неуспешный выход сами по себе не уничтожают действующую сессию и её кэш.

**Why this priority**: Один браузер может последовательно использовать разные реквизиты; кэш не является доказательством авторизации.

**Independent Test**: Загрузить список аккаунта А, выполнить выход и войти в Б. Проверить отсутствие данных А, включая позднее завершившийся запрос. Отдельно подставить временный сбой, подтверждённый отказ доступа и ошибку выхода.

**Acceptance Scenarios**:

1. **Given** список аккаунта А загружен, **When** существующий выход успешно завершён, **Then** кэш подключения очищен, активные запросы не могут вернуть данные А после очистки, открыт обычный login.
2. **Given** выход завершился ошибкой, **When** пользователь остаётся в приложении, **Then** существующая ошибка выхода отображается прежним способом, кэш не очищается как при успешном завершении сессии.
3. **Given** предыдущий запрос А не завершён, **When** пользователь подключился к Б, **Then** ответ А не становится данными Б и не отображается его потребителям.
4. **Given** поставщик однозначно подтвердил недействительность сохранённого подключения, **When** ответ обработан, **Then** применяется существующий сценарий завершения сессии и очистки клиентского кэша.
5. **Given** поставщик временно недоступен, **When** запрос списка не удался, **Then** сессия сохраняется и потребитель получает временную ошибку, а не сообщение об отсутствии чатов.

### Edge Cases

- Отсутствующие необязательные name, username и phoneNumber не являются поводом придумывать имя, фото, превью или время последнего сообщения. Подтверждённый chatId остаётся идентификатором.
- Неверный JSON, неверная форма корневого ответа и некорректные обязательные данные личного чата не считаются корректным пустым списком. Правила нормализации, неизвестных типов и повторяющихся chatId уточняются в техническом контракте; UI не получает произвольное тело ответа поставщика.
- Отмена запроса и его завершение после выхода или смены подключения не возвращают старые данные.
- Разные подключения не объединяют результаты по совпадающему chatId. Реквизиты инстанса не используются в клиентском ключе кэша.
- Ошибка обновления при имеющихся данных отличается от ошибки первоначальной загрузки.
- Список не сортируется по выдуманному времени последнего сообщения: GetChats не возвращает такие поля.
- Ошибки сети, таймауты, ограничения частоты и невалидные ответы сохраняют действующую сессию, если нет подтверждённого отказа доступа.
- Фоновый периодический опрос списка не является частью этого шага. Автоматические повторы и обновления при событиях браузера должны быть явно настроены с учётом существующих ограничений API, а не оставлены неявным поведением библиотеки.

### Verification Approach

Новая серверная логика, внутренний HTTP-контракт и правила изоляции/очистки кэша проходят TDD после отдельного разрешения реализации: сохраняемые тесты, подтверждённый поведенческий Red, минимальный Green и Refactor. Ошибка отсутствующей зависимости или импорта не считается Red.

Серверные проверки покрывают сессию, фильтрацию типов, подготовку данных, пустой ответ, некорректные ответы и категории ошибок. Проверки query-слоя покрывают общее выполнение запроса, состояния первоначальной загрузки и обновления, ручной повтор, раздельные подключения, отмену и поздние ответы. Браузерные проверки провайдера и выхода должны использовать фактический публичный контракт и существующий тестовый стенд; конкретный способ подключения тестового потребителя без изменения продуктового дизайна выбирается в плане.

Все автоматические проверки используют фиктивные аккаунты и ответы. Новые тестовые зависимости не выбираются заранее. Проверки качества и регрессия входа, профиля, поиска и выхода выполняются после завершения серии правок. Ручная проверка настоящего списка проводится пользователем без передачи секретов. Готовность API и хука не выдаётся за завершённый редизайн или подключённый список в новом каркасе.

## Requirements

### Functional Requirements

- **FR-001**: Наш сервер получает список через GetChats, используя реквизиты существующей действующей сессии; браузер обращается только к нашему HTTP API.
- **FR-002**: При отсутствии или истечении сессии поставщик не вызывается; возвращается существующая категория отсутствия сессии.
- **FR-003**: Потребитель получает только личные чаты аккаунта; группы, супергруппы и каналы в этот шаг не входят.
- **FR-004**: Данные списка содержат подтверждённый chatId и доступные данные подписи; дополнительные поля поставщика, реквизиты, URL с токеном и вымышленные поля не передаются потребителю.
- **FR-005**: Корректный пустой результат, ожидание и ошибка различимы. Некорректный ответ поставщика не выдаётся за отсутствие чатов.
- **FR-006**: Подтверждённая недействительность подключения использует существующее завершение сессии. Временные ошибки сохраняют её и позволяют повторить запрос. Категории и правила HTTP 429 согласуются с действующим серверным подходом в техническом плане.
- **FR-007**: TanStack Query управляет общим запросом и временным кэшем списка внутри текущего подключения; состояния запроса не дублируются отдельным глобальным store или копией списка в каждом компоненте.
- **FR-008**: Публичный хук предоставляет данные, первоначальное ожидание, обновление, ошибку и действие повторной загрузки для отдельной задачи UI.
- **FR-009**: Одновременные одинаковые обращения одного подключения используют общее выполнение. При наличии свежего кэша его можно повторно использовать; сроки свежести, удержания, повторы и события обновления задаются явно до реализации.
- **FR-010**: После успешного выхода и подтверждённого завершения сессии кэш очищается. Отменённые и поздние запросы не восстанавливают его. Ошибка выхода не считается успешным завершением.
- **FR-011**: Новое подключение не видит данные предыдущего аккаунта; клиентские ключи и передаваемые данные не раскрывают idInstance или apiTokenInstance.
- **FR-012**: Данные находятся только во временном кэше памяти. После перезагрузки и нового входа список запрашивается через API; собственная БД и сохранение в localStorage/IndexedDB отсутствуют.
- **FR-013**: GetAccountSettings, серверная проверка главной и передача профиля в шапку сохраняют действующий контракт. Вход, форма поиска и её серверный контракт не переводятся на TanStack Query в этой задаче.
- **FR-014**: Реализация предоставляет слой данных для агента редизайна. Разметка списка, стили, компоновка панелей, история, отправка и получение сообщений не добавляются под видом получения списка.
- **FR-015**: TanStack Query является согласованной новой зависимостью; установку выполняет пользователь по правилам проекта. Версия, команды, совместимость и проверка провайдера фиксируются в плане.
- **FR-016**: Существующие пользовательские изменения сохраняются. Изменения общих точек подключения провайдера, LogoutButton, роутов, констант и тестовых фикстур согласуются по принадлежности и очередности с соседней работой до записи; редизайн не перезаписывается.

### Scope Boundaries

- В объёме: серверный GetChats, подготовка данных личных чатов, внутренний HTTP API, провайдер TanStack Query, публичный хук списка, изоляция кэша и его очистка при завершении подключения, соответствующие тесты и описание подключения для UI.
- За пределами: GetChatHistory и count, хранение или отображение истории, SendMessage, ReceiveNotification и DeleteNotification, перенос поиска и входа на mutations, клиентский кэш профиля, изменения серверного профиля, группы, превью последних сообщений, редизайн и адаптивный каркас, публикация и Git staging/commit.
- Визуальный результат этого шага — доступные потребителю реальные данные и состояния загрузки. Подключение и оформление списка в новом каркасе принадлежат отдельной задаче UI; завершение одного слоя не означает готовность всего интерфейса.

### Data Effects & User Decision

- **Changed data**: Читаются данные личных чатов через API; временный query-кэш и код приложения. Данные Telegram не изменяются, новых БД нет.
- **Preview**: Перед реализацией пользователь получает эту спецификацию, затем технический комплект и полный анализ; реальная переписка и реквизиты не включаются в примеры.
- **Confirmation**: Выбор TanStack Query и GetChats уже согласован. Письменная спецификация согласована; отдельное разрешение реализации проходит существующую точку процесса, без дополнительных подтверждений на каждое чтение списка.
- **Cancellation**: Отмена загрузки не изменяет Telegram. Завершение подключения исключает применение его незавершённых ответов.
- **Idempotency and duplicates**: GetChats является чтением; повтор не создаёт чат. Общие запросы и повторяющиеся идентификаторы обрабатываются без дублирования результата.
- **Failure result**: Потребитель получает нормализованную ошибку. Временный сбой сохраняет сессию; ранее подтверждённые данные текущего подключения могут оставаться доступны вместе с ошибкой обновления.

### Key Entities

- **Личный чат**: Подтверждённый chatId и безопасные доступные поля подписи из GetChats.
- **Результат загрузки**: Данные или нормализованная ошибка; первоначальное ожидание и обновление различаются.
- **Контекст подключения**: Граница жизни и изоляции временного query-кэша, не замена серверной сессии.
- **Публичный слой данных**: Провайдер и хук, используемые интерфейсом без собственного хранения копии списка.

## Success Criteria

- **SC-001**: Фиктивный смешанный ответ даёт только личные чаты; корректный пустой ответ, ошибка и ожидание различимы, вымышленные данные не добавляются. Покрывает FR-001–FR-005.
- **SC-002**: Без сессии нет вызова поставщика; подтверждённый отказ завершает подключение, временные сбои допускают повтор без удаления сессии. Покрывает FR-002, FR-006.
- **SC-003**: Два потребителя используют один незавершённый запрос и общий результат; свежий кэш повторно доступен, обновление и повтор работают по явно записанным настройкам. Покрывает FR-007–FR-009.
- **SC-004**: После успешного выхода или перехода от А к Б данные А недоступны, в том числе при позднем ответе; ошибка выхода не очищает кэш как успешный выход. Покрывает FR-010–FR-012.
- **SC-005**: Действующие вход, профиль, поиск и выход проходят соответствующую регрессию; новая зависимость подключена способом, совместимым с Next.js, без постоянного хранилища. Покрывает FR-013, FR-015.
- **SC-006**: Публичный контракт слоя данных и общие точки подключения описаны для отдельной задачи UI; редизайн не перезаписан, непроверенная визуальная интеграция не объявлена выполненной. Покрывает FR-008, FR-014, FR-016.

## Assumptions and Dependencies

- Пользователь подтвердил ближайший объём: GetChats, TanStack Query, изоляция и очистка; профиль остаётся серверным, перенос поиска отложен. Редизайн передаётся другому агенту пользователем.
- Исходные источники проекта: AGENTS.md, GIT_POLICY.md, docs/CODING_RULES.md, конституция, specs/006-login-session, specs/008-logout, specs/009-recipient-lookup и specs/013-account-profile.
- GetChats возвращает чаты текущего аккаунта с chatId, name, type, phoneNumber и username. Превью, время последнего сообщения и аватар в описанном ответе отсутствуют. Источник: [GetChats](https://green-api.com/telegram/docs/api/service/GetChats/), проверен 2026-10-01.
- TanStack Query выбран для серверных данных и временного кэша. Документация: [обзор](https://tanstack.com/query/latest/docs/framework/react/overview), [настройки](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults), [Next.js / Server Components](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr).
- В package.json пока нет TanStack Query. Установка не проводилась; версия и команды зафиксированы в техническом плане.
- Нет подтверждения проверки GetChats на настоящем инстансе; автоматическое покрытие будет использовать фиктивные данные. Ручная проверка пользователя остаётся отдельной.
- Точные контракты, нормализация полей, настройки кэша и способ browser-проверки публичного хука относятся к технической подготовке. Смена подтверждённых границ или правил доступа требует согласования.

Документ описывает согласованные договорённости. Технический комплект подготовлен по plan.md; анализ выполняется отдельным read-only этапом с сохранением analysis.md после прохода. Исполняемые тесты и продуктовый код задачи не создавались.
