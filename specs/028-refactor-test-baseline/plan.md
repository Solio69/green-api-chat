**Согласование spec.md**: пользователь делегировал этому чату выбор первой задачи и полный цикл её подготовки.
**Разрешение на реализацию**: дано в переписке для выбранной задачи после устранения разногласий комплекта; разрешён локальный commit в `refactor` после ревью. Повторное подтверждение не требуется.

## Summary

Результат 028 — воспроизводимая исходная точка: полный реестр существующих сценариев, карта восьми критических гарантий, план их переноса, фактический исходный прогон и список пробелов. Продуктовый код и исполняемые тесты сохраняются. Это отдельная завершённая задача, на которую опираются 029–055.

## Technical Context

Windows, PowerShell 7; Node 24.14.1, npm 11.11.0; существующий Next.js/React/TypeScript стек и Playwright 1.63.0. Три тестовых конфигурации и отдельные PowerShell-контракты процесса. Vitest ещё не установлен. Данные синтетические, хранения приложения не добавляется.

Исходный HEAD фиксируется перед прогоном. При начале задачи staged были только 57 документов рефакторинга, созданных в этом чате; исходники и тесты совпадали с HEAD. Проверяемая область дополнительно фиксируется хешами. Результаты прежнего обзора не заменяют новый прогон.

## Tasks and Dependencies

Подготовка и анализ → фиксация контекста → runner inventory и просмотр assertions → карта гарантий → последовательный baseline → сверка, ревью документов и обновление roadmap → итоговый read-only анализ → запись verification и commit.

Реализация стартует только после полного анализа spec/plan/tasks. Обнаруженный продуктовый дефект записывается и не исправляется в 028. Failed в продуктовой регрессии не равен провалу задачи инвентаризации: её требование — правдиво зарегистрировать результат. Не выполненная собственная проверка полноты реестра или ссылок блокирует завершение 028.

## Verification

Команды перечислены в quickstart. Выполнить корневой typecheck и отдельный query typecheck, линтеры, Prettier, три Playwright-набора и PowerShell-набор. Production build оценивается по E2E webServer, чтобы не дублировать сборку. Независимые read-only проверки можно объединять; запуски с общими сборками/отчётами последовательны.

Реестр сверяется с runner totals и всеми `*.spec.ts`/`*.tests.ps1`; каждый ID уникален, каждому файлу и сценарию назначен целевой уровень. Для каждой G01–G08 указано доказательство и ограничение. StrictMode replay отделяется от production rerender; no-op listing не объявляется тестированием поведения.

Не создаются новые бизнес-тесты, поэтому Red/Green не заявляются. Собственные изменения — документы: их проверяют полнотой, ссылками, форматом, сопоставлением с исходниками и diff.

## Post-design Constitution Check

C1–C8 повторно PASS с тем же явно ограниченным исключением C4. Проект не получает новых функций, зависимостей или глобальных правил. Разрешение на commit относится только к этому чату и текущей ветке.

## Complexity Tracking

JSON нужен для точной карты нескольких сотен сценариев, Markdown — для чтения и ревью. Не создаётся постоянный генератор, новая тестовая инфраструктура или пустые API-контракты ради шаблона.
