## User Scenarios & Testing

### User Story 1 — Карта проверок и исходное поведение (Priority: P1)

Разработчик видит, какие гарантии приложения уже проверяются, какие проверки отсутствуют и на какое исходное состояние можно опираться при рефакторинге.

**Why this priority**: Это обязательная часть результата этапа R01; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Проверить полноту реестра по фактическому списку тестов и файлов, затем выполнить исходные команды на синтетическом окружении. Сравнить заявленные гарантии с режимами запуска. Новый продуктовый код и исполняемые тесты в этой задаче не создаются.

**Acceptance Scenarios**:

1. **Given** есть текущие тестовые наборы, **When** составлен реестр, **Then** каждый обнаруженный тестовый файл имеет назначение и целевой уровень; ни один критический сценарий не исчезает без отметки о пробеле.
2. **Given** браузерный стенд собран в production, **When** проверяется заявление о Strict Mode replay, **Then** в реестре указано отсутствие доказательства дополнительного цикла эффектов и связь с задачей 030.
3. **Given** проверка недоступна из-за окружения, **When** подведён исходный результат, **Then** она отмечена Blocked или NotRun с причиной, а прошедшие проверки отмечены независимо.

### Edge Cases

- Тесты, создаваемые параметризацией или циклами.
- Сценарии с несколькими уровнями проверки и намеренным дублированием.
- Уже подготовленные пользовательские изменения и занятые тестовые порты.
- Устаревшее упоминание SSE в прежней документации: действующий транспорт определяется спецификацией 027 и текущим кодом.

### Verification Approach

Проверить полноту реестра по фактическому списку тестов и файлов, затем выполнить исходные команды на синтетическом окружении. Сравнить заявленные гарантии с режимами запуска. Новый продуктовый код и исполняемые тесты в этой задаче не создаются.

Это проверка состояния и документация. Новая бизнес-логика не реализуется. Результаты запусков фиксируются только после их выполнения; отсутствие готового окружения обозначается отдельно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмка документационного результата отражена в [verification.md](verification.md). Продуктовые результаты различаются: E2E содержит DEFECT-01, полный проект не объявляется зелёным.

## Requirements

### Functional Requirements

- **FR-001**: Составить реестр существующих тестовых файлов и сценариев; для каждого указать предмет проверки, текущий runner и целевой уровень: unit, integration, component или browser/E2E.
- **FR-002**: Связать критические гарантии из общей дорожной карты с конкретными проверками либо явно зарегистрированным пробелом. Отдельно учитывать авторизацию, историю, отправку, receive/ACK, unread и доступность.
- **FR-003**: Зафиксировать команды и результаты исходных проверок типов, линтеров, форматирования, трёх существующих тестовых наборов и production-сборки. Результаты прошлого обзора хранить отдельно от нового прогона.
- **FR-004**: Указать воспроизводимый контекст прогона: состояние HEAD и незакоммиченных изменений, версии инструментов, режим приложения и фиктивное окружение без секретов.
- **FR-005**: Проверить соответствие названия каждого lifecycle-теста реально исполняемому режиму React; production-проверку не засчитывать как подтверждение Strict Mode replay.
- **FR-006**: Составить карту переноса тестов с устойчивыми идентификаторами сценариев; изменение количества тестов само по себе не считать потерей или приростом покрытия.
- **FR-007**: Различать Passed, Failed, Blocked и NotRun; обнаруженные дефекты поведения регистрировать отдельно, без исправления в этой задаче.

### Scope Boundaries

- **В объёме**: Реестр, матрица покрытия, исходные прогоны и отчёт о пробелах.
- **За пределами**: Перенос тестов, исправление продукта, установка новых зависимостей и изменение существующих контрактов.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Создаются документы проверки; команды могут создавать игнорируемые отчёты и результаты сборки. Исходники и пользовательские данные сохраняются.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Подготовка и выполнение выбранной задачи делегированы пользователем в этом чате. Переход к реализации разрешён после полного анализа и устранения разногласий; повторное согласование не требуется. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Сценарий, тестовый файл, уровень проверки, команда, результат прогона, зарегистрированный пробел.

## Success Criteria

- **SC-001**: Все обнаруженные тестовые файлы включены в реестр, а все восемь групп гарантий дорожной карты имеют покрытие или явно обозначенный пробел (FR-001, FR-002).
- **SC-002**: Для каждой предусмотренной команды есть результат и контекст, достаточный для повторения (FR-003, FR-004, FR-007).
- **SC-003**: Пробел Strict Mode и карта переноса однозначно связаны со следующими задачами (FR-005, FR-006).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Сохранение чужих правок обязательно. Пользователь прямо разрешил этому чату staging и commit в refactor после ревью; общая политика проекта не редактируется. Push и отправка реальных сообщений не входят в задачу.

### Предшествующие задачи

- Предшествующая задача не требуется; это первая точка фиксации исходного состояния.

Зависимости определяют готовность к реализации; писать и читать спецификации можно до завершения предыдущих задач. Если указанный исходный путь будет перенесён предшественником, используется его новое место из карты 035, а не воссоздаётся старый модуль.
