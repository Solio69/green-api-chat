## User Scenarios & Testing

### User Story 1 — Владение состоянием подключения и очистка памяти (Priority: P1)

Все данные переписки принадлежат конкретному подключению и имеют единый жизненный цикл, а общая Query-инфраструктура не знает конкретные функции чата.

**Why this priority**: Это обязательная часть результата этапа R07; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Vitest с реальным QueryClient и управляемыми ресурсами, React Testing Library для потребителей и cleanup, Playwright для реальной видимости/resize. Сохранение сроков проверяется управляемым временем.

**Acceptance Scenarios**:

1. **Given** подключение A накопило историю и unread, **When** оно закрывается и создаётся B с тем же chatId, **Then** B не видит данные A, поздний ответ A ничего не восстанавливает.
2. **Given** входящее сообщение было прочитано, **When** то же уведомление доставлено повторно, **Then** unread не появляется снова.
3. **Given** чат выбран, но его панель скрыта, **When** приходит входящее и затем панель показывается, **Then** счётчик сначала увеличивается, затем очищается только для видимого чата.
4. **Given** одна функция cleanup выбрасывает ошибку, **When** сеанс закрывается, **Then** остальные ресурсы освобождаются и кеш очищается.

### Edge Cases

- Одинаковый chatId в разных scope.
- Скрытая вкладка и мобильный возврат к списку.
- Повтор close, Strict Mode replay и ошибка очистки.
- Просмотр старых сообщений в видимом чате сохраняет текущую семантику прочтения.

### Verification Approach

Vitest с реальным QueryClient и управляемыми ресурсами, React Testing Library для потребителей и cleanup, Playwright для реальной видимости/resize. Сохранение сроков проверяется управляемым временем.

Для сохранения поведения используются исходная карта 028 и подтверждённые регрессионные проверки. Искусственный Red для перемещения кода не требуется. Новая или изменяемая бизнес-логика, включая согласованные защиты от гонок, выполняется через Red → Green → Refactor после разрешения реализации. Обнаруженное расхождение с текущим контрактом сначала фиксируется, а не исправляется незаметно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации имеют статус **NotRun**; фактические результаты будут приведены в verification.md.

## Requirements

### Functional Requirements

- **FR-001**: Отделить общий Query-сеанс от настроек списка чатов и конкретных проекций переписки; опции запросов принадлежат соответствующим модулям.
- **FR-002**: Определить владельца и ключи состояния сообщений, ранних статусов, проблем, списка, временных чатов, unread и выбора; connectionScope участвует во всех требующих изоляции ключах.
- **FR-003**: Сохранить текущие staleTime и gcTime списка, срок жизни накопленных сообщений и правила очистки памяти без введения browser persistence.
- **FR-004**: При закрытии сеанса остановить его ресурсы и очистить все принадлежащие ему данные; ошибка одного cleanup не препятствует оставшимся.
- **FR-005**: Сохранить уникальный учёт входящих chatId/idMessage после очистки unread, независимость чатов и правило видимости вкладки и панели.
- **FR-006**: Не считать историю, исходящие, ignored и статусные события новыми входящими; возврат видимой переписки очищает только её счётчик.
- **FR-007**: Предоставить стабильные read-интерфейсы для React; вычисляемые значения не дублируются в независимых хранилищах и закрытый сеанс не публикует данные.
- **FR-008**: Сохранить различие повторного доступа к тому же чату и переключения выбора, включая очистку черновика только по существующим правилам.

### Scope Boundaries

- **В объёме**: Общий Query lifecycle, владение проекциями, ключи, read-хуки и очистка.
- **За пределами**: Новые лимиты памяти, постоянное хранение, точный серверный unread Telegram и изменение правил черновика.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Перераспределяется ответственность клиентской памяти; данные по-прежнему живут только в текущем подключении.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Query-сеанс, scope, владелец проекции, read-модель, cleanup, выбранная переписка.

## Success Criteria

- **SC-001**: Общий Query-модуль не импортирует feature-код, а все проекции имеют явных владельцев (FR-001, FR-002).
- **SC-002**: Матрица close/scope change/late response подтверждает полную изоляцию и прежние сроки кеша (FR-003, FR-004, FR-007).
- **SC-003**: Unread и выбор проходят прежние сценарии повторов, видимости и переключения (FR-005, FR-006, FR-008).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Пользователь разрешил этому чату commit/push в refactor после полного цикла; отправка реальных сообщений в тестах не используется.
