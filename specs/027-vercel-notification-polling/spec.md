## User Scenarios & Testing

### US1 — Переписка на Vercel (P1)

Пользователь входит с cookie-сессией, получает сообщения и статусы в существующем интерфейсе без постоянного Node-процесса и внешней БД.

**Independent Test**: Получение и ACK исполняются разными экземплярами обработчика с одним секретом; сообщение применено, затем удалено; следующий запрос получает следующий элемент.

1. Given авторизованная вкладка, When GREEN-API возвращает сообщение, Then браузер применяет его к Query и только затем подтверждает удаление.
2. Given очередь пуста, When завершается ожидание пяти секунд, Then HTTP-запрос заканчивается и браузер начинает следующий после ограничивающей частоту паузы.
3. Given потерян ответ/ACK, When получение повторено, Then уникальное сообщение/счётчик не дублируются; удаление не зависит от памяти прежнего сервера.
4. Given повреждённое событие, When оно получено, Then очередь не удаляется и получение приостановлено с существующей ошибкой.

### US2 — Одна вкладка в одном браузере (P1)

1. Given первая вкладка держит Web Lock, When открыта вторая с той же cookie/connectionScope на том же origin, Then вторая показывает ограничение и не получает/не отправляет.
2. Given первая закрыта, When во второй нажато повторное подключение, Then Web Lock доступен и переписка работает.
3. Given потерян доступ/изменено подключение/закрыта страница, When поздний ответ приходит, Then он не изменяет закрытый Query-сеанс.

### Edge Cases

Поддельный/просроченный/чужой ACK; Origin/Host/scope/body guards; отмена запроса; ошибки сети/лимиты GREEN-API; DeleteNotification false после потерянного успешного ответа; StrictMode; браузер без Web Locks; смена чата во время отправки; закрытие вкладки при незавершённом запросе. Доступность нескольких устройств и разные origins/профили браузера не координируются. Открытые страницы приостанавливаемых браузером вкладок могут сохранять lock.

## Requirements

- **FR-001**: Удалить SSE и процессный registry из runtime; каждый receive/settings/ACK запрос завершается отдельно и не зависит от другого экземпляра.
- **FR-002**: Получать через ReceiveNotification с receiveTimeout=5, общим серверным deadline=8 секунд; последовательный клиентский цикл с ограничением частоты и backoff, без параллельных receive/ACK одной вкладки.
- **FR-003**: ACK содержит подписанный proof конкретного receiptId, connectionScope и срока действия; проверка cookie, Origin и scope предшествует удалению; секрет/реквизиты в proof не передаются.
- **FR-004**: Удалять только после успешной клиентской обработки; повтор ACK безопасен: при false проверить голову очереди, тот же receipt — retry, другая/пустая — обработано; повреждённое событие не удалять.
- **FR-005**: Сохранять Query merge/dedup/unread/status/unknown-chat и свежую историю при восстановлении; устаревшие ответы не применяются.
- **FR-006**: Web Locks ограничивает вкладки одного origin/connectionScope; без API получение/отправка блокируются с понятной ошибкой. Без постоянного браузерного хранения.
- **FR-007**: Отправка — обычный cookie/scope/Origin защищённый запрос; одна попытка в текущей вкладке; убрать общий server lease и его фиктивные гарантии; автоматического повторения отправки нет.
- **FR-008**: Закрытие/выход отменяет чтение и освобождает browser lock; cleanup/StrictMode не порождают второй цикл; settings и предупреждение исходящих сохраняются.
- **FR-009**: Настроить ограниченную длительность Next.js handlers для Vercel и документировать GitHub import, Node 24, SESSION_PASSWORD, build/start; публикация и реальные реквизиты вне задачи.
- **FR-010**: TDD серверных/клиентских контрактов, проверка regression, правил/code style до и после кода; удалить неприменимые tests/process-runtime, актуализировать связанные документы с текущим контрактом.

## Scope Boundaries

В объёме: одна миграция получения/ACK/владения и связанной проверки отправки для Vercel, необходимые тесты/доки. Дизайн, истории/пагинация, browser notifications, Redis/БД, новые зависимости, Git writes, публикация, настройки реального инстанса — за пределами.

## Data Effects & User Decision

Cookie сохраняется; сообщения/счётчики — Query RAM. Сервер выдаёт подписанное разрешение ACK на пять минут, ограниченное сроком сессии; после expiry повторное получение выдаёт свежий proof. Разрешение реализации уже дано. Отмена чтения не удаляет уведомление. Повтор удалённого ACK восстанавливается проверкой головы очереди; доставка допускает повторы, отправка не обещает exactly-once.

## Key Entities

Cookie context; normalised NotificationDelivery; signed ACK proof; browser Web Lock; per-view send controller. Серверное постоянное состояние отсутствует.

## Success Criteria

- **SC-001**: Receive на A и ACK на независимом B успешно проходят, подделка/чужой scope/expiry не вызывают delete.
- **SC-002**: Синтетическая очередь → Query → ACK → delete работает для incoming/status/ignored; повторы не удваивают unread.
- **SC-003**: Две реальные страницы одного browser context ограничены; после освобождения вторая получает право без серверного registry.
- **SC-004**: Login/history/send/logout/UI regression, production build и штатные quality checks Passed.
- **SC-005**: Полный комплект, read-only analysis, review/refactor, verification и инструкция деплоя готовы; реальный Vercel smoke отдельно NotRun.

## Dependencies

Установленные Next.js 16/React 19/Query/iron-session/Playwright; HTTPS Vercel либо localhost для Web Locks; общий SESSION_PASSWORD в серверных окружениях одного деплоя; GREEN-API HTTP queue настроена вручную. Недостаток внешней координации между устройствами согласован текущим запросом.
