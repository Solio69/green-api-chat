# Контракт трёх регрессионных сценариев

**Связанные требования**: FR-001, FR-005–FR-009.
**Статус**: реализован; три сценария успешно выполнены.
Результаты — в [verification.md](../verification.md).
Базовый адрес берётся из [контракта запуска](runner.md). Реальные реквизиты
и внешние сервисы не используются.

## P01 — стартовая страница

**Файл**: tests/e2e/home.spec.ts.
**Тип**: браузерный smoke.
**Имя**: shows the foundation page.

Page fixture открывает /. Полученный ответ не null, успешен по HTTP.
Через getByRole('heading', { level: 1, name: PAGE.HEADING, exact: true })
проверяется видимость GREEN-API Chat. Используется web-first ожидание видимости,
без waitForTimeout, SCSS-селекторов и сравнения снимков.
Стили, пиксельное соответствие и будущий интерфейс чата не являются ожиданиями.

## P02 — GET health

**Файл**: tests/e2e/health.spec.ts.
**Тип**: интеграционный HTTP-контракт.
**Имя**: returns the health contract on consecutive GET requests.

Используется request fixture без page/browser. В рамках одного теста выполняются
два последовательных GET /api/health с maxRedirects: 0 и failOnStatusCode: false.
У каждого ответа независимо проверяются:

- HTTP 200;
- Content-Type: application/json; допускается единственный charset=utf-8,
  регистр и пробелы параметра не меняют смысл;
- Cache-Control: no-store;
- глубокое равенство разобранного JSON объекту { status: 'ok' }, без лишних полей.

Каждый запрос ограничен REQUEST из тестовых таймаутов. Ожидание семантики JSON
не зависит от пробелов или порядка ключей сериализованной строки.
Имена заголовков используются в нормализованном нижнем регистре,
соответствующем API Playwright.

## P03 — POST health

**Файл**: tests/e2e/health.spec.ts.
**Тип**: интеграционная проверка метода.
**Имя**: rejects POST for the health endpoint.

request fixture выполняет POST /api/health без тела с ограничением времени
и maxRedirects: 0, чтобы проверять прямой ответ маршрута.
Ожидается HTTP 405. Для запроса явно используется failOnStatusCode: false,
чтобы ответ 405 был доступен для утверждения теста.
Тело и Content-Type ответа 405 не проверяются — их прикладной формат не согласован.

## Общие определения

tests/constants.ts содержит только используемые параметры и ожидания:

- TEST_SERVER: HOST 127.0.0.1, PORT 3101; BASE_URL вычисляется из них.
- TEST_TIMEOUTS: лимиты из runner; использованные значения деструктурируются.
- ROUTES: HOME / и HEALTH /api/health.
- PAGE: HEADING GREEN-API Chat.
- HTTP_STATUS: OK 200 и METHOD_NOT_ALLOWED 405.
- HTTP_HEADERS: CONTENT_TYPE content-type и CACHE_CONTROL cache-control.
- HEALTH_RESPONSE: единственное поле status: ok.
- CACHE_CONTROL: NO_STORE no-store.
- JSON_CONTENT_TYPE: регулярное выражение для согласованных вариантов media type.

Все обычные объекты объявлены as const. Ожидания не импортируются из src/.
Это независимое представление внешнего контракта. Параметры одного использования
в конфигурации, например название reporter, не требуют бессмысленного отдельного
слоя констант. Имена совпадающих деструктурируемых ключей получают ясные алиасы.

Три теста не зависят друг от друга, общего пользовательского состояния нет.
P02 включает два запроса, но остаётся одним тестом; P03 и P01 отдельные.
Тесты не проверяют само наличие или значения констант как внутреннее устройство кода.
