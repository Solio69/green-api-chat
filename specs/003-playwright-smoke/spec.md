# Feature Specification: E02 — автотесты основы на Playwright

**Feature Directory**: specs/003-playwright-smoke
**Created**: 2026-09-29
**Status**: Реализована и проверена; спецификация согласована
**User Approval**: Согласована пользователем 2026-09-29 в переписке
**Workflow Mode**: Standard
**Implementation Authorization**: Получено от пользователя 2026-09-29 в переписке
**Input**: Небольшой постоянный набор регрессионных проверок готовой основы:
страница в Chromium, два GET /api/health и неподдерживаемый POST.
Запуск через NPM Scripts с production-сборкой и собственным проверочным сервером.

## User Scenarios & Testing

### User Story 1 — запускать проверки одной командой (Priority: P1)

Как разработчик, я хочу запускать постоянный набор тестов кнопкой в NPM Scripts,
чтобы воспроизводить проверки без ручного запуска нескольких терминалов.

**Why this priority**: Автоматизация должна быть удобна для регулярного использования.
**Independent Test**: При установленных зависимостях и браузере запустить команду
из package.json через NPM Scripts и проверить результат и завершение сервера.

**Acceptance Scenarios**:

1. **Given** зависимости и Chromium установлены пользователем, конкурирующие
   dev/production-серверы остановлены и проверочный порт свободен,
   **When** запускается команда проверки, **Then** она создаёт актуальную
   production-сборку, запускает собственный сервер, ждёт его готовности,
   выполняет три сценария и завершается с кодом 0 при их успехе.
2. **Given** проверка обнаружила несовпадение ожидаемого результата,
   **When** прогон завершается, **Then** видны имя упавшего теста и причина,
   код завершения ненулевой, собственный проверочный сервер остановлен.
3. **Given** отсутствует требуемый пакет или Chromium, сборка неуспешна либо
   проверочный порт занят, **When** запускается команда, **Then** успешный прогон
   не заявляется; диагностика позволяет определить причину, автоматической
   установки и остановки чужого процесса не происходит.

### User Story 2 — проверять страницу и HTTP-контракт (Priority: P1)

Как разработчик, я хочу автоматически проверять наблюдаемое поведение страницы
и API, чтобы изменения конфигурации или кода не нарушали готовую основу.

**Why this priority**: Это доступные сейчас границы приложения без внешних аккаунтов.
**Independent Test**: Запустить три сценария против реального локального
production-сервера; использовать согласованные ожидания независимо от реализации.

**Acceptance Scenarios**:

1. **Given** приложение запущено, **When** Chromium открывает /,
   **Then** ответ страницы успешен и виден заголовок первого уровня GREEN-API Chat.
2. **Given** приложение запущено без реквизитов GREEN-API,
   **When** выполняются два последовательных GET /api/health,
   **Then** каждый возвращает HTTP 200, Content-Type application/json
   с допустимым charset=utf-8, Cache-Control: no-store и JSON-объект
   с единственным полем status и значением ok.
3. **Given** приложение запущено, **When** выполняется POST /api/health,
   **Then** возвращается HTTP 405. Формат тела этого ответа не фиксируется,
   поскольку он не определён прикладным контрактом.

### User Story 3 — поддерживать проверки вместе с проектом (Priority: P2)

Как разработчик, я хочу иметь сохранённые тесты и короткую инструкцию,
чтобы воспроизвести прогон после установки проекта и расширять покрытие по задачам.

**Why this priority**: Разовые проверки не обеспечивают регулярной обратной связи.
**Independent Test**: Сопоставить инструкцию с командами проекта и выполнить
описанный запуск; проверить состав файлов и результаты существующих quality-команд.

**Acceptance Scenarios**:

1. **Given** репозиторий содержит тестовую основу, **When** разработчик читает
   инструкцию, **Then** понимает, какие зависимости и браузер установить,
   какую команду запускать и где смотреть причину неуспешного прогона.
2. **Given** тесты и конфигурация подготовлены, **When** выполняются проверки
   типов, линтера и форматирования, **Then** новые TypeScript-файлы также входят
   в соответствующие проверки; отчёты, трассировки и прочие результаты прогона
   не попадают в Git.

### Edge Cases

- Найдено ноль тестов: команда завершается неуспешно; отсутствие проверок
  не приравнивается к успешно проверенному приложению.
- Сервер не готов за ограниченное время или завершился раньше: прогон сообщает
  об ошибке окружения и завершается, вместо бесконечного ожидания.
- Порт занят: используется диагностируемый отказ; чужой сервер не подменяет
  проверяемую сборку и не останавливается автоматически.
- Пользователь прерывает прогон: принадлежащие прогону процессы освобождаются.
  Способ завершения и проверки на Windows определяется техническим планом.
- Повторный прогон не зависит от результатов, порядка или данных предыдущего.
  Параллельные независимые прогоны в одной рабочей папке не входят в объём.
- Дополнительное поле в health JSON, другой HTTP-статус, отсутствие no-store
  или невидимый заголовок приводят к ошибке соответствующего теста.
- Изменение имён переменных, деструктуризации, SCSS-классов или пробелов JSON
  при сохранении согласованного поведения не должно ломать проверки.

### Verification Approach

Существующее приложение получает регрессионные тесты. Его поведение и серверный
контракт в этой задаче не меняются; успешный первый запуск не объявляется TDD.
Искусственно изменять продуктовый код ради Red не требуется.

Браузерный сценарий является smoke-проверкой приложения, HTTP-сценарии —
интеграционными проверками контракта. Они обращаются к реальному Next.js,
а не вызывают обработчик напрямую с подменённым окружением фреймворка.

Конфигурация тестового инструмента проверяется фактическим успешным прогоном,
контрольной ошибкой ожидания с ненулевым кодом завершения и последующим
успешным прогоном после удаления контрольной ошибки. Это проверка тестовой
инфраструктуры, а не подтверждение Red для написанной ранее бизнес-логики.
Безопасный способ контрольной проверки, команды и очистка задаются в plan/tasks.

Проверяются применение quality-команд к новым файлам, независимость ожиданий
от продуктовых констант, ограниченное ожидание сервера, его остановка и
сохранность исходников. Необходимые проверки отсутствующих зависимостей и
занятого порта планируются без удаления пользовательских пакетов и процессов.

Для будущей новой и изменяемой бизнес-логики и серверных контрактов обязателен TDD.
На подготовке каждой задачи агент самостоятельно определяет нужный уровень
проверок, сценарии и достаточность существующих инструментов, обосновывает
необходимость нового инструмента и включает это в spec/plan/tasks.
Установку выполняет пользователь; инструменты не добавляются без конкретной
задачи и согласования в рамках принятого процесса.

## Requirements

### Functional Requirements

- **FR-001**: В проекте сохраняется набор из трёх сценариев на Playwright:
  страница в Chromium, последовательные GET health и неподдерживаемый POST.
- **FR-002**: Команда из package.json доступна через NPM Scripts и выполняет
  актуальную production-сборку, запуск проверочного сервера и тестирование.
  Предварительная ручная сборка и отдельный ручной запуск сервера не требуются.
- **FR-003**: Успех означает, что все три сценария действительно найдены и прошли.
  Ошибка теста, сборки, запуска или отсутствие тестов дают ненулевой код завершения.
- **FR-004**: Проверочный сервер имеет ограниченное ожидание готовности, принадлежит
  прогону и завершается при штатном успехе, ошибке или прерывании прогона.
  Чужие процессы не останавливаются и не используются как проверочная сборка.
- **FR-005**: Браузерный тест подтверждает успешное открытие / и видимость h1
  GREEN-API Chat через семантический поиск элемента без привязки к SCSS-классам.
- **FR-006**: HTTP-тест подтверждает для каждого из двух последовательных GET
  весь согласованный контракт health: 200, JSON, no-store и только status: ok.
- **FR-007**: HTTP-тест подтверждает ответ 405 на POST /api/health, без
  дополнительного прикладного требования к телу ошибки фреймворка.
- **FR-008**: Ожидаемые значения тестов независимы от исходников обработчика
  и продуктовых констант. При необходимости общих ожиданий используются
  тестовые определения, фиксирующие контракт, а не импорт его реализации.
- **FR-009**: Тесты работают локально без реквизитов, обращения к GREEN-API,
  отправки сообщений, изменения аккаунтов или данных БД.
- **FR-010**: Конфигурация и тесты проверяются типами, линтером и форматтером.
  Служебные результаты прогона исключены из Git, существующие исходники,
  правила и PowerShell-комплект сохраняются.
- **FR-011**: Инструкция описывает установку пользователем, запуск через
  NPM Scripts, ожидаемый результат, диагностику и завершение проверки.
  Разработка приложения и проверочные прогоны в одной папке выполняются по очереди.
- **FR-012**: Итог сопровождается проверкой соответствия спеке, предкоммитным
  ревью и фактическим verification с Passed/Failed/Blocked/NotRun.
  Изменение продуктового поведения требует отдельного обсуждения.

### Scope Boundaries

- В объёме: Playwright, один браузер Chromium, три регрессионных сценария,
  запуск собственного production-сервера, диагностика прогона, quality-команды,
  правила игнорирования результатов и документация.
- За пределами: установка Vitest и React Testing Library, unit-тесты будущей
  бизнес-логики, остальные браузеры, визуальные снимки, целевой процент покрытия,
  проверки производительности, CI, Vercel и интеграция с реальным GREEN-API.
- Это отдельная небольшая задача эпика E02 перед обсуждением деплоя E02.3.
  Инструменты и тесты для следующих возможностей оцениваются в их собственных спеках.

### Data Effects & User Decision

- **Changed data**: Тесты, настройки, npm scripts, документация и правила
  игнорирования; lock-файл обновляется установкой пользователя.
  Сборка и тесты создают локальные игнорируемые артефакты.
- **Preview**: Эта spec и чек-лист требований; после её согласования —
  технический план, исследование, задачи и анализ согласованности.
- **Confirmation**: Спецификация согласована пользователем в переписке.
  После технического плана и анализа получено отдельное разрешение на код и тесты.
- **Cancellation**: Прерывание подготовки сохраняет документы; прерывание прогона
  завершает его собственные процессы без автоматического отката Git или файлов.
- **Idempotency and duplicates**: Повторный запуск заново проверяет текущую сборку;
  сообщения, аккаунты, сессии и записи БД не создаются.
- **Failure result**: Неуспешная проверка не маскируется успешным кодом.
  Причина и доступные результаты сохраняются; установки и исправления
  окружения выполняются в пределах полномочий проекта.

### Key Entities

Прикладных сущностей и хранилища нет. Тестовые сценарии и локальные результаты
прогона не требуют БД или отдельной модели продуктовых данных.

## Success Criteria

- **SC-001**: Из NPM Scripts запускается один полный прогон, который проверяет
  актуальную production-сборку и завершает собственный сервер без ручного запуска.
  Связь: FR-001–FR-004, FR-011.
- **SC-002**: Все три сценария проходят; GET проверяется дважды, POST получает 405,
  страница открывается в Chromium с видимым согласованным заголовком.
  Связь: FR-005–FR-009.
- **SC-003**: Контрольное неверное ожидание даёт упавший тест и ненулевой код;
  после удаления контрольной ошибки полный набор снова проходит.
  Ошибки окружения отделены от нарушения контракта. Связь: FR-003, FR-004, FR-008.
- **SC-004**: Новые TypeScript-файлы входят в успешные typecheck/lint/format-проверки;
  генерируемые результаты игнорируются, исходники приложения и комплект процесса
  сохранены. Связь: FR-010.
- **SC-005**: Документация достаточна для воспроизведения запуска; verification
  содержит реальные результаты, ограничения, ревью и дальнейшие действия.
  Связь: FR-011, FR-012.

## Assumptions and Dependencies

- Локальная основа E02.2 реализована и проверена. Проект использует Next.js,
  TypeScript, Node 24.x и npm 11.x; зависимости приложения установлены пользователем.
- Пользователь согласовал Playwright первым инструментом, Chromium и три
  указанных сценария; остальные инструменты добавляются по конкретной потребности.
- Пользователь предпочитает запуск npm scripts через кнопки VS Code.
- Агент не скачивает и не устанавливает зависимости или браузеры. Нужные команды,
  совместимые версии и способ локального запуска определяются техническим планом.
- Скрипт сборки и тестовый прогон не должны запускаться одновременно с разработкой
  или другим прогоном в той же рабочей папке; чужие процессы остаются под
  управлением пользователя.
- Это регрессионное покрытие существующих требований, а не новая возможность чата.
  [HTTP-контракт основы](../002-nextjs-foundation/contracts/health.md) сохраняется.
