## Summary

Постоянные регрессионные тесты проверяют production-приложение: видимый заголовок
страницы, два GET health и неподдерживаемый POST. Один test:e2e управляет сборкой,
собственным сервером и тремя тестами. Пользователь запускает его через NPM Scripts.
Продуктовые исходники и поведение API сохраняются.

## Considered Options

| Вариант | Преимущества | Ограничения и риски | Выбор и причина |
| --- | --- | --- | --- |
| Playwright webServer | Штатный жизненный цикл сервера и отчётность | Очистка процессов на Windows требует реальной приёмки | Выбран; не нужен свой orchestrator |
| Ручной start перед тестами | Меньше настроек | Не выполняет требование одного запуска | Не выбран |
| Собственная обёртка Node/PowerShell | Управляемая логика запуска | Дополнительный код и тестирование управления процессами | Не добавляется |
| List и HTML-отчёт | Краткий результат и просмотр ошибок кнопкой | Два игнорируемых каталога артефактов | Выбраны; встроены в Playwright |
| Только list | Минимальная конфигурация | Менее удобный просмотр диагностики пользователем | Дополнительная библиотека для HTML не требуется |

Playwright/Chromium уже согласованы; Vitest/RTL не включаются.
Варианты, факты и официальные источники находятся в [research.md](research.md).

### Runner

test:e2e запускает playwright test. Встроенный webServer выполняет npm run build
и только при успехе — npm run start на 127.0.0.1:3101. Готовность проверяется по /.
reuseExistingServer=false; чужой сервер не используется для проверки текущей сборки.
Таймауты, завершение процессов, полный и выборочный запуск определены в runner.

По завершении сохраняются list-результат и HTML-отчёт. HTML не открывается
автоматически. test:report показывает отчёт по явному запуску пользователя;
этот просмотр имеет собственный процесс и завершается Ctrl+C.
test:install-browser — отдельная явная установка Chromium пользователем,
не часть прогонов или автоматических hooks.

Постоянный набор содержит ровно три теста. forbidOnly=true, workers=1, retries=0.
Пропуски и expected failures не используются. Ревью проверяет отсутствие
test.skip/fixme/fail; --list и итог 3 passed подтверждают полный состав.

### Проверки поведения

home.spec.ts открывает страницу и проверяет успешный HTTP-ответ и видимый h1
через getByRole. health.spec.ts содержит один тест с двумя GET и один с POST.
Request fixture не требует browser/page; никакой подмены Next.js или вызова
GET напрямую из импортированного обработчика нет.

constants.ts содержит используемые настройки и контрактные ожидания независимо
от src/. HTTP-коды, имена заголовков и тело извлекаются деструктуризацией.
JSON сравнивается целиком; Content-Type учитывает допустимый charset.
Прямые HTTP-запросы не следуют редиректам и доступны для проверки при статусе 405.
Согласованные ожидания находятся в контракте scenarios.

### Качество и воспроизводимость

tsconfig.json включает playwright.config.ts и tests/e2e/**/*.ts.
Отдельная команда typecheck сохраняется: Playwright не заменяет проверку типов.
ESLint и Prettier охватывают новые TypeScript-файлы; исключаются только их артефакты.
Границы существующих правил Spec Kit не расширяются.

В .gitattributes добавляются /playwright.config.ts text eol=lf и
/tests/e2e/** text eol=lf. В Git, Prettier и ESLint игнорируются
test-results/ и playwright-report/. Скриншоты, трассы и отчёты не коммитятся.

1. После отдельного разрешения сохранить состояние и хеши, подготовить manifest,
   npm scripts, параметры runner и общие тестовые определения.
2. Пользователь устанавливает зависимости и Chromium; агент проверяет их наличие.
3. Написать три постоянных теста согласованного поведения и включить новые файлы
   в quality-команды и правила игнорирования.
4. Подготовить README; подтвердить discovery и успешный полный прогон.
5. Выполнить контрольные ошибки, проверить процессы и итоговый успешный прогон.
6. Завершить анализ, соответствие спеке, предкоммитное ревью и verification.

Все шаги последовательны. Новая бизнес-логика или изменение серверного контракта
не входят в задачу; формального Red для уже существующей реализации нет.
Контрольное неверное ожидание доказывает работу теста, не подменяет TDD.
В следующих задачах новая логика сохраняет порядок Red → Green → Refactor.

## Verification

Протокол V01–V09 в runner задаёт команды, предосторожности временных правок
и ожидаемые результаты. Контрольная ошибка TypeScript также проверяет, что build
не пропускает неправильные типы в тестовых файлах.
Прерывание и освобождение процессов проверяются на Windows, не по документации.

Итог: успешные typecheck/lint/format:check, 3 passed, открываемый HTML-отчёт,
порт 3101 освобождён. Отчёт показывает факты, а не наличие файлов.
Passed/Failed/Blocked/NotRun различаются; текущие результаты V01–V09
находятся в verification.md и приёмочном чек-листе.

После проверок сравнить src/ и защищённые файлы с контрольным снимком,
просмотреть каждый diff и новый файл, git diff --check, локальные ссылки,
игнорирование артефактов и неизменность Git index. Удалить только собственный probe.
Тесты Spec Kit не повторяются без изменения их исполняемого комплекта.
