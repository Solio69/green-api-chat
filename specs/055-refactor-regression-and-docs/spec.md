## User Scenarios & Testing

### User Story 1 — Итоговая регрессия и документация проекта (Priority: P1)

Пользователь получает проверенное итоговое состояние и понятные инструкции, в которых объём завершения подтверждён результатами, а не наличием новых инструментов.

**Why this priority**: Это обязательная часть результата этапа R10; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Один полный финальный прогон после завершения правок; проверка ссылок и команд документации, сопоставление реестра и результатов CI. Если обязательный запуск заблокирован, задача остаётся незавершённой с указанной причиной.

**Acceptance Scenarios**:

1. **Given** завершены изменения и подготовлено окружение, **When** выполняется итоговый набор команд, **Then** каждая обязательная проверка имеет результат на итоговом состоянии.
2. **Given** разработчик впервые читает README, **When** он следует инструкциям тестирования, **Then** он видит необходимые зависимости и корректные команды для логики, React и браузера.
3. **Given** workflow ещё не опубликован, **When** оформляется итоговый отчёт, **Then** локальная готовность указана отдельно, успешный GitHub run не выдуман.
4. **Given** обязательная проверка не пройдена, **When** обновляется дорожная карта, **Then** соответствующая задача не отмечается завершённой и причина видна.

### Edge Cases

- Новый исходный код появился после итогового прогона.
- Локально нет установленного браузера или зависимости.
- CI проверял другую ревизию.
- Старый документ описывает SSE вместо текущего polling.

### Verification Approach

Один полный финальный прогон после завершения правок; проверка ссылок и команд документации, сопоставление реестра и результатов CI. Если обязательный запуск заблокирован, задача остаётся незавершённой с указанной причиной.

Это проверка состояния и документация. Новая бизнес-логика не реализуется. Результаты запусков фиксируются только после их выполнения; отсутствие готового окружения обозначается отдельно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации сейчас имеют статус **NotRun**: этот документ задаёт объём, а не подтверждает выполненный рефакторинг.

## Requirements

### Functional Requirements

- **FR-001**: Выполнить итоговые штатные проверки типов всех окружений, ESLint, Stylelint, Prettier, Vitest, оставшихся Playwright-наборов и production-сборки на одном идентифицируемом состоянии проекта.
- **FR-002**: Для каждого результата указать команду, режим и статус Passed/Failed/Blocked/NotRun; не переносить прошлый успешный результат на изменённое состояние без основания.
- **FR-003**: Сопоставить итоговую карту сценариев с исходной 028: каждая критическая гарантия имеет проверку либо явно указанное незакрытое замечание.
- **FR-004**: Актуализировать README и действующие документы об архитектуре, кодстайле и запуске: модули, public API, уровни тестов, команды, фиктивное окружение, CI и правила добавления новых проверок.
- **FR-005**: Сохранить исторические спецификации, но актуальные инструкции должны отражать HTTP polling из 027 и итоговую структуру; старые ссылки не должны вести читателя к несуществующей текущей реализации.
- **FR-006**: Разделить готовность локального workflow и подтверждённый запуск на GitHub: указать ссылку и ревизию успешного запуска либо явный непроверенный статус до публикации пользователем.
- **FR-007**: Обновить дорожную карту по фактической приёмке всех задач, перечислить оставшиеся ограничения и отдельные предложения; не объявлять полный рефакторинг завершённым при незакрытых обязательных проверках.
- **FR-008**: Проверить итоговый diff на непредусмотренные изменения, реальные реквизиты и временные файлы; Git-публикация, установка пакетов и действия во внешних системах остаются в рамках действующих разрешений.

### Scope Boundaries

- **В объёме**: Итоговая регрессия, действующая документация, сводка фактической готовности.
- **За пределами**: Автоматическая публикация Git, деплой, production-мониторинг, реальные сообщения и произвольные новые улучшения.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Проверки используют фиктивные данные; документы не содержат настоящих реквизитов. Пользователь сохраняет контроль над публикацией.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Итоговое состояние, результат проверки, карта покрытия, инструкция, статус этапа.

## Success Criteria

- **SC-001**: Все обязательные команды имеют достоверный результат и контекст; критические сценарии сопоставлены с исходной картой (FR-001, FR-002, FR-003).
- **SC-002**: Действующие документы и ссылки соответствуют итоговому коду и тестовым уровням (FR-004, FR-005).
- **SC-003**: Локальная и GitHub готовность различены, статусы этапов подтверждены, итоговый diff проверен (FR-006, FR-007, FR-008).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Подготовка спецификаций не включает commit, push или отправку реальных сообщений.
