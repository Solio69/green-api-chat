# Research: серверная отправка текста

**Дата**: 2026-10-02. **Этап**: техническая подготовка согласованной spec;
вся feature020 разрешена2026-10-02; HTTP интеграция с022/023 завершена.

## Проверенные факты

1. [SendMessage Telegram](https://green-api.com/telegram/docs/api/sending/SendMessage/)
   принимает chatId/message, добавляет текст в очередь и возвращает строковый
   idMessage. Документирован максимум 4096 символов; единица Unicode не названа.
   Успех не гарантирует доставку; дополнительный ключ идемпотентности не описан.
2. [Частота API](https://green-api.com/telegram/docs/api/ratelimiter/) задаёт
   SendMessage 50 запросов/сек на инстанс. Это иной предел, чем GetChatHistory
   и GetChats; искусственный лимит один запрос/сек для отправки не переносим.
3. [JavaScript String.length](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/length)
   считает UTF-16 code units; итератор строки считает code points. Это не подсчёт
   пользовательских grapheme clusters и не доказательство способа подсчёта GREEN-API.
4. Фактический проект: Node 24, Next 16.3.7, React 19.3.0, Query 5.104.0,
   iron-session 9.0.1. GetChats имеет один повтор 429; мутация SendMessage этот
   алгоритм не наследует. Авторизация/сессия и scope уже реализованы.
5. [Chat ID Telegram](https://green-api.com/telegram/docs/api/chat-id/) описывает
   положительный личный ID, отрицательные группы и legacy phone@c.us. Для проекта
   выбран подтверждённый chatId из GetChats(type:user)/CheckAccount, без отправки
   по телефонному alias. Shared validator 018 проверяет структуру непротиворечиво
   opaque контракту 014; это не отдельный server lookup существования получателя.

## Решения и альтернативы

| Решение                                           | Причина и альтернатива                                                                                                           | Практическое ограничение                                                            |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| POST /api/messages, cookie + scope + X-Chat-Owner | Один серверный контракт; server action теснее связывает форму с Next и усложняет независимый HTTP-тест                           | Proof принадлежит 022/023, не клиентскому tabId                                     |
| Одна локальная отправка в runtime инстанса        | Browser disabled сам по себе не защищает вторую вкладку или повтор HTTP                                                          | Не означает exactly-once или отмену удалённого сообщения                            |
| Один fetch, deadline 10 секунд, redirect:error    | Сохраняет обычный provider timeout, не переиспользует retry читающего метода                                                     | После dispatch timeout/5xx/непонятный 200 — неопределённый исход                    |
| Локальный счётчик 4096 code points                | Array.from(message).length не режет surrogate-pair emoji пополам; UTF-16 счётчик неоправданно уменьшает доступную длину          | Это правило счётчика приложения; provider может отказать в Unicode-граничном случае |
| Bounded JSON body 64 KiB только для отправки      | 4096 astral code points в JSON с двумя escaped UTF-16 units требуют до 49152 байт плюс поля; нынешние auth 8192 байт не подходят | Больший предел не применяется глобально ко входу/поиску                             |
| attemptId UUID только корреляция                  | Поздний ответ связывается с локальной попыткой без текста; ID не пересылается поставщику как несуществующий idempotency key      | Повтор запроса с тем же ID после settlement не гарантированно подавлен              |

Текст не обрезается и не нормализуется; trim используется только для запрета
whitespace-only. В textarea не вводится UTF-16 maxLength, противоречащий выбранному
счётчику. Расхождение с provider length остаётся безопасным однозначным отказом
валидации, если такой отказ получен; реальных пробных сообщений агент не отправляет.

## Авторизация и отмена

Cookie POST требует matching Origin(request.url.origin) до body/lease/effects;
missing/null/invalid/foreign возвращает 403 invalid_request/not_sent, не logout.
Это same-origin guard 023, без изменения existing auth/chats API и без доверия
произвольным forwarded headers. JSON media type и HttpOnly-cookie не заменяют guard.

Cookie и scope проверяются до внешнего вызова. Current owner capability и
attached SSE проверяет tryAcquireSend из 022; ключ реестра — инстанс, не scope.
Вторая попытка отвергается, а не ставится в очередь. Текущий замок сохраняется
до settlement локального upstream даже при закрытии вкладки или смене owner.
Сигнал браузера после dispatch не используется как доказательство отмены: сервер
дожидается ответа/10-секундного deadline и освобождает lock в finally.

Нет дополнительных запросов GetStateInstance/GetChats перед каждым SendMessage:
сессия и owner проверяются локально; реальный отказ поставщика обрабатывается по
существующей классификации авторизации. Временная ошибка не уничтожает cookie.

Новый чистый safe-identifier 020 не prerequisite 019/022: они используют прежний
privacy pattern 014 и не импортируют будущие sending-файлы, сохраняя DAG.

## Ошибка и неопределённый исход

До dispatch отказ имеет outcome:not_sent. Подтверждённые provider 400 validation,
401/403 и 429 классифицируются без повтора. После dispatch транспортный разрыв,
5xx, неизвестный протокол, redirect и 200 без пригодного idMessage имеют
outcome:unknown: отсутствие доставки не доказано. Ошибка cookie cleanup после
provider отказа не меняет фактическую степень уверенности в результате отправки.
Непойманная ошибка после dispatch консервативно возвращает unknown.

Окончательные status/code/outcome и безопасные ответы определены в
[API-контракте](contracts/send-api.md); уточнение HTTP-кода не заменяет смысл outcome.

## Необходимые действия и пределы

Новых пакетов, БД и миграций нет. Для автоматических проверок достаточно
существующих Playwright integration/E2E и fake provider. Настройка реального
инстанса и ручная отправка выполняются только пользователем; деплой здесь не
выбирается. Состояние после рестарта не восстанавливается собственным хранилищем.
