# Feature Specification: Серверная отправка текстового сообщения

**Feature Directory**: specs/020-send-message-api
**Created**: 2026-10-02
**Status**: Approved — спецификация согласована
**User Approval**: Согласована пользователем 2026-10-02 в составе 018–025
**Workflow Mode**: Standard
**Implementation Authorization**: CodeNotAuthorized
**Verification Status**: NotRun — код и исполняемые тесты не входят в текущий этап
**Input**: Подготовить отдельный серверный шаг отправки текста через SendMessage
в Telegram, сохранив зашифрованную HttpOnly-cookie и изоляцию подключений.

## User Scenarios & Testing

### User Story 1 — Получить подтверждение принятия текста API (Priority: P1)

Пользователь отправляет текст выбранному личному получателю через приложение,
не передавая реквизиты GREEN-API клиентскому JavaScript.

**Why this priority**: Серверный контракт нужен до соединения формы с отправкой.
**Independent Test**: После отдельного разрешения на код проверить серверную
границу с фиктивным поставщиком, не отправляя настоящие сообщения.

**Acceptance Scenarios**:

1. **Given** действующая сессия, её scope и корректный текст для личного chatId,
   **When** поступает запрос отправки, **Then** сервер вызывает SendMessage с
   реквизитами сессии и возвращает подтверждённый idMessage, chatId и scope.
2. **Given** ответ поставщика с idMessage, **When** сервер формирует результат,
   **Then** он означает принятие сообщения API; доставка и прочтение не заявляются.
3. **Given** истёкшая сессия либо запрос старого scope после смены подключения,
   **When** поступает отправка, **Then** она отклоняется до вызова GREEN-API.
4. **Given** вкладка не является рабочей вкладкой этого подключения либо другая
   отправка ещё выполняется, **When** запрошена отправка, **Then** внешняя
   отправка не начинается. Механизм владения вкладкой определяют 022/023.

### User Story 2 — Различать отказ и неопределённый результат (Priority: P1)

Потребитель получает понятный результат ошибки, чтобы не отправить второй текст
автоматически после потери ответа на первый запрос.

**Why this priority**: Отправка имеет внешний эффект; повтор может создать дубль.
**Independent Test**: Проверить отсутствие повторного вызова поставщика при
тайм-ауте, разрыве сети и неподтверждённом ответе; классификация ошибок
уточняется в техническом контракте в пределах требований ниже.

**Acceptance Scenarios**:

1. **Given** пустой, состоящий только из пробелов или неподдерживаемый запрос,
   **When** выполняется валидация, **Then** API поставщика не вызывается.
2. **Given** поставщик однозначно отказал в отправке,
   **When** сервер получает такой ответ, **Then** возвращается безопасная ошибка
   без реквизитов и сырого ответа поставщика.
3. **Given** запрос мог быть принят, но подтверждение не получено,
   **When** соединение обрывается, **Then** не заявляется ни успешная доставка,
   ни доказанный факт отсутствия сообщения; автоматический повтор не выполняется.
4. **Given** неопределённый результат,
   **When** клиент показывает действие пользователя,
   **Then** сначала предлагается проверить историю; повтор остаётся ручным с
   предупреждением о возможном дубле. Отсутствие текста в истории не доказывает
   отсутствие отправки, совпадение текста не доказывает принадлежность попытке.

### Edge Cases

- Строка с переносами и Unicode; лимит поставщика — 4096 символов. Его точная
  единица подсчёта Unicode не документирована на странице метода и требует
  технической проверки при подготовке контракта, не нового продуктового gate.
- Неподдерживаемый групповой chatId, некорректный JSON, неверные типы полей.
- HTTP 200 без пригодного idMessage не подтверждает успешное принятие.
- HTTP 200 с idMessage может позднее сопровождаться статусом failed; это не
  меняет факт принятия запроса API и обрабатывается отдельной задачей статусов.
- Два отдельных корректных запроса одинакового текста не считаются одним
  действием без согласованного механизма идемпотентности.
- Разрыв соединения браузера и выход после начала запроса не гарантируют отмену
  уже принятого поставщиком сообщения. Поздний результат сохраняет старый scope.
- Ошибки авторизации и временные ошибки различаются; временный сбой не означает
  недействительность cookie. Детали следуют существующим контрактам сессии.

### Verification Approach

После согласования спецификации и отдельного разрешения на код — TDD
Red → Green → Refactor для серверной валидации, вызова поставщика, классификации
ответов, изоляции scope и отсутствия повторной отправки. HTTP integration/E2E
проверяют cookie, отсутствие секретов и единственный внешний вызов на попытку.
Сценарии и команды уточняются в будущих plan/tasks. Сейчас тесты не создаются и
не запускаются; ревью текста не является проверкой работающего API.

## Requirements

### Functional Requirements

- **FR-001**: Сервер использует SendMessage для отправки текста в личный Telegram
  chatId; реквизиты получает только из действующей серверной сессии.
- **FR-002**: Запрос привязан к connectionScope. Отсутствующая сессия и чужой
  scope отклоняются до внешнего эффекта; несовпадение scope не удаляет действующую
  cookie. Результат остаётся связан с исходным подключением и chatId.
- **FR-003**: Обязательные данные — chatId и текст сообщения. Пустое либо
  состоящее только из пробелов содержимое не отправляется. Максимум поставщика —
  4096 символов; конкретный подсчёт проверяется на техническом этапе. Непустой
  допустимый исходный текст передаётся без изменения пробелов и переносов.
- **FR-004**: Подтверждённый успех содержит валидный idMessage и означает
  принятие API, без утверждения delivered/read.
- **FR-005**: Клиент не получает apiTokenInstance, idInstance, upstream URL с
  реквизитами или сырой ответ поставщика; тексты ошибок безопасны и на русском.
- **FR-006**: Не вводить автоматическую повторную отправку после неопределённого
  сетевого результата. Читающий запрос GetChats и мутация SendMessage не обязаны
  иметь одинаковую retry-политику.
- **FR-007**: Контракт различает невалидный запрос, недоступную сессию, смену
  подключения, подтверждённый отказ и неопределённый исход. Конкретные коды и
  сообщения определяются будущим техническим контрактом; неизвестный исход не
  выдаётся за гарантированное отсутствие сообщения. Сначала предлагается
  проверить историю, повтор остаётся ручным с предупреждением о возможном дубле.
  Нельзя доказывать исход отсутствием текста в окне истории или угадывать связь
  сообщения с попыткой по одному совпадению текста.
- **FR-008**: Результат пригоден для сопоставления с историей и уведомлениями по
  connectionScope + chatId + idMessage, включая случай уведомления до HTTP-ответа.
- **FR-009**: Серверный шаг не меняет список и UI самостоятельно; его соединение
  с Query и формой принадлежит задаче 021. Очередь Receive/Delete и SSE ему не
  принадлежат.
- **FR-010**: На подключение разрешена одна отправка за раз, только из единственной
  рабочей вкладки. Вторая вкладка показывает ограничение и не может отправлять.
  Контроль рабочей вкладки принадлежит 022/023; способ серверной проверки и
  предотвращения перекрывающихся отправок определяется будущим планом без
  введения несогласованного API.

### Scope Boundaries

- В объёме: серверная текстовая отправка, проверка запроса, сессия и scope,
  подтверждение принятия, безопасные ошибки без автоматического повтора.
- За пределами: форма, стили, вложения, цитирование, группы, уведомления набора,
  массовая отправка, очередь отложенной отправки приложения, БД, browser storage,
  серверная идемпотентность между рестартами и обещание exactly-once.
- Уведомления delivered/read/failed и их объединение определяются отдельной
  спекой уведомлений; сервер отправки не имитирует эти события.

### Data Effects & User Decision

- **Changed data**: Отправка создаёт внешнее сообщение через очередь GREEN-API.
  Это не только изменение локального состояния; своя БД не создаётся.
- **Preview**: Текст и выбранный получатель видны в будущей форме 021.
- **Confirmation**: Явная отправка пользователем; дополнительный диалог для
  каждой обычной отправки не вводится.
- **Cancellation**: Отмена HTTP-запроса не является подтверждением отмены
  внешнего сообщения. При неопределённом исходе сначала предлагается история;
  повтор остаётся ручным с предупреждением о возможном дубле.
- **Idempotency and duplicates**: Публичная страница SendMessage не описывает
  ключ идемпотентности. Это не доказательство поддержки безопасного повторения.
  Нельзя обещать подавление одинаковых отдельных отправок на стороне поставщика.
- **Failure result**: Необработанный сетевой исход не должен становиться
  доказанным отказом. Сначала предлагается проверить историю; введённый текст
  сохраняется, если пользователь остаётся в исходном открытом чате. Ручной
  повтор предупреждает о возможном дубле, автоматического повтора нет.

### Key Entities

- **Send attempt**: connectionScope, chatId, исходный текст и результат текущего
  действия; хранение попыток в БД не требуется и не согласовано.
- **Accepted message**: Подтверждённый idMessage в исходном scope и чате;
  фактические статус и время поступают из соответствующих источников.

## Success Criteria

- **SC-001**: Корректная попытка вызывает ровно один SendMessage и возвращает
  подтверждённый idMessage исходного подключения и получателя (FR-001/002/004).
- **SC-002**: Невалидные данные, отсутствие сессии и чужой scope вызывают ноль
  SendMessage (FR-002/003).
- **SC-003**: Все предусмотренные ошибки не раскрывают секреты; неопределённый
  исход вызывает ноль автоматических повторов и не заявляет доставку (FR-005/007).
- **SC-004**: Успешный HTTP-ответ не создаёт delivered/read без события или
  фактических данных истории (FR-004/008).
- **SC-005**: Нерабочая вкладка и попытка второй отправки при текущей незавершённой
  не вызывают новый SendMessage (FR-010).

## Assumptions and Dependencies

- Telegram text-only и React заданы тестовым заданием и согласованным проектом.
- Существующая сессия — зашифрованная HttpOnly-cookie; Next.js работает в одном
  постоянном Node-процессе. Новая инфраструктура и пакеты не вводятся.
- Изоляция provider/lifecycle/scope уже определена в
  [014 Query contract](../014-chat-list-query/contracts/query-layer.md).
- Существующие пользовательские требования —
  [UI-011, UI-017, UI-019–021](../../docs/chat-ui-spec.md).
- Получение через ReceiveNotification → Next.js → SSE — отдельный слой.
- Единственная рабочая вкладка и её ограничения определяются 022/023; отправка
  использует этот же факт владения рабочим чатом, не заводит независимый выбор
  вкладки. Механизм идентификации относится к техническому планированию.
- [Общий контракт пласта](../../docs/messaging-specs.md) определяет границы
  истории, отправки и получения, общую идентичность и обработку гонок. Отправка
  не создаёт независимый кэш сообщений и не присваивает роль очереди уведомлений.
- Эта спецификация разрешает только обсуждение и документацию; ни её наличие,
  ни согласование общего пласта не разрешают писать код.

## Продуктовые решения

Существенных открытых продуктовых вопросов по этому шагу нет. Пользователь
2026-10-02 подтвердил ручной повтор с предупреждением после предложения проверить
историю и отправку исходного текста без изменения пробелов/переносов. Требования
включены в согласованный пользователем 2026-10-02 полный текст спецификации.

## Вопросы технического исследования

- Единицу длины Unicode надо проверить до технического контракта, не выдавая
  догадку за ограничение API. Точные DTO, ошибки и порядок применения данных
  определяются последующим планированием в пределах утверждённых требований,
  а не создают дополнительное продуктовое согласование сами по себе.
