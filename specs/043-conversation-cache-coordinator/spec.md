## User Scenarios & Testing

### User Story 1 — Единое применение событий к кешу переписки (Priority: P1)

История, отправка и уведомления применяются к состоянию переписки в определённом месте, а количество React-потребителей не умножает побочные действия.

**Why this priority**: Это обязательная часть результата этапа R07; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Integration-тесты Vitest с настоящим QueryClient и управляемыми завершениями; React Testing Library с двумя потребителями; Playwright для сквозного получения и ручного восстановления истории.

**Acceptance Scenarios**:

1. **Given** панель и редактор читают историю одного чата, **When** запрос завершается, **Then** содержимое применяется один раз, оба потребителя видят одинаковое состояние.
2. **Given** история ожидает ответ и пришло live-сообщение, **When** затем завершается история, **Then** live-факт и подтверждённый статус сохраняются без дублей.
3. **Given** получено входящее неизвестного чата, **When** координатор применяет его, **Then** сообщение, временная запись чата и unread согласованы до ACK.
4. **Given** пользователь повторно выбирает тот же чат, **When** открытие обработано, **Then** выполняется новая проверка последних 10 сообщений с сохранением накопленной модели.

### Edge Cases

- Два одновременно смонтированных читателя состояния.
- Пустая успешная история и история с ошибкой.
- Повторный ACK, повторная доставка и прерванное применение.
- Ручной refetch одновременно с recovery.

### Verification Approach

Integration-тесты Vitest с настоящим QueryClient и управляемыми завершениями; React Testing Library с двумя потребителями; Playwright для сквозного получения и ручного восстановления истории.

Для сохранения поведения используются исходная карта 028 и подтверждённые регрессионные проверки. Искусственный Red для перемещения кода не требуется. Новая или изменяемая бизнес-логика, включая согласованные защиты от гонок, выполняется через Red → Green → Refactor после разрешения реализации. Обнаруженное расхождение с текущим контрактом сначала фиксируется, а не исправляется незаметно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации имеют статус **NotRun**; фактические результаты будут приведены в verification.md.

## Requirements

### Functional Requirements

- **FR-001**: Выделить прикладной координатор применения проверенных событий истории, принятой отправки и уведомлений; чистые преобразования использует модель 042.
- **FR-002**: Убрать применение истории из отдельных подписок каждого потребителя useChatHistory. Одно завершение запроса применяется независимо от числа смонтированных компонентов.
- **FR-003**: Согласованно обновлять сообщения, статусные проблемы, факты неизвестного чата и unread в рамках одной принятой операции, сохраняя обработку повторной доставки.
- **FR-004**: Разделить команду обновления истории, состояние запроса и чтение готовой модели; компоненты не следят за внутренними счётчиками обновления Query Cache ради бизнес-действий.
- **FR-005**: Сохранить свежий запрос последних 10 сообщений при каждом открытии, включая повторный выбор того же чата, и сохранение накопленных сообщений при временной ошибке.
- **FR-006**: Проверять scope, принадлежность чату и активность сеанса при применении; поздний результат старого обращения не подменяет новую выбранную переписку.
- **FR-007**: Сохранить порядок apply-before-ACK и подтверждать обработку только после успешного применения или осознанного пропуска события.
- **FR-008**: Сохранить ручную проверку истории после unknown отправки и восстановление истории при recovery подключения.

### Scope Boundaries

- **В объёме**: Прикладное применение событий, query-команды и read-хуки, соединение с отправкой и уведомлениями.
- **За пределами**: Замена TanStack Query, пагинация, изменение unread-семантики и новая сортировка чатов.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Меняется путь записи в память подключения. Сетевые контракты и пользовательское поведение сохраняются.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Событие переписки, координатор, состояние запроса, кеш сообщений, проекции чатов и unread.

## Success Criteria

- **SC-001**: Тест двух потребителей подтверждает одно применение истории и отсутствие лишних побочных действий (FR-001, FR-002, FR-004).
- **SC-002**: Гонки history/live/send и повторы дают согласованную модель во всех связанных проекциях (FR-003, FR-005, FR-006).
- **SC-003**: ACK, ручная проверка unknown и recovery сохраняют прежнюю последовательность и результат (FR-007, FR-008).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Пользователь разрешил этому чату commit/push в refactor после полного цикла; отправка реальных сообщений в тестах не используется.
