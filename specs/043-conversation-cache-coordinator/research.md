# Research 043: координатор кеша переписки

Дата: 2026-10-03. Исходники: `use-chat-history.ts`, `message-cache.ts`, `apply-notification.ts`, `create-send-controller.ts`, session-chat/unread cache, `fetch-history.ts`, `create-query-session.ts`; 29/29 целевых integration baseline. CI 042 проверяется отдельно. Новых пакетов и HTTP контрактов нет.

## Факты

`useChatHistory` вызывается панелью, редактором и тестовыми потребителями. Каждый hook подписывается на один Query Cache key и на `dataUpdateCount`, затем вызывает `applyHistoryMessages` и `publishMessageIssues`. TanStack Query дедуплицирует сам запрос, но не эти подписки: одно завершение вызывает несколько merge/cache-write, включая повторную публикацию проблемы. Кеш сообщений уже отдельно хранится по `(connectionScope, chatId)` и переживает observer teardown; request key содержит `accessId`, поэтому повторное открытие того же чата даёт новую проверку. `fetchHistory` валидирует scope, chatId, DTO и abort после async JSON. `applyMessageFacts` валидирует вход до записи и сохраняет статусные факты. `applyNotification` последовательно записывает сообщение, временный чат и unread, затем возвращает `true` для ACK. Принятая отправка записывает сообщение и временный чат после проверки owner context.

## Варианты

| Вариант | Преимущества | Риск/цена | Выбор |
| --- | --- | --- | --- |
| Применять результат истории внутри общего `queryFn`; остальные source-specific записи объединить одним координатором с явными командами, оставив совместимые adapters | Один fetch = одно применение, UI остаётся read-only, Query владеет запросом, существующие cache helpers сохраняются | Нужно внимательно проверить abort/смену доступа и порядок before-ACK | Выбран |
| Подписка QueryCache один раз на сессию | Централизация событий | Сложная фильтрация query state/count и жизненный цикл подписки, риск повторов при remount | Отклонён |
| Оставить подписку только у панели | Малый diff | Побочный эффект снова зависит от наличия панели и её mount order, не решает владение | Отклонён |

`queryFn` — единственное место применения ответа конкретного сетевого запроса; после `fetchHistory` проверяются `signal` и `session.isActive()`, затем выполняются merge и публикация issue до успешного возврата. Актуальность доступа обеспечивает ключ с accessId и отмена Query при смене наблюдаемого ключа. При ошибке или отмене накопленная модель не меняется. Координатор применяет accepted/incoming/status, группирует cache уведомления через `notifyManager.batch`; предварительные валидаторы выполняются до записи. Не обещаем транзакцию с rollback между несколькими Query key; цель — синхронная согласованная операция и отсутствие частичной записи на невалидном входе. `refreshChats` остаётся после успешного применения и не задерживает ACK сетевым запросом. Порядок fetch/merge/live и repeat/recovery подтверждается Query/production E2E.
