## User Scenarios & Testing

### User Story 1 — Единый серверный контекст сессии (Priority: P1)

Серверные обработчики получают проверенный контекст подключения из одного места, а отправка сообщений больше не зависит от модуля уведомлений ради чтения сессии.

**Why this priority**: Это обязательная часть результата этапа R05; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Vitest проверяет решения и зависимости контекста, Playwright HTTP/E2E подтверждает реальные cookie и маршруты. Production build проверяет server-only границы. Поведение сравнивается с реестром 028.

**Acceptance Scenarios**:

1. **Given** запрос содержит действительную cookie, **When** любой защищённый обработчик получает контекст, **Then** он получает тот же scope и проверенные реквизиты без повторной собственной реализации.
2. **Given** сессия истекла или секрет окружения отсутствует, **When** контекст прочитан, **Then** результаты различимы и обработчик возвращает прежний контракт ошибки.
3. **Given** два запроса имеют разные cookie, **When** обработчики выполняются независимо, **Then** контекст одного запроса недоступен другому, а ответы не содержат реквизитов.

### Edge Cases

- Повреждённая cookie и нечисловой срок действия.
- Server Component и Route Handler имеют разные права записи cookie.
- GET списка и POST уведомлений сохраняют свои политики ошибок.
- Параллельные запросы разных подключений.

### Verification Approach

Vitest проверяет решения и зависимости контекста, Playwright HTTP/E2E подтверждает реальные cookie и маршруты. Production build проверяет server-only границы. Поведение сравнивается с реестром 028.

Для сохранения поведения используются исходная карта 028 и подтверждённые регрессионные проверки. Искусственный Red для перемещения кода не требуется. Новая или изменяемая бизнес-логика, включая согласованные защиты от гонок, выполняется через Red → Green → Refactor после разрешения реализации. Обнаруженное расхождение с текущим контрактом сначала фиксируется, а не исправляется незаметно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации сейчас **NotRun**; результаты будут в verification.md.

## Requirements

### Functional Requirements

- **FR-001**: Выделить общий серверный модуль чтения сессии с явным результатом: окружение не настроено, действительной сессии нет или доступен авторизованный контекст.
- **FR-002**: Сосредоточить чтение cookie, проверку срока действия и получение connectionScope; сохранить действующую привязку scope к реквизитам и сроку сессии.
- **FR-003**: Передавать потребителям только необходимые данные. Секрет подписи ACK доступен только соответствующему серверному коду и не сериализуется в HTTP-ответы или клиентские props.
- **FR-004**: Перевести защищённые обработчики поиска получателя, чатов, истории, отправки и уведомлений, а также чтение сессии страницами на общий контекст; сохранить различия в статусах ошибок, перенаправлениях и завершении сессии.
- **FR-005**: Отделить чтение сессии от её удаления, чтобы чтение в Server Component не выполняло недопустимую запись cookie; контекст не сохраняется глобально между запросами.
- **FR-006**: Сохранить тестируемость через зависимости и проверить серверную границу на уровне сборки. Чистые типы не должны требовать импорта серверного runtime.
- **FR-007**: Удалить ставшее ненужным дублирование после перевода потребителей; вход и создание сессии сохраняют свою отдельную операцию.

### Scope Boundaries

- **В объёме**: Серверное чтение и типы контекста, перевод существующих потребителей, контрактные тесты.
- **За пределами**: Новая схема авторизации, изменение cookie, сроков, HTTP-статусов или модели хранения сессий.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Меняется организация серверных файлов. Сессионные данные и протоколы совместимы с текущей реализацией.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Авторизованный контекст, состояние конфигурации, connectionScope, операция удаления cookie.

## Success Criteria

- **SC-001**: Во всех целевых обработчиках единый источник контекста и нет зависимости отправки от notifications ради сессии (FR-001, FR-002, FR-004, FR-007).
- **SC-002**: Контрактные тесты различают отсутствие конфигурации, отсутствие сессии и действительный доступ (FR-001, FR-004).
- **SC-003**: Проверены изоляция запросов, граница секрета и отсутствие записи cookie из чтения страницы (FR-003, FR-005, FR-006).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Пользователь разрешил этому чату review, commit и push в refactor. Чужие изменения сохраняются; реальные сообщения не отправляются.
