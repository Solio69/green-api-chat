## User Scenarios & Testing

### User Story 1 — Проверка асинхронного кода линтером с типами (Priority: P1)

Разработчик автоматически замечает потерянные Promise и неверные асинхронные обработчики в приложении и тестах.

**Why this priority**: Это обязательная часть результата этапа R02; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Проверить ESLint на временных примерах, затем lint всего применимого кода и тесты затронутой асинхронной логики. Новое поведение, если оно потребуется, выделяется и проходит TDD.

**Acceptance Scenarios**:

1. **Given** Promise потерян без обработки, **When** запущен ESLint, **Then** возникает диагностическое сообщение ожидаемого правила.
2. **Given** операция корректно ожидается или имеет обоснованный обработчик ошибки, **When** запущен ESLint, **Then** допустимый пример проходит.
3. **Given** исправление замечания могло изменить порядок действий, **When** проверяется затронутый сценарий, **Then** наблюдаемые порядок завершения и обработка ошибки соответствуют прежнему контракту.

### Edge Cases

- React event handlers с асинхронной работой.
- Асинхронные cleanup и Promise.finally.
- Тестовые колбэки и сигнатуры сторонних библиотек.

### Verification Approach

Проверить ESLint на временных примерах, затем lint всего применимого кода и тесты затронутой асинхронной логики. Новое поведение, если оно потребуется, выделяется и проходит TDD.

Проверяется действующая конфигурация: успешный штатный сценарий и контролируемый нарушающий пример должны дать ожидаемый результат. Ошибка установки или импорта не считается подтверждением TDD. Если выяснится, что требуется изменить бизнес-логику, такая часть выполняется по согласованному контракту через Red → Green → Refactor.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Приёмочные проверки реализации сейчас имеют статус **NotRun**: этот документ задаёт объём, а не подтверждает выполненный рефакторинг.

## Requirements

### Functional Requirements

- **FR-001**: Подключить информацию TypeScript к lint для всех применимых TS/TSX-файлов приложения и тестов, сохранив работоспособность JS-конфигураций.
- **FR-002**: Включить проверки необработанных Promise и некорректного использования Promise в синхронных контрактах; совместимые зависимости и конфигурацию определить в плане.
- **FR-003**: Для каждого нового правила проверить ошибочный пример, допустимый пример и предусмотренные исключения на действующем проектном конфиге.
- **FR-004**: Просмотреть найденные нарушения во всех применимых файлах. Сохранить ожидание завершения, обработку ошибок и намеренные fire-and-forget операции; простое добавление void не считается доказательством безопасности.
- **FR-005**: Не отключать правило глобально ради прохождения; необходимое узкое исключение сопровождать объяснением контрактной причины.
- **FR-006**: Обновить карту исполняемых правил и команды; сохранить разделение между линтером, Prettier и Stylelint. Изменение пользовательских соглашений по стилю не входит в задачу.

### Scope Boundaries

- **В объёме**: Два вида проверок Promise, конфигурация, необходимые локальные исправления и документация.
- **За пределами**: Полный набор строгих правил без разбора пользы, смена форматтера и изменение требований к стилю.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Меняется конфигурация и затронутый код; поведение сохраняется и проверяется по риску каждого исправления.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Правило ESLint, диагностическое сообщение, допустимое исключение, асинхронный контракт.

## Success Criteria

- **SC-001**: Каждое включённое правило доказано положительным и отрицательным примером (FR-001–FR-003).
- **SC-002**: Штатный lint проходит без скрытия нарушений; затронутые асинхронные сценарии проходят регрессию (FR-004, FR-005).
- **SC-003**: Документация соответствует реально включённым правилам (FR-006).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Подготовка спецификаций не включает commit, push или отправку реальных сообщений.
