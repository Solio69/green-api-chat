## User Scenarios & Testing

### User Story 1 — Перенос авторизации в функциональный модуль (Priority: P1)

Авторизация становится первым завершённым примером нового модуля, сохраняя вход, защищённую главную страницу и выход.

**Why this priority**: Это обязательная часть результата этапа R04; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Проверить module imports, typecheck и production build; выполнить серверные тесты сессии и браузерные сценарии входа/выхода. Для чистого переноса искусственный Red не требуется.

**Acceptance Scenarios**:

1. **Given** нет действующей сессии, **When** пользователь открывает защищённую страницу, **Then** он попадает на существующую форму входа.
2. **Given** провайдер временно недоступен при проверке доступа, **When** страница проверяет текущую сессию, **Then** пользователь видит существующее восстановление, сессия не теряется.
3. **Given** пользователь вошёл, **When** он выходит, **Then** cookie этого браузера удаляется, клиентский кеш закрывается и защищённая страница требует вход.

### Edge Cases

- Неверный или отсутствующий SESSION_PASSWORD.
- Истёкшая и повреждённая cookie.
- Поздний результат после выхода.
- Другие браузеры и устройства сохраняют собственные сессии.

### Verification Approach

Проверить module imports, typecheck и production build; выполнить серверные тесты сессии и браузерные сценарии входа/выхода. Для чистого переноса искусственный Red не требуется.

Для сохранения поведения используются исходная карта 028 и подтверждённые регрессионные проверки. Искусственный Red для перемещения кода не требуется. Новая или изменяемая бизнес-логика, включая согласованные защиты от гонок, выполняется через Red → Green → Refactor после разрешения реализации. Обнаруженное расхождение с текущим контрактом сначала фиксируется, а не исправляется незаметно.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Фактические проверки после переноса записаны в verification.md; этот документ задаёт контракт реализации.

## Requirements

### Functional Requirements

- **FR-001**: Перенести принадлежащие авторизации файлы по карте 035, сохранив имена маршрутов Next.js и публичные HTTP-контракты.
- **FR-002**: Разделить доступ к cookie и секрету, чистые решения проверки доступа и клиентские элементы авторизации; клиентские импорты не включают серверные реквизиты.
- **FR-003**: Сохранить срок сессии 24 часа, HttpOnly, SameSite и production Secure, а также существующие условия завершения и сохранения сессии.
- **FR-004**: Сохранить поведение успешного входа, временного отказа GREEN-API, потери доступа, ручного выхода и очистки Query-подключения.
- **FR-005**: Обновить импорты приложения и тестов через публичные входы модуля; переходные экспорты допустимы только по карте 035.
- **FR-006**: Оставить отделение поведения LoginForm задаче 045 и обобщение серверного контекста задаче 037, чтобы перенос файлов не смешивался с изменением логики.

### Scope Boundaries

- **В объёме**: Структурный перенос авторизации и связанных тестовых импортов с сохранением контрактов.
- **За пределами**: Изменение дизайна формы, политика длительности сессий, дополнительные способы входа и обобщение всей серверной обвязки.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Меняются пути исходников и тестов. Формат cookie, сетевые контракты и пользовательские данные остаются совместимыми.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и подготовка комплекта спецификаций. Детализация и разрешение реализации учитываются по действующему процессу и переписке; уже полученное разрешение повторно не запрашивается. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Модуль авторизации, зашифрованная cookie, безопасное состояние доступа, клиентский Query-сеанс.

## Success Criteria

- **SC-001**: Все файлы пилотного модуля соответствуют карте 035 и сборка не содержит неверных серверно-клиентских импортов (FR-001, FR-002, FR-005).
- **SC-002**: Регрессия входа, проверки доступа и выхода проходит с прежними cookie-атрибутами (FR-003, FR-004).
- **SC-003**: Diff отделяет перенос от дальнейшей переработки формы и серверного контекста (FR-006).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Пользователь разрешил этому чату review, commit и push в refactor. Чужие изменения сохраняются; реальные сообщения не отправляются.
