## Summary

Собрать смысловые соглашения в одном `docs/CODING_RULES.md` с короткими положительными и отрицательными примерами. Оставить `docs/CODE_STYLE.md` короткой картой действующих конфигураций и ручных правил, чтобы существующие ссылки работали. Согласовать проектные настройки VS Code с Prettier и ESLint: форматирование на сохранении, отсутствие конкурирующего `organizeImports`. Ручную проверку свежего сеанса редактора отделить от CLI.

## Technical Context

Действуют ESLint, Prettier и проектный `prettier.config.mjs` с `semi: false`; Stylelint завершает отдельная задача 011. У пользователя VS Code автосохранение, Prettier, ESLint fixAll и встроенный organizeImports. Лог расширения Prettier показал прежнее состояние конфигурации; это требует обновления окна и наблюдения, но не доказывает внутреннюю причину кеширования. Глобальные настройки не меняются. Продуктовый код, API и БД не затрагиваются.

## Research and Design

- [research.md](research.md) содержит исходные факты, варианты и официальные источники VS Code/Prettier.
- [quickstart.md](quickstart.md) описывает проверки и одноразовое обновление окна редактора.
- `data-model.md` и `contracts/` не применяются: пользовательские данные и API не меняются.
- `docs/CODING_RULES.md` содержит смысловые соглашения с областью действия, «так / не так» и исключениями: структура собственных компонентов и публичный index; именованные обработчики над return; объект для нескольких параметров; осмысленные логические константы для длинных условий; короткие if и стрелочные функции; безопасное условное `&&`; размещение общих констант; тестовые фикстуры и независимые ожидания; доступность, секреты; SCSS Modules, БЭМ, токены и миксины.
- Исполняемые правила форматирования, импортов и типизации остаются в ESLint/Prettier/Stylelint. Документ не копирует их полные определения и не утверждает, что ручные нормы проверяет линтер.
- `docs/CODE_STYLE.md` остаётся на том же пути как краткая карта ссылок; действующие процессные инструкции `AGENTS.md` сохраняются. Повторяющиеся смысловые нормы из AGENTS переносятся в новый документ, а AGENTS прямо ссылается на него.
- `.vscode/settings.json` задаёт проектный Prettier и formatOnSave, сохраняет ESLint fixAll, выключает встроенный organizeImports. Конфиг Prettier не переименовывается и остаётся источником `semi: false`.

## Tasks and Dependencies

1. Дождаться завершения 011; зафиксировать актуальный diff и содержание `AGENTS.md`, `CODE_STYLE.md`, конституции, ESLint/Prettier/Stylelint.
2. Составить матрицу каждого смыслового правила из текущих инструкций и согласований; записать его один раз в `CODING_RULES.md` с примером и исключением.
3. Сократить `CODE_STYLE.md` до навигационной карты, обновить ссылки в AGENTS/конституции/README, не нарушив процессные правила.
4. Добавить `.vscode/settings.json`; проверить синтаксис, приоритет настроек и отсутствие конкурирующего organizeImports. Объяснить обновление окна VS Code.
5. Провести read-only сверку ссылок, полноты правил и итоговые CLI-проверки; попросить пользователя вручную подтвердить результат сохранения файла в свежем сеансе VS Code, если нельзя наблюдать редактор. Выполнить предкоммитное ревью, сохранить `verification.md`.

Бизнес-логика и серверные контракты не меняются; искусственный TDD Red не нужен. Новое ручное правило применяется к новому или затронутому коду, существующий продуктовый код массово не переписывается.

## Verification

- Матрица FR-002 покрыта документом; каждая смысловая норма имеет один действующий источник, корректные примеры и исключения. Ссылки из AGENTS, CODE_STYLE, конституции и README разрешаются.
- Настройки проекта валидны. В CLI проверяются `npm run lint`, `npm run format:check`, `npm run typecheck`; на контрольном файле проверяется порядок импортов и отсутствие необязательных точек с запятой.
- В новом сеансе VS Code пользователь сохраняет контрольный файл, сверяет результат с CLI и отсутствие возврата точек с запятой. До фактического наблюдения это Blocked/NotRun, не Passed.
- Diff не содержит продуктового кода, секретов, собственного валидатора и новых зависимостей этой задачи. Статусы и ограничения записываются в `verification.md`.
