**Input**: До следующего прохода по UI агентам нужен единый источник смысловых правил; автоматические правила живут в конфигурациях. Собственного проверочного скрипта и skill нет.

## User Scenarios & Testing

### User Story 1 — агент следует согласованным правилам (Priority: P1)

Как разработчик, я открываю один документ с правилами для агента и вижу применимые решения, положительные и отрицательные примеры и исключения, которые нельзя надёжно поручить линтерам.

**Why this priority**: Следующий проход по UI должен сохранять договорённости без повторных замечаний на каждом файле.

**Independent Test**: Сверить каждое действующее смысловое правило проекта с новым документом, ссылками из инструкций агенту и реальными исключениями Next.js; выполнить проверку ссылок и ревью на противоречия.

**Acceptance Scenarios**:
1. **Given** агент начинает новую задачу по UI, **When** он читает корневые инструкции, **Then** он получает прямую ссылку на действующие смысловые правила до написания кода.
2. **Given** агент выбирает структуру компонента, обработчик, условия, параметры функции, константы, тестовые ожидания или SCSS-токены, **When** он сверяет решение с правилами, **Then** документ содержит короткий пример «так» и «не так» либо явное исключение.
3. **Given** правило уже надёжно проверяет готовый инструмент, **When** агент ищет его источник, **Then** документ направляет к исполняемой конфигурации и не создаёт конкурирующего варианта.

### User Story 2 — редактор и проект согласованно форматируют код (Priority: P1)

Как разработчик, я сохраняю TypeScript в VS Code и получаю тот же стиль, который проверяют проектные ESLint и Prettier, включая отсутствие необязательных точек с запятой.

**Why this priority**: Автоматическое сохранение не должно возвращать ошибки форматирования после исправлений агента.

**Independent Test**: Сравнить форматирование файла из проекта в CLI и свежем окне VS Code; проверить применённую конфигурацию и отсутствие конфликта действий при сохранении.

**Acceptance Scenarios**:
1. **Given** файл TypeScript проекта и обновлённое состояние расширения редактора, **When** файл сохраняется с автоматическим форматированием, **Then** обычные конечные точки с запятой не появляются.
2. **Given** включённое автоматическое исправление импортов, **When** файл сохраняется, **Then** порядок импортов не расходится с действующим правилом ESLint.
3. **Given** редактор продолжает использовать устаревшие параметры загруженной конфигурации, **When** выполняется описанное обновление состояния редактора, **Then** он применяет действующее проектное значение без изменения глобальных настроек пользователя.

### Edge Cases

- Структура файлов Next.js сохраняет зарезервированные имена; правило папки ComponentName относится к собственным компонентам.
- Условное && допустимо только при сохранении ожидаемого ложного значения; для отсутствующего атрибута нужен undefined, а не пустая строка.
- Короткое тело стрелочной функции не меняет возвращаемый тип; если возвращаемое значение нужно отбросить, это выражено явно.
- Тест не получает независимое ожидаемое значение из той же константы, что проверяемый код.
- Отдельный документ не дублирует полный текст исполняемых правил ESLint, Prettier и Stylelint; краткие ссылки на них допустимы.
- Текущий сеанс VS Code может держать устаревшую конфигурацию; до ручной проверки его состояние не выдаётся за подтверждённое.

### Verification Approach

Задача меняет инструкции и настройки инструментов, но не бизнес-логику, API или UI. Проверяются полнота и непротиворечивость документа, рабочие ссылки, форматирование и сортировка импортов на контрольном файле, итоговые lint, format:check и typecheck. Проверка редактора фиксируется отдельно от CLI и требует пользовательского наблюдения, если доступ к VS Code из задачи отсутствует.

## Requirements

### Functional Requirements

- **FR-001**: В проекте есть один действующий документ смысловых правил для агентов с областью действия, положительными/отрицательными примерами и необходимыми исключениями.
- **FR-002**: Документ охватывает структуру собственных компонентов, публичные импорты, именованные обработчики, передачу более одного параметра объектом, именованные логические константы для длинных условий, короткие ветки if, безопасное использование &&, короткие стрелочные функции, размещение значимых констант, независимость тестовых ожиданий, доступность, защиту реквизитов и правила SCSS Modules, БЭМ, токенов и миксинов.
- **FR-003**: Автоматически проверяемые правила имеют единственный исполняемый источник в конфигурациях ESLint, Prettier и Stylelint; ручной документ не подменяет их и не обещает автоматизацию смысловых решений.
- **FR-004**: Корневые инструкции агента ссылаются на ручные правила и действующие конфигурации; старые ссылки на CODE_STYLE.md остаются рабочими через короткую навигационную страницу без дублирования правил.
- **FR-005**: Рекомендации редактору в рамках проекта согласованы с Prettier и ESLint, не изменяют глобальные пользовательские настройки и не добавляют конкурирующих действий сортировки импортов.
- **FR-006**: Способ обновить устаревшее состояние расширения Prettier описан явно; командная проверка и проверка редактора различаются.
- **FR-007**: Документы описывают актуальное состояние без истории «было → стало»; проект не получает собственного валидатора структуры, нового skill или новых зависимостей.

### Scope Boundaries

- В объёме: документ правил для агентов, компактная карта CODE_STYLE.md, ссылки из действующих инструкций, проектные настройки форматирования и проверка.
- За пределами: собственный скрипт структуры, собственные ESLint/Stylelint-правила, skill, массовый рефакторинг существующего продуктового кода, новые возможности UI, БД, публикация и Git-коммит. Применение новых ручных правил к ранее написанным функциям выполняется при их следующем изменении или в отдельной согласованной задаче.

### Data Effects & User Decision

- **Changed data**: Документация и проектные настройки редактора; реальные реквизиты, сообщения, сессии и БД не затрагиваются.
- **Preview**: До коммита видны diff правил/конфигурации и отчёты проверки.
- **Confirmation**: Согласование spec и отдельное разрешение реализации следуют процессу проекта.
- **Cancellation**: Пользовательские и соседние изменения не откатываются автоматически.
- **Idempotency and duplicates**: Документы дают один источник для каждого типа правила; повторное форматирование не создаёт новый diff.
- **Failure result**: Неустановленное состояние редактора или неуспешная проверка отмечаются явно.

### Key Entities

Продуктовые сущности и модель данных неприменимы.

## Success Criteria

- **SC-001**: Каждое согласованное ручное правило найдено в одном месте с применимым примером или исключением; автоматические правила ведут к своим конфигурациям. Покрывает FR-001–FR-003.
- **SC-002**: Корневые инструкции и актуальная навигационная страница ведут к правилам; прежние ссылки не ломаются. Покрывает FR-004, FR-007.
- **SC-003**: CLI-проверки форматирования, ESLint и типов проходят; свежий сеанс редактора не возвращает точки с запятой и не нарушает порядок импортов. Покрывает FR-005–FR-006.
- **SC-004**: Изменения этой задачи не добавляют продуктовый код, зависимости сверх уже согласованного Stylelint, собственные валидаторы или реальные реквизиты. Покрывает FR-007.

## Assumptions and Dependencies

- Действующие соглашения описаны в docs/CODE_STYLE.md, AGENTS.md и текущем обсуждении.
- ESLint и Prettier уже настроены; конфигурация Stylelint из specs/011-scss-stylelint завершается до итоговой проверки этой задачи. Пользовательская установка зависимостей выполнена.
- VS Code пользователя включает форматирование при сохранении; журнал расширения показал устаревшее значение конфигурации. Успех ручной проверки редактора не предполагается до её фактического выполнения.
- Один пользовательский коммит может включать обе отдельно проверенные задачи и уже подготовленные продуктовые изменения; агент не выполняет Git-коммит.
- Спецификация описывает текущее целевое состояние без истории изменений.
