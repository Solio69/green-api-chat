## User Scenarios & Testing

### User Story 1 — Изоляция тестовых данных и окружений (Priority: P1)

Тесты получают независимые данные и управляемые внешние зависимости, а ожидаемый результат не вычисляется проверяемой реализацией.

**Why this priority**: Это обязательная часть результата этапа R09; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Запуск затронутых Vitest и Playwright сценариев изолированно и совместно; краткая контролируемая проверка неверного ответа для контрактного ожидания. Временный отрицательный пример не сохраняется в продукте.

**Acceptance Scenarios**:

1. **Given** один тест изменил очередь и завершился ошибкой, **When** запускается следующий независимый тест, **Then** он получает исходные данные без сообщения и счётчиков предшественника.
2. **Given** проверяется backoff, **When** управляемое время проходит заданные интервалы, **Then** наблюдаются ожидаемые запросы без реального ожидания секунд.
3. **Given** проверяется HTTP-контракт, **When** реализация возвращает неверное значение, **Then** проверка с независимо заданным ожиданием падает.
4. **Given** сценарии имеют собственные фикстуры, **When** их запускают отдельно и в другом порядке, **Then** результат не зависит от соседних сценариев.

### Edge Cases

- Падение внутри setup или cleanup.
- Незавершённый timer или fetch после теста.
- Два browser contexts одного сценария владения.
- Общий fake-сервер и одинаковые фиктивные идентификаторы.

### Verification Approach

Запуск затронутых Vitest и Playwright сценариев изолированно и совместно; краткая контролируемая проверка неверного ответа для контрактного ожидания. Временный отрицательный пример не сохраняется в продукте.

Для существующего поведения используются регрессионные проверки и сопоставление покрытия. Добавление тестов после существующей реализации не называется TDD. Обнаруженный дефект описывается отдельно; изменение продуктового поведения требует согласованного требования и Red → Green → Refactor.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Выполненные приёмочные проверки и ограничение результатов зафиксированы в [verification.md](verification.md).

## Requirements

### Functional Requirements

- **FR-001**: Разделить общие тестовые данные по предметным областям и назначению; оставить общими только действительно единые значения протокола и вспомогательные операции.
- **FR-002**: Создавать QueryClient, сеанс, очередь уведомлений, счётчики запросов и изменяемые записи заново для каждого независимого сценария; cleanup выполняется также при падении теста.
- **FR-003**: Управлять временем, случайностью и завершением обещаний в проверках retry, дедлайнов и гонок; не заменять условия ожидания произвольными sleep.
- **FR-004**: Изолировать состояние fake GREEN-API и query-стенда между browser contexts или сценариями. Если сервер по контракту общий, явно сериализовать затронутые тесты и очищать состояние до и после сценария.
- **FR-005**: Сохранять независимые ожидаемые значения HTTP, статусов и нормализации; не импортировать проверяемую функцию или константу результата для вычисления собственного oracle.
- **FR-006**: Сохранять реальные браузерные API в сценариях Web Locks, cookie, фокуса и геометрии; подменять провайдера и внешние условия на границе.
- **FR-007**: Использовать существующие средства runner и согласованные зависимости; новую библиотеку мокирования не добавлять в рамках задачи.
- **FR-008**: Подтвердить независимость выборочным запуском затронутых тестов поодиночке и вместе в ином порядке, а не только обычным полным прогоном.

### Scope Boundaries

- **В объёме**: Фабрики фикстур, области констант, управляемые зависимости и очистка тестовых окружений.
- **За пределами**: Ускорение любой ценой, обязательный параллельный запуск всех тестов и новая mock-инфраструктура.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: Меняются только синтетические данные и ресурсы тестовых запусков; реальные реквизиты и сообщения не используются.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Согласованы направление и полный цикл реализации; полученное разрешение на commit/push в `refactor` не запрашивается повторно. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Фикстура сценария, fake-провайдер, часы, очередь, независимое ожидаемое значение.

## Success Criteria

- **SC-001**: У изменяемых ресурсов есть явная область жизни и проверенная очистка при успехе и ошибке (FR-001, FR-002, FR-004).
- **SC-002**: Проверки retry и гонок управляют временем, а важные браузерные API остаются реальными (FR-003, FR-006).
- **SC-003**: Контрактные ожидания независимы; выбранные сценарии проходят отдельно и в изменённом порядке без новых библиотек (FR-005, FR-007, FR-008).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; агент самостоятельно ничего не устанавливает.
- Проектные правила Git и сохранения чужих правок остаются обязательными. Узкое разрешение пользователя допускает самостоятельные commit/push в `refactor` для этой работы; реальные сообщения не отправляются.
