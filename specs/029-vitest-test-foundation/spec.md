## User Scenarios & Testing

### User Story 1 — Тестовая основа на Vitest и React Testing Library (Priority: P1)

Разработчик может отдельно запускать проверки логики и React без production-сборки приложения, сохраняя существующие браузерные проверки.

**Why this priority**: Это обязательная часть результата этапа R01; её отдельная приёмка позволяет не смешивать готовность разных задач. P1 обозначает обязательность в этой задаче, а порядок работ задают зависимости.

**Independent Test**: Проверить конфигурацию на допустимом и заведомо падающем примерах, провести пилотные прогоны Vitest и проверить доступность прежних команд Playwright. DOM-окружение и точные версии — технические решения плана в пределах согласованного набора.

**Acceptance Scenarios**:

1. **Given** зависимости установлены по согласованному плану, **When** запущена проверка чистой функции, **Then** тест выполняется без Next.js-сервера и без браузера.
2. **Given** смонтирован существующий компонент, **When** тест взаимодействует с ним через React Testing Library, **Then** проверяется наблюдаемое состояние DOM, а следующий тест не видит его состояние.
3. **Given** ожидание пилотного теста намеренно нарушено, **When** выполнена команда тестирования, **Then** команда сообщает имя проваленного теста и завершается ненулевым кодом.

### Edge Cases

- Импорты SCSS Modules и алиаса @/.
- Глобальные DOM-типы рядом с Node-кодом.
- Утечки таймеров, mock fetch и QueryClient между файлами.
- Асинхронные Server Components остаются в проверках работающего Next.js.

### Verification Approach

Проверить конфигурацию на допустимом и заведомо падающем примерах, провести пилотные прогоны Vitest и проверить доступность прежних команд Playwright. DOM-окружение и точные версии — технические решения плана в пределах согласованного набора.

Проверяется действующая конфигурация: успешный штатный сценарий и контролируемый нарушающий пример должны дать ожидаемый результат. Ошибка установки или импорта не считается подтверждением TDD. Если выяснится, что требуется изменить бизнес-логику, такая часть выполняется по согласованному контракту через Red → Green → Refactor.

После завершения связанной серии правок выполняется подходящий набор проверок задачи. Команды и точные файлы будущих тестов фиксируются в техническом плане. Фактические результаты реализации и ограничения приведены в [verification.md](verification.md).

## Requirements

### Functional Requirements

- **FR-001**: Ввести Vitest и React Testing Library как согласованные инструменты; описать совместимые версии и необходимые вспомогательные devDependencies в техническом плане перед установкой.
- **FR-002**: Разделить окружения проверок: чистая и серверная логика исполняется в Node, React-компоненты и хуки — в DOM-окружении с development-сборкой React.
- **FR-003**: Предоставить документированные команды одиночного запуска, полного прогона и локального наблюдения; ненулевой код завершения отражает падение тестов или неправильную конфигурацию.
- **FR-004**: Обеспечить разрешение проектных импортов и очистку DOM, моков, таймеров и QueryClient между тестами; серверные зависимости не должны случайно попадать в DOM-набор.
- **FR-005**: Перенести небольшой пилотный набор: нормализацию подписи получателя и одну проверку отображения существующего простого компонента. Сохранить независимые ожидания контракта и исходные фиктивные данные.
- **FR-006**: Оставить существующие Playwright-наборы доступными во время миграции; каждый пилотный сценарий исключается из прежнего набора только после подтверждения эквивалентного результата.
- **FR-007**: Проверить конфигурацию временным контролируемым нарушением ожидания: команда должна завершиться ошибкой; после возврата корректного ожидания пилотные тесты проходят. Это проверка инструмента, а не TDD продукта.

### Scope Boundaries

- **В объёме**: Конфигурация двух окружений Vitest, команды, тестовые setup-файлы, пилотные проверки и инструкция установки.
- **За пределами**: Массовый перенос всех тестов, изменение бизнес-логики, подключение CI и дополнительные тестовые фреймворки.
- **Масштаб**: существующее тестовое приложение; без БД, фоновой серверной очереди, новых пользовательских функций и обязательного production-мониторинга.
- Тесты изменяемого кода входят в эту задачу. Этап R09 завершает общий перенос, но не откладывает проверку результатов предыдущих этапов.

### Data Effects & User Decision

- **Changed data**: После разрешения реализации меняются конфигурация, devDependencies, lockfile и пилотные тесты. Установка восьми выбранных devDependencies агентом прямо разрешена пользователем для 029.
- **Preview**: До реализации доступны требования, сценарии и критерии этого документа; после разрешённой реализации результат проверяется по diff и отчёту проверок.
- **Confirmation**: Пользователь разрешил полный цикл выбранной задачи с кодом, проверками и локальным commit; повторное согласование не требуется. Дополнительные диалоги подтверждения в интерфейс приложения не добавляются.
- **Cancellation**: Отмена подготовки или реализации останавливает дальнейшие действия; сохранённые правки остаются доступными для просмотра и не откатываются автоматически. Поведение пользовательской отмены сохраняется там, где она предусмотрена существующим сценарием.
- **Idempotency and duplicates**: Повторы и гонки, относящиеся к задаче, проверяются в сценариях и границах выше. Повторное применение документа не создаёт новую задачу или копию требований; актуализируется эта спецификация.
- **Failure result**: Незавершённая часть явно отмечается, результаты не выдают за успешные. Ошибка проверки не разрешает менять поведение за пределами требований или затрагивать пользовательские изменения.

### Key Entities

Тестовый проект Vitest, Node-окружение, DOM-окружение, fixture, команда запуска.

## Success Criteria

- **SC-001**: Node- и DOM-наборы запускаются отдельно и вместе и не требуют production-сборки (FR-001–FR-003).
- **SC-002**: Пилотные сценарии проходят повторный запуск в изолированном окружении; старое покрытие сохранено (FR-004–FR-006).
- **SC-003**: Контролируемое падение обнаруживается, а восстановленный набор проходит (FR-007).

Приёмка требует выполнения всех FR и прохождения применимых сценариев, включая ошибки и границы. Критерии SC группируют доказательства; сами по себе число тестов и наличие инструмента не подтверждают результат.

## Assumptions and Dependencies

### Подтверждённые решения

- Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS Modules.
- Согласованы функциональные модули, Vitest и React Testing Library вместе с Playwright, а также CI на GitHub Actions.
- Работа ведётся в текущем объёме проекта. Новые продуктовые требования не выводятся из слова «образцовый».
- Изменения поведения и новые зависимости за пределами согласованных инструментов обсуждаются до реализации. Версии и необходимые вспомогательные пакеты определяются техническим планом; для восьми пакетов 029 пользователь дал прямое исключение на установку агентом.
- Пользователь разрешил этому чату локальный commit в refactor после проверки кода; сохранение чужих правок обязательно. Push нового результата и реальные сообщения в задачу не входят.
