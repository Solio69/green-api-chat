# implement

Применять только к выбранной задаче этого проекта. Пользовательские решения
и ограничения сохраняются между этапами. Общий порядок:
[workflow](../../../docs/spec-kit-workflow.md);
правила: [AGENTS](../../../AGENTS.md),
[constitution](../../../.specify/memory/constitution.md),
[Git](../../../GIT_POLICY.md).
Происхождение: [provenance](../../../docs/spec-kit-provenance.md).

## Контекст вызова

Определить абсолютный $taskProject по расположению этого SKILL.md (три уровня
вверх). Взять ожидаемую задачу из текущего обсуждения, а не из имени ветки.
Явно задать SPECIFY_FEATURE_DIRECTORY и абсолютный $taskFeature.
При неизвестной задаче запросить её, не выбирать последнюю.

Любой именованный ниже script расположен в
.specify/scripts/powershell/ относительно $taskProject. Вызов из корня
или подкаталога проекта, например:

~~~powershell
& (Join-Path $taskProject '.specify/scripts/powershell/check-prerequisites.ps1') -Json -RequireTasks -IncludeTasks -ExpectedFeatureDirectory $taskFeature
~~~

В каждом вызове передавать -ExpectedFeatureDirectory $taskFeature.
Проверить успешный exit code и точное совпадение FEATURE_DIR с ожидаемым путём
до чтения документов. При ошибке остановить зависимую работу и объяснить причину.
Рабочие зависимости только локальные; hooks, публикация, установки и автоматические
Git-действия отсутствуют.

## Порядок

1. Проверить отдельное разрешение пользователя в переписке и границы задачи.
   Выполнить check-prerequisites.ps1 с -Json -RequireTasks -IncludeTasks.
2. Прочитать spec/plan/tasks, связанные документы, C1–C8 и GIT_POLICY.md.
   Проверить актуальность analysis.md; наличие одной сводки в переписке
   не заменяет полный файл отчёта. Документы с отметкой Approved сами по себе
   не заменяют разрешение.
3. Различать чек-листы: требования/готовность (Kind: Readiness или
   checklists/requirements.md) должны не содержать блокирующих пробелов;
   будущие приёмочные проверки (Kind: Acceptance) могут быть NotRun.
   Не требовать успешных тестов ещё не написанного кода. Технические пробелы
   устранить в разрешённых границах; существенные решения вернуть пользователю.
4. Выполнять tasks последовательно. Сохранять чужие изменения. После фактического
   результата отмечать задачу выполненной; при сбое сообщать частичный результат.
   Не создавать игнорируемые файлы или дополнительную инфраструктуру без нужды
   и связи с планом. Установки и операции БД передавать пользователю.
   Для новой/изменяемой бизнес-логики и серверных контрактов соблюдать TDD:
   сначала написать и запустить тест, подтвердить Red по причине поведения;
   только затем реализовать Green и выполнить Refactor с зелёными тестами.
   Ошибка окружения не считается Red; при ней сначала устранить причину в рамках
   разрешений. При чистом рефакторинге подтвердить существующее покрытие до правок.
   Для конфигурации/оформления выполнить способ проверки из spec.
   Сохранить тесты в проекте, команды и результаты Red/Green — в verification.
5. Выполнить проверки из плана; повторять затронутые после исправлений. Не выдавать
   инфраструктурную ошибку отсутствующего инструмента за проверку поведения.
6. Выполнить локальный analyze по его инструкции отдельным read-only проходом.
   После прохода сохранить актуальный analysis.md отдельным действием.
   После содержательных исправлений повторить затронутые проверки и анализ.
7. Проверить соответствие spec/plan/tasks, провести предкоммитное ревью,
   проверить область изменений и отсутствие реальных секретов.
8. Подготовить verification.md с реальными Passed/Failed/Blocked/NotRun,
   замечаниями и ограничениями; актуализировать статусы документов. Не объявлять
   задачу завершённой при обязательной заблокированной проверке.
9. Сообщить что изменено и зачем, результаты, ограничения, полезные улучшения
   с обоснованием, действия пользователя и английское название коммита.
   Самостоятельно не создавать коммит и не переходить к следующей feature.
