# analyze

Применять только к выбранной задаче этого проекта. Пользовательские решения
и ограничения сохраняются между этапами. Общий порядок:
[workflow](../../../docs/spec-kit-workflow.md);
правила: [AGENTS](../../../AGENTS.md),
[constitution](../../../.specify/memory/constitution.md),
[Git](../../../GIT_POLICY.md).
Происхождение: [provenance](../../../docs/spec-kit-provenance.md).

## Контекст вызова

Определить абсолютный $taskProject по расположению этого SKILL.md (три уровня
вверх). Взять ожидаемую задачу из текущего обсуждения, а не из имени ветки.
Явно задать SPECIFY_FEATURE_DIRECTORY и абсолютный $taskFeature.
При неизвестной задаче запросить её, не выбирать последнюю.

Любой именованный ниже script расположен в
.specify/scripts/powershell/ относительно $taskProject. Вызов из корня
или подкаталога проекта, например:

~~~powershell
& (Join-Path $taskProject '.specify/scripts/powershell/check-prerequisites.ps1') -Json -RequireTasks -IncludeTasks -ExpectedFeatureDirectory $taskFeature
~~~

В каждом вызове передавать -ExpectedFeatureDirectory $taskFeature.
Проверить успешный exit code и точное совпадение FEATURE_DIR с ожидаемым путём
до чтения документов. При ошибке остановить зависимую работу и объяснить причину.
Рабочие зависимости только локальные; hooks, публикация, установки и автоматические
Git-действия отсутствуют.

## Порядок

1. Выполнить check-prerequisites.ps1 с -Json -RequireTasks -IncludeTasks.
   Требуются spec, plan, tasks и локальная constitution.
2. Зафиксировать в памяти список и SHA-256 файлов проекта (без .git).
   Весь проход read-only: не создавать и не обновлять analysis.md, не отмечать
   задачи и не исправлять даже очевидную опечатку. Запись отчёта — отдельное
   обязательное действие после завершения прохода по шагу 7.
3. Прочитать требования FR/SC, истории и края spec; решения/структуру/ограничения
   plan; IDs, зависимости и пути tasks; принципы C1–C8. Нужные contracts и модели
   читать по ссылкам, проверяя их соответствие.
4. Построить инвентарь требований и карту покрытия задачами. Проверить дубли,
   существенные неоднозначности, неполноту, противоречия, порядок зависимостей,
   нарушения принципов и отсутствующие файлы. Запланированный новый файл
   до реализации сам по себе не является ошибкой.
   Для новой/изменяемой бизнес-логики и серверных контрактов проверить порядок
   тест и поведенческий Red → реализация и Green → Refactor, пути тестов и команды.
   Отсутствие этой зависимости нарушает C7. До реализации результаты ожидаются;
   после реализации verification должен содержать фактические Red/Green.
   Для чистого рефакторинга проверить исходное покрытие; для конфигурации
   и оформления — явно определённый в spec способ проверки.
5. Важность: CRITICAL — нарушение обязательного принципа или отсутствие базового
   покрытия; HIGH — противоречие либо непроверяемый критерий; MEDIUM — значимый
   пробел/терминология; LOW — улучшение формулировки без влияния на поведение.
6. Повторно снять список и хеши; они должны совпасть. Выдать в ответе отчёт:
   findings (ID, категория, важность, путь/строка, суть, рекомендация), покрытие
   FR/SC → задачи, замечания C1–C8, задачи без требований, метрики требований/
   задач/покрытия/неоднозначностей/дублирования и непроведённые проверки.
7. Закончить проход. Отдельным действием сохранить полный отчёт из шага 6
   в analysis.md выбранной задачи, указав дату, этап и границы проверки.
   При повторном анализе актуализировать этот файл, сохраняя описание текущего
   состояния. Запись самого отчёта после прохода не запускает новый анализ.
   При разрешённой технической подготовке исправить технические findings
   отдельным шагом и повторить анализ. Изменение согласованного поведения
   сначала вернуть пользователю.
8. Дать пользователю прямую ссылку на analysis.md и краткий результат.
   При готовности предъявить полный отчёт по локальному workflow и запросить
   разрешение реализации, если его ещё нет. При анализе уже разрешённой
   реализации повторное разрешение не требуется.
