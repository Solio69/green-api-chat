# tasks

Применять только к выбранной задаче этого проекта. Пользовательские решения
и ограничения сохраняются между этапами. Общий порядок:
[workflow](../../../docs/spec-kit-workflow.md);
правила: [AGENTS](../../../AGENTS.md),
[constitution](../../../.specify/memory/constitution.md),
[Git](../../../GIT_POLICY.md).
Происхождение: [provenance](../../../docs/spec-kit-provenance.md).

## Контекст вызова

Определить абсолютный $taskProject по расположению этого SKILL.md (три уровня
вверх). Взять ожидаемую задачу из текущего обсуждения, а не из имени ветки.
Явно задать SPECIFY_FEATURE_DIRECTORY и абсолютный $taskFeature.
При неизвестной задаче запросить её, не выбирать последнюю.

Любой именованный ниже script расположен в
.specify/scripts/powershell/ относительно $taskProject. Вызов из корня
или подкаталога проекта, например:

~~~powershell
& (Join-Path $taskProject '.specify/scripts/powershell/check-prerequisites.ps1') -Json  -ExpectedFeatureDirectory $taskFeature
~~~

В каждом вызове передавать -ExpectedFeatureDirectory $taskFeature.
Проверить успешный exit code и точное совпадение FEATURE_DIR с ожидаемым путём
до чтения документов. При ошибке остановить зависимую работу и объяснить причину.
Рабочие зависимости только локальные; hooks, публикация, установки и автоматические
Git-действия отсутствуют.

## Порядок

1. Выполнить check-prerequisites.ps1 с -Json без режима, затем setup-tasks.ps1
   с -Json, оба с явным ExpectedFeatureDirectory.
2. Прочитать spec, plan и перечисленные доступные research/model/contracts/
   quickstart. Сверить каждый необходимый документ с планом.
3. По [tasks-template.md](../../../.specify/templates/tasks-template.md) создать
   tasks.md осознанным редактированием. Если он существует, сначала прочитать,
   сохранить выполненные задачи и фактические статусы; не сбрасывать отметки.
4. Для каждой задачи дать стабильный T-ID, историю US при наличии, конкретное
   действие, точный путь, проверяемый результат и зависимости. Работа идёт
   последовательно, без маркеров параллельной реализации.
5. Включить проверки, соответствующие риску. Для средств изменения данных/
   файлов контрактные проверки предшествуют их реализации. Не писать тесты,
   лишь повторяющие текст инструкций или устройство кода.
6. Связать все FR и требующие реализации SC с задачами. Обосновать задачи без
   прямого требования. Добавить соответствие спеке, ревью, verification.md,
   следующие шаги и английское название коммита.
7. Передать документы на analyze; не начинать реализацию.
