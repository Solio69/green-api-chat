# Локальный процесс Spec Kit

Комплект работает в Windows с PowerShell 7 и встроенными средствами .NET.
Установка пакетов, Git-репозиторий и доступ к исходному проекту для работы
не нужны. Правила: [AGENTS.md](../AGENTS.md),
[конституция](../.specify/memory/constitution.md),
[политика Git](../GIT_POLICY.md).

## Порядок работы

1. Обсудить одну задачу: цель, сценарии, границы, варианты и существенные вопросы.
2. speckit-specify: составить spec.md и checklists/requirements.md. Предъявить
   пользователю спецификацию для согласования — первая точка решения.
3. speckit-clarify: устранить значимые неоднозначности; не задавать формальные
   вопросы при достаточной определённости.
4. speckit-plan: подготовить research.md, plan.md, необходимые data-model.md,
   contracts/ и quickstart.md. Объяснить отсутствие неприменимых артефактов.
5. speckit-tasks: разбить план на последовательные проверяемые шаги с путями
   файлов, зависимостями и покрытием требований.
6. speckit-analyze: read-only проверка документов. Сначала закончить проход,
   затем отдельно исправить технические замечания и повторить анализ.
   После завершённого прохода отдельным действием сохранить analysis.md в каталоге
   выбранной задачи. Сам проход остаётся read-only.
7. Полный отчёт и разрешение на реализацию — вторая точка решения.
8. speckit-implement: выполнить задачи, проверить спеку и результат,
   провести предкоммитное ревью, подготовить фактический отчёт проверки.

Внутри технической подготовки согласование каждого файла не требуется.
Изменение утверждённого поведения требует решения пользователя до зависимой работы.
Чек-лист качества requirements проверяется до реализации; будущие приёмочные
проверки со статусом NotRun сами по себе не блокируют её начало.

## Тесты до реализации поведения

В spec заранее описываются сценарии, границы и способ проверки. Для новой
и изменяемой бизнес-логики и серверных контрактов обязателен TDD.
Написание исполняемых тестов, как и продуктового кода, начинается только
после двух точек согласования: spec и отдельного разрешения на реализацию.

1. Red: написать сохраняемый автотест согласованного поведения и запустить его.
   Подтвердить, что он падает именно из-за отсутствующего/неверного поведения.
   Неработающее окружение, недостающий пакет или ошибка импорта Red не заменяют.
2. Green: реализовать минимально необходимое поведение и получить успешный тест.
3. Refactor: улучшить код, сохранив поведение, и повторить затронутые тесты.

При серии небольших правок по ревью не запускать проверки после каждого
замечания. Один Red-прогон для нового поведения остаётся до реализации;
Green и регрессию выполнять после завершения всех правок задачи или крупной
фичи. Для чистого рефакторинга использовать уже подтверждённый baseline и
запускать подходящие проверки один раз в конце серии.

Plan задаёт инструменты, файлы тестов и команды; tasks ставит подтверждение Red
перед соответствующей реализацией. Анализ проверяет эти зависимости.
Verification фиксирует команды, причины Red и результаты Green/итогового запуска.
Написанные после реализации тесты не подтверждают соблюдение TDD.

При чистом рефакторинге проверяются покрытие и ранее подтверждённая успешность
существующих тестов; искусственное падение не требуется. Для конфигурации и оформления
способ проверки явно определяется в каждой спеке. Если они затрагивают
бизнес-логику или серверный контракт, соответствующая часть проходит TDD.
Установка тестовых инструментов остаётся действием пользователя.

## Выбор задачи и вызовы

Запускать из корня проекта или его подкаталога. Корень определяется расположением
комплекта. Каждый исполняемый script проверяет контекст заново. Не использовать
ветку, последний каталог или общий feature.json для выбора задачи.

Пример для текущего проекта (заменить имя feature на обсуждаемую задачу):

~~~powershell
Set-Location -LiteralPath 'D:\Pet-projects\green-api-chat'
$env:SPECIFY_FEATURE_DIRECTORY = 'specs/001-project-workflow'
$taskFeature = [IO.Path]::GetFullPath(
    (Join-Path (Get-Location).Path 'specs/001-project-workflow')
)
& '.\.specify\scripts\powershell\check-prerequisites.ps1' -Json -PathsOnly -ExpectedFeatureDirectory $taskFeature
~~~

Проверить exit code и буквальное совпадение FEATURE_DIR с $taskFeature.
SPECIFY_FEATURE_DIRECTORY разрешает абсолютный или относительный от корня путь;
ExpectedFeatureDirectory должен быть абсолютным. Разрешён прямой каталог
specs/NNN-slug: не менее трёх цифр, строчные латинские слова/цифры через дефисы.
Ошибочный путь, выход из проекта и ссылки junction/symlink отклоняются.
Это защита от случайных ошибок одного локального писателя, не файловая транзакция
между произвольными процессами.

Во всех командах далее передавать -ExpectedFeatureDirectory $taskFeature:
- check-prerequisites -PathsOnly — проверить только контекст; spec может отсутствовать.
- setup-spec — создать отсутствующую spec.md из локального шаблона.
- check-prerequisites -RequireSpec — этапы clarify, plan и checklist.
- setup-plan — создать отсутствующий plan.md при существующей spec.
- check-prerequisites без режима — требуются spec и plan.
- setup-tasks — проверить контекст и вернуть шаблон, не создавать tasks.md.
- check-prerequisites -RequireTasks -IncludeTasks — analyze и implement.

Это сокращённые имена файлов из .specify/scripts/powershell/.
-Json выводит один JSON в stdout при успехе. Ошибка — ненулевой exit и stderr.
-Help работает без контекста. Режимы PathsOnly/RequireSpec/RequireTasks
взаимоисключающие. IncludeTasks игнорируется с PathsOnly.
Повторный setup-spec/setup-plan сохраняет готовый файл (CREATED=false).
При ошибке записи возможный частичный файл указывается явно; автоматического
удаления пользовательского документа или отката нет.

## Отчёт анализа

Обязательный артефакт — specs/NNN-slug/analysis.md. Во время проверки не писать
файлы; сначала сравнить перечень и хеши проверяемых файлов, закончить проход,
затем отдельным действием сохранить полный отчёт. Его собственная запись
не считается изменением во время прохода и не требует бесконечного самоанализа.

В отчёте указать дату, этап, проверенные документы, замечания с важностью и
местом, покрытие FR/SC → задачи, C1–C8, задачи без требований, метрики,
непроведённые проверки и ограничения. Различать анализ согласованности документов,
результаты тестов и ревью реализации. Сводка в чате не заменяет файл:
в сообщении пользователю обязательна прямая ссылка на analysis.md.

При повторном анализе актуализировать этот же файл после завершения прохода;
описывать текущее состояние. Изменения анализируемых требований, плана или задач
требуют проверки их согласованности. Полученное разрешение реализации фиксировать
в spec/plan/tasks; не запрашивать его повторно для уже разрешённого объёма.

## Отчёт перед реализацией

Перечислить каждый подготовленный файл и каждый контракт отдельно: путь,
назначение, статус. Указать clarify, исследование, результаты анализа,
число требований и задач, покрытие, замечания и их устранение, зависимости,
риски, непроведённые проверки, общие изменённые файлы и ожидаемое решение.
Наличие всех документов не заменяет разрешение пользователя.

## Завершение и проверки

Проверить соответствие spec/plan/tasks, фактически выполнить необходимые
проверки, провести предкоммитное ревью и записать verification.md.
Отметить выполненные задачи; заблокированные не выдавать за завершённые.
Предложить полезные улучшения с причиной; не расширять задачу ради них.
Дать пользователю команды для дальнейших действий и название коммита
с feat:, fix:, refactor: или chore:.

Контрактные проверки комплекта:

~~~powershell
& '.\tests\spec-kit\workflow.tests.ps1'
~~~

Они работают на отдельной временной копии. При Failed/Blocked вывод содержит
причину; полный успех при непроведённой проверке не заявляется.
[Происхождение и состав](spec-kit-provenance.md).
