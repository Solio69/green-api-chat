## Согласованные решения

| Область                      | Решение                                                                                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Основа                       | Next.js и React в одном постоянном Node-процессе; зашифрованная HttpOnly cookie; токен не передаётся клиентскому JavaScript из cookie                               |
| Хранение                     | Переписка и факты текущего сеанса только в памяти Query/процесса; без собственной БД, Redis и постоянного browser storage                                           |
| История                      | При каждом обращении к выбранному чату свежий GetChatHistory с count: 10; известные сообщения сохраняются и объединяются без дублей                                 |
| Подгрузка                    | Загрузка более старых сообщений и увеличение count отложены; в текущем объёме нет pagination, cursor или offset                                                     |
| Нетекстовый элемент          | «Неподдерживаемое сообщение» без загрузки вложений; API count не превращается в десять отфильтрованных текстовых сообщений                                          |
| Получение                    | ReceiveNotification на сервере Next.js → SSE в браузер → отдельный HTTP ACK после обработки → DeleteNotification                                                    |
| Вкладки                      | Одна рабочая вкладка на GREEN-API инстанс; вторая показывает явное ограничение и не отправляет сообщения                                                            |
| Нет активной вкладки         | Чтение останавливается; неподтверждённое событие не удаляется; после возврата чтение возобновляется и история обновляется с count: 10                               |
| Границы восстановления       | Очередь GREEN-API ограничена сроком хранения; десять сообщений и временная память не гарантируют восстановление всех старых событий и статусов                      |
| Принятие отправки            | Локальное добавление исходящего сообщения только после успешного SendMessage с idMessage; это ещё не доставка                                                       |
| Ожидание отправки            | Одна отправка за раз на подключение; поле текущей попытки и повторная отправка заблокированы; переключение и закрытие доступны                                      |
| Ввод                         | Переключение или закрытие очищает ввод; отдельного хранилища черновиков по чатам нет; допустимый текст передаётся с исходными пробелами и переносами                |
| Неопределённый исход         | Если тот же чат открыт, текст сохраняется; нет автоматической повторной отправки; предлагается проверить историю, повтор ручной с предупреждением о возможном дубле |
| Новый отправленный чат       | Принятый новый чат текущего сеанса не исчезает, если последующий GetChats ещё не включает его; объединение по chatId без дублей                                     |
| Ошибка статуса без idMessage | Ошибка соответствующего чата или подключения; галочки случайного сообщения не изменяются                                                                            |
| Ненужное событие             | Валидное событие вне объёма осознанно пропускается клиентом и подтверждается ACK; повреждённое не удаляется, получатель останавливается с понятной ошибкой          |

После обновления истории нельзя по совпадающему тексту достоверно установить
исход отдельной отправки. Ручной повтор может создать второе сообщение;
автоматическое сопоставление попыток по тексту не предлагается.

## Общий контракт данных и принадлежности

- Клиентский кеш и публикация результата изолируются существующим connectionScope. Сообщение сопоставляется по connectionScope, chatId и idMessage, а не по тексту или позиции в списке.
- Область Query-сессии не равна очереди инстанса: expiry в cookie может отличаться у двух сессий одного инстанса. Ограничение рабочего владельца относится к инстансу, чтобы разные scope не создавали конкурирующих читателей.
- История, входящие события и принятая отправка объединяются по одной идентичности. Поздняя история не стирает уже применённые новые события; устаревшее или более слабое подтверждение не понижает read/delivered.
- Статус, пришедший раньше сообщения, является частичным фактом в памяти. Он не создаёт пузырь без фактического сообщения. Отказ без idMessage не связывается с последней отправкой по догадке.
- Неизвестный личный чат из проверенного входящего сообщения сразу добавляется в список текущего подключения; сообщение сохраняется в Query. Используется фактическая доступная подпись, а при её отсутствии — chatId. GetChats уточняет данные; при сбое или отсутствии записи в ответе локально известный чат остаётся в памяти. Слияние по chatId не создаёт дублей и не меняет выбранный чат.
- Правило добавления после SendMessage относится к локальной попытке отправки. История содержит фактические сообщения, в том числе отправленные вне приложения; их не связывают с текущей попыткой по совпадению текста.
- ACK означает завершённую клиентскую обработку: применение факта либо осознанный пропуск валидного нецелевого события. Запись сервера в SSE сама по себе не даёт права вызвать DeleteNotification. Успех уточняющего GetChats не является условием ACK.
- Выход, истечение сессии, смена подключения, освобождение рабочей вкладки и поздние ответы не переносят данные или права в новое подключение. Отмена HTTP не гарантирует отмену уже принятой GREEN-API отправки.
- Конкретный DTO, адреса HTTP/SSE/ACK, право владельца, порядок атомарных действий, отмена запросов, таймауты, обратная задержка после ошибок и настройки кеша определяются в технических планах. Они не объявляются выбранными ради шаблона спецификации.

тестовым контекстом, без объявления полного пользовательского сценария готовым.

У каждой feature собственный checklists/requirements.md. Пройденная readiness
проверяет качество текста, а не согласование пользователя, завершённый analyze
или результат исполнения. У018/025 есть отдельное разрешение кода и фактические
verification; у019 также есть изолированная проверенная реализация; у020–024 готовы технические планы, задачи и анализ документов.

## Отложенные возможности и технические вопросы

- Подгрузка старой истории, полное восстановление всех событий, собственная БД, постоянные браузерные черновики и несколько одновременно рабочих вкладок не входят в комплект.
- Новый дизайн, дополнительные контакты/аватары, группы, вложения, реакции, редактирование и удаление сообщений не вводятся. Используется текущий согласованный макет.
- Отправка текста, получение ответов и статусы не объединяются в одну большую реализацию; параллельно разрешена подготовка документов.
- Настройки уведомлений с именами outgoingWebhook/outgoingAPIMessageWebhook/outgoingMessageWebhook относятся также к очереди HTTP API. Для статусов потребуются действия пользователя в кабинете; агент их не изменяет.
- Политики SendMessage, неоднозначного DeleteNotification, освобождения владельца, ранних/противоречащих статусов и частоты запросов определены в research/contracts. Unicode-единица лимита провайдера документально не подтверждена: локальная граница — 4096 кодовых точек, а фактический отказ API остаётся отдельным безопасным результатом; принятие такого текста провайдером не обещается.
- Площадка для постоянного Node-процесса и SSE не выбрана. Деплой, Git-операции и установка зависимостей не разрешены подготовкой документов.

## Общие технические границы

- 025 предоставляет один target, accessId каждого открытия, selectionEpoch
  смены/закрытия и мобильную панель. Она опирается на готовый014 и может идти
  первой; новые API сообщений не нужны для самого выбора.
- 018 создаёт серверную историю и базовый кеш сообщений;019 добавляет отображение
  и общие производители фактов. Контракт модели и объединения принадлежит
  [019/message-cache](../specs/019-chat-history-window/contracts/message-cache.md).
  История запрашивается свежим accessId, накопленные сообщения остаются в Query
  до закрытия подключения. HTTP-снимок и объединённый кеш — разные данные.
- 019 также определяет локальные записи чатов текущего сеанса для021/023.
  Подпись поиска/события хранится отдельно от фактических name/username/phone;
  неизвестные поля PersonalChat не заполняются выдуманными значениями.
- 022 владеет одним реестром читателей на инстанс и правом отправки020.
  023 использует fetch с потоком SSE, cookie и X-Connection-Scope/X-Chat-Owner.
  В URL нет секретов. ownerCapability — случайное право текущей рабочей вкладки,
  хранится только в памяти; это не токен GREEN-API.
- 023 определяет claim/stream/ACK/release; ACK связан с текущей доставкой и
  владельцем, а серверный receiptId не принимается произвольным клиентским
  параметром. 020 использует тот же реестр для одной локальной отправки.
- Остановка потока прекращает новые Receive/Send/Delete без активной вкладки;
  уже начатые операции завершаются локально с защитой старого owner epoch.
  Отмена HTTP не обещает отмену удалённого принятия сообщения.
- 018 расширяет общий QuerySession обработкой нормализованных ошибок сессии
  и регистрацией cleanup; 021/023 используют её, а не разные способы выхода.
  ownership_busy не считается connection_changed и не удаляет cookie.

Этот раздел связывает документы, а не копирует все DTO и таймауты. Точные
контракты остаются в соответствующих feature; зависимости реализации
последовательны. Параллельно пишутся только документы.

## Состояние согласования

Все существенные вопросы поведения этого комплекта закрыты. Для неизвестного
личного чата пользователь выбрал немедленное добавление по проверенному
уведомлению с последующим уточнением через GetChats. Технические решения вынесены в research/plan/contracts; доступность настоящих provider-сценариев проверяется после разрешения кода.

Тексты восьми спецификаций согласованы 2026-10-02. Технический комплект подготовлен;
025 и018 реализованы после отдельного разрешения и закоммичены пользователем.
Проверки018/025 описаны в их verification. Изолированные проверки019 Passed; проверки020–024 и совместные сценарии пока NotRun/NotRunExternal.
