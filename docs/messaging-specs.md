# История, получение и отправка — комплект спецификаций

**Дата**: 2026-10-03. История018/019, отправка020, форма021,
нормализация022, применение событий023, статусы024, выбор025 и счётчики026
соединены в общий сценарий. Текущий транспорт, ACK и границы вкладок определяет
[027](../specs/027-vercel-notification-polling/spec.md).
Проверки и ограничения: [готовность](messaging-readiness.md).

## Согласованные решения

| Область                      | Решение                                                                                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Основа                       | Next.js и React на Vercel с независимыми HTTP-функциями; зашифрованная HttpOnly cookie; токен не передаётся клиентскому JavaScript из cookie                               |
| Хранение                     | Переписка и факты текущего сеанса только в памяти Query; без собственной БД, Redis и постоянного browser storage                                           |
| История                      | При каждом обращении к выбранному чату свежий GetChatHistory с count: 10; известные сообщения сохраняются и объединяются без дублей                                 |
| Подгрузка                    | Загрузка более старых сообщений и увеличение count отложены; в текущем объёме нет pagination, cursor или offset                                                     |
| Нетекстовый элемент          | «Неподдерживаемое сообщение» без загрузки вложений; API count не превращается в десять отфильтрованных текстовых сообщений                                          |
| Получение                    | Последовательный browser POST → серверный ReceiveNotification (5 с) → JSON → отдельный ACK после обработки → DeleteNotification                                                    |
| Вкладки                      | Одна рабочая вкладка на origin/connectionScope в одном браузере через Web Locks; вторая показывает явное ограничение и не отправляет сообщения                                                            |
| Нет активной вкладки         | Чтение останавливается; неподтверждённое событие не удаляется; после возврата чтение возобновляется и история обновляется с count: 10                               |
| Границы восстановления       | Очередь GREEN-API ограничена сроком хранения; десять сообщений и временная память не гарантируют восстановление всех старых событий и статусов                      |
| Принятие отправки            | Локальное добавление исходящего сообщения только после успешного SendMessage с idMessage; это ещё не доставка                                                       |
| Ожидание отправки            | Одна отправка за раз на подключение; поле текущей попытки и повторная отправка заблокированы; переключение и закрытие доступны                                      |
| Ввод                         | Переключение или закрытие очищает ввод; отдельного хранилища черновиков по чатам нет; допустимый текст передаётся с исходными пробелами и переносами                |
| Неопределённый исход         | Если тот же чат открыт, текст сохраняется; нет автоматической повторной отправки; предлагается проверить историю, повтор ручной с предупреждением о возможном дубле |
| Новый отправленный чат       | Принятый новый чат текущего сеанса не исчезает, если последующий GetChats ещё не включает его; объединение по chatId без дублей                                     |
| Ошибка статуса без idMessage | Ошибка соответствующего чата или подключения; галочки случайного сообщения не изменяются                                                                            |
| Ненужное событие             | Валидное событие вне объёма осознанно пропускается клиентом и подтверждается ACK; повреждённое не удаляется, получатель останавливается с понятной ошибкой          |

После обновления истории нельзя по совпадающему тексту достоверно установить
исход отдельной отправки. Ручной повтор может создать второе сообщение;
автоматическое сопоставление попыток по тексту не предлагается.

## Общий контракт данных и принадлежности

- Клиентский кеш и публикация результата изолируются существующим connectionScope. Сообщение сопоставляется по connectionScope, chatId и idMessage, а не по тексту или позиции в списке.
- Область Query-сессии не равна очереди инстанса: expiry в cookie может отличаться у двух сессий одного инстанса. Web Locks координирует только один origin/connectionScope в одном браузере. Разные cookie-сессии, устройства, профили и origins могут конкурировать за очередь; глобального владельца нет.
- История, входящие события и принятая отправка объединяются по одной идентичности. Поздняя история не стирает уже применённые новые события; устаревшее или более слабое подтверждение не понижает read/delivered.
- Статус, пришедший раньше сообщения, является частичным фактом в памяти. Он не создаёт пузырь без фактического сообщения. Отказ без idMessage не связывается с последней отправкой по догадке.
- Неизвестный личный чат из проверенного входящего сообщения сразу добавляется в список текущего подключения; сообщение сохраняется в Query. Используется фактическая доступная подпись, а при её отсутствии — chatId. GetChats уточняет данные; при сбое или отсутствии записи в ответе локально известный чат остаётся в памяти. Слияние по chatId не создаёт дублей и не меняет выбранный чат.
- Правило добавления после SendMessage относится к локальной попытке отправки. История содержит фактические сообщения, в том числе отправленные вне приложения; их не связывают с текущей попыткой по совпадению текста.
- ACK означает завершённую клиентскую обработку: применение факта либо осознанный пропуск валидного нецелевого события. Передача сервером JSON сама по себе не даёт права вызвать DeleteNotification. Успех уточняющего GetChats не является условием ACK.
- Выход, истечение сессии, смена подключения, освобождение рабочей вкладки и поздние ответы не переносят данные или права в новое подключение. Отмена HTTP не гарантирует отмену уже принятой GREEN-API отправки.
- Конкретный DTO, адреса HTTP/ACK, Web Lock, порядок последовательных действий, отмена запросов, таймауты, обратная задержка после ошибок и настройки кеша определяются в технических планах. Они не объявляются выбранными ради шаблона спецификации.

## Отложенные возможности и технические вопросы

- Подгрузка старой истории, полное восстановление всех событий, собственная БД, постоянные браузерные черновики и несколько одновременно рабочих вкладок не входят в комплект.
- Новый дизайн, дополнительные контакты/аватары, группы, вложения, реакции, редактирование и удаление сообщений не вводятся. Используется текущий согласованный макет.
- Функциональные границы отправки, получения, формы и статусов остаются раздельными;027 меняет только общую транспортную архитектуру.
- Настройки уведомлений с именами outgoingWebhook/outgoingAPIMessageWebhook/outgoingMessageWebhook относятся также к очереди HTTP API. Для статусов потребуются действия пользователя в кабинете; агент их не изменяет.
- Политики SendMessage, неоднозначного DeleteNotification, освобождения владельца, ранних/противоречащих статусов и частоты запросов определены в research/contracts. Unicode-единица лимита провайдера документально не подтверждена: локальная граница — 4096 кодовых точек, а фактический отказ API остаётся отдельным безопасным результатом; принятие такого текста провайдером не обещается.
- Площадка — Vercel. Транспорт определён027; деплой, Git-операции и установка зависимостей не входят в текущую реализацию.

## Общие технические границы

- 025 предоставляет target, accessId каждого открытия и selectionEpoch смены/закрытия.
- 019 владеет общей моделью сообщений, объединением кеша, ранними статусами и
  локальными записями чатов. История — свежие10; накопленные факты живут в Query RAM.
- 027 владеет stateless settings/receive/ACK, подписанным proof, ограниченными
  таймаутами, browser lease и последовательным клиентским циклом. Нормализация
  событий и их применение сохраняются из022/023. Общего серверного registry нет.
- 020 проверяет cookie, Origin, scope и текст перед SendMessage; 021 удерживает
  одну текущую попытку. Серверного send lease нет. Автоматические повторы запрещены.
- ACK связан с receiptId, scope и expiry подписью HMAC. Для проверки не нужна память
  прежнего экземпляра. Произвольный receiptId от клиента не принимается.
- При потерянном delete-ответе повторный ACK с false проверяет голову очереди:
  тот же receipt требует повторения; другая или пустая голова завершает ACK.
  Другое уведомление не удаляется. Истёкший proof требует нового получения.
- Закрытие отменяет цикл и освобождает Web Lock; поздние результаты изолированы
  scope/epoch. Отмена HTTP не обещает отмены уже принятой провайдером отправки.
- 024 показывает подтверждённые статусы; 026 считает только новые уникальные входящие
  вне открытого диалога. История, дубли, исходящие и статусы счётчик не увеличивают.

## Состояние согласования и размещение

Пользователь разрешил полный комплект027 и реализацию без повторного gate.
Фиксированная площадка — Vercel, без Redis/БД/постоянного сервера. Инструкция
GitHub import и SESSION_PASSWORD: [quickstart027](../specs/027-vercel-notification-polling/quickstart.md).
Реальное размещение и проверка GREEN-API выполняются пользователем.
