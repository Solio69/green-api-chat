# Правила написания кода GREEN-API Chat

Документ действует для нового и затронутого кода приложения, тестов и стилей. Он описывает решения, которые нельзя надёжно проверить готовым линтером. Исполняемые правила находятся в [ESLint](../eslint.config.mjs), [Prettier](../prettier.config.mjs) и [Stylelint](../stylelint.config.mjs); порядок работы и TDD заданы в [AGENTS.md](../AGENTS.md). Уже существующий код не меняем массово только ради ручного правила: применяем его при следующем изменении или в отдельной согласованной задаче.

## Компоненты и границы

Собственный компонент занимает `src/components/ComponentName/`. Имя папки, файла компонента и SCSS-модуля — `PascalCase`; `index.ts` экспортирует публичный компонент, а локальные константы лежат рядом в `constants.ts`. Внутренние файлы можно импортировать напрямую, когда нужен именно их контракт.

Так:

```text
src/components/CredentialField/
  CredentialField.tsx
  CredentialField.module.scss
  constants.ts
  index.ts
```

```tsx
import { CredentialField } from '@/components/CredentialField'
```

Не так: импортировать `CredentialField.tsx` по внутреннему пути из другого компонента или складывать несколько самостоятельных компонентов в одну папку. Зарезервированные файлы Next.js (`page.tsx`, `layout.tsx`, `route.ts` и другие) сохраняют имена фреймворка; собственный модуль страницы может называться `LoginPage.module.scss`.

Выделяй компонент по самостоятельной роли или повторяемой разметке с поведением. Не создавай общий `Button` с вариантами оформления ради предполагаемого будущего переиспользования. Состояние и проверка формы остаются у компонента, управляющего сценарием; поле получает значение и обработчик через пропсы.

## Импорты

Внутри `src` импортируй файл из той же папки через `./`, например `./constants` или `./ComponentName.module.scss`. Файлы из других папок импортируй через `@/`. Импорты CSS/SCSS, включая глобальные стили, ставь последними после библиотек, функций, констант и компонентов. В тестах путь `../constants` допустим: алиас `@/` указывает только на `src`, а общие тестовые константы находятся в `tests`.

Так: `import styles from './ComponentName.module.scss'` в файле компонента рядом со стилем. Не так: `import styles from '@/components/ComponentName/ComponentName.module.scss'` из той же папки.

## Функции и условия

Собственные функции приложения, тестов и конфигурации объявляй стрелочными через `const`: это относится к компонентам, обработчикам, тестовым хелперам и обработчикам маршрутов. Для страницы Next.js оставляй обязательный default export: объяви именованный `const`, затем `export default` с его именем. Готовые правила ESLint проверяют объявления `function`, обычные функциональные выражения и заменяемые колбэки; `arrow-body-style` проверяет блок с одним `return`, а `no-restricted-syntax` — синхронный обработчик с одним вызовом.

Методы классов и объектные методы, для которых важен собственный `this` или контракт метода, сохраняют синтаксис метода. Генераторы, перегрузки и API, требующие обычную `function`, допускаются только если стрелочная форма не сохраняет контракт; причину указывай при ревью. Не превращай метод в поле со стрелкой ради единообразия.

Обработчик события объявляй до `return` компонента, давай имя по действию и передавай в JSX по имени.

```tsx
const handleTokenVisibilityToggle = () => setTokenVisible((visible) => !visible)

return <button onClick={handleTokenVisibilityToggle}>Показать</button>
```

Не так: `<button onClick={() => setTokenVisible(!tokenVisible)}>` — логика и имя действия теряются внутри разметки. Пропсы, DOM-ссылки и обработчики типизируй по их контракту; `as` не должен скрывать непроверенные данные.

Если у собственной функции больше одного аргумента, передавай именованный объект. Это делает вызов читаемым и устойчивым к перестановке параметров.

```ts
const openChat = ({ chatId, title }: { chatId: string; title: string }) => ({
  chatId,
  title,
})

openChat({ chatId, title })
```

Не так: `openChat(chatId, title)`, когда оба аргумента задаёт наш код. Исключение — сигнатуры браузера, React, Next.js или сторонней библиотеки, которые мы не выбираем.

Если в условии больше одного сравнения, дай всему условию логическое имя перед `if`. Для короткой ветки с одним `return` опускай фигурные скобки; для нескольких действий и многострочного ответа оставляй блок.

```ts
const isAccessDenied = status === 401 || status === 403
if (isAccessDenied) return null
```

Не так: `if (status === 401 || status === 403) { return null }`. Скобки в `return { status }` принадлежат объекту и остаются. Сложную последовательность веток пиши через `if / else if` или `switch`; вложенный тернарник также запрещает ESLint.

Когда условие возвращает объект или `null` и отсутствие должно остаться именно `null`, используй `&&`: `const credentials = session && readCredentials(session)`. Не подменяй им тернарник, если левая часть может быть `false`, `0` или пустой строкой: эти значения попадут в результат. Для отсутствующего JSX-атрибута нужен `undefined`, поэтому `aria-describedby={errorId ? errorId : undefined}` остаётся корректным.

Короткая стрелочная функция с одним выражением записывается без блока, если результат и ожидание завершения сохраняются: `const getValue = () => readValue()`. Форму дополнительно проверяют ESLint `arrow-body-style` и `no-restricted-syntax` в указанных выше случаях. Не так: `const getValue = () => { return readValue() }`. Литерал объекта оборачивай в скобки: `() => ({ value })`. Для `try`, `throw`, нескольких действий и асинхронного ожидания, которое нельзя потерять, сохраняй блок. Не превращай асинхронную операцию в `void`, если вызывающий код должен дождаться её или обработать ошибку.

## Константы и тесты

Выноси повторяемые и согласованные значимые значения в именованные константы, если имя помогает понять смысл. Не выноси каждую одноразовую строку, название теста, SVG-атрибут или структурное значение. Между группами объявлений оставляй одну пустую строку; связанные `const` держи вместе. Формат пробелов автоматически задаёт Prettier.

Общие значения интерфейса, включая `EMPTY_STRING` и повторно используемые HTML-значения, находятся в `src/lib/ui/constants.ts`; тексты конкретной формы — рядом с формой. Семантические значения протокола, cookie, кодировку и части URL/ID храни у соответствующего модуля. HTTP-статусы, методы, имена и значения заголовков находятся в `src/lib/http/constants.ts`, статусы и коды ошибок JSON-ответов — в `src/lib/api/constants.ts`. Пользовательские тексты ошибок располагаются рядом с интерфейсом, внутренние сообщения `Error` — рядом с серверной логикой.

Объекты констант объявляй с `as const`, добавляй только используемые значения. В потребителе деструктурируй нужные значения на уровне модуля, совпадающим ключам давай понятные алиасы:

```ts
const { OK: HTTP_OK } = HTTP_STATUS
const { OK: RESPONSE_OK } = API_RESPONSE_STATUS
```

Не так: дублировать HTTP 200 и строку `'ok'` в каждом маршруте. Не задавай вручную заголовки, которые уже корректно формирует фреймворк: `Response.json` сам добавляет `Content-Type`. Исключение для констант — буквальное значение, необходимое статическому анализу Next.js.

В тестах используй проектную константу, если значение и смысл совпадают; общие фикстуры интеграционных и браузерных тестов держи в `tests/constants.ts`, уникальную ошибку сценария — локально. Независимое ожидание публичного контракта не импортируй из той же константы, которую использует проверяемый код: иначе одинаковая ошибка в коде и тесте останется незамеченной. Так: проверять ожидаемый HTTP-код контракта независимо; не так: `expect(response.status).toBe(HTTP_STATUS.OK)`, если маршрут и тест читают один и тот же объект `HTTP_STATUS`. Для PowerShell-проверок повторяемые фикстуры находятся в их локальном наборе констант. Тесты проверяют поведение, а не повторяют структуру констант или токенов.

## Доступность и реквизиты

Используй семантические HTML-элементы, связанный `label` и `input`, клавиатурное управление и видимый `:focus-visible`. Ошибку связывай с полем через `aria-describedby` только когда она есть. Так: отсутствующий атрибут — `undefined`; не так: пустая строка вместо отсутствия атрибута.

Не выводи реальные реквизиты в клиентские логи, URL, тестовые фикстуры или документы и не сериализуй их в нативную HTML-форму. Для автоматических проверок используй фиктивные значения; серверные секреты остаются на сервере.

## SCSS

Используй SCSS Modules и БЭМ; вложенные элементы и модификаторы пиши через `&`. Имена CSS-классов проверяет Stylelint, а имена собственных файлов компонента следуют правилу PascalCase выше.

```scss
.credentialField {
  &__input {
    &--withToggle {
      padding-inline-end: tokens.$control-min-height + tokens.$space-xs;
    }
  }
}
```

Не так: дублировать полный селектор `.credentialField__input` рядом с корнем или добавлять цвет буквально в компонент. Все цвета и общие отступы, размеры, скругления, тени и типографику храни в `src/styles/_tokens.scss`. В компонентах используй семантические токены; структурные `0`, `100%` и `auto` не требуют токена. Повторяемые группы свойств выноси в `src/styles/_mixins.scss`; миксин ради одного свойства или гипотетического применения не нужен. Подключай partial-файлы через `@use` с именами `tokens` и `mixins`; сами partial-файлы не содержат CSS-селекторов.

Фокус должен быть видимым. У поля с ошибкой рамка и подсветка соответствуют ошибке; не показывай одновременно зелёный и красный контуры. Выбор нужного токена, миксина и визуальной семантики проверяется на ревью, а синтаксис и автоматические правила — `npm run lint:styles`.

## Завершение задачи

После серии правок запускай проверки по риску изменения: `npm run lint`, `npm run lint:styles`, `npm run format:check`, `npm run typecheck` и соответствующие тесты. Предкоммитное ревью проверяет область diff, секреты, неиспользуемые значения и совпадение со спекой. Порядок TDD и статус проверок определяет [AGENTS.md](../AGENTS.md); этот документ не заменяет его.
