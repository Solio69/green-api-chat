# План рефакторинга GREEN-API Chat

Документ задаёт общий список работ по улучшению архитектуры, компонентов,
тестов и автоматических проверок в текущем объёме тестового задания.
Это ориентир для последовательной работы и учёта готовности этапов.

**Дата:** 3 октября 2026 года.
**Согласовано:** направления рефакторинга, функциональные модули, Vitest
с React Testing Library вместе с Playwright и добавление CI.
**Подготовлено:** 28 спецификаций и 28 чек-листов качества требований по всем 10 этапам.
**Поручено:** довести задачи 030–055 до конца. Для каждой подготовить полный комплект, выполнить анализ, реализацию, проверки и ревью, затем самостоятельно commit и push в refactor. Повторное согласование уже утверждённого объёма не требуется; новые продуктовые решения остаются отдельным вопросом.
**Реализация этапов:** 028–047 выполнены; R01–R07 завершены, R08 продолжается. Следующая задача 048 — список чатов.

## Принятые решения

1. Организовать приложение по функциональным модулям. Внутри разделить
   отображение, прикладную логику и взаимодействие с API; общие зависимости
   выделять по фактическому использованию.
2. Упростить модель переписки: явно описать состояния получения уведомлений
   и централизовать применение истории, отправленных сообщений и событий.
3. Убрать повторение серверной обвязки: чтение сессии, контекст подключения,
   проверки запросов и общие части транспорта GREEN-API.
4. Последовательно отделить поведение компонентов от отображения, начиная
   с форм входа и поиска получателя.
5. Использовать Vitest для проверок чистой и прикладной логики, Vitest
   с React Testing Library для компонентов и хуков, Playwright для проверок
   в настоящем браузере и сквозных сценариев. Постепенно перенести подходящие
   существующие тесты, сохраняя покрытие поведения.
6. Усилить автоматические проверки и добавить CI. Для репозитория на GitHub
   предлагается GitHub Actions.

Сохраняются Next.js, React, TypeScript, TanStack Query, iron-session и SCSS
Modules. Архитектурные изменения выполняются в рамках существующих функций
и согласованного интерфейса. Структурные правила размещения компонентов и импортов уточняются в
035 под согласованные функциональные модули. Иные правила кодстайла,
включая использование констант, требуют отдельного обсуждения.

## Что должны сохранять проверки

- Изоляцию подключений и очистку состояния при выходе или потере доступа.
- Привязку позднего ответа к исходному чату и попытке отправки.
- Различие между подтверждённым отказом и неизвестным исходом отправки.
- Применение уведомления до ACK и последовательность receive и ACK.
- Отсутствие дублей сообщений и непрочитанных при повторной доставке.
- Сохранение подтверждённых статусов доставки и прочтения при загрузке истории.
- Поведение рабочей и второй вкладки, завершение подписок и сетевых операций.
- Клавиатурное управление, фокус, прокрутку и адаптивную компоновку.

Перечень служит основой R01. При подготовке проверяется существующее покрытие;
новые тесты добавляются для установленных пробелов.

## Решение по тестовым инструментам

Согласованы два runner с разными областями ответственности. React Testing
Library используется внутри тестов Vitest для взаимодействия с React.

| Инструмент                     | Область проверок                                                                                                                                                |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Vitest                         | Валидация, нормализация, объединение сообщений, переходы состояний, обработка ошибок и интеграция модулей, которой не требуется работающий Next.js или браузер. |
| Vitest и React Testing Library | Компоненты, хуки, формы, подписки, обновления состояния, очистка эффектов и Strict Mode.                                                                        |
| Playwright                     | Production-приложение, реальные HTTP-маршруты и cookie, сквозные сценарии, несколько вкладок, Web Locks, фокус, прокрутка, геометрия и адаптивность.            |

В R01 настраиваются Vitest и React Testing Library и переносится небольшой
набор подходящих тестов. Остальные проверки переносятся при работе над
соответствующими модулями; R09 завершает миграцию. Существующий тест удаляется
после подтверждения эквивалентного покрытия в новом месте. Проверки настоящих
браузерных API и вёрстки сохраняются в Playwright. Асинхронные Server Components
и взаимодействие с Next.js проверяются через браузерные и HTTP-сценарии.

Для lifecycle используется development-сборка React и корневой `StrictMode`
в тесте Vitest с React Testing Library. Тест наблюдает фактический цикл setup
и cleanup. Обёртка `StrictMode` в production-стенде не подтверждает повторный
запуск эффектов. Основные E2E проверяют production-сборку.
[Документация React](https://react.dev/reference/react/StrictMode)
и [руководство Next.js по Vitest](https://nextjs.org/docs/app/guides/testing/vitest).

Выбор инструментов даёт отдельные проверки логики, React и полного приложения.
Достаточность покрытия оценивается по карте сценариев и рисков. Наличие двух
runner само по себе не доказывает полноту тестов. Контракт окружений задан в спецификации 029; конкретное DOM-окружение, версии и необходимые
вспомогательные зависимости определяются её техническим планом. Скорость
альтернатив на этом репозитории не измерялась.

## Состав CI

Предлагается GitHub Actions: проверка типов приложения и всех тестовых
конфигураций, ESLint, Stylelint, Prettier, Vitest для логики, компонентов и
хуков, Playwright для браузерных и сквозных сценариев production. Оставшиеся
проверки React-стенда выполняются до их переноса. Конфигурация должна исключать
лишние повторные сборки и конфликты окружений; результаты обоих runner учитываются
в общем результате CI.

Спецификации 033 и 034 задают события и состав проверок, изоляцию окружений и отчёты.
Точные ветки, runner, лимиты времени и срок хранения артефактов фиксируются техническим планом. Согласованные зависимости
фиксируются в package.json и lockfile и устанавливаются в чистом CI-окружении;
тесты используют фиктивные реквизиты.
[Руководство Playwright по CI](https://playwright.dev/docs/ci-intro).

Готовый workflow и подтверждённый запуск на GitHub учитываются отдельно.
Публикация Git-изменений выполняется по действующей политике проекта;
настройки защиты веток и публикация приложения обсуждаются отдельно.
