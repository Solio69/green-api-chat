# Кодстайл GREEN-API Chat

Этот документ фиксирует действующие соглашения по коду проекта. Дополняем его по мере согласования новых правил. Порядок работы описан в [AGENTS.md](../AGENTS.md), ограничения Git — в [GIT_POLICY.md](../GIT_POLICY.md).

## Компоненты и файлы

- Собственные React-компоненты и их SCSS-модули называем в `PascalCase`: `CredentialField.tsx`, `CredentialField.module.scss`.
- Каждый собственный компонент размещаем в отдельной папке `src/components/ComponentName/`. Публичный импорт компонента идёт через `index.ts` этой папки:

  ```text
  src/components/CredentialField/
    CredentialField.tsx
    CredentialField.module.scss
    index.ts
  ```

  ```tsx
  import { CredentialField } from '@/components/CredentialField';
  ```

- Константы компонента храним рядом с ним в `constants.ts`; их можно импортировать напрямую. `index.ts` экспортирует публичный компонент, а не все внутренние файлы папки.
- Обязательные имена файлов Next.js App Router (`page.tsx`, `layout.tsx`, `route.ts` и другие специальные файлы) сохраняем. Их собственные SCSS-модули называем по назначению, например `HomePage.module.scss`.
- Выделяем компонент по самостоятельной роли или повторяемой разметке с поведением. Не вводим общий компонент с вариантами оформления только ради потенциального переиспользования.

## TypeScript и JSX

- Пишем все `import` подряд, без пустых строк между ними. После последнего импорта оставляем одну пустую строку перед остальным кодом. Правило действует и для приложения, и для тестов.
- Используем строгую типизацию TypeScript. Пропсы, ссылки на DOM и обработчики имеют явные подходящие типы; `any` не используем для обхода ошибок типизации.
- Состояние и проверка формы остаются у компонента, который управляет сценарием. Поле получает значение и обработчик изменения через пропсы; кнопки отвечают за своё действие и разметку.
- Сохраняем семантические HTML-элементы, связанные `label`/`input`, клавиатурное управление и видимое состояние `:focus-visible`. Ошибку связываем с полем через `aria-describedby` только при наличии ошибки. Когда атрибут должен отсутствовать, передаём `undefined`, а не пустую строку.
- Не добавляем в клиентский код вывод реквизитов в логи и не сериализуем их в нативную HTML-форму. Поведение с реквизитами проверяют тесты безопасности формы.

## Константы

- Повторяющиеся и согласованные значимые значения выносим в именованные константы. Каждую одноразовую строку, атрибут SVG или структурное значение автоматически не выносим: имя должно делать код понятнее.
- Общие для интерфейса значения, включая `EMPTY_STRING` и повторно используемые HTML-значения, находятся в `src/lib/ui/constants.ts`. Тексты конкретной формы — в `src/components/LoginForm/constants.ts`.
- HTTP-коды, имена заголовков и повторно используемые значения заголовков находятся в `src/lib/http/constants.ts`; общие статусы JSON-ответов — в `src/lib/api/constants.ts`.
- Объекты констант объявляем с `as const` и добавляем в них только используемые значения. В потребителе деструктурируем нужные значения на уровне модуля; совпадающим именам даём понятные алиасы, например `HTTP_OK` и `RESPONSE_OK`.
- Не задаём вручную заголовки, которые корректно формирует используемый API фреймворка: `Response.json` сам добавляет `Content-Type`.
- В тестах используем существующие общие константы, когда значение и его смысл совпадают; не дублируем их в тестовом наборе ради другого имени. Отдельные константы для тестов создаём только для уникальных тестовых данных, настроек или независимых ожиданий проверяемого контракта. Ожидаемый текст или ответ не берём из той же константы, которую использует проверяемый код: иначе тест не заметит ошибочное изменение контракта.

## SCSS

- Используем SCSS Modules и БЭМ. Элементы и модификаторы записываем через вложенность `&`:

  ```scss
  .credentialField {
    &__input {
      &--withToggle {
        padding-inline-end: tokens.$control-min-height + tokens.$space-xs;
      }
    }
  }
  ```

- Все цвета, а также общие отступы, размеры, скругления, тени и типографику храним в `src/styles/_tokens.scss`. В стилях компонентов используем семантические имена токенов. Структурные значения вроде `0`, `100%` и `auto` не требуют токенов.
- Повторяющиеся группы CSS-свойств выносим в `src/styles/_mixins.scss`; миксин ради одного свойства или предполагаемого будущего применения не создаём.
- Подключаем общие partial-файлы через `@use` с пространствами имён `tokens` и `mixins`. В них нет самостоятельных CSS-селекторов.
- Фокус остаётся видимым. Для поля с ошибкой цвет границы, фокуса и подсветки соответствует ошибке; зелёный и красный контуры одновременно не показываем.

## Проверка изменений

- Перед сдачей затронутого кода запускаем подходящие проверки: `npm run typecheck`, `npm run lint`, `npm run format:check` и тесты по риску изменения. Для браузерного поведения формы используется `npm run test:e2e`.
- Тесты проверяют поведение и контракт, а не повторяют реализацию констант или SCSS-токенов. Правила TDD и проверки чистого рефакторинга заданы в [AGENTS.md](../AGENTS.md).
- После проверки просматриваем diff: нет ли лишних изменений, секретов, старых импортов и неиспользуемых значений.
