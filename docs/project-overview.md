## Цель и результат

Создать минимальный React-интерфейс для отправки и получения текстовых сообщений
в Telegram через GREEN-API. Приложение включает собственную серверную часть.
Результат — GitHub-репозиторий, понятная инструкция локального запуска и обязательная
публичная демоверсия.

Ключевой сценарий: пользователь вводит `idInstance` и `apiTokenInstance`,
создаёт чат по номеру телефона, отправляет текст и видит ответ собеседника,
отправленный из Telegram. Если получателя не удалось найти по телефону,
форма предлагает поиск по Telegram username.

Документ описывает границы проекта и согласованный состав эпиков. Он не заменяет
спецификации отдельных возможностей и не разрешает писать код.

## Согласованные решения и исходные требования

- Мессенджер — Telegram; интеграция — GREEN-API.
- Условие задания допускает Telegram как альтернативу MAX.
- Поиск по телефону — основной сценарий. При ответе CheckAccount exist: false
  форма показывает согласованное пояснение и кнопку «Найти по @username».
  Кнопка переключает форму на поиск по имени пользователя.
  Ошибки сети, авторизации и лимитов обрабатываются отдельно.

  Цвета и общие значения оформления вынесены в SCSS-константы;
  повторяющиеся группы свойств — в миксины. Правило действует во всём проекте.
- Служебный адрес /api/health проверяет способность сервера ответить на запрос.
  Главная страница приложения располагается по адресу /.
- Пользователь сообщил о создании публичного репозитория. Участие ИИ
  обозначается в README кратко и честно.
- Собственная серверная часть обязательна.
- Публичная демоверсия обязательна. Vercel рассматривается как целевая площадка.
- Пользователь участвует на каждом этапе. Работа идёт последовательно,
  по одной небольшой согласованной задаче с отдельным проверяемым результатом.
- Состав и порядок шести эпиков согласованы. Каждый эпик подробно дробится

- Переписка сохраняется после перезагрузки страницы. Поведение после выхода
  и нового входа, закрытия браузера и истечения сессии ещё не согласовано.

  тарифе Telegram Developer; авторизация подтверждена пользователем и статусом
  «Авторизован» на предоставленном скриншоте.
- Пользователь подтвердил сохранение настроек: уведомления о входящих сообщениях

  остальные типы уведомлений выключены. Отправка по chatId проверена:
  API вернул HTTP 200, собеседник получил сообщение. Получение текстового ответа

## Предлагаемые границы

В обязательный объём входят подключение инстанса, создание личного чата по телефону,
отправка и получение текста, понятные состояния ожидания и ошибок, серверное
обращение к GREEN-API, проверка основного сценария и документация запуска.
При отсутствии результата поиска по телефону доступен поиск по Telegram username.

Предлагается не включать группы, вложения, звонки, реакции, редактирование сообщений,
собственную регистрацию пользователей и поддержку нескольких мессенджеров.

Переписка должна переживать перезагрузку страницы. Количество одновременно
доступных чатов, поведение истории после выхода и нового входа, срок жизни сессии,
мобильная компоновка и дополнительные статусы сообщений требуют согласования.
Они не считаются автоматически включёнными или исключёнными.

## Согласованный флоу поиска получателя

1. Пользователь вводит номер телефона и запускает поиск.
2. Если CheckAccount возвращает exist: false, форма показывает сообщение:
   «Не удалось найти пользователя по номеру. Проверьте номер или попробуйте
   поиск по @username».
3. Кнопка «Найти по @username» переключает форму на поиск по имени пользователя.
4. Найденный получатель используется для открытия чата и отправки сообщения.

Интерфейс не утверждает, что аккаунт не существует: отрицательный результат
может быть связан с настройками приватности. Ошибки сети, авторизации и лимитов
не отображаются как отсутствие получателя; для них предусматриваются отдельные
состояния. Подробности валидации, повторных попыток и неуспешного поиска по username
определяются в спеке E04.

## Техническая основа

Выбран Next.js + TypeScript. React-интерфейс и серверное HTTP API находятся
в одном приложении, что упрощает совместный локальный запуск и размещение
на Vercel. Серверные обработчики предлагается реализовать через Route Handlers.
Конкретная организация модулей и версии зависимостей определяются в техническом
плане E02. Граница серверного и клиентского кода должна быть явной.

Предлагаемая граница ответственности:

`React-интерфейс → наше HTTP API на Vercel → GREEN-API → Telegram`

Сервер проверяет запросы и сессию, обращается к GREEN-API и возвращает интерфейсу
необходимые данные и понятные ошибки. Конкретные контракты появятся в спеках.

### Получение сообщений на Vercel

GREEN-API для Telegram поддерживает `ReceiveNotification` с ожиданием от 5 до
60 секунд. Обработанное уведомление подтверждается через `DeleteNotification`.
У Vercel Functions ограничена длительность одного запроса.

Предлагается последовательный опрос через наше API с ограниченным временем
ожидания. Каждый запрос завершается ответом; следующий запускается согласно
согласованному поведению интерфейса. Таймаут GREEN-API должен укладываться в лимит
функции с запасом на сеть и обработку. Это архитектурное предложение на основе
документации, а не результат проверки работающего приложения.

В спеке получения сообщений нужно определить момент подтверждения, защиту от
повторов, поведение при обрыве ответа, нескольких вкладках и повторных запросах.
Нельзя считать уведомление доставленным интерфейсу только потому, что сервер
получил его от GREEN-API.

### Сессия и хранение

Общую память процесса Vercel нельзя использовать как надёжное хранилище сессий:
запросы могут обслуживаться разными экземплярами.

Варианты для обсуждения:

- Зашифрованная cookie с HttpOnly: меньше инфраструктуры; нужно согласовать
  время жизни, выход и ограничения отзыва сессии. Cookie содержит зашифрованные
  данные на стороне браузера, поэтому это не хранение исключительно на сервере.
- Непрозрачный идентификатор в cookie и серверное хранилище сессий:
  проще централизованно отзывать сессии и координировать запросы; требуется
  дополнительное хранилище и его настройка.

Хранение сессии и хранение переписки — отдельные решения. После перезагрузки
приложение должно восстанавливать переписку; одной памяти React для этого
недостаточно. Источник восстановления, место хранения и внешние сервисы
определяются после согласования поведения при выходе и новом входе.
Постоянная база сообщений пока не выбрана.

## Рабочие ограничения

- Git: применяется локальная [политика проекта](../GIT_POLICY.md).
  По умолчанию разрешены только команды чтения. Staging — исключительно по прямой
  просьбе и только с явно перечисленными файлами; коммит агент не создаёт.
- Агент не скачивает и не устанавливает пакеты и ПО. Необходимые команды передаются
  пользователю с объяснением назначения.
- Агент не выполняет миграции и команды изменения данных в БД.
- Код без согласованной спеки и разрешения на реализацию не меняется, кроме случая
  отдельного явного поручения пользователя.
- Название коммита предлагается с префиксом `feat:`, `fix:`, `refactor:`
  или `chore:` по смыслу изменения.
- Учетные данные не включаются в репозиторий, документацию и демонстрационные
  материалы.
- Отправка результата работодателю — отдельное действие по прямому поручению.

## Открытые решения

Ближайшие вопросы:

- Как проверить успешный сценарий создания чата по телефону на доступном
  для такого поиска получателе? Причина отрицательного результата текущего
  тестового поиска не установлена. Обработка exist: false с предложением
  поиска по username согласована.

До проектирования сессии и истории:

- Должна ли переписка быть доступна после выхода из нашего приложения
  и повторного подключения того же инстанса?
- Что происходит после закрытия браузера и истечения сессии?

При декомпозиции соответствующих эпиков:

- Валидация телефона и username; поведение при неуспешном поиске по username,
  повторных попытках и отдельных ошибках сервиса. Переход к username после
  exist: false и текст сообщения для поиска по телефону согласованы.
- Подготовка аккаунтов GitHub и Vercel; допустимые расходы на размещение
  приложения и дополнительные сервисы.
- Где хранится сессия, сколько она живёт и что означает выход.
- Один или несколько чатов; состояние чатов после нового входа.
- Источник и границы истории, срок хранения и удаление пользовательских данных.
- Поведение нескольких вкладок или сессий с одним инстансом.
- UI для мобильных устройств, язык интерфейса и необходимые статусы сообщений.
- Защита публичного API от злоупотреблений с учётом выбранной архитектуры.
- Как проверяющий будет знакомиться с демоверсией до ввода своих реквизитов.
