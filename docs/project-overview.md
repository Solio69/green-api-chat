## Цель и результат

Создать минимальный React-интерфейс для отправки и получения текстовых сообщений
в Telegram через GREEN-API. Приложение включает собственную серверную часть.
Результат — GitHub-репозиторий, понятная инструкция локального запуска и обязательная
публичная демоверсия.

Ключевой сценарий: пользователь вводит `idInstance` и `apiTokenInstance`,
создаёт чат по номеру телефона, отправляет текст и видит ответ собеседника,
отправленный из Telegram. Если получателя не удалось найти по телефону,
форма предлагает поиск по Telegram username.

Документ описывает границы проекта и согласованный состав эпиков. Он не заменяет
спецификации отдельных возможностей и не разрешает писать код.

## Согласованные решения и исходные требования

- Мессенджер — Telegram; интеграция — GREEN-API.
- Условие задания допускает Telegram как альтернативу MAX.
- Поиск по телефону — основной сценарий. При ответе CheckAccount exist: false
  форма показывает согласованное пояснение и кнопку «Найти по @username».
  Кнопка переключает форму на поиск по имени пользователя.
  Ошибки сети, авторизации и лимитов обрабатываются отдельно.
- Стек — Next.js + TypeScript; пользовательский интерфейс построен на React.
- Стили — SCSS Modules с БЭМ-именованием и вложенностью через &.
  Цвета и общие значения оформления вынесены в SCSS-константы;
  повторяющиеся группы свойств — в миксины. Правило действует во всём проекте.
- Служебный адрес /api/health проверяет способность сервера ответить на запрос.
  Согласованный маршрут формы входа — /login, защищённой главной — /.
- Рабочий репозиторий приватный по подтверждению пользователя. Разработка ведётся
  в нём; для сдачи планируется отдельная публичная копия готового проекта.
  Состав файлов копии согласовывается перед её подготовкой; служебные материалы
  агентской разработки исключаются из версии для сдачи.
- Собственная серверная часть обязательна.
- Публичная демоверсия обязательна. Публикация запланирована на финальный этап E06
  из репозитория для сдачи через GitHub-интеграцию Vercel. Аккаунты GitHub и Vercel
  у пользователя есть. Тариф, расходы и настройки публикации ещё не согласованы.
- Пользователь участвует на каждом этапе. Работа идёт последовательно,
  по одной небольшой согласованной задаче с отдельным проверяемым результатом.
- Состав и порядок шести эпиков согласованы. Каждый эпик подробно дробится
  на задачи; согласование эпика не разрешает реализовать его целиком.
- После перезагрузки и повторного входа список личных чатов восстанавливается
  через GetChats, история выбранного чата — через GetChatHistory. Сессия входа

- Для загрузки и временного кэша списка и истории выбран TanStack Query.
  Собственная БД и постоянное хранение переписки в браузере не используются.
  Объём истории и правила обновления кэша уточняются в отдельных задачах.
- Для спецификаций используется процесс Spec Kit по образцу agent-flow-harness,

- Для новой/изменяемой бизнес-логики и серверных контрактов обязателен TDD:

## Предлагаемые границы

В обязательный объём входят подключение инстанса, создание личного чата по телефону,
отправка и получение текста, понятные состояния ожидания и ошибок, серверное
обращение к GREEN-API, проверка основного сценария и документация запуска.
При отсутствии результата поиска по телефону доступен поиск по Telegram username.

Предлагается не включать группы, вложения, звонки, реакции, редактирование сообщений,
собственную регистрацию пользователей и поддержку нескольких мессенджеров.

Переписка восстанавливается через GREEN-API после перезагрузки и нового входа.
Список включает существующие личные чаты аккаунта из GetChats. Слой 014 обрабатывает личные чаты из ответа GetChats без собственного лимита;
его настройки кэша согласованы. Объём истории и поведение при новых сообщениях
уточняются в следующих feature-спецификациях. Мобильная компоновка и статусы описаны в docs/chat-ui-spec.md.

## Согласованный флоу поиска получателя

1. Пользователь вводит номер телефона и запускает поиск.
2. Если CheckAccount возвращает exist: false, форма показывает сообщение:
   «Не удалось найти пользователя по номеру. Проверьте номер или попробуйте
   поиск по @username».
3. Кнопка «Найти по @username» переключает форму на поиск по имени пользователя.
4. Найденный получатель используется для открытия чата и отправки сообщения.

Интерфейс не утверждает, что аккаунт не существует: отрицательный результат
может быть связан с настройками приватности. Ошибки сети, авторизации и лимитов
не отображаются как отсутствие получателя; для них предусматриваются отдельные
состояния. Валидация и обработка ошибок определены в [009](../specs/009-recipient-lookup/spec.md).
Открытие найденной переписки остаётся отдельной задачей D06.

## Техническая основа

Выбран Next.js + TypeScript. React-интерфейс и серверное HTTP API находятся
в одном приложении, что упрощает совместный локальный запуск и размещение
на Vercel. Серверные обработчики предлагается реализовать через Route Handlers.
Конкретная организация модулей и версии зависимостей определяются в техническом
плане E02. Граница серверного и клиентского кода должна быть явной.

Предлагаемая граница ответственности:

`React-интерфейс → наше HTTP API на Vercel → GREEN-API → Telegram`

Сервер проверяет запросы и сессию, обращается к GREEN-API и возвращает интерфейсу
необходимые данные и понятные ошибки. Конкретные контракты появятся в спеках.

### Получение сообщений на Vercel

GREEN-API для Telegram поддерживает `ReceiveNotification` с ожиданием от 5 до
60 секунд. Обработанное уведомление подтверждается через `DeleteNotification`.
У Vercel Functions ограничена длительность одного запроса.

Предлагается последовательный опрос через наше API с ограниченным временем
ожидания. Каждый запрос завершается ответом; следующий запускается согласно
согласованному поведению интерфейса. Таймаут GREEN-API должен укладываться в лимит
функции с запасом на сеть и обработку. Это архитектурное предложение на основе
документации, а не результат проверки работающего приложения.

В спеке получения сообщений нужно определить момент подтверждения, защиту от
повторов, поведение при обрыве ответа, нескольких вкладках и повторных запросах.
Нельзя считать уведомление доставленным интерфейсу только потому, что сервер
получил его от GREEN-API.

### Сессия и хранение

Общую память процесса Vercel нельзя использовать как надёжное хранилище сессий:
запросы могут обслуживаться разными экземплярами.

Для входа согласована зашифрованная HttpOnly-cookie с `idInstance` и
`apiTokenInstance` внутри. Она действует 24 часа от успешного входа;
открытие главной не продлевает срок. Данные находятся у браузера только
в зашифрованном виде, сервер проверяет cookie и актуальное состояние инстанса.
Отдельное серверное хранилище сессий для этого шага не требуется.
Явный выход удаляет cookie в текущем браузере и переводит на `/login`.
Другие устройства и ранее скопированные cookie не отзываются централизованно;
для этого понадобилось бы серверное хранилище сессий.

Сессия и история переписки имеют разные роли. Список восстанавливается через
GetChats, история выбранного чата — через GetChatHistory. TanStack Query
управляет запросами и кэшем в памяти; сервер берёт реквизиты GREEN-API из сессии.
При выходе клиентский кэш очищается; после повторного подтверждённого входа
данные снова загружаются через API. Собственная БД сообщений и постоянное
браузерное хранилище переписки не создаются. Количество сообщений и настройки
истории ещё требуют согласования. Слой списка 014 реализован и проверен:
GetChats → GET /api/chats → useChats, Query 5.104.0 установлена пользователем.
Для списка staleTime 60 секунд, gcTime 5 минут, без polling/focus/client retry.
Provider и очистка при выходе подключены; видимый список подключает 015.

уведомлений о входящих сообщениях и сохранение пустого адреса отправки

Пользователь подтвердил, что не подключал инстанс к другим интеграциям.

В наблюдаемом ответе API senderData.chatId — строка из цифр,
senderData.senderPhoneNumber равен 0. Это наблюдение одного тестового ответа;
оно не устанавливает причину неуспешного поиска по телефону. Значения
идентификаторов, реквизиты и текст переписки в документе не сохраняются.

Ограничения выбранного тестового тарифа по документации GREEN-API:
обмен и уведомления доступны для трёх чатов, CheckAccount ограничен 100 запросами
в месяц. Отправка одному получателю по телефону и по chatId учитывается как

провайдер рекомендует получить chatId через CheckAccount и использовать его.
Это ограничение тестового окружения, а не согласованный лимит интерфейса.

## Подключение и вход — границы и согласованная декомпозиция E03

**Согласованные границы:** форма содержит два поля из задания — `idInstance`
и `apiTokenInstance`. Сервер приложения отправляет запросы к GREEN-API по
`apiUrl` `https://4100.api.green-api.com`; это фиксированный адрес сервера, а не поле
формы и не адрес получателя сообщения. Партнёрский `partnerApiUrl` не
используется. Интерфейс, подписи полей и ошибки — на русском.
[Формат запросов GREEN-API](https://green-api.com/telegram/docs/request-format/).

Подключение Telegram выполняется в личном кабинете GREEN-API.
Если инстанс не авторизован, приложение показывает пояснение и ссылку на кабинет.
Встроенные экраны входа по коду или QR в согласованный объём не входят.
Согласованный сценарий входа сохраняет доступ после обновления страницы
в пределах 24 часов: при открытии защищённой главной сервер заново проверяет
состояние инстанса. При HTTP 429 `GetStateInstance` повторяется один раз
после паузы 1,1 секунды; при повторном 429 сессия сохраняется. Временный
сбой GREEN-API не удаляет сессию.

## Рабочие ограничения

- Git: применяется локальная [политика проекта](../GIT_POLICY.md).
  По умолчанию разрешены только команды чтения. Staging — исключительно по прямой
  просьбе и только с явно перечисленными файлами; коммит агент не создаёт.
- Агент не скачивает и не устанавливает пакеты и ПО. Необходимые команды передаются
  пользователю с объяснением назначения.
- Агент не выполняет миграции и команды изменения данных в БД.
- Код без согласованной спеки и разрешения на реализацию не меняется, кроме случая
  отдельного явного поручения пользователя.
- Название коммита предлагается с префиксом `feat:`, `fix:`, `refactor:`
  или `chore:` по смыслу изменения.
- Учетные данные не включаются в репозиторий, документацию и демонстрационные
  материалы.
- Отправка результата работодателю — отдельное действие по прямому поручению.
